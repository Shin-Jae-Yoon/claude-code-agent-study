# 환각 방지에 지침으로 충분한가 검증 장치까지 필요한가

두 정리본이 같은 지침 계열 기법을 다뤘지만 거기서 멈출지에 대한 판단이 갈렸다. 한쪽은 스킬 본문에 넣을 지침 3종으로 정리했고, 다른 쪽은 같은 3종에 반례를 붙인 뒤 구조적 검증 장치를 추가로 요구했다. 핵심 대비는 **지침은 확률을 낮추고, 검증은 결정론적이다**라는 문장이다.

## 근거와 출처

- [3장 재윤 정리](../../chapters/ch3/jaeyoon/정리본.md) — **지침 계열 3종.** 불확실성 표현 허용 / 정보 출처 제한 / 출처 명시를 각각 SKILL.md 본문 예시로 작성했다. 자기 검증도 붙였다 — 지금 쓰고 있는 `pre-chapter-prep`의 규칙 2·3이 정확히 그 장치이며, "그래서 이 문서에 '아직 없음'이 반복된다".
- [3장 준호 정리](../../chapters/ch3/junho/Chapter%2003.%20에이전트%20스킬.md) — **지침 + 구조.** 같은 3종을 다루되 각각에 실패 조건을 달았다. 불확실성 지침은 "확실하지 않으면 말하지 마라"가 아니라 "확실하지 않은 부분은 그렇다고 표시하고 말하라"여야 하고, 출처 지침은 사후 철회 루프까지 가야 한다. 그리고 구조 계열을 별도로 세웠다 — plan-validate-execute(분석 → `changes.json` 생성 → 스크립트 검증 → 실행)로 "존재하지 않는 필드를 참조했다"는 환각을 검증 단계에서 죽인다.

## 연결

- [출처를 요구하면 출처를 지어낸다](./cite-sources-invites-fabricated-sources.md) — 지침만으로 부족하다는 쪽의 핵심 반례다.
- [Opus 5에서는 출력 규범은 남기고 절차 지시는 뺀다](./opus5-keep-output-norms-drop-procedure-instructions.md) — 이 긴장을 복잡하게 만든다. 지침 중 일부는 더 필요해졌고 일부는 빼라고 하기 때문이다.
- [스크립트는 출력만큼만 토큰을 쓴다](./scripts-cost-only-their-output.md) — 구조적 검증이 스크립트로 구현된다면 비용 면에서도 유리하다는 연결이다.
- [Hooks는 LLM 판단 밖에서 결정론적으로 실행된다](./hooks-run-deterministically-outside-llm-judgment.md) — **"검증은 결정론적이다" 쪽의 구현 수단이 2장에 이미 있었다.** 스크립트가 스킬 안의 결정론이라면 Hooks는 생명주기에 붙은 결정론이다.
- [좋은 프롬프트보다 좋은 피드백 루프가 중요하다](./feedback-loop-beats-prompt-quality.md) — 같은 방향의 2장 주장이다. 지시를 다듬는 것보다 신호 구조를 만드는 편이 낫다.
- [제한처럼 읽히지만 막지 않는 장치가 반복해서 나타난다](./controls-that-read-as-limits-but-do-not-block.md) — 선언은 확률을 바꾸고 강제는 결정론적이라는 같은 교훈의 권한 영역판이다.

## 열린 질문

- 우리 스킬은 전부 지침 계열만 쓰고 있다. plan-validate-execute를 도입한다면 어느 스킬이 먼저인가? 결정론적 검증이 가능한 산출물(제텔카스텐 링크 유효성, Codex 변환 결과)이 후보로 보인다.
