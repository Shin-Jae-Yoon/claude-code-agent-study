# Mid Zettelkasten Synthesis

챕터별 정리본을 재료로 사용하되 결과를 챕터 안에 격리하지 말고 저장소 공통 제텔카스텐에 누적하라.

## 입력과 출력

- 입력: 한 챕터의 팀원별 정리본 2개 이상 또는 사용자가 지정한 Markdown 파일들
- 일반적인 입력: `chapters/chN/*/정리본.md`
- 기본 출력: 저장소 루트의 `zettelkasten/`

항상 원본 정리본을 보존하라. 기존 지식망과의 비교는 아래 스크립트로 하고, 메모 파일을 전부 읽지 마라.

## 스크립트

판단이 필요 없는 조회와 검증은 스크립트가 한다. **두 스크립트 모두 Bash로 실행하라. 코드를 Read 하지 마라** — 코드를 읽으면 실행 결과만 토큰을 쓰는 이점이 사라진다. 사용법은 아래가 전부이고, 인자는 `--help`로 확인할 수 있다.

```bash
# 합성 전 — 기존 메모 인벤토리 (메모 전체를 읽는 대신 메모당 한 줄 요약으로 받는다)
python3 "${CLAUDE_SKILL_DIR}/scripts/index_notes.py"

# 합성 중 — 만들려는 주제와 겹치는 기존 메모 찾기 (중복 생성 방지)
python3 "${CLAUDE_SKILL_DIR}/scripts/index_notes.py" --query "서브에이전트 컨텍스트 격리"

# 합성 후 — 링크·스키마·고립 검사 (오류가 있으면 종료 코드 1)
python3 "${CLAUDE_SKILL_DIR}/scripts/check_links.py"
```

`index_notes.py`는 메모 목록(slug·type·status·태그·제목), 태그 분포, 지도별 수록 수, 어느 지도에도 없는 메모를 출력한다. `check_links.py`는 깨진 상대 링크, frontmatter 스키마 위반, 위키 링크 사용, 제목 중복, 파일명 대소문자 충돌을 **오류**로, 고립 메모·H1 불일치·지도 후보를 **경고**로 보고한다.

`${CLAUDE_SKILL_DIR}`가 비어 있으면 `.claude/skills/mid-zettelkasten-synthesis/scripts/`로 대체하라. 저장소 위치는 `--root`로 넘길 수 있고, 생략하면 `$CLAUDE_PROJECT_DIR/zettelkasten`을 찾는다.

## 디렉터리 역할

```text
zettelkasten/
├── README.md
├── notes/
├── maps/
└── syntheses/
```

- `notes/`: 독립적으로 이해할 수 있는 주장, 질문, 실천법, 긴장 또는 사례 하나를 파일 하나로 저장하라.
- `maps/`: 관련 원자 메모를 주제와 관점에 따라 묶는 탐색 지도를 저장하라. 지식의 원문을 중복하지 마라.
- `syntheses/`: 이번 입력에서 무엇을 발견하고 어떤 메모를 생성·갱신했는지 기록하라.
- `README.md`: 전체 진입점과 주요 지도 링크를 유지하라.

## 합성 절차

1. 입력 파일의 경로와 작성자를 목록화하고, `index_notes.py`를 실행해 기존 지식망을 파악하라. 지도 구조가 필요하면 `zettelkasten/README.md`만 추가로 읽어라.
2. 각 문서에서 주장, 질문, 경험, 사례와 실패를 분리하라. 단순 키워드는 태그나 지도 후보일 뿐 원자 메모로 만들지 마라.
3. 표현이 달라도 의미가 같은 내용을 묶되 다음 신호를 구분하라.
   - **반복**: 둘 이상의 독립 문서에서 등장
   - **강조**: 한 문서에서 근거·사례와 함께 깊게 다룸
   - **긴장**: 문서 간 해석이나 경험이 다름
   - **독창**: 한 문서에만 있지만 후속 가치가 높음
4. 반복 횟수를 중요도의 신호로만 사용하라. 반복됐다는 이유로 사실이나 팀 합의로 단정하지 마라.
5. 새 메모 후보마다 `index_notes.py --query "<후보 주제>"`를 실행해 기존 메모와 비교하라. 상위 결과만 실제로 열어보고 [원자 메모 스키마](references/note-schema.md)에 따라 판정하라.
   - 같은 주장: 새 파일을 만들지 말고 기존 메모에 출처와 근거를 추가하라.
   - 겹치지만 다른 주장: 별도 메모를 만들고 관계를 설명하는 링크를 추가하라.
   - 충돌하는 주장: 양쪽을 보존하고 `contrasts` 관계로 연결하라.
6. 원자 메모끼리 관련, 보완, 대조, 선행, 적용 관계를 표준 Markdown 상대 링크로 연결하라.
7. 관련 메모가 3개 이상 모이면 `maps/`에 주제 지도를 생성하거나 기존 지도를 갱신하라. `check_links.py`의 "지도 후보" 항목이 이 조건을 만족하는 태그를 알려주지만, 태그가 같다고 같은 주제인 것은 아니므로 묶을지는 직접 판단하라.
8. 입력 단위가 챕터라면 `syntheses/chN.md`에 처리 결과를 기록하라. 챕터가 아니면 `syntheses/YYYYMMDD-source-slug.md`를 사용하라.
9. 주요 지도의 링크와 간단한 설명을 `zettelkasten/README.md`에 반영하라.

## 파일명과 링크

- 원자 메모는 `short-descriptive-slug.md` 형식의 구체적인 영문 소문자 kebab-case를 사용하라.
- 파일명을 안정적인 식별자로 취급하고 같은 주제의 파일을 임의로 바꾸지 마라.
- `[[...]]` 위키 링크와 별도 YAML `id`를 사용하지 마라.
- 모든 링크는 GitHub에서 이동 가능한 표준 Markdown 상대 링크로 작성하라.
- 모든 주장에 원본 파일과 작성자를 출처로 남기고 작성자 이름을 추측하지 마라.

## 마무리 점검

**`check_links.py`를 실행하라. 오류가 0건이 될 때까지 고치고 다시 실행하라.** 통과하지 못한 채로 완료를 보고하지 마라.

스크립트가 판정하는 것(링크 유효성, 스키마 값, 위키 링크, 제목 중복, 파일명 충돌)은 직접 눈으로 훑지 마라. 경고는 자동으로 고치지 말고 아래 기준으로 판단하라.

- 고립 메모 경고: 관련 메모나 지도에 연결하거나, 독립 상태인 이유를 합성 기록에 적어라.
- H1 불일치 경고: 제목을 바꿀 의도였는지 확인하고 한쪽에 맞춰라.

스크립트가 판정할 수 없어 직접 확인해야 하는 것은 다음뿐이다.

- 새 메모가 실제로 하나의 독립적인 주장 또는 질문만 담는가.
- 링크마다 연결 이유가 설명되어 있는가.
- 표현이 다를 뿐 의미가 같은 메모를 새로 만들지는 않았는가. (파일명·제목이 다르면 스크립트는 중복을 못 잡는다)

## 스크립트 유지

- Python 3 표준 라이브러리만 사용하라. 외부 패키지 설치를 요구하지 마라.
- 스키마 허용 값을 바꿀 때는 `scripts/zk.py`의 `ALLOWED_TYPES`·`ALLOWED_STATUS`와 [원자 메모 스키마](references/note-schema.md)를 함께 고쳐라. 한쪽만 바꾸면 검사와 문서가 어긋난다.
