Chapter 3 · 재윤

에이전트 스킬

클로드의 기능을 확장하는 지식 모듈

중심 메시지

스킬은 점진적 공개로 비용 없이 지식을 늘린다.

컨텍스트 윈도우는 공용 자산이다. 그런데 지식을 늘리면 컨텍스트를 먹는다 — 이 모순을 푸는 메커니즘이 점진적 공개(progressive disclosure)다. 쓰지 않는 지식의 비용은 0에 수렴한다. 토큰 비용 프레임워크, 최적화 5전략, 스크립트 우선, context: fork는 전부 이 한 문장을 실현하는 수단이다.

핵심 메커니즘

세 단계 점진적 공개

스킬은 세 가지 유형의 콘텐츠를 단계적으로 로드한다. 필요하지 않은 콘텐츠가 컨텍스트 윈도우를 선점하는 것을 방지하기 위해서다. 핵심은 파일이 접근되기 전까지는 컨텍스트를 소비하지 않는다는 것.

메타데이터

시작 시 자동 · 시스템 프롬프트

프론트매터의 name과 description만 상주한다.

~100 토큰 스킬당 고정 · 20개면 2,000토큰(전체의 1%)

~2,000 토큰 200줄(영문)/150줄(한국어) 이내 권장
3

리소스 / 코드

필요시 개별 접근

지원 파일 — 문서, 스크립트, 템플릿, 참조 자료.

사실상 무제한 접근 전까지 비용 0

그래서 무엇이 가능해지나 — 스킬에 포괄적인 API 문서, 대규모 데이터셋, 풍부한 예시를 포함하더라도 사용하지 않는 콘텐츠에 대한 컨텍스트 비용은 발생하지 않는다. 뒤에 나올 ECC의 286개 스킬이 이 원리의 극단 사례다.

대비 ① · 호출 방식

Commands vs Skills

둘 다 /이름으로 부를 수 있지만, 클로드가 알아서 꺼내 쓰느냐가 갈린다.

Commands

사용자가 직접 선택

  • 수동 호출만 — / 형태로 사용자가 고른다
  • 위치: .claude/commands/
  • 명령당 마크다운 파일 하나
  • 클로드는 이게 있는지도 신경 쓰지 않는다
사람이 판단 언제 쓸지를 사람이 안다는 전제
VS
Skills

클로드가 자동으로 찾아 사용

  • 자동 매칭 + 수동 호출 둘 다 가능
  • 위치: .claude/skills/<이름>/SKILL.md
  • 디렉터리 단위 — 지원 파일 번들 가능
  • description을 보고 활성화 여부를 클로드가 결정
description이 8할 트리거를 못 쓰면 스킬은 없는 것과 같다

우리 저장소 실측 — .claude/commands/는 프로젝트·사용자 어디에도 없다. 확장은 전부 스킬 쪽에 있다. 다만 스킬 9개 중 2개는 disable-model-invocation: true로 자동 호출을 끄고 수동 호출만 남겨 Command처럼 쓴다. (mid-update-claude-code-docs, pre-tell-me-about-claude-code)

# 커밋 메시지 생성

## 지침
1. `git diff --staged` 실행
2. 50자 미만의 요약, 상세 설명, 영향 구성 요소로 제안

## 유의사항
- 현재형 사용
- 무엇을 왜 설명, 어떻게가 아님

규칙 세 가지

  • name — 소문자·영숫자·하이픈, 최대 65자. 동명사 권장 (commit-helper ✗ → generating-commit-messages ✓)
  • description — 기능 + 사용 트리거를 모두 포함. 최대 1,024자. 클로드가 이 필드만 보고 활성화를 결정한다.
  • 200줄 이내 — 넘으면 스킬이 너무 많은 기능을 담았다는 신호. 분할하거나 reference.md로 분리 → SRP 유도
allowed-tools model context agent

우리 저장소 실측 — 9개 SKILL.md는 31~130줄로 전부 200줄 이내다. description은 전부 기능 + 트리거 문구를 담고 있고, 일부는 부정 조건까지 붙였다: "단순 요약이나 출처 없는 브레인스토밍에는 사용하지 않는다"

비용

토큰 비용 프레임워크

20만 토큰 기준 — 시스템 프롬프트·인프라가 1~2만, 대화 히스토리가 누적된다. 스킬에 실질적으로 쓸 수 있는 예산은 약 3만~5만 토큰. 이 안에서 가치를 극대화하는 게 목표다.

추정식계산우리 저장소 실측 대입
1단계스킬 수 × 100토큰9개 × 100 ≈ 900토큰
2단계동시 활성화 수(1~3) × 평균 SKILL.md이 발표를 만든 스킬 66줄 ≈ 660토큰
3단계로드된 지원 파일 줄 수 × 10(16+78+83) × 10 ≈ 1,770토큰

목표: 스킬 토큰 비용을 전체 컨텍스트의 15% 이내로 유지.

최적화 5전략

1. description 밀도

100토큰 예산 안에서 발견 가능성을 최대화한다.

2. 아는 건 빼기

useState 사용법 같은 범용 지식은 제거. 프로젝트 고유 컨벤션·팀 패턴·비공개 API 명세만 남기면 토큰 50~70% 절감.

3. 도메인별 분리

단, 1단계 깊이만 — 지원 파일이 또 다른 지원 파일을 부르면 부분적으로만 읽힐 위험.

4. 예시 최적화

예시 5개면 1,000~2,500토큰 = 예산의 20~50%. 대표 1~2개만 본문에, 나머지는 EXAMPLES.md로.

5. 스크립트 우선

복잡한 검증·변환·반복 처리는 scripts/로. 본문엔 사용법만(입력·출력·오류 처리).

# Spring REST 컨트롤러 생성

## 핵심 원칙
생성자 주입만 사용하며, 요청·응답은 엔티티가 아닌
DTO(record)로 주고받는다. 컨트롤러는 검증과 위임만 담당.

## 네이밍 규칙
- 요청 DTO : <동작><도메인>Request (e.g. UserCreateRequest)
- 응답 DTO : <도메인>Response  (e.g. UserResponse)

## 유의사항
- @RequestBody에는 @Valid, 제약은 DTO에 선언
- 예외는 @RestControllerAdvice에서 일괄 변환
- 트랜잭션은 Service 계층에만

상세 패턴은 [reference.md](./reference.md) 참조
템플릿은 [templates/Controller.java] 참조

예시 세트 — API 문서화 스킬

입력의 다양성(단순 → 복잡 → 엣지) + 출력의 일관성(동일 형식·품질)이 좋은 예시 세트의 조건. 

### 예시 1: 간단한 GET
입력:
@GetMapping("/users/{userId}")
public UserResponse getUser(@PathVariable Long userId) {
    return userService.findById(userId);
}
출력: GET /users/{userId}
  경로 파라미터 · userId (Long, required)
  응답 · 200 조회 성공 / 404 없음

### 예시 2: 요청 본문 있는 POST
입력:
@PostMapping("/users")
@ResponseStatus(HttpStatus.CREATED)
public UserResponse createUser(
    @RequestBody @Valid UserCreateRequest request) { ... }
출력: POST /users
  응답 · 201 생성 / 400 검증 실패 / 409 이메일 중복

### 예시 3: 인증 필요한 DELETE
입력:
@DeleteMapping("/users/{userId}")
@PreAuthorize("hasRole('ADMIN')")
@ResponseStatus(HttpStatus.NO_CONTENT)
public void deleteUser(@PathVariable Long userId, ...) { ... }
출력: DELETE /users/{userId}
  인증 · Bearer 토큰 필수 (ADMIN)
  응답 · 204 / 401 / 403 / 404

환각 방지 3종 세트

① 불확실성 표현 허용

"모르겠다"라고 답하도록 명시적으로 허용한다.
"이 설정값은 공식 문서에서 확인이 필요합니다."

금지: 확인 안 된 버전 정보 단정, 테스트 안 한 기본값 제시, 추측 기반 에러 코드

② 지식 범위 제한

참조 가능한 출처를 열거한다 — 프로젝트 소스, 의존성 파일, 내부 문서.

밖의 정보가 필요하면 "프로젝트 파일에서 확인되지 않습니다"라고 명시하게 한다.

③ 출처 명시

모든 기술 정보에 출처를 붙인다. 설정 옵션은 파일 경로:줄번호까지.

사용자가 신뢰성을 직접 검증할 수 있게 된다.

이 발표 자료 자체가 ①의 사례다 — pre-chapter-prep 스킬 규칙에 "적용예시는 파일을 읽고 확인된 것만. 기억으로 쓰지 마라. 없으면 '아직 없음'으로."가 박혀 있다. 그래서 정리본에 "아직 없음"이 반복해서 등장한다.

대비 ③ · 고급 최적화

context: fork — 격리 실행

기본적으로 스킬은 부모 대화의 컨텍스트 안에서 활성화된다. 대규모 코드베이스 분석처럼 토큰을 많이 쓰는 작업에선 이게 문제가 된다. context: fork는 스킬을 완전히 분리된 서브에이전트 컨텍스트에서 돌린다.

포크 없음 (기본)

탐색 과정이 부모 대화에 쌓인다

  • 수백 개 파일 탐색의 중간 결과물(파일 내용, grep 결과)이 그대로 컨텍스트에 적재
  • 대화 품질이 급격히 저하
  • plan 단계의 탐색이 run 단계 구현에 간섭

  • 부모 대화 히스토리에 접근 불가

agent는 context: fork일 때만 유의미하다.
Explore 코드베이스 탐색 특화 읽기 전용 · Plan 컨텍스트 수집과 계획 수립 · general-purpose 기본값

쓰기 좋은 곳 / 쓰면 안 되는 곳

  • ✅ 대규모 코드베이스 분석 — 수만 토큰 탐색을 요약 하나로
  • ✅ 세션 격리 워크플로 — SPEC 생성, TDD 사이클, 테스트 전략 수립
  • ❌ 부모 맥락이 필요한 스킬 — 이전 대화, 사용자 선호도에 의존하는 작업
  • ❌ 소규모 작업 — 서브에이전트 생성 오버헤드가 더 크다

공식문서 경고 — 지침만 있고 수행할 task가 없는 스킬을 포크하면, 서브에이전트는 가이드라인만 받고 실행할 프롬프트가 없어 빈손으로 돌아온다.

우리 저장소 실측 — context: fork·agent·model을 쓰는 스킬은 하나도 없다. 대신 pre-chapter-prep은 본문에 "HTML 생성은 초점이 좁아 서브에이전트에 위임해도 좋다"고 자연어로 적어 부분 격리한다.

이 스킬을 통째로 포크하면 안 되는 이유도 명확하다 — 역질문 게이트(사람과의 대화)가 불가능해지기 때문이다. 대신 mid-zettelkasten-synthesis를 도입 대상으로 확정했다. 저장소 전체를 훑는 대규모 탐색인 데다 "원자 메모와 주제 지도를 재구성하라"는 명확한 task가 있어 위 경고에도 걸리지 않는다.

실무 영향 — 팀이 .claude/skills/deploy를 커밋해도, 팀원이 ~/.claude/skills/deploy를 갖고 있으면 그 사람 로컬에선 개인 스킬이 실행된다. 팀 표준이 조용히 무력화될 수 있다.

단, 플러그인 스킬은 plugin-name:skill-name 네임스페이스라 충돌하지 않는다. Command와 Skill이 같은 이름이면 Skill이 우선(이건 노트와 일치).

2

allowed-tools — 제한이 아니라 사전 승인이다 (가장 중요)

교재 노트

도구를 제한한다

  • "파일 수정, 명령 실행 같은 위험한 작업이 원천 차단된다"
  • 나열되지 않은 도구는 못 쓴다고 서술
  • 읽기 전용 작업에 안전장치로 소개
safe-file-reader …라는 이름의 예시는 실제로 안전하지 않다
≠
공식문서

도구를 사전 승인한다

  • "grants permission … so Claude can use them without prompting"
  • "It does not restrict which tools are available: every tool remains callable"
  • 유효 범위는 호출한 그 턴에만 — 다음 메시지에서 해제
  • 진짜 제한은 disallowed-tools
허용 ≠ 제한 읽기 전용 강제는 disallowed-tools나 권한 설정으로

보안 함의 — 공식문서는 이렇게 덧붙인다. "Review project skills before trusting a repository, since a skill can grant itself broad tool access."

스킬을 PR로 주고받는 우리 팀에는 직접적인 리뷰 항목이다. 3장이 말한 "스킬 변경도 코드 리뷰하라"의 진짜 이유.

3

SKILL.md 길이 — 임계값만 다르다

교재 노트

200줄 (한국어 150줄) 이내

  • 넘으면 분할하거나 reference.md로 분리
vs
공식문서

under 500 lines

  • "Move detailed reference material to separate files."

방향(상세 자료는 별도 파일로)은 같고 숫자만 다르다. 노트 쪽이 더 보수적이므로 노트 기준을 지키면 공식 기준도 자동 충족. 우리 9개는 31~130줄로 양쪽 다 통과.

덤 — 노트에 없던 최신 사항

⏳ 스킬 콘텐츠 생명주기 (점진적 공개의 이면)

"the rendered SKILL.md content enters the conversation as a single message and stays there for the rest of the session"

  • 노트는 "필요할 때 로드된다"까지만 다룬다. 실제로는 한 번 로드되면 세션 내내 남는다 → 2단계는 일회성이 아니라 누적 고정비
  • 그래서 공식 권고가 "every line is a recurring token cost"
  • 자동 압축 시 스킬당 앞 5,000토큰, 합산 25,000토큰 예산으로 재부착
  • allowed-tools 승인은 콘텐츠와 달리 다음 메시지에 해제

🧾 노트에 없는 프론트매터 필드

  • when_to_use — 트리거 문구를 description에 덧붙임
  • disallowed-tools — 진짜 도구 제한
  • background — fork 전용, 기본 true(백그라운드 실행)
  • effort — 추론 강도 (low~max)
  • paths — glob 매칭 시에만 자동 로드
  • hooks, arguments, user-invocable: false

1단계 예산도 설정 가능 — description+when_to_use는 1,536자에서 잘리므로 핵심 사용 사례를 맨 앞에. 목록 예산은 skillListingBudgetFraction으로 조정.

공식문서 · 스크립트 우선의 실물

codebase-visualizer

교재 "코드 실행 통합"을 그대로 구현한 공식 예제. 대화형 HTML 트리뷰를 만든다.

allowed-tools: Bash(python3 *)
---
python3 ${CLAUDE_SKILL_DIR}/scripts/visualize.py .

SKILL.md에는 사용법만, 스크립트 코드는 컨텍스트에 안 들어간다. ${CLAUDE_SKILL_DIR} 덕분에 개인·프로젝트·플러그인 어디에 깔려도 경로가 풀린다. Python 내장 라이브러리만 써서 설치할 패키지도 없다.

ECC — Everything Claude Code

286 스킬 · 68 에이전트 · 94 커맨드

스킬을 286개 깔아도 세션이 안 터지는 이유가 정확히 이 장의 주제다. 1단계 메타데이터만 상주하고 본문은 on-demand로 로드되기 때문.

"Keeping those jobs separate is how ECC adds capability without dumping the entire repository into every session."
표어도 "Optimize the context window. Persist everything else."

대표 스킬: tdd-workflow, security-review, e2e-testing, search-first. Claude Code·Codex·Cursor·OpenCode에서 함께 동작 — 우리가 .codex/skills를 미러링하는 것과 같은 문제의식.

잘하고 있는 것 — 팀 스킬 개발

표준화된 구조

.claude/skills/README.md가 pre-/mid-/접두사 없음 규칙을 명문화. 폴더 대신 접두사를 쓴 이유까지 적혀 있다 — 스킬 탐색은 한 단계만 보기 때문.

리뷰 프로세스

승격 4단계: 개인 제작 → 모임 논의 → 접두사 붙여 이동 → PR로 통합. 실제로 #7, #8 PR 병합 이력이 남아 있다.

문서화 분리

4개 스킬이 SKILL.md와 별도로 README.md를 갖는다 — 지침(클로드용)과 설명(사람용)의 분리.

정리

다음에 만들 것

실측에서 비어 있던 4칸을 채운다.

1

sync-claude-skills-to-codex에 scripts/ 도입

변환 규칙이 결정론적인데 지금은 매번 LLM이 수행한다. 스크립트로 옮기면 실행 결과(변환 파일 목록 + PASS/FAIL)만 컨텍스트에 남는다.

2

mid-zettelkasten-synthesis에 context: fork

저장소 전체 탐색이라 포크 이득이 크고, 명확한 task가 있어 공식문서 경고에 걸리지 않는다.

3

범용 유틸리티 스킬을 ~/.claude/skills/에 신설

현재 개인 스킬 디렉터리 자체가 없다. Java/Spring 코드 리뷰처럼 프로젝트와 무관한 것부터. 단, 정정 ①의 함정 주의 — 개인 스킬이 프로젝트 스킬을 덮어쓰므로 pre-/mid-와 겹치는 이름은 금물.

4

기존 스킬에 EXAMPLES.md 보강

"다양한 입력 + 일관된 출력" 예시 세트가 전무하다. 3단계 파일로 분리하면 비용 없이 품질을 올릴 수 있다.

스킬은 점진적 공개로 비용 없이 지식을 늘린다.

1단계 메타데이터만 상주하고, 본문은 부를 때, 지원 파일은 읽을 때, 스크립트는 결과만.
ECC가 스킬 286개를 깔고도 세션이 멀쩡한 이유이고 — 우리가 아직 scripts/와 context: fork를 안 써서 남겨둔 여지이기도 하다.
