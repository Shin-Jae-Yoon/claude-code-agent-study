# Chapter 3. 에이전트 스킬

> 상태: **확정본** — 역질문 답변 반영 완료
> 실측 기준일: 2026-08-12 (내 클로드 시스템 · 공식문서 · 외부 저장소 모두 이 날짜 기준)

## 중심 메시지

> **스킬은 점진적 공개(progressive disclosure)로 비용 없이 지식을 늘린다.**

스킬은 클로드의 기능을 확장하는 **지식 모듈**이다. 이 장의 전제는 **컨텍스트 윈도우는 공용 자산**이라는 것 — 유용한 지식과 패턴을 공유 가능한 형태로 캡슐화해 팀 전체 또는 커뮤니티가 함께 활용할 수 있어야 한다는 의미다.

그런데 지식을 늘리면 컨텍스트를 먹는다. 이 모순을 푸는 메커니즘이 **점진적 공개**다. 필요하지 않은 콘텐츠가 컨텍스트 윈도우를 선점하지 못하게 단계적으로 로드하기 때문에, 스킬을 아무리 많이 갖춰도 **쓰지 않는 지식의 비용은 0에 수렴한다.** 이 장의 나머지 내용(토큰 비용 프레임워크, 최적화 5전략, 스크립트 우선, `context: fork`)은 전부 이 한 문장을 실현하는 수단이다.

## 1. 스킬의 개념과 구조

### 1.1 스킬의 구성: 메인 + 서브

- **메인**: `SKILL.md` (스킬별 지침 파일)
- **서브**: `scripts/`, `templates/`, `reference.md` … (선택적 지원 파일)

### 1.2 Commands와 Skills

| 구분 | Commands | Skills |
| --- | --- | --- |
| 호출 | 사용자가 `/` 형태로 직접 선택 | 프롬프트 내용에 따라 클로드가 자동으로 찾아 사용 |
| 위치 | `.claude/commands/` | `.claude/skills/` |

**내 클로드 시스템에서 확인한 예시**

- 프로젝트·사용자 어디에도 `.claude/commands/`는 없다. 확장은 전부 `.claude/skills/` 쪽에 있다.
- 다만 이 저장소 스킬 중 2개는 `disable-model-invocation: true`로 **자동 호출을 끄고 `/` 수동 호출만 남겨** Command에 가깝게 쓰고 있다 (`mid-update-claude-code-docs`, `pre-tell-me-about-claude-code`).

### 1.3 스킬의 유형

| 유형 | 위치 | 범위 |
| --- | --- | --- |
| 개인 스킬 | `~/.claude/skills/` | 개발자 개인의 모든 프로젝트 |
| 프로젝트 스킬 | 프로젝트 루트의 `.claude/skills/` | 저장소에 포함되어 팀과 공유, 자동 배포 가능 |
| 플러그인 스킬 | 플러그인에 번들되어 배포 | 마켓플레이스로 설치 후 바로 사용 |

**내 클로드 시스템에서 확인한 예시** — 세 유형이 전부 실측된다.

- **개인 스킬**: `~/.claude/skills/` 디렉터리 자체가 **없다**. 개인 전용 범용 스킬은 아직 만들지 않았다.
- **프로젝트 스킬**: `.claude/skills/`에 9개 (`pre-chapter-prep`, `pre-chapter-ideas`, `pre-tell-me-about-claude-code`, `mid-chapter-merge`, `mid-zettelkasten-synthesis`, `mid-study-deep-dive`, `mid-study-wrapup`, `mid-update-claude-code-docs`, `sync-claude-skills-to-codex`).
- **플러그인 스킬**: `ouroboros@ouroboros` v0.51.0이 설치·활성화되어 있다. `~/.claude/settings.json`의 `enabledPlugins`에 `true`, 마켓플레이스는 `extraKnownMarketplaces`에 GitHub `Q00/ouroboros`로 등록, 실체는 `~/.claude/plugins/cache/ouroboros/ouroboros/0.51.0`에 캐시되어 있다. 이 플러그인이 `ouroboros:interview`, `ouroboros:seed` 같은 스킬을 함께 제공한다.

### 1.4 스킬 디렉터리 기본 구조

```text
my-skill/
├── SKILL.md
├── reference.md
├── scripts/
│   └── helper.py
└── templates/
    └── template.txt
```

**내 클로드 시스템에서 확인한 예시**

- `references/`를 쓰는 스킬은 3개다: `mid-study-deep-dive/references/research-lenses.md`(16줄), `mid-zettelkasten-synthesis/references/note-schema.md`(78줄), `sync-claude-skills-to-codex/references/codex-adaptation-rules.md`(83줄).
- `scripts/`와 `templates/`는 **어느 스킬에도 없다.** 현재 모든 스킬이 문서형이다.

### 1.5 SKILL.md 파일 구조

`.claude/skills/skill-name/`에 위치하며 **YAML 프론트매터 + 마크다운 본문**으로 구성한다.

| 필드 | 필수 | 내용 |
| --- | --- | --- |
| `name` | 선택 | 소문자·영숫자·하이픈만, 최대 65자. 생략하면 디렉터리 이름을 사용. **동명사 형태 권장** |
| `description` | **필수** | **기능 + 사용 트리거**를 모두 포함. 최대 1,024자. 클로드가 요청 분석 시 이 필드를 참조해 활성화 여부를 결정 |
| `allowed-tools` | 선택 | 활성화 시 사용 가능한 도구 목록 (e.g. `Read, Grep, Glob`) |
| `model` | 선택 | 스킬 실행 시 사용할 모델 |
| `context` | 선택 | 추가 컨텍스트 설정 |
| `agent` | 선택 | 서브에이전트 관련 설정 |

`name` 네이밍:

- `commit-helper` (X)
- `generating-commit-messages` (O), `analyzing-code-patterns` (O)

`description`은 구체적으로: `"PDF 파일에서 텍스트와 표 추출, 양식 작성, 문서 병합. PDF 파일 작업 시 사용"`처럼 쓰는 편이 효과적이다.

```markdown
---
name: generating-commit-messages
description: git diff에서 명확한 커밋 메시지 생성. 커밋 메시지 작성 또는 스테이징된 변경 사항 검토 시 사용
---

# 커밋 메시지 생성

## 지침
1. `git diff --staged` 실행
2. 50자 미만의 요약, 상세 설명, 영향을 받는 구성 요소로 메시지 제안

## 유의사항
- 현재형 사용
- 무엇을 왜 설명, 어떻게가 아님
```

**SKILL.md는 200줄 이내 유지 권장.** 초과하면 스킬이 너무 많은 기능을 담고 있다는 신호다 → 더 작은 단위로 분할하거나 상세 내용을 `reference.md`로 분리한다. 결과적으로 SRP를 따르도록 유도한다.

> ⚠️ **공식문서와 다름** — 현재 공식문서는 `Keep SKILL.md under 500 lines`로 안내한다. [5. 공식문서 대조 ③](#-교재-200줄-vs-공식-500줄) 참조.

**내 클로드 시스템에서 확인한 예시**

- 9개 SKILL.md 줄 수: 31 / 52 / 53 / 66 / 66 / 67 / 70 / 71 / 130줄. **전부 200줄 이내**이고, 한국어 기준 권장선(150줄)도 넘지 않는다. 최장은 `mid-study-wrapup`(130줄).
- `name`은 9개 모두 정의되어 있지만 동명사 형태는 아니다 (`pre-chapter-prep`, `mid-chapter-merge` 등 명사형). 대신 `.claude/skills/README.md`에 정의된 **`pre-`(모임 전) / `mid-`(모임 중) / 접두사 없음(상시)** 규칙으로 시점 그룹을 표시한다.
- `description`은 교재 권장대로 **기능 + 트리거**를 모두 담는다. 예: `mid-zettelkasten-synthesis`는 `"제텔카스텐으로 정리", "정리본 연결", "공통 내용 메모", "zettelkasten synthesis"`라고 트리거 문구를 직접 나열하고, 여기에 더해 **부정 조건**(`단순 문서 요약에는 사용하지 않는다`)까지 붙였다.

### 1.6 세 단계 점진적 작동 방식

| 단계 | 레벨 | 로딩 시점 | 토큰 비용 | 콘텐츠 |
| --- | --- | --- | --- | --- |
| 1단계 | 메타데이터 | 시작 시 자동 (시스템 프롬프트) | 스킬당 약 100토큰 | 프론트매터의 `name`, `description` |
| 2단계 | 지침 | 스킬 트리거 시 (Bash로 읽기) | 2,000토큰(200줄) 이하 권장 | SKILL.md 본문의 워크플로·유의사항·가이드라인 등 절차적 지식 |
| 3단계 | 리소스/코드 | 필요시 개별 접근 | 사실상 무제한 | 지원 파일 (문서·스크립트·템플릿) |

3단계 지원 파일의 종류:

- **마크다운 문서**: 전문화된 가이드와 워크플로 (e.g. `FORMS.md`, `REFERENCE.md`)
- **실행 가능한 스크립트**: Bash로 실행되어 결정론적 작업 수행 (e.g. `fill_form.py`, `validate.py`)
- **참조 자료**: DB 스키마, API 문서, 템플릿, 예시

핵심은 **파일이 접근되기 전까지는 컨텍스트를 소비하지 않는다**는 점이다. 그래서 스킬에 포괄적인 API 문서, 대규모 데이터셋, 풍부한 예시를 포함해도 사용하지 않는 콘텐츠에 대한 컨텍스트 비용은 발생하지 않는다.

**내 클로드 시스템에서 확인한 예시**

- 3단계 참조가 실제로 걸려 있다. `mid-study-deep-dive/SKILL.md:21` → `[탐구 렌즈](references/research-lenses.md)`, `mid-zettelkasten-synthesis/SKILL.md:43` → `[원자 메모 스키마](references/note-schema.md)`, `sync-claude-skills-to-codex/SKILL.md:22` → `[Codex 변환 규칙](references/codex-adaptation-rules.md)`.
- 지금 이 문서를 만드는 `pre-chapter-prep`은 **2단계 지침만으로 동작**한다 (지원 파일 없이 66줄).

### 1.7 스킬 컨텍스트 비용

20만 토큰 컨텍스트 윈도우 기준 예산 배분:

- 시스템 프롬프트 / 기본 인프라: 약 1만 ~ 2만 토큰
- 대화 히스토리 / 프로젝트 파일 읽기: 세션이 진행될수록 누적
- **스킬에 실질적으로 할당 가능한 예산: 약 3만 ~ 5만 토큰**

이 예산 안에서 스킬의 가치를 극대화하는 것이 컨텍스트 비용 프레임워크의 핵심 목표다.

**1단계 — 메타데이터 (고정 비용)**

- 스킬당 약 100토큰 고정 소비 (`name` 약 15~20, `description` 약 60~80)
- `allowed-tools`, `model` 같은 나머지 필드는 시스템 프롬프트에 직접 노출되지 않아 이 비용에 미포함
- 20개 스킬 기준 총 2,000토큰 (전체 컨텍스트의 1% 수준)

**2단계 — 지침 (변동 비용)**

- 활성화 시 발생. 영문 200줄 / **한국어 150줄** 이내
- 파일 내 코드 예시 최소화, 상세 예시는 3단계로 분리

**3단계 — 지원 파일 (가장 예측하기 어려운 변동 비용)**

- **문서 파일**: 읽기로 한 시점에 컨텍스트로 로드
- **실행 파일**: **결과만 컨텍스트에 반영 (토큰 비용 0)**
  - e.g. 데이터 스키마 검증 규칙을 `reference.md`에 200줄로 기술하면 약 2,000토큰을 소비하지만, `validate_schema.py`로 구현하면 실행 결과(PASS/FAIL과 오류 메시지)의 100~200토큰만 소비

**최적화 전략 5가지**

1. **`description` 토큰 밀도 극대화** — 한정된 100토큰 예산 내에서 최대한의 발견 가능성 확보
2. **클로드가 이미 아는 지식은 본문에서 제거** — 파이썬 리스트 컴프리헨션, 리액트 `useState` 같은 범용 지식은 빼고, 클로드가 모르는 정보(프로젝트 고유 컨벤션, 팀 특화 패턴, 비공개 내부 API 명세)를 넣는다. 이 기준을 따르면 동일 기능 대비 약 50~70% 적은 토큰으로 구현 가능
3. **지원 파일을 도메인별로 분리** — 단, **SKILL.md로부터 1단계 깊이만 유지**해 지원 파일이 또 다른 지원 파일을 불러오지 않게 한다. 중첩 참조는 클로드가 파일을 부분적으로만 읽을 위험이 있다
4. **입출력 예시 최적화** — 예시 세트 1개가 평균 200~500토큰이면 5개는 1,000~2,500토큰으로 SKILL.md 예산의 20~50%에 달한다. 대표적이고 다양한 예시 1~2개만 SKILL.md에 두고 나머지는 `EXAMPLES.md`로 분리, 엣지 케이스가 필요할 때만 참조하게 한다
5. **스크립트 우선 전략** — 복잡한 검증 규칙, 데이터 변환 로직, 반복 처리 절차는 `scripts/`로 구현하고 SKILL.md에는 사용법(입력 형식, 출력 형식, 오류 처리)만 간결하게 기술

**비용 추정식**

```text
1단계 = 스킬 수 × 100토큰
2단계 = 동시 활성화 스킬 수(보통 1~3개) × 평균 SKILL.md 토큰 수
3단계 = 로드된 지원 파일 총 줄 수 × 10 (근삿값)
```

목표는 스킬 토큰 비용을 **전체 컨텍스트 윈도우의 15% 이내**로 유지하는 것.

**내 클로드 시스템에서 확인한 예시** — 위 식에 실측치를 대입해 봤다.

- **1단계**: 프로젝트 스킬 9개 × 100 ≈ **900토큰**. (여기에 ouroboros 플러그인 스킬 30여 개가 더해지므로 실제 고정 비용은 이보다 크다.)
- **2단계**: 이 세션에서 활성화된 `pre-chapter-prep`은 66줄 → 약 660토큰 규모.
- **3단계**: 지원 파일이 전부 로드된다고 가정해도 (16+78+83)줄 × 10 ≈ **1,770토큰**.
- 전략 3의 **1단계 깊이 유지**는 지켜지고 있다. `references/*.md`가 다른 지원 파일을 로드하는 구조는 없다. (`note-schema.md` 안에 보이는 링크들은 **결과물인 메모의 작성 예시** 안에 들어 있는 예시 링크이지, 스킬이 따라가는 로딩 체인이 아니다.)
- 전략 5의 **스크립트 우선**은 아직 미적용이다. `scripts/`가 하나도 없다. 도입한다면 `sync-claude-skills-to-codex`의 파일 변환·복사처럼 결정론적인 절차가 1순위 후보다.

### 1.8 도구 접근 권한 제한

`allowed-tools`로 스킬 활성화 시 사용할 도구를 제한할 수 있다.

```markdown
---
name: safe-file-reader
description: 변경 없이 파일 읽기. 읽기 전용 파일 액세스에 사용
allowed-tools: Read, Grep, Glob
---
```

- 파일 수정, 명령 실행 같은 위험한 작업이 원천 차단된다.
- 코드 리뷰, 보안 감사, 문서 분석 같은 **읽기 전용 작업**에서 유용하다.

> 🚨 **공식문서와 정반대** — 이 절의 서술은 **틀렸다.** 공식문서상 `allowed-tools`는 **제한이 아니라 사전 승인(grant)**이다. 실제 제한은 `disallowed-tools`가 담당한다. 이 장에서 가장 중요한 정정이므로 [5. 공식문서 대조 ②](#-교재-도구-제한-vs-공식-사전-승인)에서 따로 다룬다.

**내 클로드 시스템에서 확인한 예시**

- `pre-tell-me-about-claude-code`: `allowed-tools: WebFetch(domain:code.claude.com) WebSearch` — 공식문서 근거로만 답하게 하는 목적에 맞춰 **도메인까지 좁혀 사전 승인**했다. (다만 위 정정에 따르면 이건 "다른 도구를 못 쓰게 막는" 설정이 아니라 "이 도구는 물어보지 않고 쓰라"는 설정이다.)
- `mid-update-claude-code-docs`: `allowed-tools: WebFetch(domain:code.claude.com) Read Write Edit Glob Bash(date +%F)` — Bash를 통째로 열지 않고 `date +%F` 하나만 사전 승인했다.
- 나머지 7개 스킬은 `allowed-tools`가 없다. 즉 매번 권한 프롬프트를 거치는 상태다.

### 2.1 스킬 목록 확인과 조합

"사용 가능한 스킬이 뭐야?" 또는 "모든 사용 가능한 스킬을 나열해 줘"라고 요청하면 된다. 직접 확인할 수도 있다.


복잡한 작업에서는 여러 스킬을 조합한다.

- e.g. API 개발 작업: `analyzing-api-requirements` → `implementing-rest-endpoints` → `testing-api-endpoints`
- 각 스킬은 개발 과정의 특정 단계에 집중하고, 필요한 시점에 순차적으로 또는 병렬로 활성화된다.

**주의점**: 유사한 기능의 스킬 여러 개가 동시에 활성화될 수 있다. 각 스킬은 **고유한 트리거 용어**를 `description`에 지정해야 한다.

- `데이터 처리` (X) — 너무 모호
- `Excel 스프레드시트 분석`, `CSV 파일 변환` (O) — 구체적

**내 클로드 시스템에서 확인한 예시**

- 스터디 흐름 자체가 스킬 조합이다. `pre-chapter-prep`(개인 정리본+발표) → `mid-chapter-merge`(3인 통합) → `mid-zettelkasten-synthesis`(원자 메모) → `mid-study-deep-dive`(질문·최신 변경점) → `mid-study-wrapup`(회고) 순으로 단계별 스킬이 나뉘어 있다.
- 충돌 회피도 실측된다. `mid-chapter-merge`(정리본 통합)와 `mid-zettelkasten-synthesis`(메모 연결)는 둘 다 "여러 정리본을 입력받는" 유사 스킬인데, 전자는 `"챕터 결과물", "3개 통합", "주간 결과물"`, 후자는 `"제텔카스텐으로 정리", "공통 내용 메모"`로 트리거를 분리했다.

### 2.2 커스텀 스킬 개발

**요약 3단계**: ① 목적 정의 → ② SKILL.md 작성 → ③ 지원 파일 추가

| 단계 | 할 일 |
| --- | --- |
| 목적 정의 | 작업 범위 결정 / 활성화 트리거 정의 / 필요 도구 식별 |
| SKILL.md 작성 | YAML 프론트매터 (`name` + `description`) / 본문 지침 작성 |
| 지원 파일 추가 | `reference.md` / `scripts/` / `templates/` |

**상세 절차**

1. 스킬의 목적과 범위를 명확히 정의한다. (어떤 작업을 지원할 것인지, 언제 활성화되어야 하는지, 어떤 도구가 필요한지)
2. `mkdir -p ~/.claude/skills/<스킬명>` 으로 디렉터리를 생성한다. 위치 선택은 [1.3 스킬의 유형](#13-스킬의-유형) 참조.
3. `SKILL.md`를 작성한다. 프론트매터에 `name`과 `description`을 정의하고 본문에 구체적인 지침을 쓴다.
4. 지원 파일을 추가한다. 복잡하면 `reference.md`에 상세 레퍼런스, `scripts/`에 헬퍼 스크립트, `templates/`에 코드 템플릿을 배치한다. SKILL.md에서 **상대 링크로 참조**하면 필요할 때 클로드가 점진적으로 로드한다.

**e.g. Spring REST 컨트롤러 생성을 지원하는 커스텀 스킬**

```markdown

allowed-tools: Read, Write, Edit, Grep

# Spring REST 컨트롤러 생성

## 핵심 원칙

컨트롤러는 생성자 주입만 사용하며, 요청·응답은 엔티티가 아닌 DTO(record)로 주고받는다.
비즈니스 로직은 Service에, 영속성 접근은 Repository에 둔다. 컨트롤러는 검증과 위임만 담당한다.

## 파일 구조

패키지는 계층이 아닌 도메인 기준으로 나눈다.
1. `domain/user/UserController.java`
2. `domain/user/UserService.java`
3. `domain/user/UserRepository.java`
4. `domain/user/dto/UserCreateRequest.java`, `UserResponse.java`
5. `domain/user/UserEntity.java`

## 네이밍 규칙

- 클래스 : PascalCase (e.g. UserController)
- 요청 DTO : `<동작><도메인>Request` (e.g. UserCreateRequest)
- 응답 DTO : `<도메인>Response` (e.g. UserResponse)
- 서비스 메서드 : 동사로 시작 (e.g. createUser, findUserById)

## 유의사항

- 컨트롤러당 하나의 도메인
- `@RequestBody`에는 `@Valid`를 붙이고 제약은 DTO에 선언
- 예외는 `@RestControllerAdvice`에서 일괄 변환, 컨트롤러에서 try-catch 금지
- 트랜잭션은 Service 계층에만 (`@Transactional(readOnly = true)` 기본)

상세 패턴은 [reference.md](./reference.md) 참조
템플릿은 [templates/Controller.java](./templates/Controller.java) 참조
```

**예시 세트 설계**

입출력 예시 세트를 **다양하게 2개 이상** 작성해 패턴을 정확히 학습하도록 돕는다. 좋은 예시 세트란:

- **입력의 다양성**: 간단한 입력, 복잡한 입력, 엣지 케이스 모두 포함
- **출력의 일관성**: 모든 예시가 동일한 형식과 품질 기준을 따름

**e.g. API 문서화 스킬 (Spring 기준 예시 세트)**

`````markdown
### 예시 1: 간단한 GET 엔드포인트

입력:
```java
@GetMapping("/users/{userId}")

    return userService.findById(userId);
}

출력:

경로 파라미터

응답

- 404: 사용자를 찾을 수 없음

}
```

출력:

요청 본문
```json

응답

- 400: 유효성 검사 실패

}
```

출력:

인증: Bearer 토큰 필수 (ADMIN 역할)

경로 파라미터

응답
- 204: 삭제 성공(본문 없음)
- 401: 인증 실패
- 403: 권한 부족
- 404: 사용자를 찾을 수 없음
`````

```markdown
# API 문서 생성

## 정확성 원칙

확실하지 않은 정보에 대해서는 다음과 같이 표현한다.
- "이 설정값은 공식 문서에서 확인이 필요합니다."
```

```text
├── reference.md
├── scripts/
│   ├── format_data.py
│   ├── validate_schema.py
│   └── requirements.txt

    └── data_template.json
```

**내 클로드 시스템에서 확인한 예시**

- **아직 없음.** 9개 스킬 중 `scripts/`를 가진 스킬은 하나도 없다.
- 도입한다면 `sync-claude-skills-to-codex`가 1순위다. 지금은 "`.claude/skills`를 읽고 변환 규칙에 따라 `.codex/skills`에 쓴다"를 매번 LLM이 수행하는데, 규칙이 결정론적이라 스크립트로 옮기면 토큰 비용이 실행 결과(변환 파일 목록 + PASS/FAIL)만 남는다.

### 2.5 테스트와 검증 방법

1. `description`이 구체적인지 확인
2. 스킬 디렉터리 경로 확인 (개인 스킬 / 프로젝트 스킬)
3. YAML 유효성 검사 — 시작과 종료에 `---`, **탭 사용 금지**, 올바른 들여쓰기, 유효한 구문
4. 디버그 모드 활용 — `claude --debug`로 스킬 로딩 문제 확인

**내 클로드 시스템에서 확인한 예시**

- 1·2·3은 통과 상태다. 9개 SKILL.md 전부 `---` 쌍과 `name`/`description`을 갖췄고 `.claude/skills/<이름>/SKILL.md` 경로 규칙을 지킨다.
- 4의 `claude --debug`는 아직 돌린 적 없다. `~/.claude/debug/` 디렉터리가 존재하지 않는다.

## 3. 스킬 고급 사용과 최적화

API 설계, 프론트엔드 구현, DB 설계, 테스트 자동화처럼 여러 영역이 유기적으로 연결된 복잡한 시스템에서는 **토큰 효율성 최적화**와 **팀 단위 협업 개발**의 고급 패턴이 필요하다.

### 3.1 동적 스킬 로딩 패턴

앞서 본 세 단계 점진적 작동 방식을 **동적 로딩 패턴**이라고 부른다.

```text
database-operations/
├── SKILL.md                     # 1단계: 핵심 원칙(100줄 이내)
├── reference/
│   ├── queries.md               # 2단계: 쿼리 작성 상세 가이드
│   ├── migrations.md            # 2단계: 마이그레이션 패턴
│   └── optimization.md          # 2단계: 성능 최적화 기법
├── templates/
│   ├── model.py.template        # 3단계: 모델 템플릿
│   └── migration.py.template    # 3단계: 마이그레이션 템플릿
└── scripts/
    └── generate_model.py        # 3단계: 모델 생성 스크립트
```

> (확인 필요) 원문 노트의 단계 표기가 1.6절 표와 어긋난다. 1.6절 기준으로는 `reference/`·`templates/`·`scripts/`가 모두 3단계다. 위 구조도의 "2단계/3단계"는 로딩 우선순위를 나눈 표기로 보인다.

### 3.2 스킬 성능 최적화

토큰 효율성과 응답 품질의 균형을 찾는 작업이다.

1. **정보 밀도 향상** — 불필요한 설명 제거, 핵심 정보를 간결하게. 같은 내용을 더 적은 토큰으로 전달하면 컨텍스트를 더 효율적으로 쓸 수 있다.
2. **조건부 로딩** — 필요한 정보만 로드하도록 구성. SKILL.md에 "복잡한 쿼리 작성 시에는 `queries.md` 참조"처럼 **조건을 명시**한다.
3. **캐싱 고려** — 자주 쓰는 정보는 SKILL.md에 직접 포함, 드물게 쓰는 정보는 별도 파일로 분리.

```markdown
# 데이터베이스 작업

## 핵심 원칙(항상 적용)
- ORM 우선 사용, 필요시 raw SQL
- 인덱스 설계 먼저, 쿼리 작성 나중
- 트랜잭션 범위 최소화

## 빠른 참조(자주 사용)
- 기본 CRUD: Model.create(), Model.get(), Model.update(), Model.delete()
- 필터링: Model.filter(field=value)
- 정렬: Model.order_by('field')

## 상세 가이드(필요시 로드)
- 복잡한 조인 쿼리: [queries.md](./reference/queries.md)
- 마이그레이션 전략: [migrations.md](./reference/migrations.md)
- 쿼리 최적화: [optimization.md](./reference/optimization.md)
```

**내 클로드 시스템에서 확인한 예시**

- **조건부 로딩**이 실제로 적용되어 있다. `mid-study-deep-dive/SKILL.md:21`은 `[탐구 렌즈](references/research-lenses.md)에서 **관련 렌즈만 골라** 질문을 만들라`고 조건을 걸었고, `sync-claude-skills-to-codex/SKILL.md:20`도 `직접 참조하는 references/, scripts/, assets/를 읽어라`로 범위를 한정한다.

### 3.3 스킬 버전 관리

SKILL.md 안에 Version History 섹션을 두어 변경사항을 문서화하는 것을 권장한다.

```markdown
## Version History

### v2.1.0(2025-12-01)
- 새로운 마이그레이션 패턴 추가
- 성능 최적화 가이드 업데이트

### v2.0.0(2025-11-15)
- ORM 전환에 따른 전면 개편
- raw SQL 예시를 ORM 예시로 대체

### v1.0.0(2025-10-01)
- 초기버전 릴리즈
```

> 원문 노트에서 v1.0.0의 날짜가 v2.1.0과 동일한 `2025-12-01`로 적혀 있어 오기로 보인다. 위에서는 순서가 맞도록 표기했다. (확인 필요)

**내 클로드 시스템에서 확인한 예시**

- **아직 없음.** `.claude/` 전체에 `Version History` 섹션을 가진 파일이 없다. 대신 스킬 변경 이력은 **Git 커밋**에 남는다.

### 3.4 팀 스킬 개발

- 팀 스킬은 프로젝트 저장소의 `.claude/skills/`에 저장하고 **Git으로 관리**한다.
- 마켓플레이스 배포가 목적이라면 **플러그인**을 통한 배포를 권장한다.

**원칙 3가지**

1. **표준화된 구조** — 팀 내 모든 스킬이 동일한 디렉터리 구조와 파일 명명 규칙을 따른다.
2. **리뷰 프로세스** — 스킬 변경도 코드 리뷰한다. `description`의 명확성, 예시의 품질, 도구 권한 설정의 적절성을 검토한다.
3. **피드백 수집 및 반영**

**내 클로드 시스템에서 확인한 예시** — 이 장에서 가장 잘 실천된 부분이다.

- **표준화**: `.claude/skills/README.md`가 `pre-`/`mid-`/접두사 없음 규칙과 `pre-<skill-name>/SKILL.md` 구조를 명문화했다. 폴더 대신 접두사를 쓴 이유까지 적혀 있다 — *"클로드 코드 스킬 탐색은 `.claude/skills/<이름>/SKILL.md` 한 단계만 본다. `.claude/skills/모임전/...`처럼 폴더로 묶으면 스킬로 인식이 안 된다."*
- **리뷰 프로세스**: 승격 절차 4단계(개인 제작 → 모임 논의 → 접두사 붙여 이동 → **PR로 통합 관리**)가 문서화되어 있고, 실제로 Git 이력에 `#7`, `#8` PR 병합이 남아 있다.
- **소유권 기록**: README에 누가 만든 스킬을 승격했는지(홍섭 4개, 재윤 2개, 준호 2개)까지 적혀 있다.
- 여기에 더해 `.codex/skills/`에 동일 스킬 9개가 미러링되어 있다. 하나의 원본(`.claude/skills`)을 다른 도구 형식으로 변환·배포하는 구조다.

### 3.5 디버깅 기법

`claude --debug`로 스킬 로딩 과정의 문제를 확인할 수 있고, 로그는 `~/.claude/debug/`에 세션별로 저장된다.

체크 포인트:

1. 스킬 검색 경로는 올바른가?
2. 동일한 이름의 스킬이 여러 위치에 있는가?
   - `duplicates removed: 0`이 아니면 여러 위치에 동일 스킬이 있었던 것
   - 우선순위는 **`project > user > managed`**, 낮은 우선순위 스킬은 무시된다
   - > ⚠️ **공식문서와 반대** — 공식문서는 `enterprise > personal > project` 순으로 덮어쓴다고 명시한다. [5. 공식문서 대조 ①](#-교재-project--user--managed-vs-공식-enterprise--personal--project) 참조.
3. 플러그인 스킬이 정상 로드되었는가? — `plugin skills` 개수로 확인. 설치했는데 0이면 플러그인 활성화 상태를 점검한다.

**일반적인 문제와 해결**

| 문제 | 원인 | 해결 |
| --- | --- | --- |
| 스킬이 활성화되지 않음 | `description`이 요청과 매칭되지 않거나 너무 모호 | 더 구체적인 트리거 용어를 포함하도록 `description` 수정 |
| 여러 스킬이 충돌 | 유사한 `description`을 가진 스킬이 동시 활성화 | `description`에 고유 용어를 사용해 명확히 구분 |
| 스크립트 실행 오류 | 종속성 미설치, 실행 권한 부족, 경로 형식 오류 | 스크립트를 독립 실행해 진단 |
| YAML 파싱 오류 | 프론트매터 구문 오류 | 스킬 전체가 로드되지 않으므로 구문부터 확인 |

**내 클로드 시스템에서 확인한 예시**

- **아직 없음** — `~/.claude/debug/`가 없다(디버그 모드 미사용).
- 다만 **우선순위 규칙(`project > user > managed`)이 무해한 이유**는 실측된다. `~/.claude/skills/`가 비어 있어 프로젝트 스킬과 이름이 겹칠 여지가 없다. 반대로 앞으로 개인 스킬을 만들 때 `pre-`/`mid-` 접두사와 겹치는 이름을 쓰면 조용히 무시될 수 있다.

### 3.6 재사용 가능한 스킬 패턴

| 패턴 | 성격 | 저장 위치 |
| --- | --- | --- |
| **프로젝트 특화** | 특정 프로젝트의 규칙과 관행, 고유 아키텍처·명명 규칙·코딩 스타일 | 주로 프로젝트 스킬 (팀 공유) |
| **도메인 특화** | 특정 기술 패턴, 프레임워크에 특화 | — |
| **범용 유틸리티** | 코드 리뷰, 문서 생성, 테스트 작성, 리팩터링 등. **재사용성이 가장 높음** | 주로 개인 스킬, 또는 마켓플레이스로 커뮤니티 공유 |

재사용성이 높은 스킬의 특징: 특정 프로젝트나 기술 스택에 종속되지 않고 일반적인 패턴을 다루며, 다양한 상황에 적용할 수 있도록 `description`에 충분한 트리거 조건을 포함한다.

**e.g. 범용 코드 리뷰 스킬**

```markdown
---
name: reviewing-code-changes
description: 코드 변경 사항 검토, 잠재적 버그 식별, 개선 제안. 풀 리퀘스트 또는 코드 리뷰 시 사용
allowed-tools: Read, Grep, Glob
---

# 코드 리뷰

## 검토 체크리스트

### 정확성
- [ ] 비즈니스 로직이 요구 사항을 충족하는가?
- [ ] 엣지 케이스가 처리되는가?
- [ ] 오류 처리가 적절한가?

### 유지보수성
- [ ] 코드가 읽기 쉬운가?
- [ ] 함수/클래스가 단일 책임을 가지는가?
- [ ] 중복이 최소화되었는가?

### 성능
- [ ] 불필요한 연산이 있는가?
- [ ] N+1 쿼리 문제가 있는가?
- [ ] 메모리 누수 가능성이 있는가?

### 보안
- [ ] 입력 검증이 적절한가?
- [ ] 민감 정보가 노출되지 않는가?
- [ ] SQL 인젝션, XSS 등 취약점이 없는가?

## 리뷰 결과 형식

1. 요약: 전체적인 코드 품질 평가
2. 필수 수정: 병합 전 반드시 수정해야 할 항목
3. 권장 수정: 개선하면 좋지만 선택적인 항목
4. 긍정적 피드백: 잘 작성된 부분에 대한 인정
```

**내 클로드 시스템에서 확인한 예시**

- 현재 9개 스킬은 **전부 프로젝트 특화 패턴**이다. 스터디 운영 루틴(모임 전/중)에 강하게 묶여 있어 다른 저장소로 가져가면 그대로 쓰기 어렵다.
- **범용 유틸리티 패턴은 아직 없다.** 만든다면 위치는 `~/.claude/skills/`인데, 그 디렉터리 자체가 없는 상태다. → 제작 대상으로 확정 ([7. 다음 적용](#7-확정한-관점과-다음-적용)).

### 3.7 스킬 문서화 유의사항

포함해야 할 핵심 요소:

- 스킬의 목적과 적용 범위
- 실제 사용 예시
- 다른 스킬과의 관계(조합 패턴)
- 알려진 제한 사항이나 주의 사항

**내 클로드 시스템에서 확인한 예시**

- 4개 스킬이 `SKILL.md`와 별도로 `README.md`를 갖고 있다 (`pre-chapter-prep`, `pre-chapter-ideas`, `mid-chapter-merge`, `mid-study-wrapup`). **지침(클로드가 읽는 것)과 설명(사람이 읽는 것)을 분리**한 구조다.
- "다른 스킬과의 관계"는 개별 스킬이 아니라 `.claude/skills/README.md`의 **스킬 맵 표**가 담당한다.

### 3.8 스킬의 격리 실행 (`context: fork`)

**기본 동작**: 스킬은 **부모 대화의 컨텍스트 안에서** 활성화된다.

문제는 대규모 코드베이스 분석처럼 토큰을 많이 쓰는 작업이다. 부모 대화의 컨텍스트 윈도우를 잠식하거나, 중간 결과물이 이후 대화의 품질을 떨어뜨린다. 이를 해결하는 프론트매터 필드가 **`context: fork`**다.

`context: fork`가 설정된 스킬은:

- 부모 대화로부터 **완전히 분리된 서브에이전트 컨텍스트**에서 실행된다
- **스킬 본문이 서브에이전트를 구동하는 프롬프트**가 된다
- 서브에이전트는 부모 대화의 히스토리에 접근할 수 없다
- 작업이 완료되면 **결과만** 부모 대화에 반환된다

```markdown
---
name: code-analysis
description: Analyze code quality and generate detailed reports. Use for comprehensive code review
context: fork
agent: Explore
allowed-tools:
    - Read
    - Grep
    - Glob
---
```

`agent` 필드는 **`context: fork`가 설정된 경우에만** 유의미하며 서브에이전트의 동작 모드를 결정한다.

| `agent` 값 | 성격 |
| --- | --- |
| `Explore` | 코드베이스 탐색에 최적화된 **읽기 전용** 모드 |
| `Plan` | 컨텍스트를 수집하고 실행 계획을 수립하는 데 특화 |
| `general-purpose` | **기본값.** 범용 서브에이전트, 별도 제약 없이 작업 수행 |

**`context: fork`가 적합한 상황**

1. **대규모 코드베이스 분석** — 수백 개 파일을 탐색하며 아키텍처를 파악하는 작업은 수만 토큰을 소비할 수 있다. 부모 대화에서 진행하면 탐색 중간 결과물(파일 내용, grep 결과)이 컨텍스트를 채워 대화 품질이 급격히 저하된다. 포크하면 **최종 분석 결과(1,000~2,000토큰)만** 부모 대화에 전달된다.
2. **세션 격리가 필요한 워크플로** — SPEC 문서 생성, TDD/DDD 구현 사이클, 테스트 전략 수립. 각 단계가 독립 컨텍스트에서 실행되어야 단계 간 간섭을 막는다. plan 단계에서 생성된 방대한 탐색 컨텍스트가 run 단계의 구현 작업에 간섭하는 것을 원천 차단한다.

**토큰 관리 효과**: 서브에이전트는 수만 토큰 규모의 탐색을 수행하지만 메인 에이전트에는 1,000~2,000토큰의 요약만 반환한다. 포크 없이 실행하면 탐색 과정에서 30,000~50,000토큰을 소비해 부모 대화의 잔여 컨텍스트가 크게 하락한다.

**`context: fork`를 쓰면 안 되는 경우**

- **부모 대화의 컨텍스트를 참조해야 하는 스킬** (이전 대화 내용, 사용자 선호도 등). 포크된 서브에이전트는 부모 히스토리를 상속받지 않으므로 대화 맥락에 의존하는 작업에는 부적절하다.
- **소규모 작업** — 서브에이전트 생성 오버헤드가 오히려 비효율적이다.

**내 클로드 시스템에서 확인한 예시**

- `context: fork`, `agent`, `model` 필드를 쓰는 스킬은 **하나도 없다.**
- 대신 지금 이 스킬(`pre-chapter-prep`)은 3단계 지침에서 *"HTML 생성은 초점이 좁아 서브에이전트에 위임해도 좋다 (컨텍스트 격리)"*라고 **본문 자연어로** 위임을 권한다. 즉 **프론트매터 필드가 아니라 본문 지시로 부분 격리**하는 형태다.
- 이 방식은 위 "쓰면 안 되는 경우"와도 맞아떨어진다. 이 스킬 전체를 `context: fork`로 만들면 1→2단계의 **역질문 게이트(사람과의 대화)**가 불가능해진다. 부모 대화 맥락이 필수인 스킬이기 때문이다.
- **도입 대상 확정: `mid-zettelkasten-synthesis`.** 저장소 전체의 정리본과 기존 `notes/`를 훑는 대규모 탐색이라 포크 이득이 크고, "원자 메모와 주제 지도를 재구성하라"는 **명확한 task**가 있어 아래 공식문서 경고에도 걸리지 않는다.

**공식문서에서 추가 확인한 사항** (2026-08-12)

- ⚠️ **경고**: *"`context: fork` only makes sense for skills with explicit instructions. If your skill contains guidelines like 'use these API conventions' without a task, the subagent receives the guidelines but no actionable prompt, and returns without meaningful output."* — 지침만 있고 수행할 task가 없는 스킬을 포크하면 빈손으로 돌아온다.
- **`background` 필드**(v2.1.218+): 포크된 서브에이전트는 **기본적으로 백그라운드로 실행**되어 사용자는 계속 작업할 수 있고 결과가 나중에 도착한다. `background: false`를 주면 호출한 턴에서 결과를 기다린다.
- `agent: Explore` / `Plan`은 **CLAUDE.md와 git status를 로드하지 않아** 컨텍스트를 더 줄인다. 즉 포크 스킬에 `agent: Explore`를 쓰면 서브에이전트는 SKILL.md 내용과 자기 시스템 프롬프트만 본다.
- 스킬과 서브에이전트는 **양방향**으로 결합된다.

  | 방식 | 시스템 프롬프트 | Task | 추가 로드 |
  | --- | --- | --- | --- |
  | `context: fork` 스킬 | 에이전트 타입에서 | SKILL.md 내용 | CLAUDE.md (Explore·Plan 제외) |
  | `skills` 필드를 가진 서브에이전트 | 서브에이전트 본문 | 클로드의 위임 메시지 | 사전 로드된 스킬 + CLAUDE.md |

## 5. 공식문서 대조 — 교재와 다른 3가지 ★

> 출처: [Claude Code 공식문서 — Extend Claude with skills](https://code.claude.com/docs/en/skills), 2026-08-12 확인.
> 교재 노트는 그대로 두고, **현재 동작 기준으로 정정이 필요한 지점만** 아래에 모았다.

### ① 교재 `project > user > managed` vs 공식 `enterprise > personal > project`

**순서가 반대다.** 공식문서 원문:

> *"When skills share the same name across levels, **enterprise overrides personal, and personal overrides project**."*

| | 노트 | 공식문서 |
| --- | --- | --- |
| 우선순위 | `project > user > managed` | `enterprise > personal > project` |
| 의미 | 프로젝트 스킬이 개인 스킬을 이긴다 | **개인 스킬이 프로젝트 스킬을 이긴다** |

실무 영향이 크다. 팀이 `.claude/skills/deploy`를 커밋해도, 팀원 중 누군가 `~/.claude/skills/deploy`를 갖고 있으면 **그 사람 로컬에서는 개인 스킬이 실행된다.** 팀 표준이 조용히 무력화될 수 있다는 뜻이다.

추가로 공식문서가 확인해 주는 것들:

- **플러그인 스킬은 `plugin-name:skill-name` 네임스페이스**를 쓰므로 다른 레벨과 **충돌하지 않는다.**
- 같은 이름의 Command와 Skill이 있으면 **Skill이 우선**한다 (이건 노트와 일치).
- 하위 디렉터리의 중첩 `.claude/skills/`도 로드된다 (모노레포용). 이름이 겹치면 `apps/web:deploy`처럼 **디렉터리 한정 이름**으로 둘 다 살아남는다.

### ② 교재 "도구 제한" vs 공식 "사전 승인"

**이 장에서 가장 중요한 정정이다.** 노트는 `allowed-tools`를 "위험한 작업을 원천 차단하는 장치"로 서술했지만, 공식문서는 정반대로 설명한다.

> *"The `allowed-tools` field **grants permission** for the listed tools during the turn that invokes the skill, so Claude can use them without prompting you for approval. (…) **It does not restrict which tools are available: every tool remains callable**, and your permission settings still govern tools that are not listed."*

| | 노트의 서술 | 공식문서의 실제 동작 |
| --- | --- | --- |
| `allowed-tools` 역할 | 사용 가능한 도구를 **제한** | 나열된 도구를 **사전 승인**(프롬프트 없이 사용) |
| 나열되지 않은 도구 | 차단됨 | **여전히 호출 가능** (기존 권한 설정을 따름) |
| 유효 범위 | (언급 없음) | **호출한 그 턴에만.** 다음 메시지를 보내면 해제 |
| 진짜 "제한"은? | — | **`disallowed-tools`** (활성화 동안 도구 풀에서 제거) |

즉 노트의 `safe-file-reader` 예시(`allowed-tools: Read, Grep, Glob`)는 **파일 수정을 막지 못한다.** 읽기 전용을 강제하려면 `disallowed-tools`를 쓰거나 권한 설정으로 막아야 한다.

공식문서는 보안 주의도 덧붙인다.

> *"Review project skills before trusting a repository, since a skill can grant itself broad tool access."*

프로젝트 `.claude/skills/`의 `allowed-tools`는 워크스페이스 신뢰 대화상자를 수락한 뒤 적용되며, **스킬이 스스로에게 넓은 도구 권한을 부여할 수 있으므로** 저장소를 신뢰하기 전에 검토해야 한다. 우리처럼 스킬을 PR로 주고받는 팀에는 직접적인 리뷰 항목이다.

### ③ 교재 200줄 vs 공식 500줄

> *"Keep `SKILL.md` under 500 lines. Move detailed reference material to separate files."*

| | 노트 | 공식문서 |
| --- | --- | --- |
| SKILL.md 길이 | 200줄(영문)/150줄(한국어) 이내 | **500줄 미만** |

방향(상세 자료는 별도 파일로 분리)은 같고 임계값만 다르다. 노트 쪽이 더 보수적이므로 **노트 기준을 지키면 공식 기준도 자동으로 만족**한다.

### 덤 — 노트에 없는 최신 사항

**스킬 콘텐츠 생명주기** (점진적 공개의 이면)

> *"When you or Claude invoke a skill, the rendered `SKILL.md` content enters the conversation as a single message and **stays there for the rest of the session**."*

노트는 "필요할 때 로드된다"까지만 다룬다. 공식문서는 **한 번 로드되면 세션 내내 남는다**는 점을 추가한다. 그래서 *"every line is a recurring token cost"*다. 2단계 비용은 일회성이 아니라 **누적 고정비**로 봐야 한다.

- 동일 내용을 재호출하면 사본을 또 붙이지 않고 "이미 로드됨" 메모만 추가한다 (v2.1.202+).
- 자동 압축 시 스킬당 앞부분 **5,000토큰**까지, 전체 합산 **25,000토큰** 예산으로 재부착된다. 한 세션에서 스킬을 많이 호출했다면 오래된 것부터 통째로 사라질 수 있다.
- `allowed-tools` 승인은 콘텐츠와 달리 **다음 메시지에서 해제**된다.

**1단계 메타데이터 예산이 실제로 설정 가능하다**

- `description` + `when_to_use` 합산 텍스트는 스킬 목록에서 **1,536자**로 잘린다 → **핵심 사용 사례를 맨 앞에** 두라는 게 공식 권장.
- 목록 전체 예산은 `skillListingBudgetFraction` 설정이나 `SLASH_COMMAND_TOOL_CHAR_BUDGET` 환경변수로 조정한다. 우선순위가 낮은 스킬은 `skillOverrides`에서 `"name-only"`로 지정해 description 없이 이름만 노출시킬 수 있다.
- 노트의 "스킬당 약 100토큰" 추정은 여전히 유효한 감각이지만, **실제로는 예산제이고 튜닝 가능한 값**이다.

**노트에 없는 프론트매터 필드**

| 필드 | 역할 |
| --- | --- |
| `when_to_use` | 트리거 문구·예시 요청을 `description`에 덧붙임 (1,536자 캡에 함께 포함) |
| `disallowed-tools` | 스킬 활성화 동안 도구 풀에서 **제거** (진짜 제한) |
| `background` | `context: fork` 전용. 기본 `true`(백그라운드 실행), `false`면 그 턴에서 대기 |
| `effort` | 스킬 활성화 동안의 추론 강도 (`low`~`max`) |
| `paths` | glob 패턴에 맞는 파일을 다룰 때만 자동 로드 |
| `hooks` | 스킬 생명주기에 한정된 훅 |
| `arguments` / `argument-hint` | 위치 인자와 자동완성 힌트 |
| `user-invocable: false` | `/` 메뉴에서 숨김 (클로드만 사용하는 배경지식용) |
| `metadata` / `license` / `compatibility` | [Agent Skills 스펙](https://agentskills.io) 계열 필드 |

**유용한 치환자**: `${CLAUDE_SKILL_DIR}` — SKILL.md가 있는 디렉터리. 스킬이 개인·프로젝트·플러그인 어디에 설치되든 번들 스크립트 경로가 올바르게 풀린다.

## 6. 외부 레퍼런스 — 남들은 이 장을 어떻게 실천하고 있나

> 전부 2026-08-12에 확인. 각 프로젝트가 자체 문서에서 밝힌 수치이며 독립 검증된 값은 아니다.

### 6.1 [anthropics/skills](https://github.com/anthropics/skills) — 공식 예제 저장소

교재가 `description` 예시로 든 PDF 스킬의 **실물**이 여기 있다. 문서 스킬(`docx`, `pdf`, `pptx`, `xlsx`)이 `scripts/`와 `references/`를 갖춘 프로덕션급 예제로 제공되고, `spec/`(Agent Skills 명세)과 `template/`(스킬 템플릿)도 함께 있다.

```bash
/plugin marketplace add anthropics/skills
/plugin install document-skills@anthropic-agent-skills
```

최소 요구사항은 여전히 `SKILL.md` 하나뿐이라는 점도 확인된다.

### 6.2 공식문서의 `codebase-visualizer` — "스크립트 우선 전략"의 실물

교재 2.4절(코드 실행 통합)을 그대로 구현한 공식 예제다.

```yaml
---
name: codebase-visualizer
description: Generate an interactive collapsible tree visualization of your codebase. Use when exploring a new repo, understanding project structure, or identifying large files.
allowed-tools: Bash(python3 *)
---
```

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/visualize.py .
```

핵심은 **SKILL.md에는 스크립트 사용법만 적고, 스크립트 코드 자체는 컨텍스트에 들어가지 않는다**는 것이다. Python 3 내장 라이브러리만 써서 설치할 패키지도 없다. 우리가 아직 `scripts/`를 하나도 안 쓰고 있으므로 가장 따라 하기 좋은 형태다.

### 6.3 [ECC — Everything Claude Code](https://github.com/affaan-m/ecc) — 점진적 공개의 극단 사례

> *"Access to 68 agents, **286 skills**, and 94 legacy command shims"*
> *"Keeping those jobs separate is how ECC adds capability **without dumping the entire repository into every session**."*

스킬 **286개**를 깔아도 세션이 안 터지는 이유가 정확히 이 장의 주제다. 1단계 메타데이터만 상주하고 본문은 on-demand로 로드되기 때문이다. 표어도 *"Optimize the context window. Persist everything else."*로 같은 이야기를 한다.

대표 스킬: `tdd-workflow`(RED→GREEN→REFACTOR), `security-review`, `e2e-testing`, `search-first`, `continuous-learning-v2`. Claude Code·Codex·Cursor·OpenCode에서 함께 동작한다 — 우리가 `.codex/skills`를 미러링하는 것과 같은 문제의식이다.

```bash
/plugin marketplace add https://github.com/affaan-m/ECC
/plugin install ecc@ecc

# 필요한 스킬만 골라 설치도 가능
./install.sh --target claude --skills tdd-workflow,security-review
```

### 6.4 [OMC — oh-my-claudecode](https://github.com/Yeachan-Heo/oh-my-claudecode) — 스킬 + 멀티에이전트

19개 전문 에이전트와 39개 스킬로 Claude·Gemini·Codex를 함께 굴리는 멀티에이전트 오케스트레이션 플러그인이다. 이 장과 관련해 눈여겨볼 두 가지:

- **자체 스코프**를 쓴다: `.omc/skills/`(프로젝트) / `~/.omc/skills/`(사용자). 교재의 개인·프로젝트 2단 구조와 같은 발상이다.
- 프론트매터에 **`triggers` 배열**을 둔다 — 교재가 "고유 트리거 용어를 `description`에 넣어라"라고 한 걸 **별도 필드로 분리**한 셈이다.

```yaml
name: Fix Proxy Crash
description: aiohttp proxy crashes on ClientDisconnectedError
triggers: ["proxy", "aiohttp", "disconnected"]
source: extracted
```

```bash
/plugin marketplace add https://github.com/Yeachan-Heo/oh-my-claudecode
/plugin install oh-my-claudecode
```

`/skill list | add | remove | edit | search`로 스킬을 관리하고, 반복 패턴을 스킬로 저장해 재사용한다.

> 참고: ECC와 OMC는 공식 Anthropic 산출물이 아니라 서드파티 커뮤니티 플러그인이다. 프로젝트 스킬은 도구 권한을 스스로 부여할 수 있으므로(§5-②) **설치 전 스킬 내용을 검토**해야 한다.

## 7. 확정한 관점과 다음 적용

**중심 메시지**: 스킬은 **점진적 공개로 비용 없이 지식을 늘린다.** ECC의 286개 스킬이 그 증거다.

**발표에서 강조할 것**

1. 3단계 점진적 공개와 토큰 비용 프레임워크 (메커니즘)
2. `context: fork` 격리 실행 (30,000~50,000토큰 → 1,000~2,000토큰)
3. 공식문서 대조 3건 — 특히 **`allowed-tools`는 제한이 아니라 사전 승인**

**다음에 만들 것 (4가지 전부)**

| # | 할 일 | 이유 |
| --- | --- | --- |
| 1 | `sync-claude-skills-to-codex`에 **`scripts/` 도입** | 변환 규칙이 결정론적. 실행 결과(PASS/FAIL)만 컨텍스트로 → 토큰 비용 급감 |
| 2 | `mid-zettelkasten-synthesis`에 **`context: fork`** | 저장소 전체 탐색이라 포크 이득이 크고, 명확한 task가 있어 공식 경고에 걸리지 않음 |
| 3 | **범용 유틸리티 스킬**을 `~/.claude/skills/`에 신설 | 현재 개인 스킬 디렉터리 자체가 없음. Java/Spring 코드 리뷰처럼 프로젝트 무관한 것부터 |
| 4 | 기존 스킬에 **`EXAMPLES.md`** 보강 | "다양한 입력 + 일관된 출력" 예시 세트가 전무. 3단계 파일로 분리해 비용 없이 품질 확보 |

단, #3은 §5-①의 우선순위 함정을 조심해야 한다. **개인 스킬이 프로젝트 스킬을 덮어쓰므로** `pre-`/`mid-` 접두사와 겹치는 이름을 쓰면 팀 스킬이 조용히 무시된다.
