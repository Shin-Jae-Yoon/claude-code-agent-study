Chapter 3 · 통합 발표

에이전트 스킬 — 3인 정리본 통합

개인 정리본 3개를 4개 고정 렌즈(공통 · 흥미로운 것 · 갈린 관점 · 팀이 더 팔 것)로 종합했다. 개인 통찰은 원문 그대로 보존한다.

홍섭 — 커맨드/스킬 통합의 실체 + 팀 배포 실사례 재윤 — 점진적 공개 + 공식문서 대조 준호 — 스킬 운영·배포·측정 레퍼런스

참여자별 원문 보존

홍섭커맨드/스킬 통합의 실체 + 팀 배포(nova-workflow)
  • 통합의 실체 = 호출 방식 통합(확정). 둘 다 같은 SKILL.md 포맷을 쓰고 /슬래시와 자연어 양쪽을 지원한다. 성격은 disable-model-invocation 유무로 갈린다.
  • 발표 대비축: 커맨드(화이트박스 — 사람이 직접 지정) vs 스킬(블랙박스 — 클로드가 자동 선택).
  • 실측: nova의 commit·pr·handoff는 disable-model-invocation + argument-hint → 커맨드형. humanize-korean은 트리거 문구를 잔뜩 넣어 "AI 티 없애줘"만으로 발동 → 스킬형.
  • 스킬 유형 3종을 전부 실물로 보유 — 로컬(~/.claude/skills/*) / 프로젝트(이 레포) / 팀 배포: 회사 개발팀에 만들어 준 nova-workflow 플러그인, 18개 스킬 마켓플레이스 배포.
  • name 동명사 규칙은 공식 강제가 아니다(조사 확정). 게다가 name은 디스플레이 라벨이고 실제 커맨드명은 디렉토리 이름에서 온다. 동사형(commit, pr)도 정상.
  • 분량 = SRP로 해석. pre-chapter-prep 66줄, nova-api-planner 68줄 양호 / humanize-korean 257줄 초과 — 오케스트레이터라 길어짐, 리팩터 후보로 스스로 지목.
  • 지원 파일 역할: references/(필요할 때만 로드) · scripts/(결과만 컨텍스트에) · templates/(산출물 뼈대). 공통 규칙은 도메인 분리 · 깊이 1단계 · 중첩 참조 금지.
  • 실측: references/ + evals/는 마케팅 스킬군에 있음. scripts/·templates/는 플러그인 루트에만 있고 스킬 안엔 admin-guide-writer 하나뿐 → "references 위주, script/template 활용이 약하다".
  • context/agent/background 3필드 실체 확인. agent는 Explore/Plan/general-purpose. 적절 = 초점 좁고 산출물만 필요한 작업 / 부적절 = 메인 맥락을 계속 왕복하는 작업. 도입 후보: pre-chapter-prep의 HTML 생성 단계.
  • 토큰 5원칙: description 압축 / 범용 지식 빼기(50~70% 절감) / 도메인 분리 1단계 / 예시는 EXAMPLES.md로(예시가 토큰의 20~50%) / 로직은 스크립트로.
  • Q1 · E2E 테스트 스킬화 → 스킬화 O, 단 env 값은 스킬에 안 넣는다. 절차는 SKILL.md, 값은 settings.local.json. settings.json의 env가 정답(모든 세션 자동 적용). 우선순위 Local > Project > User.
  • Q2 · 토큰 15% 모니터링 → /context의 Skills row로 점유 확인, statusline에 컨텍스트 바 상시 표시.
재윤점진적 공개로 비용 없이 지식 늘리기 + 공식문서 대조
  • 중심 메시지 — 스킬은 점진적 공개로 비용 없이 지식을 늘린다. 전제는 "컨텍스트 윈도우는 공용 자산". 토큰 프레임워크 · 최적화 5전략 · 스크립트 우선 · context: fork는 전부 이 한 문장의 수단.
  • 3단계: 메타데이터(상시, ~100토큰) / 지침(트리거 시) / 지원 파일(필요시). 핵심은 접근 전까지 컨텍스트를 소비하지 않는다.
  • 비용 프레임워크: 20만 윈도우에서 스킬 예산 3만~5만 토큰, 목표 15% 이내. 추정식 1단계 = 스킬 수 × 100, 3단계 = 로드된 줄 수 × 10.
  • 추정식에 자기 실측치 대입 — 1단계 9개 × 100 ≈ 900토큰, 2단계 66줄 ≈ 660토큰, 3단계 (16+78+83)줄 × 10 ≈ 1,770토큰.
  • 실측 요약: 개인 스킬 없음(디렉터리 자체 없음) / 프로젝트 9개, 31~130줄 전부 200줄 이내 / 플러그인 ouroboros v0.51.0 활성 / scripts/·templates/·context: fork·예시 세트 전부 없음. → 1·2단계는 기준을 지키고, 3단계와 격리 실행은 비어 있다.
  • context: fork: 포크 없이 30,000~50,000토큰 → 포크하면 요약 1,000~2,000토큰만 부모로.
  • 판단: pre-chapter-prep 전체를 포크하면 역질문 게이트(사람과의 대화)가 불가능해진다 → 부적합. 대신 mid-zettelkasten-synthesis를 도입 대상으로 확정(대규모 탐색 + 명확한 task).
  • 공식문서 대조 3건 ★ — ① 우선순위가 반대(enterprise > personal > project) ② allowed-tools는 제한이 아니라 사전 승인 ③ 200줄 vs 500줄.
  • 덤: 스킬 콘텐츠는 한 번 로드되면 세션 끝까지 남는다 → 2단계는 일회성이 아닌 누적 고정비. description + when_to_use는 합산 1,536자에서 잘림.
  • 외부 레퍼런스 4종: anthropics/skills · 공식 codebase-visualizer(SKILL.md엔 사용법만, 스크립트 코드는 컨텍스트에 안 들어감) · ECC 286 스킬 · OMC의 triggers 배열.
  • 교재 예시를 Java + Spring으로 변환 — 리액트 컴포넌트 스킬 → creating-spring-rest-controllers, API 문서화 → @GetMapping/@PostMapping/@PreAuthorize 3단 세트. 난이도 배치는 원문 유지.
준호스킬 운영·배포·측정 레퍼런스
  • 한눈에: 스킬은 폴더다 / 커스텀 커맨드는 스킬로 통합됐다(신규는 무조건 스킬) / 차이는 frontmatter 두 필드 / 점진적 공개가 핵심 설계 / 만드는 것보다 측정이 어렵다.
  • 스킬만 되는 것: 딸린 파일, 중첩 디렉터리 자동 탐색, --add-dir 로드, 플러그인 패키징. 이름 충돌 시 스킬이 이긴다.
  • 호출 제어 두 필드: disable-model-invocation(나만 호출 — 부수 효과로 목록에서 빠져 컨텍스트 비용도 준다) / user-invocable: false(클로드만). 주의: user-invocable은 UI 설정이라 자율 실행을 못 막는다.
  • 스킬이 많아지면 description이 잘린다. 리스팅 예산은 윈도우의 1%, 넘치면 덜 쓰는 스킬의 description부터 통째로 사라진다(이름만 남음). → /doctor, skillListingBudgetFraction, skillOverrides: name-only.
  • 우선순위 enterprise > personal > project. 플러그인은 plugin:skill 네임스페이스라 충돌 없음. 프로젝트 스킬 탐색은 상위 방향(루트까지) + 하위 방향(그 디렉터리 파일을 다룰 때 로드).
  • ⚠️ Cowork·클라우드 세션은 로컬 ~/.claude/skills/를 읽지 않는다. 개인 스킬만 만들어두면 웹에선 "스킬을 찾을 수 없다"가 된다.
  • SKILL.md는 한 번 호출되면 세션 끝까지 남고 다시 읽지 않는다 → 본문 한 줄이 반복되는 상주 비용. 작업 내내 적용될 내용은 절차가 아니라 상시 지침처럼 쓴다.
  • 참조는 한 단계만(또 참조하면 head -100 식 부분 읽기로 정보가 불완전해진다), 100줄 넘는 참조엔 목차.
  • scripts/는 읽히는 게 아니라 실행된다. 실행인지 참조인지 반드시 명시할 것 — 애매하면 통째로 읽어버려 토큰 이점이 사라진다.
  • 자유도(degrees of freedom): 높음=서술형(코드 리뷰) / 중간=템플릿 / 낮음=정확한 스크립트(DB 마이그레이션). 양옆이 절벽인 좁은 다리에선 가드레일, 탁 트인 들판에선 방향만.
  • 환각 방지: 불확실성 허용은 "말하지 마라"가 아니라 "표시하고 말하라" / 출처 명시 + 사후 철회(출처만 요구하면 출처를 지어내는 실패 모드가 남는다) / 구조 계열 plan-validate-execute.
  • Opus 5 — 두 방향이 반대다 ★: 불확실성 지침은 더 필요해졌고(사실 주장 환각이 4.8보다 약간 더 많음), 검증 지시는 빼야 한다(과잉 검증으로 토큰만 낭비). 유지 = 출력 규범 / 제거 = 절차 지시.
  • context: fork 함정 2가지: 백그라운드 포크는 좁은 도구 집합으로 돈다 / 백그라운드 포크의 편집은 체크포인트 바깥이라 /rewind로 못 되돌린다. Explore·Plan은 CLAUDE.md를 건너뛴다.
  • --debug가 잡는 고약한 실패 ★: YAML이 깨지면 본문을 빈 메타데이터로 로드 → 직접 호출은 되는데 매칭할 description이 없다 → "자동 발동만 안 된다"로 보여 오진하기 쉽다.
  • skill-creator — 만들었으면 측정하자. 발동률과 출력 품질은 스킬을 끈 상태와의 비교로만 알 수 있다. Anthropic 자체 시험에서 공개 스킬 6개 중 5개 트리거 개선. OTEL skill_activated로 자동/수동 발동 비율 추적.
  • 팀 배포 호환성 ★: Claude Code 밖에선 6개 필드만 허용되고 스펙 밖 필드는 무시가 아니라 하드 에러. 개인 요금제라 조직 보안 스캐닝을 못 쓰면 리뷰를 사람이 대신해야 한다.

공통 셋 다 짚은 것

메커니즘

세 정리본이 독립적으로 같은 결론에 도달한 것

  • 커맨드와 스킬은 이미 통합됐고, 남은 차이는 "누가 호출하느냐" 하나다. 셋 다 disable-model-invocation을 성격 구분자로 지목 — 홍섭은 "통합의 실체", 준호는 두 필드 표, 재윤은 이 저장소 스킬 2개가 이미 그렇게 쓰인다는 실측으로.
  • 점진적 공개 3단계 — 읽히지 않은 파일은 토큰을 0 쓴다. 재윤은 중심 메시지로, 준호는 L1/L2/L3 표로, 홍섭은 "references는 필요할 때만 로드"로 같은 곳에 도달.
  • 컴팩션 재부착 예산 — 스킬당 앞 5,000토큰, 합산 25,000토큰. 세 정리본에 같은 수치가 독립적으로 등장한다. 준호는 "스킬이 중간부터 안 듣는다"는 체감의 정체로, 홍섭은 15% 모니터링 참고값으로, 재윤은 "2단계는 누적 고정비"의 근거로.

실천 원칙

셋 다 같은 선을 그은 작성 규칙

  • 스크립트 우선 — 로직은 코드로 내리고 결과만 컨텍스트에. 재윤은 토큰으로(2,000토큰 vs 100~200토큰), 홍섭은 5원칙 ⑤로, 준호는 "실행인지 참조인지 명시하라"는 함정까지.
  • 지원 파일은 도메인별로, 깊이는 1단계까지, 중첩 참조 금지. 준호가 이유를 가장 구체적으로 댔다 — 참조가 또 참조하면 부분 읽기로 정보가 불완전해진다.
  • context: fork와 agent 3옵션(Explore/Plan/general-purpose, 생략 시 general-purpose). 셋 다 "결론만 필요한 좁은 작업엔 적합, 부모 맥락이 필요하면 부적합"으로 같은 선.
  • description이 발동을 결정한다 — "무엇을 + 언제"를 트리거 문구까지 담아 쓴다. 셋 다 최우선 필드로 꼽았다.

흥미로운 것 인상 깊었던 개념·경험

각자의 실물 경험

책이 아니라 자기 시스템에서 나온 것

  • 홍섭nova-workflow — 교재의 "팀 배포 스킬"을 실물로 갖고 있다. 18개 스킬을 마켓플레이스로 사내 배포. 셋 중 유일하게 팀 배포 경로를 실제로 운영해 본 축이다.
  • 홍섭자기 스킬을 기준에 대보고 초과를 인정한 것 — humanize-korean 257줄을 "리팩터 후보"로 스스로 지목. 실측이 자기 비판으로 이어진 드문 경우.
  • 홍섭name은 라벨이고 실제 커맨드명은 디렉토리 이름에서 온다 — 동명사 규칙을 확인하러 갔다가 그보다 중요한 사실을 발견. 이름 규칙 논쟁의 전제 자체가 바뀐다.
  • 재윤ECC의 286개 스킬 — "286개를 깔아도 세션이 안 터지는 이유가 정확히 이 장의 주제"라는 프레이밍. 중심 메시지를 외부 사례로 직접 증명했다.
  • 재윤OMC의 triggers 배열 — 교재가 "description에 트리거 용어를 넣어라"라고 한 걸 별도 필드로 분리한 설계. 같은 문제의 다른 해법.

모르면 못 찾는 함정

주로 준호 정리본에서, 그리고 두 사람이 교차 확인한 것

  • 재윤 × 준호allowed-tools는 제한이 아니라 사전 승인이다. 재윤은 교재의 "원천 차단" 서술을 정정했고, 준호는 처음부터 "호출 턴 동안 승인 없이 쓸 도구, 다음 메시지에 해제"로 적었다. 보안 경고도 양쪽에 있다 — 스킬이 스스로에게 넓은 도구 권한을 줄 수 있다.
  • 재윤 × 준호우선순위는 enterprise > personal > project — 교재의 project > user > managed와 반대. 재윤이 실무 위험까지 짚었다: 팀이 커밋한 스킬을 팀원의 개인 스킬이 덮어써 팀 표준이 조용히 무력화된다.
  • 준호YAML이 깨지면 본문을 빈 메타데이터로 로드한다 — 증상이 "직접 부르면 되는데 자동 발동만 안 된다"로 나타나 description 문제로 오진하기 쉽다.
  • 준호Cowork·클라우드 세션은 로컬 개인 스킬을 읽지 않는다. 배포 표면을 처음부터 전제해야 한다.
  • 준호리스팅 예산을 넘으면 덜 쓰는 스킬의 description부터 통째로 사라진다. 스킬 저장소가 커질수록 현실적인 발동 실패 원인.
  • 준호"만들었으면 측정하자" — 발동하는 걸 봤다고 잘 동작하는 게 아니다. Anthropic 자체 시험에서 공개 스킬 6개 중 5개 트리거가 개선됐다.
  • 준호Opus 5에서 갈린 두 변화 — 불확실성 지침은 더 필요해졌고, 검증 지시는 빼야 한다. "유지 = 출력 규범 / 제거 = 절차 지시".
  • 준호자유도(degrees of freedom) — 스킬을 얼마나 촘촘히 쓸지의 기준. 좁은 다리엔 가드레일, 들판엔 방향만.

갈린 관점 같은 걸 서로 다르게 봄

① 200줄 기준을 어떻게 대할 것인가 — 셋이 전부 다르다

같은 숫자를 실무 기준 / 보수적 안전선 / 잘못된 수치로 처리했다.

홍섭
실무 기준으로 채택

200줄 = SRP. 자기 스킬을 실제로 재서 66·68줄은 양호, 257줄은 리팩터 후보로 분류했다.

재윤
보수적 안전선으로 유지

공식이 500줄임을 확인하고도 교재 기준(200/150줄)을 유지. 근거는 "노트 기준을 지키면 공식 기준도 자동 만족".

준호
수치 자체를 경계

200줄은 "공식 근거 없는 수치". 나아가 "기준은 줄 수가 아니라 토큰" — 숫자를 못박으면 "150줄 안에 넣었으니 됐다"가 되면서 정작 중요한 판단이 생략된다.

팀 규약을 쓸 때 정면으로 부딪히는 지점. 어느 숫자를 쓸지가 아니라, 숫자를 쓸지 말지부터 갈린다.

② "description 100토큰"도 같은 구도

수치의 성격 — 감각적 추정치냐, 실제 스펙이냐.

홍섭
원칙으로 채택

5원칙 ①로 그대로 — "100토큰 예산 안에서 발견 확률 극대화".

재윤
사용 + 보정

비용 추정식의 기본 단위로 쓰되, 별도로 "실제로는 예산제이고 튜닝 가능한 값"이라 보정.

준호
잘못된 수치로 분류

실제는 name 64자, description 1,024자, Claude Code에선 description + when_to_use 합산 1,536자 캡.

③ pre-chapter-prep에 context: fork를 붙일 것인가 — 정반대 판단

같은 스킬을 두고 도입 후보 vs 부적합으로 갈렸다.

홍섭 — 첫 적용 지점으로 지목

이 스킬은 이미 3단계 HTML 생성을 "서브에이전트 위임 가능"이라 명시하고 있다. 여기에 context: fork + agent: general-purpose를 붙이는 게 자연스럽다.

재윤 — 부적합으로 판정

스킬 전체를 포크로 만들면 1→2단계의 역질문 게이트(사람과의 대화)가 불가능해진다. 부모 맥락이 필수인 스킬이다. 대신 mid-zettelkasten-synthesis를 도입 대상으로 확정.

층위가 다르다 — 홍섭은 3단계(HTML 생성)만, 재윤은 스킬 전체. context는 스킬 단위 필드라 "일부 단계만 포크"가 성립하는지부터 확인해야 결론이 난다. 준호의 기준을 대면 판단 재료가 둘 더 붙는다 — "지침만 있고 task가 없으면 빈손으로 돌아온다", "다른 스킬과 스택해서 쓰는 스킬은 포크에서 확장이 끊긴다".

④ 스킬 품질을 무엇으로 측정하나 — 축이 다르다

셋을 합치면 로드 → 발동 → 품질 → 비용의 전 구간이 되지만, 지금은 각자 한 축씩만 보고 있다.

홍섭 — 비용 축

/context의 Skills row와 statusline으로 토큰 점유를 보고 15% 목표와 비교.

재윤 — 정합성 축

description 구체성, 경로 규칙, YAML 유효성, --debug — "제대로 로드되는가"까지.

준호 — 효과 축

skill-creator의 eval·벤치마크·블라인드 A/B로 발동률과 출력 품질을, OTEL skill_activated로 자동/수동 발동 비율을.

⑤ 환각 방지 — 지침으로 충분한가, 검증 장치까지 필요한가

재윤 — 지침 3종

스킬 본문에 넣을 불확실성 허용 / 정보 출처 제한 / 출처 명시로 정리. 지금 이 스킬의 규칙 2·3이 정확히 그 장치라는 실측까지.

준호 — 지침 + 구조

같은 3종에 반례를 덧붙인다 — "출처만 요구하면 출처 자체를 지어내는 실패 모드가 남는다". 그래서 plan-validate-execute: 지침은 확률을 낮추지만 검증은 결정론적이다.

이번 장의 정정 교재 노트와 현재 동작이 다른 지점

⚠️ allowed-tools는 도구를 제한하지 않는다

재윤·준호가 독립적으로 같은 지점에 도달했다. 공식문서 원문: "It does not restrict which tools are available: every tool remains callable." 진짜 제한은 disallowed-tools이고, 승인 범위도 호출한 그 턴에만 유효하다.

교재 예시 — 이름과 달리 막지 못한다name: safe-file-reader
allowed-tools: Read, Grep, Glob
→ 파일 수정이 여전히 가능하다.
실제로 읽기 전용을 강제하려면disallowed-tools로 도구 풀에서 제거하거나 권한 설정으로 막는다.

우리 팀에 직결되는 이유: 스킬을 PR로 주고받는데, 공식문서는 "a skill can grant itself broad tool access"라며 저장소를 신뢰하기 전 스킬 검토를 권한다. 준호 지적대로 개인 요금제라 조직 보안 스캐닝을 못 쓰면 그 리뷰를 사람이 대신해야 한다.

결론이 필요한 것

사람마다 다르게 답해서 팀이 정해야 하는 것

  • 충돌context: fork 도입 대상. pre-chapter-prep의 HTML 단계인가(홍섭), 스킬 전체는 부적합하니 mid-zettelkasten-synthesis인가(재윤). context가 스킬 단위 필드인 이상 "3단계만 포크"가 성립하는지부터.
  • 규약SKILL.md 분량 기준을 200 / 500 / "숫자 안 씀" 중 무엇으로. 준호의 "숫자를 못박으면 판단이 생략된다"는 경고를 규약에 어떻게 반영할지.
  • 규약스킬 PR 리뷰 체크리스트. allowed-tools·번들 스크립트 확인을 승격 절차에 넣을지.
  • 재윤개인 스킬이 프로젝트 스킬을 덮어쓴다. 앞으로 ~/.claude/skills/를 만들 때 pre-/mid- 접두사와 겹치면 팀 스킬이 조용히 무시된다. 네이밍 규약이 필요한지.
  • 준호우리 공통 스킬 9개는 웹·Cowork에서 동작하나? claude.ai 배포 시 스펙 밖 필드는 하드 에러인데, 우리 스킬이 쓰는 Claude Code 전용 필드가 무엇인지 점검 필요.

만들 것 · 확인할 것

각 정리본의 액션과 열린 질문

  • 공통 실측scripts/·templates/가 비어 있다. 재윤은 하나도 없고, 홍섭은 플러그인 루트에만 있고 스킬 안엔 하나뿐. 출발점은 공식 codebase-visualizer — SKILL.md엔 사용법만, 스크립트 코드는 컨텍스트에 안 들어간다.
  • 재윤다음에 만들 것 4가지 — ① sync-claude-skills-to-codex에 scripts/ ② mid-zettelkasten-synthesis에 context: fork ③ 범용 유틸리티 스킬을 ~/.claude/skills/에 신설 ④ 기존 스킬에 EXAMPLES.md.
  • 홍섭E2E API 테스트 스킬화 — 설계는 확정(절차는 SKILL.md, env 값은 settings.local.json). 실제 제작이 남았다.
  • 팀eval을 도입할 것인가. 준호의 "평가부터 만든다"가 가장 강한 권고인데 가장 자주 빠진다는 지적. skill-creator로 우리 스킬 9개의 발동률을 재볼지.
  • 재윤교재 노트 내부 불일치 2건 (확인 필요) — 동적 로딩 구조도의 "2단계/3단계" 표기가 1.6절 표와 어긋남. Version History 예시에서 v1.0.0과 v2.1.0의 날짜가 같은 2025-12-01로 적혀 있어 오기로 보임.
