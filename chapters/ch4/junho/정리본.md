## 1. 서브에이전트의 개념과 아키텍처

### 1.1 한 줄 정의

**서브에이전트 = 메인 세션이 Agent 도구로 띄우는, 자기만의 컨텍스트 윈도우·시스템 프롬프트·도구 권한을 가진 별도의 Claude 인스턴스.**

핵심 메커니즘은 딱 하나로 요약된다:

> **작업(work)은 안에서, 결론(conclusion)만 밖으로.**

중간 도구 호출과 그 결과는 전부 서브에이전트 컨텍스트 안에 남고, 부모에게는 **최종 메시지 한 개**만 Agent 도구의 결과로 돌아온다. 컨텍스트 보존·병렬화·최소 권한이 전부 이 한 가지 성질에서 파생된다.

### 1.2 스킬 vs 서브에이전트

| | 스킬 (Skill) | 서브에이전트 (Subagent) |
|---|---|---|
| 역할 | **무엇을 알아야 하는지** 정의 | 그 지식으로 **어떻게 작업을 수행할지** 구현 |
| 실행 위치 | 메인 대화 컨텍스트 안 | 격리된 별도 컨텍스트 |
| 결과 | 대화에 그대로 누적 | 요약만 반환 |

공식문서도 같은 선을 긋는다 — *"격리된 서브에이전트 컨텍스트가 아니라 메인 대화 컨텍스트에서 돌아가는 재사용 가능한 프롬프트/워크플로가 필요하면 Skills를 써라."*

둘은 결합도 된다:
- 서브에이전트 frontmatter의 `skills:` 필드 → 시작 시점에 스킬 **전문(full content)** 을 서브에이전트 컨텍스트에 주입
- 스킬의 `context: fork` → 반대 방향. 스킬 내용을 지정한 에이전트에 주입

### 1.3 오케스트레이터–워커 패턴

Anthropic이 Research 기능을 만들 때 쓴 구조와 같은 패턴이다.

```
        ┌──────────────────────────┐
        │   Lead / Orchestrator    │  ← 계획 수립, 위임, 결과 종합
        │   (메인 대화)             │
        └───────┬──────┬──────┬────┘
                │      │      │        ← Agent 도구 호출
        ┌───────▼┐ ┌───▼───┐ ┌▼──────┐
        │Worker A│ │WorkerB│ │WorkerC│  ← 각자 독립 컨텍스트
        └────────┘ └───────┘ └───────┘
             │         │         │
             └─────────┴─────────┘
                  최종 요약만 반환
```

- 리드 에이전트는 **마이크로매니징하지 않는다.** 명확히 정의된 작업만 넘기고 결과를 종합한다.
- Anthropic 내부 평가에서 Opus 4 리드 + Sonnet 4 서브에이전트 구성이 단일 Opus 4 대비 **90.2% 향상**. 대신 토큰은 일반 채팅의 약 **15배**.
- BrowseComp 분석에서 성능 분산의 약 80%를 설명한 요인이 **토큰 사용량**이었다. 즉 멀티에이전트가 잘 되는 이유의 상당 부분은 "병렬로 더 많이 생각할 수 있어서"다.

**교훈: 공짜가 아니다.** 결과의 가치가 15배 토큰을 정당화할 때만 쓴다.

### 1.4 단일 책임 원칙

공식문서 Best practices 첫 줄이 이거다 — *"각 서브에이전트는 하나의 특정 작업에 탁월해야 한다."*

- 만능 에이전트 1개 < **역할별 5~7개의 좁은 스페셜리스트 로스터**
- 30개짜리 난립도 마찬가지로 나쁨. 서로의 수정을 밟는다.
- 잘 도는 로스터의 조건: ① 하나의 job ② 그 job에 필요한 **최소 도구** ③ 리드가 병합하기 좋은 **고정된 반환 형태**

### 1.5 '적정 고도' (right altitude)

Anthropic의 *Effective context engineering for AI agents* 에 나오는 개념. 시스템 프롬프트를 쓸 때의 **골디락스 존**이다.

```
너무 낮음 ─────────────── 적정 고도 ─────────────── 너무 높음
if-else 하드코딩          행동을 유의미하게        "코드를 잘 리뷰해라"
브리틀한 분기 나열         제약하되, 스크립트하지    막연한 상위 지시
                        않은 상황도 판단 가능      공유 맥락을 잘못 가정
```

- **너무 낮으면**: 취약하고 유지보수 비용이 폭발. 예상 못 한 상황에서 깨진다.
- **너무 높으면**: 모델에 구체적 신호를 못 준다. 없는 공유 맥락을 있다고 가정한다.
- 서브에이전트 프롬프트에 적용하면 → *"When invoked: 1. git diff 실행 2. 수정된 파일에 집중 3. 즉시 리뷰 시작"* 처럼 **워크플로는 고정하되 판단은 남기는** 형태. 공식문서 예제(code-reviewer, debugger)가 정확히 이 고도다.
- 공식문서 권장: 프롬프트를 `<background_information>`, `<instructions>`, `## Tool guidance`, `## Output description` 같은 **섹션으로 구조화**할 것.

### 1.6 컨텍스트 격리 — 가장 큰 장점

메인 대화가 자산에서 부채로 바뀌는 순간이 있다. 함수 호출부를 찾느라 파일 40개를 읽으면, 그 40개가 계속 컨텍스트를 점유하면서 이후 모든 턴을 느리게 만들고 auto-compaction을 앞당긴다. 작업 자체는 필요했지만 **부산물을 메인 스레드에 남길 이유는 없었다.**

**비-fork 서브에이전트가 시작할 때 받는 것 / 못 받는 것:**

| 받음 | 못 받음 |
|---|---|
| 자기 시스템 프롬프트 + Agent 도구의 프롬프트 문자열 | 부모의 대화 기록·도구 결과 |
| CLAUDE.md 계층 전체 (Explore/Plan은 제외) | 부모의 시스템 프롬프트 |
| git status 스냅샷 (Explore/Plan은 제외) | 메인 대화의 auto memory |
| `skills:`에 명시한 스킬 전문 | 이미 호출된 스킬 내용 |
| 도구 정의 (상속 또는 `tools` 부분집합) | output style |

> **실무상 가장 중요한 한 줄:**
> 부모 → 서브에이전트로 가는 **유일한 통로는 Agent 도구의 프롬프트 문자열**이다.
> 파일 경로, 에러 메시지, 이미 내린 결정은 **그 프롬프트에 직접 다 넣어야 한다.**

### 1.7 "각 서브에이전트가 독립적인 20만 토큰 컨텍스트" — 보완 필요

책의 서술은 방향은 맞지만 숫자는 고정값이 아니다. 공식문서:

> 서브에이전트의 컨텍스트 윈도우 크기는 **부모가 아니라 자기 모델**에 의해 결정된다. 더 작은 윈도우를 가진 모델에 위임하면 그 서브에이전트는 작은 윈도우를 갖는다.

즉 `model: haiku`로 띄운 서브에이전트와 메인 Opus 세션의 윈도우는 다르다. "**독립적인 컨텍스트 윈도우를 갖는다**"가 정확한 서술이고, 200K는 모델별 값일 뿐이다.

추가로: 서브에이전트도 **auto-compaction을 지원**한다. 메인과 동일한 로직이고 트랜스크립트에 `compact_boundary` 이벤트가 남는다.

### 1.8 multi-Claude workflow

한 세션 안의 서브에이전트를 넘어서는 층위들. 2026년 기준으로 계층이 꽤 늘었다.

| 층위 | 무엇 | 격리 단위 |
|---|---|---|
| **서브에이전트** | 한 세션 안의 워커 | 컨텍스트 윈도우 |
| **fork (`/subtask`)** | 현재 대화 전체를 상속한 서브에이전트 | 출력만 격리 |
| **background agents** | 독립 세션 여러 개를 한 곳에서 모니터링 | 세션 |
| **agent teams** | Claude가 직접 스폰·감독하는 세션 팀 | 세션 + 메시징 |
| **cross-session messaging** | 세션끼리 메시지 주고받기 | 세션 |
| **git worktree** | 저장소 사본 자체를 분리 (`isolation: worktree`) | 파일시스템 |
| **Dynamic Workflows** | 수십~수백 에이전트를 스크립트로 오케스트레이션 | 대화 밖 |

책의 "multi-Claude workflow"는 원래 여러 터미널에 Claude를 띄우고 worktree로 충돌을 피하는 수동 패턴을 가리킨다. 지금은 상당 부분이 제품 기능으로 흡수됐다 — **스터디에서 언급하면 좋을 변화 포인트.**

## 2. 언제 서브에이전트를 사용하는가

### 2.1 책의 3가지 판단 기준

**① 작업의 복잡도**
- 단순 파일 수정, 짧은 코드 생성 → 메인 대화에서 직접
- 여러 파일 분석, 장기 실행 작업 → 서브에이전트 위임

**② 컨텍스트 소모량**
- 대규모 파일 읽기, 명령 실행이 필요하면 위임 고려

**③ 전문성 요구 수준**
- 특정 도메인의 상세 지침이 필요하면, 그 지침으로 구성된 서브에이전트

### 2.2 공식문서의 대조표

**메인 대화를 쓸 때:**
- 잦은 왕복이나 반복적 다듬기가 필요할 때
- 계획 → 구현 → 테스트처럼 **여러 단계가 같은 맥락을 공유**할 때
- 빠르고 좁은 수정
- **레이턴시가 중요할 때** (fork가 아닌 서브에이전트는 맨바닥에서 컨텍스트를 다시 모아야 함)

**서브에이전트를 쓸 때:**
- 메인 컨텍스트에 필요 없는 **장황한 출력**이 나오는 작업
- **도구/권한 제한을 강제**하고 싶을 때
- 작업이 자기완결적이고 요약으로 반환 가능할 때

### 2.3 한 문장으로 압축한 기준

> **부산물이 크고 결론이 작으면 위임한다. 맥락이 공유되고 상호작용이 빡빡하면 메인에 머문다.**

위임은 결국 **"레이턴시 + 콜드스타트"와 "깨끗한 윈도우"의 트레이드**다.

### 2.4 부가 팁

- 대화에 **이미 있는 내용**에 대한 곁가지 질문은 서브에이전트가 아니라 **`/btw`**. 전체 컨텍스트를 보되 도구 접근이 없고, 답이 히스토리에 남지 않는다.
- 병렬 리서치 시 주의: 서브에이전트들이 각자 **상세한 결과**를 반환하면 결국 메인 컨텍스트를 잡아먹는다. 반환 형식을 좁게 지정할 것.
- 컨텍스트 윈도우를 초과할 정도로 지속적 병렬성이 필요하면 → agent teams

## 3. 공식문서 심화 — 책에 없거나 최신화된 것들

### 3.1 내장 서브에이전트

정의하지 않아도 이미 있는 것들. **커스텀을 만들기 전에 이것부터 익숙해질 것.**

| 이름 | 모델 | 도구 | 용도 |
|---|---|---|---|
| **Explore** | 메인 상속 (Claude API에선 Opus 상한) | 읽기 전용, Write/Edit 거부 | 파일 탐색, 코드 검색 |
| **Plan** | 메인 상속 | 읽기 전용 | plan mode의 코드베이스 리서치 |
| **General-purpose** | 메인 상속 | 서브에이전트가 쓸 수 있는 전부 | 탐색+수정이 함께 필요한 다단계 작업 |
| claude | 상속 | 전부 | 특화 에이전트에 안 맞는 캐치올 |
| statusline-setup | Sonnet | — | `/statusline` |
| claude-code-guide | Haiku | — | Claude Code 기능 질문 |

패턴이 보인다: **읽기 전용 리서치 에이전트(Explore/Plan)는 가볍고 싸게, 만능 에이전트(general-purpose)는 메인 모델과 전체 도구를 상속.** 최소권한 아이디어가 내장 에이전트에 이미 인코딩되어 있다.

- Explore/Plan은 **CLAUDE.md와 git status를 일부러 건너뛴다** (속도·비용). 그래서 "vendor/ 무시" 같은 규칙이 꼭 필요하면 **위임 프롬프트에 다시 적어야** 한다.
- Explore 호출 시 Claude가 철저도(thoroughness)를 지정: `quick` / `medium` / `very thorough`
- Explore를 Haiku로 고정하고 싶으면 → 같은 이름 `Explore`로 사용자/프로젝트 에이전트를 정의하면 내장을 덮어쓴다
- v2.1.198부터 `/agents`의 대화형 생성 마법사는 사라졌다. **Claude에게 만들어 달라고 하거나 파일을 직접 쓴다.**

### 3.2 정의 방법과 스코프

Markdown + YAML frontmatter. 우선순위 순:

| 위치 | 범위 | 우선순위 |
|---|---|---|
| Managed settings | 조직 전체 | 1 (최상) |
| `--agents` CLI 플래그 | 현재 세션 | 2 |
| `.claude/agents/` | 현재 프로젝트 | 3 |
| `~/.claude/agents/` | 내 모든 프로젝트 | 4 |
| 플러그인의 `agents/` | 플러그인 활성 범위 | 5 (최하) |

```markdown
---
name: code-reviewer
description: Reviews code for quality and best practices
tools: Read, Glob, Grep
model: sonnet
---

You are a code reviewer. When invoked, analyze the code and provide
specific, actionable feedback on quality, security, and best practices.
```

- **필수 필드는 `name`, `description` 둘뿐.**
- 본문이 그대로 시스템 프롬프트가 된다. Claude Code의 전체 시스템 프롬프트는 상속하지 않는다.
- 파일명은 `name`과 달라도 된다. **식별자는 `name` 뿐.**
- 디렉터리를 감시하므로 파일을 수정하면 **재시작 없이 몇 초 내 반영**. 단 ① 그 스코프의 첫 `agents` 디렉터리를 새로 만든 경우 ② `--add-dir` 하위 ③ `--disable-slash-commands` 세션 → 재시작 필요.
- **`name` 없으면 문서로 간주하고 조용히 스킵**, `description` 없으면 디버그 로그에만 남기고 스킵. 안 뜰 때 `--debug`로 확인.

### 3.3 주요 frontmatter 필드

| 필드 | 설명 |
|---|---|
| `name` / `description` | 필수. description은 **Claude가 위임 여부를 판단하는 근거** |
| `tools` | 허용 목록. 생략 시 전부 상속 |
| `disallowedTools` | 거부 목록. 둘 다 있으면 **disallowed 먼저 적용 후 tools 해석** |
| `model` | `sonnet`/`opus`/`haiku`/`fable`/풀 ID/`inherit`. 기본 `inherit` |
| `permissionMode` | `default`(수동)/`acceptEdits`/`auto`/`dontAsk`/`bypassPermissions`/`plan` |
| `skills` | 시작 시 컨텍스트에 **프리로드**할 스킬 |
| `memory` | `user`/`project`/`local` — 세션을 넘는 영속 메모리 |
| `mcpServers` | 이 서브에이전트에만 붙일 MCP 서버 (인라인 정의 가능) |
| `hooks` | 이 서브에이전트가 활성일 때만 도는 라이프사이클 훅 |
| `isolation` | `worktree` → 임시 git worktree에서 실행 |
| `maxTurns` | 최대 에이전틱 턴 수 |
| `effort` | `low`~`max`. 세션 effort를 덮어씀 |
| `background` | `true` → 항상 백그라운드 |
| `color` | 태스크 목록 표시색 |

### 3.4 자주 쓰는 도구 조합

| 용도 | 도구 |
|---|---|
| 읽기 전용 분석 | `Read`, `Grep`, `Glob` |
| 테스트 실행 | `Bash`, `Read`, `Grep` |
| 코드 수정 | `Read`, `Edit`, `Write`, `Grep`, `Glob` |
| 전체 | `tools` 생략 |

- `tools` 목록의 항목이 **하나도 실제 도구로 해석되지 않으면 서브에이전트 실행 자체를 거부**하고 에러를 낸다 (오타 방어).
- MCP 서버 단위 패턴 지원: `mcp__github`, `mcp__server__*`, `disallowedTools`에선 `mcp__*`
- **백그라운드 서브에이전트는 내장 도구 집합이 더 좁다.** 같은 정의라도 포그라운드/백그라운드에서 도구가 다르게 해석될 수 있음 — 디버깅할 때 함정.
- MCP 서버를 서브에이전트 frontmatter에 **인라인으로만** 정의하면, 그 도구 설명이 메인 대화 컨텍스트를 먹지 않는다. **컨텍스트 절약 테크닉.**

### 3.5 호출 방법 3단계

1. **자연어**: `"code-reviewer 서브에이전트로 최근 변경 좀 봐줘"` → Claude가 판단
2. **@-멘션**: `@"code-reviewer (agent)"` → **그 서브에이전트가 도는 것을 보장**
3. **세션 전체**: `claude --agent code-reviewer` 또는 `.claude/settings.json`의 `"agent"` → 메인 스레드 자체가 그 프롬프트·도구·모델을 뒤집어씀

> @-멘션은 **어떤 서브에이전트를 부를지**를 정하는 것이지, **어떤 프롬프트를 받을지**를 정하는 게 아니다. 태스크 프롬프트는 여전히 Claude가 작성한다.

자동 위임을 유도하려면 description에 `"use proactively"` 같은 문구를 넣는다.

### 3.6 중첩과 동시성 한도

- 기본적으로 서브에이전트도 서브에이전트를 띄울 수 있다. **메인 아래 3계층**까지.
- `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` 로 조절. `1`이면 중첩 off.
- 깊이 한도에 도달하면 Agent 도구를 아예 회수 → 그 서브에이전트는 직접 일하고 요약 하나를 반환.
- 동시 실행 기본 **20개**. 초과 시 `Concurrent subagent limit reached`. `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`로 조절.
- **세션 전체 누적 개수에는 제한이 없다.**
- SDK에선 `maxBudgetUsd` / `max_budget_usd` 로 비용 상한까지 걸 수 있다.

> Opus 5는 이전 모델보다 **위임을 훨씬 적극적으로 한다.** 그래서 Opus 5로 돌릴 땐 depth/concurrency/spend 한도가 특히 중요하다.

### 3.7 fork — 대화 전체를 상속하는 서브에이전트

`/subtask <작업>` 으로 실행.

| | fork | 일반 서브에이전트 |
|---|---|---|
| 컨텍스트 | 대화 기록 **전체** | 전달한 프롬프트만 |
| 시스템 프롬프트·도구 | 메인과 동일 | 정의 파일에서 |
| 모델 | 메인과 동일 | `model` 필드 |
| 프롬프트 캐시 | **메인과 공유** | 별도 |

- **입력 격리는 포기하고 출력 격리만 취하는** 형태. 배경 설명을 다시 할 필요가 없다.
- 시스템 프롬프트와 도구 정의가 부모와 동일해서 **첫 요청이 부모의 프롬프트 캐시를 재사용** → 같은 맥락이 필요한 작업이면 새 서브에이전트보다 싸다.
- 인터랙티브 세션에선 fork mode가 **기본 on**.

### 3.8 안전장치 두 가지 (스터디에서 다루면 좋음)

**① 서브에이전트 출력 스캐닝 (v2.1.210+)**
서브에이전트는 내가 검토하지 않은 파일·웹페이지·명령 출력을 읽었을 수 있고, 그 안에 메인 대화를 겨냥한 지시문이 섞여 있을 수 있다. Claude Code는 리드가 읽기 전에 최종 보고를 스캔해서:
- `<system-reminder>` 같은 하네스 전용 태그 흉내 → 백슬래시 삽입으로 무력화
- `Human:` / `Assistant:` 로 시작하는 줄 → 콜론 앞에 백슬래시
- 권한 설정 언급(`bypassPermissions` 등) → 텍스트는 그대로 두되 `[harness: ...]` 마커 줄을 앞에 붙임

**아무것도 삭제하거나 고쳐 쓰지 않는다.** 악의 여부를 판단하지도 않는다. 도구 제한의 대체재가 아니라 보조장치.

**② PreToolUse 훅으로 조건부 검증**
`tools` 필드보다 세밀한 통제가 필요할 때. 예: Bash는 주되 SELECT만 허용.

```yaml
hooks:
  PreToolUse:
    - matcher: "Bash"
      hooks:
        - type: command
          command: "./scripts/validate-readonly-query.sh"
```
스크립트가 **exit code 2**로 종료하면 실행이 차단되고 stderr가 Claude에게 전달된다. 시스템 프롬프트로 "쓰기 하지 마"라고 시키고, 훅은 백스톱으로 두는 이중 방어.

### 3.9 영속 메모리

`memory: user | project | local` → 대화를 넘어 살아남는 디렉터리를 준다.

| 스코프 | 위치 |
|---|---|
| `user` | `~/.claude/agent-memory/<name>/` |
| `project` | `.claude/agent-memory/<name>/` (버전관리 공유 — **권장 기본값**) |
| `local` | `.claude/agent-memory-local/<name>/` |

- 시스템 프롬프트에 `MEMORY.md`의 앞 200줄(또는 25KB)이 주입된다.
- 마크다운 본문에 "발견한 코드경로·패턴·아키텍처 결정을 메모리에 갱신하라"고 적어두면 스스로 지식베이스를 쌓는다.
- auto memory를 끄면 이 필드는 무효가 된다.

### 3.10 재개(resume)

- 서브에이전트 호출은 매번 **새 인스턴스**다. 이어서 하려면 명시적으로 재개해야 한다.
- 완료 시 Claude가 **agent ID**를 받는다. Claude는 `SendMessage` 도구의 `to`에 ID나 이름을 넣어 재개한다.
- **Explore와 Plan은 one-shot이라 agent ID를 반환하지 않는다 → 재개 불가.** 이어갈 일이면 general-purpose나 커스텀을 써라.
- 트랜스크립트는 별도 파일(`~/.claude/projects/{project}/{sessionId}/subagents/agent-{agentId}.jsonl`)에 저장되어 **메인 대화가 compaction돼도 영향받지 않는다.** 기본 30일 보관.

### 3.11 공통 패턴 3가지

**대량 출력 격리**
```
서브에이전트로 테스트 스위트를 돌리고, 실패한 테스트와 에러 메시지만 보고해줘
```

**병렬 리서치**
```
인증, DB, API 모듈을 각각 별도 서브에이전트로 동시에 조사해줘
```
→ 서로 의존하지 않는 경로일 때만 효과적.

**체이닝**
```
code-reviewer로 성능 문제를 찾고, 그다음 optimizer로 고쳐줘
```
→ 각 단계 결과가 Claude로 돌아오고, Claude가 다음 서브에이전트에 필요한 맥락만 전달.

## 4.2 서브에이전트 사용하기

### 4.2.1 실행 가능한 서브에이전트 확인 — 명령어가 바뀌었다

책은 `/agents`로 확인한다고 하는데, **v2.1.198부터 `/agents`는 패널을 열지 않는다.** 실행하면 서브에이전트 파일 위치를 알려주는 안내만 출력된다. 생성·편집은 Claude에게 시키거나 파일을 직접 쓴다.

지금 확인하는 방법은 목적에 따라 셋으로 갈린다.

| 알고 싶은 것 | 명령 |
|---|---|
| **지금 도달 가능한 에이전트 목록** | `/list-agents` (별칭 `/peers`) |
| **이 세션에서 백그라운드로 도는 것 전부** | `/tasks` |
| **백그라운드 세션 전체를 한 화면에서** | `claude agents` (agent view, 셸에서) |
| 정의 파일이 어디 있는지 | `/agents` (안내만 출력) |
| 설정 문제 진단 (중복 name 등) | `/doctor` |

> **함정**: `/agents`(슬래시 커맨드)와 `claude agents`(CLI 서브커맨드)는 이름만 비슷할 뿐 완전히 다르다. 후자는 **agent view** — 백그라운드 세션 대시보드다.

`/list-agents` 출력 구조:

```
<이 세션 자신의 이름>          ← 다른 세션이 나를 부를 때 쓰는 이름
├─ 서브에이전트                 ← 현재 세션 안에서 도는 것
├─ 팀메이트                     ← 이 세션의 agent team (v2.1.239+부터 표시)
├─ 다른 로컬 세션               ← 같은 머신, 백그라운드 세션 포함
├─ 클라우드 세션                ← `cloud` 라벨, Remote Control 연결 시에만
└─ 다른 머신의 Remote Control   ← `Remote Control` 라벨, 끊기면 `offline`
```

로컬 세션은 **작업 디렉터리도 함께** 보여준다. 이름이 겹칠 때 구분하라는 배려다.

이름이 붙은 백그라운드 서브에이전트는 **@-멘션 typeahead에도 상태와 함께** 나타난다.

에이전트의 출처(프로젝트/사용자/내장/플러그인)와 우선순위는 위 3.2절 표 참조. 내장 에이전트는 3.1절 참조.

### 4.2.2 description 기반 자동 선택

Claude는 **각 서브에이전트의 `description` 필드**를 보고 위임 여부와 대상을 정한다. 그래서 description은 "이게 무엇인가"가 아니라 **"언제 이걸 써야 하는가"**를 쓰는 자리다.

```yaml
# 나쁨 — 무엇인지만 설명
description: A code reviewer

# 좋음 — 언제 위임할지 + 트리거 문구
description: Expert code review specialist. Proactively reviews code for
  quality, security, and maintainability. Use immediately after writing
  or modifying code.
```

- `"use proactively"` 같은 문구를 넣으면 적극적 위임을 유도한다.
- 자동 위임이 안 될 때 점검 순서 (공식 트러블슈팅):
  1. **`Agent`가 allowedTools에 있는가** — 없으면 `canUseTool` 콜백으로 떨어지거나 `dontAsk` 모드에서 거부된다
  2. **이름을 명시**했는가 — `"Use the code-reviewer agent to..."`
  3. **description이 충분히 구체적인가**

명시 호출 3단계는 3.5절 참조 (자연어 → @-멘션 → `--agent`).

### 4.2.3 resume — 명시적 재개

**서브에이전트 호출은 매번 새 인스턴스다.** 이어서 하려면 재개해야 한다.

```
Use the code-reviewer subagent to review the authentication module
[에이전트 완료]

Continue that code review and now analyze the authorization logic
[Claude가 이전 대화 컨텍스트를 그대로 가진 서브에이전트를 재개]
```

메커니즘:

- 서브에이전트가 완료되면 Claude가 **agent ID**를 받는다 (Agent 도구 결과에 `agentId: <id>` 텍스트 블록)
- Claude는 `SendMessage` 도구의 `to`에 ID나 이름을 넣어 재개한다
- 재개된 서브에이전트는 **이전 도구 호출·결과·추론을 전부 유지**한 채 멈춘 지점에서 이어간다
- `SendMessage`는 agent teams가 켜져 있지 않아도 쓸 수 있다. 팀 프로토콜 메시지(`shutdown_request`, `plan_approval_response`)만 팀을 요구한다

주의할 점들:

- **Explore와 Plan은 one-shot이라 agent ID를 반환하지 않는다 → 재개 불가.** 이어갈 작업이면 `general-purpose`나 커스텀 에이전트를 써야 한다.
- 완료된 서브에이전트가 `SendMessage`를 받으면 **새 Agent 호출 없이 백그라운드에서 auto-resume** 된다. Claude가 `TaskStop`으로 멈춘 것도 마찬가지.
- 단 **내가 직접 멈춘 것**(`/tasks`에서 `x`, SDK `stop_task`)은 auto-resume 되지 않는다 (v2.1.191+). 거절 응답이 돌아온다. 패널에 행이 남아 있는 동안 트랜스크립트에 직접 타이핑하면 취소 상태가 풀린다.
- 이름 재사용 검사 (v2.1.199+): 그 이름이 여전히 같은 에이전트를 가리키는지 확인한다. 재스폰된 백그라운드 에이전트가 이름을 가져갔으면 **잘못된 에이전트에게 배달하는 대신 거절**하고, 그 이름이 지금 누구를 가리키는지 알려준다.
- v2.1.198부터 **서브에이전트는 자기를 띄운 에이전트의 메시지를 정상적인 작업 지시로 취급**한다. 작업 중간 코스 수정도 가능. 단 두 가지는 불변:
  - 어떤 에이전트의 메시지도 **대기 중인 권한 프롬프트의 승인이 되지 않는다**
  - 어떤 에이전트의 메시지도 **서브에이전트의 권한 설정·CLAUDE.md·구성을 바꾸지 못한다**

트랜스크립트:

```
~/.claude/projects/{project}/{sessionId}/subagents/agent-{agentId}.jsonl
```

- 메인 대화가 compaction돼도 **영향받지 않는다** (별도 파일)
- 같은 세션을 resume하면 Claude Code 재시작 후에도 서브에이전트를 재개할 수 있다
- `cleanupPeriodDays` (기본 30일) 후 자동 삭제

### 4.2.4 예외 처리 및 복구

**① API 에러로 중단된 경우 (v2.1.199+)**

에러 텍스트가 마치 서브에이전트의 조사 결과인 것처럼 반환되던 문제가 고쳐졌다. 어디서 돌았느냐에 따라 다르다:

| 위치 | 이미 텍스트를 냈다면 | 아무것도 안 냈거나 도구 호출만 했다면 |
|---|---|---|
| **포그라운드** | 부분 출력 + "잘렸고 작업을 끝내지 못했다"는 note | `Agent terminated early due to an API error` + 에러 상세 |
| **백그라운드** | failed로 표시, 종료 메시지에 API 에러 이름과 **마지막 출력 포함** (부분 작업 보존) | 동일 |

복구: 에러가 해소되면 재시도를 요청하거나 서브에이전트를 재개한다.

**② 도구가 하나도 안 잡히는 경우**

`tools` 목록의 항목이 전부 오타이거나 서브에이전트가 쓸 수 없는 도구만 적혀 있으면, **실행 자체를 거부**하고 해석 안 된 항목을 에러에 나열한다 (`Agent would be spawned with zero tools`). v2.1.208 이전엔 도구 없이 실행돼서 빈 결과나 이상한 결과를 돌려줬다.

**③ 한도에 걸린 경우**

| 에러 | 원인 | 대응 |
|---|---|---|
| `Concurrent subagent limit reached` | 동시 20개(기본) 초과 | 에러가 Claude에게 재시도하지 말라고 알림. 실행 수가 줄면 다시 가능 |
| `Budget limit reached` | `maxBudgetUsd` 초과 | 추가 스폰 거부 + 도는 백그라운드 서브에이전트 중지 + `error_max_budget_usd`로 쿼리 종료 |
| 깊이 한도 도달 | 중첩 3계층(기본) | Agent 도구를 회수 → 그 서브에이전트가 직접 일하고 요약 반환 |

**④ 정의 파일이 안 잡히는 경우**

- `name` 없음 → 문서로 간주하고 조용히 스킵
- `name`이 `-`로 시작하거나 `:` 포함 → 스킵 + 디버그 로그
- `description` 없음 → 스킵 + 디버그 로그
- YAML 파싱 실패 → 스킵 + 파싱 에러 로그
- 새 `agents` 디렉터리의 첫 파일 → **재시작 필요** (감시 대상은 세션 시작 시점에 존재하던 디렉터리뿐)
- `--add-dir` 하위 → 감시 안 함, 재시작 필요
- 동명 프로그램적 정의가 파일 정의를 덮어씀

사전 점검: `claude plugin validate .claude/agents` (v2.1.233+) — 프론트매터 파싱 실패 파일을 찾아준다. 단 파싱은 되는데 `name`이 없는 파일은 안 잡는다.

**⑤ 출력에 지시문이 섞여 온 경우**

3.8절의 출력 스캐닝 참조. 스캔은 악의 여부를 판단하지 않고, 보고서가 유도한 도구 호출도 여전히 세션의 권한 검사와 샌드박싱을 거친다. **도구 제한의 대체재가 아니다.**

### 4.2.5 서브에이전트 성능 측정

측정할 것은 **두 가지이고, 따로 재야 한다**:

1. **불러야 할 때 부르는가** (트리거 정확도) — description의 문제
2. **불렀을 때 결과가 맞는가** (출력 품질) — 본문 프롬프트의 문제

트리거되는 걸 봤다는 건 Claude가 찾았다는 뜻이지, 의도한 일을 했다는 뜻이 아니다.

**기본 방법: baseline 비교**

현실적인 프롬프트 몇 개를 모아, 각각을 **fresh session**에서 ① 에이전트 있이 ② 없이 돌려 비교한다. fresh session이 중요한 이유는, **에이전트를 만들면서 쌓인 컨텍스트가 지시문의 구멍을 가리기 때문**이다.

**관측 수단**

| 수단 | 얻는 것 |
|---|---|
| `/tasks` → Enter | 서브에이전트 트랜스크립트 열람 (완료 후 30초 창) |
| 트랜스크립트 파일 직접 읽기 | 전체 도구 호출·결과·`compact_boundary`의 `preTokens` |
| `--forward-subagent-text` | `-p` + `--output-format stream-json`에서 서브에이전트의 텍스트·thinking 블록을 `parent_tool_use_id`와 함께 방출 → **각 서브에이전트 트랜스크립트를 프로그램적으로 재구성**. 중첩 서브에이전트도 forward됨(v2.1.219+). v2.1.211+ |
| `total_cost_usd` (result 메시지) | 서브에이전트 요청 포함 총 비용 |
| `--max-budget-usd` | 상한을 걸고 초과 여부로 비용 프로파일 파악 |
| `/context` | 메인 대화의 컨텍스트 점유 — 위임 전후 비교 |

**skill-creator 플러그인의 eval 루프**

스킬용으로 만들어졌지만 **서브에이전트 평가에도 그대로 쓸 수 있는 구조**다.

```
/plugin marketplace add anthropics/claude-plugins-official
/plugin install skill-creator@claude-plugins-official
/reload-plugins        # 설치 요약에 이 안내가 뜨면
```

그 다음 `evaluate my summarize-changes skill with skill-creator` 처럼 요청하면:

| 산출물 | 내용 |
|---|---|
| `evals/evals.json` | 프롬프트·입력 파일·기대 동작을 테스트 케이스로 저장 |
| (실행) | **케이스당 서브에이전트를 하나씩** 띄워 깨끗한 컨텍스트로 돌리고 토큰 수·소요 시간 기록 |
| `grading.json` | 각 assertion에 대해 pass/fail + 근거 |
| `benchmark.json` | with-skill vs without-skill의 통과율·시간·토큰 집계 → **통과율 향상 대비 토큰·시간 오버헤드** 비교 |
| (blind A/B) | 두 버전을 눈가림 비교 → 커밋 전에 개선인지 확인 |
| (description 튜닝) | should-trigger / should-not-trigger 프롬프트를 생성해 hit rate를 재고 description 수정 제안 |
| (HTML 리뷰 뷰어) | 각 출력을 검토하고 정성 피드백을 기록 → 다음 반복이 그걸 읽음 |

**최적화 레버** (측정 후 돌릴 것들)

- `model`을 낮춰본다 (탐색·경로수집은 haiku로 충분한 경우가 많다)
- `tools`를 좁힌다 — 선택지가 줄면 판단도 빨라진다
- `effort`를 낮춘다
- `maxTurns`로 폭주를 막는다
- **출력 형식을 고정**한다 — 반환 토큰이 줄고 병합이 쉬워진다
- `isolation: worktree`로 되돌리기 비용을 낮춘다

## 4.3 커스텀 서브에이전트 개발과 스킬 주입

### 4.3.1 정의 파일 구조

```markdown
---
name: code-reviewer            # 필수
description: Reviews code...   # 필수
tools: Read, Glob, Grep        # 선택
model: sonnet                  # 선택
---

You are a code reviewer. When invoked, analyze the code and provide
specific, actionable feedback on quality, security, and best practices.
```

- **프론트매터 = 메타데이터와 구성 / 본문 = 시스템 프롬프트**
- 서브에이전트는 **이 시스템 프롬프트 + 기본 환경 정보(작업 디렉터리 등)만** 받는다. Claude Code의 전체 시스템 프롬프트는 상속하지 않는다.
- 파일명은 `name`과 달라도 된다. **식별자는 `name`뿐.**
- `.claude/agents/`와 `~/.claude/agents/`는 **재귀 스캔**되므로 `agents/review/`, `agents/research/` 식으로 정리해도 된다. 서브폴더 경로는 식별에 영향 없다.
  - **예외**: 플러그인은 서브폴더가 스코프 식별자에 포함된다 → `agents/review/security.md` in `my-plugin` = `my-plugin:review:security`
- name은 전체 트리에서 유일하게. 같은 디렉터리(서브폴더 포함) 안에서 겹치면 **파일시스템 읽기 순서**로 하나만 로드된다 — 문서화된 우선순위가 없다. `/doctor`가 잡아준다.
- `-p` 모드에서 `--append-subagent-system-prompt`로 **모든 서브에이전트 시스템 프롬프트 끝에 텍스트를 덧붙일 수 있다** (중첩 포함, fork는 제외). v2.1.205+

작업 디렉터리 동작:
- 메인 대화의 cwd에서 시작한다
- 서브에이전트 안의 `cd`는 Bash/PowerShell 호출 사이에 유지되지 않고, 메인 대화의 cwd에도 영향을 주지 않는다
- `isolation: worktree`면 자기 worktree 안에서 명령이 돈다. worktree 밖으로 나가려는 명령은 실패한다. git을 메인 체크아웃으로 리다이렉트하는 명령은 차단되고, worktree 안에 머문다고 검증할 수 없는 형태의 명령은 **git을 안 쓰더라도 거부**된다.

### 4.3.2 YAML 프론트매터 — 필수 / 선택 구분

**필수는 딱 둘: `name`, `description`.** 나머지는 전부 선택이지만 실무에서의 무게는 다르다.

| 등급 | 필드 | 왜 |
|---|---|---|
| **필수** | `name` | 소문자+하이픈. `:` 금지(플러그인 스코프 예약), `-`로 시작 금지. 훅이 `agent_type`으로 받는 값 |
| **필수** | `description` | Claude의 위임 판단 근거. 이게 부실하면 에이전트가 아예 안 불린다 |
| **사실상 필수** | `tools` 또는 `disallowedTools` | 최소권한. 생략하면 서브에이전트가 쓸 수 있는 도구 전부 상속 |
| **사실상 필수** | `model` | 생략 시 `inherit`. 탐색용을 Opus로 돌리면 돈이 샌다 |
| 상황별 | `permissionMode` | 부모 모드를 덮어씀 (예외 있음, 아래) |
| 상황별 | `skills` | 도메인 지식 프리로드 — 4.3.4 |
| 상황별 | `memory` | 세션을 넘는 학습 |
| 상황별 | `hooks` | 결정론적 게이트 |
| 상황별 | `mcpServers` | 이 에이전트에만 붙일 외부 도구 |
| 상황별 | `isolation: worktree` | 위험한 리팩터링의 안전망 |
| 튜닝 | `maxTurns`, `effort`, `background`, `color`, `initialPrompt` | |

### 4.3.3 고급 설정 필드

**`disallowedTools` — 상속 풀에서 빼기**

```yaml
---
name: no-writes
description: Inherits the available tools except file writes
disallowedTools: Write, Edit
---
```

- `tools`가 화이트리스트라면 이건 블랙리스트. **Bash와 MCP 도구 등 나머지는 그대로 유지**된다
- 둘 다 있으면 **`disallowedTools`가 먼저 적용되고, 남은 풀에서 `tools`가 해석**된다. 양쪽에 다 적힌 도구는 제거된다
- MCP 서버 단위 패턴: `mcp__github`, `mcp__github__*`, `disallowedTools`에선 `mcp__*`로 전체 MCP 제거

**`permissionMode` — 부모가 이기는 경우가 있다**

| 모드 | 동작 |
|---|---|
| `default` (별칭 `manual`) | 수동 — 권한을 묻는다 |
| `acceptEdits` | 작업 디렉터리·additionalDirectories 안의 파일 편집과 흔한 파일시스템 명령 자동 수락 |
| `auto` | 백그라운드 분류기가 명령과 보호 디렉터리 쓰기를 검토 |
| `dontAsk` | 권한 프롬프트 자동 거부. 명시 허용된 도구는 동작 |
| `bypassPermissions` | 프롬프트 건너뜀 |
| `plan` | 읽기 전용 탐색 |

**우선순위 함정** — frontmatter를 써도 무시되는 경우가 있다:
- 부모가 `bypassPermissions` 또는 `acceptEdits`면 **부모가 이기고 덮어쓸 수 없다**
- 부모가 `auto`면 서브에이전트도 auto를 상속하고 **frontmatter의 `permissionMode`는 무시**된다. 분류기가 부모 세션과 같은 차단·허용 규칙으로 평가한다
- `permissions.disableBypassPermissionsMode`가 켜져 있으면 `permissionMode: bypassPermissions`는 무시되고 부모 모드로 돈다 (v2.1.223+)

**`hooks` — 서브에이전트 생애주기에 거는 훅**

두 자리가 있다:

| 위치 | 범위 |
|---|---|
| 서브에이전트 frontmatter | **그 서브에이전트가 활성일 때만** 돌고, 끝나면 정리됨 |
| `settings.json` | 세션 전역. 서브에이전트 안에서도 발화 |

- frontmatter의 `Stop` 훅은 런타임에 **`SubagentStop`으로 자동 변환**된다
- 프로젝트 레벨 에이전트 파일의 frontmatter 훅은 **그 폴더의 워크스페이스 신뢰를 수락해야** 돈다 (v2.1.218+). 부모 폴더 신뢰로는 부족하고, `-p` 세션도 신뢰로 치지 않는다. 신뢰 전까지 서브에이전트는 돌되 훅만 건너뛰고 디버그 로그에 이유를 남긴다
- `~/.claude/agents/`의 사용자 에이전트와 `--agents`로 넘긴 정의는 이 단계가 필요 없다
- **플러그인 서브에이전트는 보안상 `hooks`·`mcpServers`·`permissionMode`를 무시**한다. 필요하면 파일을 `.claude/agents/`로 복사해야 한다

세션 레벨 이벤트:

| 이벤트 | matcher | 발화 시점 |
|---|---|---|
| `SubagentStart` | agent type 이름 | 서브에이전트 시작 |
| `SubagentStop` | agent type 이름 | 서브에이전트 완료 |
| `PreToolUse` / `PostToolUse` | 도구 이름 | 서브에이전트의 도구 호출 전후 |

> matcher는 **anchor 없는 정규식**으로 평가된다. 플러그인 스코프 이름처럼 콜론이 있으면 `^my-plugin:db-agent$`로 감싸야 그것만 매치된다.

**`memory` — 세션을 넘는 학습**

```yaml
---
name: code-reviewer
description: Reviews code for quality and best practices
memory: user
---

You are a code reviewer. As you review code, update your agent memory with
patterns, conventions, and recurring issues you discover.
```

| 스코프 | 위치 | 언제 |
|---|---|---|
| `user` | `~/.claude/agent-memory/<name>/` | 모든 프로젝트에서 기억 |
| `project` | `.claude/agent-memory/<name>/` | 프로젝트 한정 + 버전관리 공유 — **권장 기본값** |
| `local` | `.claude/agent-memory-local/<name>/` | 프로젝트 한정, 커밋 안 함 |

켜면 일어나는 일:
- 시스템 프롬프트에 메모리 디렉터리 읽기·쓰기 지침이 들어간다
- `MEMORY.md`의 **앞 200줄 또는 25KB 중 먼저 오는 쪽**이 시스템 프롬프트에 포함되고, 초과하면 정리하라는 지침이 붙는다
- Read/Write/Edit 도구가 자동으로 활성화된다

주의: **auto memory를 끄면**(`autoMemoryEnabled`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY`) 이 필드는 아무 효과가 없다.

운용 팁:
- 시작 전: "리뷰하기 전에 네 메모리에서 전에 본 패턴을 확인해"
- 끝난 후: "이제 배운 걸 메모리에 저장해"
- 아예 마크다운 본문에 자가 유지 지침을 박아두는 게 낫다

### 4.3.4 `skills` 필드 — 상세

이게 "스킬 주입"의 실체다.

**무엇을 하는가**

> `skills`에 나열한 스킬의 **전문(full content)이 서브에이전트 시작 시점에 컨텍스트로 주입**된다. description만이 아니라 본문 전체다.

일반 세션과 정확히 반대다:

| | 일반 세션 | 서브에이전트 `skills` |
|---|---|---|
| 컨텍스트에 항상 있는 것 | 스킬 **description 목록** | — |
| 본문이 들어오는 시점 | 호출(invoke)될 때 | **시작 시점에 이미 들어와 있음** |
| 발견 과정 | Claude가 목록을 보고 고름 | 고를 필요 없음 |

즉 **"이 에이전트는 반드시 이 지식을 갖고 시작한다"를 보장하는 장치**다. 탐색·선택 단계가 사라지므로 실패 지점이 하나 줄어든다.

**접근 제어가 아니라 프리로드 제어다**

이걸 헷갈리기 쉽다. `skills`에 안 적어도 서브에이전트는 **Skill 도구로 project/user/plugin 스킬을 발견하고 호출할 수 있다.**

완전히 막으려면:
- `tools` 목록에서 `Skill`을 빼거나
- `disallowedTools`에 `Skill`을 추가

> 반대로 `tools`에 `Skill`을 적어서 프리로드하려 하면 안 된다. 프리로드는 `skills` 필드가 담당한다.

**프리로드할 수 없는 스킬**

- **`disable-model-invocation: true`인 스킬은 프리로드 불가.** 프리로드는 "Claude가 호출할 수 있는 스킬 집합"에서 가져오는데, 이 플래그가 그 집합에서 뺀 것이기 때문이다.
- 번들 `/verify`도 같은 이유로 프리로드할 수 없다 (사용자만 실행 가능).
- 목록의 스킬이 없거나 조직 정책으로 비활성이면 **조용히 건너뛰고 디버그 로그에 경고**를 남긴다. 에러가 아니다 → `--debug` 없이는 모른다.

**에이전트 팀에서의 함정 (중요)**

> 서브에이전트 정의를 **팀메이트 역할로 재사용**할 때, `skills`와 `mcpServers` frontmatter는 **적용되지 않는다.**
> 팀메이트는 일반 세션처럼 프로젝트/사용자 설정에서 스킬과 MCP 서버를 로드한다.

같은 정의 파일이 서브에이전트로 돌 때와 팀메이트로 돌 때 다르게 동작한다는 뜻이다. 4.4에서 다시 다룬다.

**역방향: 스킬의 `context: fork`**

`skills` 필드가 "서브에이전트에 스킬을 넣는" 방향이라면, 반대 방향도 있다.

```yaml
---
name: deep-research
description: Research a topic thoroughly
context: fork
agent: Explore
---

Research $ARGUMENTS thoroughly:

1. Find relevant files using Glob and Grep
2. Read and analyze the code
3. Summarize findings with specific file references
```

돌아가는 순서:
1. 격리된 새 컨텍스트가 생긴다
2. 서브에이전트가 **SKILL.md 내용을 프롬프트로** 받는다
3. `agent` 필드가 실행 환경(모델·도구·권한)을 정한다
4. 끝나면 결과를 요약해 메인 대화로 돌려준다

**두 방향 정리** (공식문서 표):

| 방식 | 시스템 프롬프트 | 태스크 | 추가로 로드되는 것 |
|---|---|---|---|
| **스킬 + `context: fork`** | agent type에서 | SKILL.md 내용 | CLAUDE.md (Explore/Plan이면 제외) |
| **서브에이전트 + `skills`** | 서브에이전트 마크다운 본문 | Claude의 위임 메시지 | 프리로드 스킬 + CLAUDE.md |

`context: fork` 세부:
- `agent` 생략 시 `general-purpose`. 값은 `Explore`/`Plan`/`general-purpose` 또는 `.claude/agents/`의 커스텀
- **기본적으로 백그라운드에서 돈다** (v2.1.218+). 계속 일하다가 결과가 도착한다. `background: false`면 그 턴에서 기다린다
- 강제로 기다리는 경우: `-p`/SDK, `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`, 같은 스킬의 이전 호출이 아직 돌 때, scheduled task가 그 스킬로 발화할 때
- 백그라운드 fork는 **좁은 도구셋**으로 돈다 (대화를 fork하는 서브에이전트의 예외가 여기엔 적용 안 됨). 스킬 단계가 그 밖의 도구에 의존하면 `background: false`로
- 백그라운드 fork의 편집은 **체크포인트 밖**이라 `/rewind`로 못 되돌린다 → git으로
- ⚠️ **지시문 없이 가이드라인만 든 스킬에 `context: fork`를 쓰면 안 된다.** 서브에이전트가 가이드라인은 받되 실행할 태스크가 없어서 아무 의미 없는 결과를 낸다

### 4.3.5 스킬 조합: 기반 스킬 + 도메인 스킬

공식문서는 스킬 내용을 두 종류로 나눈다.

| 종류 | 성격 | 전형적 프론트매터 |
|---|---|---|
| **Reference content (기반)** | 현재 작업에 적용할 지식 — 컨벤션, 패턴, 스타일 가이드, 도메인 지식. **인라인으로 붙어야** 대화 컨텍스트와 함께 쓸 수 있다 | (기본값) |
| **Task content (도메인/작업)** | 특정 행동의 단계별 지시 — 배포, 커밋, 코드 생성 | `disable-model-invocation: true`, 종종 `context: fork` |

기반 스킬 예:

```yaml
---
name: api-conventions
description: API design patterns for this codebase
---

When writing API endpoints:
- Use RESTful naming conventions
- Return consistent error formats
- Include request validation
```

**서브에이전트에서의 조합 패턴**

```yaml
---
name: api-developer
description: Implement API endpoints following team conventions.
  Use when adding or modifying HTTP handlers, routes, or request/response schemas.
tools: Read, Edit, Write, Grep, Glob
model: sonnet
skills:
  - api-conventions          # 기반 — 공유 자산
  - error-handling-patterns  # 기반 — 공유 자산
---

Implement API endpoints. Follow the conventions and patterns from the
preloaded skills.

When invoked:
1. Locate the route registration and the existing handlers nearby
2. Implement the handler following the preloaded conventions
3. Add request validation
4. Report the files you changed and any convention you had to bend, with the reason
```

**왜 이 분업이 맞는가**

적정 고도가 두 층으로 나뉜다:

```
서브에이전트 본문  →  "무엇을 하는가" (역할, 워크플로, 출력 형식)   ← 에이전트마다 다름
프리로드 스킬     →  "어떻게 쓰는가" (컨벤션, 패턴, 레퍼런스)      ← 여러 에이전트가 공유
```

- **기반 스킬은 여러 서브에이전트가 공유**한다. `api-conventions`는 `api-developer`도, `code-reviewer`도, `test-writer`도 쓴다. 한 곳에서 고치면 전부 반영된다.
- **도메인 스킬은 한 에이전트 전용**이거나 아예 `/command`로 직접 호출한다.
- 본문에 컨벤션을 통째로 적으면 에이전트 3개에 같은 내용이 3벌 복사된다. 이게 스킬로 빼는 이유다.

**비용 감각**: 스킬 본문은 한 번 로드되면 **세션 내내 컨텍스트에 남는 반복 비용**이다. 공식문서 권고 — "어떻게/왜"를 서술하지 말고 **무엇을 하라만** 쓸 것. CLAUDE.md와 같은 간결성 기준을 적용할 것. SKILL.md는 500줄 이하로, 상세 레퍼런스는 별도 파일로 빼고 SKILL.md에서 "언제 이 파일을 읽어라"만 안내할 것.

### 4.3.6 프롬프트 작성 가이드

공식 Best practices 네 줄이 뼈대다:

> - **집중된 서브에이전트를 설계하라** — 각각 하나의 특정 작업에 탁월할 것
> - **상세한 description을 써라** — Claude가 위임을 판단하는 근거
> - **도구 접근을 제한하라** — 보안과 집중을 위해 필요한 권한만
> - **버전관리에 넣어라** — 프로젝트 서브에이전트를 팀과 공유

여기에 실제 예제(`code-reviewer`, `debugger`, `data-scientist`)와 컨텍스트 엔지니어링 원칙에서 뽑은 실무 규칙을 더하면:

**① description은 "언제"를 쓴다**
무엇을 하는지가 아니라 어떤 상황에서 불러야 하는지. 사용자가 자연스럽게 쓸 트리거 문구를 넣는다. 적극적 위임이 필요하면 `use proactively`.

**② 본문은 `When invoked:` 번호 워크플로로 연다**
공식 예제 세 개가 전부 이 형태다.
```
When invoked:
1. Run git diff to see recent changes
2. Focus on modified files
3. Begin review immediately
```
"즉시 시작하라"까지 적는 게 포인트 — 확인 질문으로 왕복하지 않게 한다.

**③ 체크리스트로 범위를 못 박는다**
`Review checklist:` 아래 항목을 나열. 무엇을 볼지 정해두면 매 실행이 같은 기준을 쓴다.

**④ 출력 형식을 고정한다**
```
Provide feedback organized by priority:
- Critical issues (must fix)
- Warnings (should fix)
- Suggestions (consider improving)
```
반환 형태가 고정되면 오케스트레이터가 여러 에이전트 결과를 **병합**할 수 있다. 로스터가 작동하는 세 조건 중 하나가 이거다.

**⑤ 하지 말 것도 명시한다**
무엇을 플래그하지 **말** 것인지를 적는 게 특히 효과가 크다. (4.3.7의 code-review 플러그인이 이걸 6항목으로 열거한다.) 적정 고도의 좋은 예 — 판단은 맡기되 경계는 못 박는다.

**⑥ 장애 보고 규약을 넣는다**
막혔을 때 조용히 부분 결과를 돌려주지 말고 **무엇이 막았는지 보고**하도록. 오케스트레이터가 재시도할지 판단할 근거가 된다.

**⑦ 최소 도구**
`code-reviewer`에 Edit를 안 주고, `debugger`엔 준다 — 버그 수정은 코드 수정을 요구하니까. 이 대비가 공식 예제의 핵심 교훈이다.

**⑧ 섹션으로 구조화한다**
컨텍스트 엔지니어링 글의 권고: `<background_information>`, `<instructions>`, `## Tool guidance`, `## Output description`.

**⑨ 부모→자식 통로는 프롬프트 문자열뿐이다**
파일 경로, 에러 메시지, 이미 내린 결정은 전부 위임 프롬프트에 직접 넣는다. 이건 서브에이전트 본문이 아니라 **호출 쪽**의 규칙이지만, 본문에 "필요한 정보가 없으면 추측하지 말고 무엇이 없는지 보고하라"를 넣어두면 누락이 드러난다.

**⑩ Explore/Plan은 CLAUDE.md를 안 읽는다**
`vendor/ 무시` 같은 규칙이 꼭 필요하면 위임 프롬프트에 다시 적는다. 다만 대부분의 규칙은 필요 없다 — 메인 대화가 Explore/Plan의 결과를 **CLAUDE.md 컨텍스트를 가진 채로** 읽기 때문이다.

**⑪ 적정 고도를 유지한다**
if-else 하드코딩도, "코드를 잘 리뷰해라"도 아닌 중간. 워크플로는 고정하되 판단은 남긴다.

**템플릿**

```markdown
---
name: <역할-이름>
description: <무엇의 전문가인지 한 줄> + <언제 위임해야 하는지> + <use proactively 필요시>
tools: <최소 집합>
model: <inherit | sonnet | haiku | opus>
skills:
  - <공유 기반 스킬>
---

You are a <역할>.

When invoked:
1. <첫 행동 — 컨텍스트 수집>
2. <범위 좁히기>
3. <즉시 작업 시작>

<Checklist / Dimensions>:
- ...

Do NOT flag / Do NOT do:
- <false positive 유형들>

For each finding, provide:
- <필드 1>
- <필드 2>

Output format:
<고정 템플릿>

If you cannot complete the task, report what blocked you rather than
returning partial results silently.
```

### 4.3.7 스킬 주입 예제 — `code-review` 해부

먼저 이름이 비슷한 셋을 구분해야 한다.

| | 정체 | 위치 |
|---|---|---|
| **번들 `/code-review`** | Claude Code 내장 스킬. 현재 diff를 보안 관점에서 리뷰, `--fix`로 적용 / `--comment`로 PR 인라인 코멘트 | 내장 |
| **`/engineering:code-review`** | engineering 플러그인의 스킬. 구조화된 렌즈로 diff 리뷰 | `<plugin>/skills/code-review/SKILL.md` |
| **`code-review` 플러그인** | Anthropic 공식. **다단계 멀티에이전트 파이프라인** | `anthropics/claude-code` → `plugins/code-review/commands/code-review.md` |

> 번들 `/code-review`는 **v2.1.218부터 forked subagent로 실행**된다(그 전엔 인라인). 그래서 스킬 스태킹(`/a /b 123`)에서 확장을 끝내는 토큰이기도 하다.

---

#### (A) `/engineering:code-review` — 스킬 설계의 교과서

실제 파일 구조:

```markdown
---
name: code-review
description: Review code changes for security, performance, and correctness.
  Trigger with a PR URL or diff, "review this before I merge", "is this code safe?",
  or when checking a change for N+1 queries, injection risks, missing edge cases,
  or error handling gaps.
argument-hint: "<PR URL, diff, or file path>"

# /code-review

> If you see unfamiliar placeholders or need to check which tools are connected,
> see [CONNECTORS.md](../../CONNECTORS.md).

Review code changes with a structured lens on security, performance,
correctness, and maintainability.

## Usage
/code-review <PR URL or file path>

Review the provided code changes: @$1
If no specific file or URL is provided, ask what to review.

## How It Works
┌───────────────────────────────────────────────┐
│  STANDALONE (always works)                    │
│  ✓ Paste a diff, PR URL, or point to files    │
│  ✓ Security audit (OWASP top 10, injection)   │
│  ...                                          │
├───────────────────────────────────────────────┤
│  SUPERCHARGED (when you connect your tools)   │
│  + Source control: Pull PR diff automatically │
│  + Project tracker: Link findings to tickets  │
│  + Knowledge base: Check against standards    │
└───────────────────────────────────────────────┘

## Review Dimensions
### Security      — SQL injection, XSS, CSRF, authz flaws, secrets, SSRF ...
### Performance   — N+1, allocations, O(n²) hot paths, missing indexes ...
### Correctness   — edge cases, race conditions, error propagation ...
### Maintainability — naming, SRP, duplication, coverage ...

## Output
(마크다운 템플릿: Summary / Critical Issues 표 / Suggestions 표 /
 What Looks Good / Verdict)

## If Connectors Available
If **~~source control** is connected: ...
If **~~project tracker** is connected: ...
If **~~knowledge base** is connected: ...

## Tips
1. Provide context — "This is a hot path" or "This handles PII" helps me focus.
2. Specify concerns — "Focus on security" narrows the review.
3. Include tests — I'll check test coverage and quality too.
```

**설계에서 배울 점 6가지**

1. **description이 트리거 문구의 나열이다.** "무엇을 한다"에 그치지 않고 `"review this before I merge"`, `"is this code safe?"` 같은 **사용자가 실제로 칠 법한 말**과 `N+1 queries`, `injection risks` 같은 **키워드**를 함께 담았다. 자동 호출 정확도를 위한 설계다.

2. **`argument-hint` + `@$1`.** 인자를 파일 참조(`@`)로 확장한다. `/code-review src/auth.ts`가 그 파일을 첨부한 것과 같아진다. 인자가 없으면 되묻게 한다 — 빈손으로 헛돌지 않는다.

3. **출력 템플릿을 프롬프트에 박아둔다.** 이게 가장 중요하다. Summary / Critical Issues 표 / Suggestions 표 / What Looks Good / Verdict. 결과 형태가 고정되니 **후처리와 병합이 가능**하고, 매 실행이 같은 구조를 낸다.

4. **커넥터 유무에 따른 조건부 분기.** `STANDALONE (always works)` / `SUPERCHARGED (when connected)`로 갈라놓았다. 커넥터가 없어도 **실패하지 않고** 할 수 있는 만큼 한다. 의존성을 필수가 아니라 증강으로 설계한 것.

5. **`allowed-tools`를 쓰지 않는다.** 리뷰는 읽기 위주이고, 세션 권한을 그대로 쓰는 게 마찰이 적다. 반대로 부작용이 있는 스킬(배포·커밋)은 `disable-model-invocation: true`를 다는 게 정석.

6. **도메인 지식이 곧 값어치다.** Review Dimensions의 체크리스트가 이 스킬의 본체다. 이게 "스킬은 무엇을 알아야 하는지를 정의한다"의 구체적 모습이다. 이 체크리스트를 서브에이전트에 `skills:`로 주입하면 그대로 4.3.5의 조합 패턴이 된다.

#### (B) Anthropic 공식 `code-review` 플러그인 — 오케스트레이션의 교과서

`anthropics/claude-code` 저장소의 `plugins/code-review/commands/code-review.md`. 109줄짜리 프롬프트 하나가 **멀티에이전트 파이프라인 전체를 기술**한다.

프론트매터:
```yaml
allowed-tools: Bash(gh issue view:*), Bash(gh search:*), Bash(gh issue list:*),
  Bash(gh pr comment:*), Bash(gh pr diff:*), Bash(gh pr view:*), Bash(gh pr list:*),
  mcp__github_inline_comment__create_inline_comment
description: Code review a pull request
```

전 에이전트 공통 가정을 맨 앞에 못 박는다:
> 모든 도구는 정상 동작한다고 가정한다. 도구를 테스트하거나 탐색적으로 호출하지 마라. **이 점을 스폰되는 모든 서브에이전트에게 분명히 전달하라.** 작업에 필요할 때만 도구를 호출하고, 모든 호출에는 명확한 목적이 있어야 한다.

파이프라인:

```
1. haiku 게이트 에이전트
   ├ PR이 closed?  draft?  리뷰 불필요(자동 PR·자명한 변경)?  이미 Claude가 코멘트함?
   └ 하나라도 참이면 → 중단                   ※ Claude가 만든 PR은 그래도 리뷰한다

2. haiku 에이전트 — 관련 CLAUDE.md 파일 "경로만" 반환 (내용 아님)
   ├ 루트 CLAUDE.md
   └ 수정된 파일이 있는 디렉터리의 CLAUDE.md

3. sonnet 에이전트 — PR 조회 + 변경 요약

4. 4개 병렬
   ├ Agent 1, 2 : sonnet — CLAUDE.md 준수 감사
   │              (파일과 경로를 공유하거나 상위인 CLAUDE.md만 고려)
   ├ Agent 3    : opus  — diff 자체만 보고 명백한 버그 스캔
   │              (diff 밖 컨텍스트 없이 검증 못 할 이슈는 플래그 금지)
   └ Agent 4    : opus  — 도입된 코드의 문제 (보안, 잘못된 로직)
   ※ 각 서브에이전트에 PR 제목·설명을 함께 전달 → 작성자 의도 파악용

5. 검증 패스 — 4단계의 이슈마다 병렬 서브에이전트를 띄워 진짜 이슈인지 검증
   ├ 버그·로직 이슈 → opus
   └ CLAUDE.md 위반 → sonnet
   (예: "변수가 정의되지 않았다"면 실제로 그런지 코드에서 확인)

6. 검증 안 된 이슈 필터링 → 고신호 이슈만 남김

7. 요약 출력 → --comment 없으면 여기서 중단 (게시 금지)

8. 게시할 코멘트 목록 작성 — "이건 네가 확인용으로만. 어디에도 게시하지 마라"

9. mcp__github_inline_comment__create_inline_comment 로 인라인 코멘트 게시
   ├ 작고 자기완결적 수정 → committable suggestion 블록 포함
   ├ 6줄 이상·구조 변경·여러 위치 → 설명만
   └ 이슈당 코멘트 하나. 중복 금지
```

플래그할 것 / 하지 말 것을 못 박는다:

> **플래그할 것 (HIGH SIGNAL만)**: 컴파일·파싱 실패(문법 오류, 타입 오류, 누락된 import, 미해결 참조) / 입력과 무관하게 확실히 틀린 결과를 내는 것(명백한 로직 오류) / 정확히 어떤 규칙을 어겼는지 인용할 수 있는 명백한 CLAUDE.md 위반
>
> **플래그하지 말 것**: 코드 스타일·품질 / 특정 입력이나 상태에 의존하는 잠재적 문제 / 주관적 제안
>
> **확신이 없으면 플래그하지 마라. false positive는 신뢰를 깎고 리뷰어의 시간을 낭비한다.**

그리고 별도 false-positive 목록:
- 기존에 이미 있던 문제
- 버그처럼 보이지만 실제로는 맞는 것
- 시니어 엔지니어라면 지적하지 않을 현학적 트집
- 린터가 잡을 문제 (린터를 돌려서 확인하지도 말 것)
- 일반적 코드 품질 우려 (테스트 커버리지 부족, 일반적 보안) — CLAUDE.md에 명시적으로 요구된 게 아니면
- CLAUDE.md에 언급됐지만 코드에서 명시적으로 무시 처리된 것 (lint ignore 주석 등)

**설계에서 배울 점 6가지**

1. **모델 티어링.** 게이트·경로수집=haiku, 요약·규칙준수=sonnet, 버그탐지·검증=opus. **비용이 판단 난이도를 정확히 따라간다.** 3.4절의 로스터 원칙(각 job에 필요한 최소한)이 모델 차원으로 확장된 것.

2. **중복 실행이 의도적이다.** Agent 1과 2가 같은 일(CLAUDE.md 준수)을, 3과 4가 비슷한 일(버그)을 병렬로 한다. 단일 리뷰어는 한 종류의 이슈에 끌려간다 — 앵커링을 중복으로 깬다.

3. **생성과 검증의 분리.** 5단계가 핵심이다. **발견한 에이전트가 자기 발견을 방어하지 않는다.** 별도 서브에이전트가 코드를 다시 보고 진짜인지 확인한다. 격리된 컨텍스트라 발견자의 추론에 오염되지 않는다.

4. **컨텍스트 절약의 정석이 2단계에 있다.** CLAUDE.md 파일의 **내용이 아니라 경로만** 반환하게 한다. 정말 필요한 에이전트만 읽으면 된다.

5. **부작용은 마지막에, 플래그로 게이트.** `--comment`가 없으면 7단계에서 무조건 중단. 8단계의 "목록을 만들되 어디에도 게시하지 마라"는 **모델에게 자기 점검을 시키는 단계**다.

6. **적정 고도의 실물.** "고신호만 잡아라"는 너무 높고, 정규식 규칙 나열은 너무 낮다. 이 프롬프트는 **플래그할 3가지 유형 + 하지 말 6가지 유형**으로 경계를 못 박고 그 안의 판단은 모델에 맡긴다.

> **스터디 프로젝트(CLI 에이전트)에 그대로 이식 가능한 골격**:
> `게이트 → 경로 수집 → 요약 → 병렬 분석(중복) → 검증 → 필터 → 보고 → (플래그 시) 부작용`

## 4.4 에이전트 팀 (Agent Teams)

### 4.4.1 개념 — 실제 개발팀의 구조를 모델링한다

서브에이전트가 **한 세션 안의 워커**라면, 에이전트 팀은 **여러 Claude Code 세션을 조율**하는 것이다.

| 구성요소 | 실제 팀에서의 대응 | 역할 |
|---|---|---|
| **Team lead** | 팀 리드 | 팀메이트를 스폰하고 작업을 조율하는 메인 세션 |
| **Teammates** | 팀원 | 각자 할당된 작업을 하는 **독립 Claude Code 인스턴스** |
| **Task list** | 티켓 보드 | 팀메이트가 claim하고 완료하는 공유 작업 목록 |
| **Mailbox** | 슬랙/메신저 | 에이전트 간 통신 시스템 |

서브에이전트와의 결정적 차이 둘:
- 팀메이트는 **서로 직접 메시지**한다 (서브에이전트는 호출자에게만 보고)
- 사용자가 **리드를 거치지 않고 개별 팀메이트와 직접 대화**할 수 있다

```
[서브에이전트]                      [에이전트 팀]

      main                            lead ←──┐
    ↙  ↓  ↘                          ↙  ↕  ↘  │
   A   B   C                        A ↔ B ↔ C │
    ↘  ↓  ↙                          ↘  ↕  ↙  │
   결과만 위로                      공유 태스크 리스트
                                    + 상호 메시징
```

### 4.4.2 활성화

```json
// settings.json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

(철자 주의: `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`)

- **실험적이고 기본 비활성.** 안 켜면 세션 시작 시 팀 셋업도, 팀 디렉터리 생성도, 팀메이트 스폰·제안도 전혀 없다
- **인터랙티브 세션 필요.** `-p`나 Agent SDK에선 팀메이트가 안 생기고, Claude가 이름 붙인 서브에이전트도 **일반 서브에이전트로 실행**된다

**v2.1.178에서 바뀐 것 (책과 다를 수 있는 부분)**
- 팀메이트 스폰에 셋업 단계가 **더 이상 필요 없다**
- `TeamCreate` / `TeamDelete` 도구가 **없어졌다**. 예전엔 팀을 먼저 만들고 이름을 붙였다
- Agent 도구의 `team_name` 입력은 받되 무시된다. 훅 페이로드의 `team_name`은 세션 파생 이름을 담고 deprecated
- 세션 종료 시 자동 정리

**⚠️ 켜면 생기는 부작용 (가장 중요한 함정)**

> 에이전트 팀이 켜져 있으면, **Claude가 스스로 이름을 붙인 서브에이전트가 팀메이트로 런치된다.** Claude는 나중에 메시지를 보내려고 서브에이전트에 이름을 붙이는 일을 알아서 한다 — 따라서 **팀 작업이라고 생각한 적 없는 위임에서도 팀이 생길 수 있다.**

왜 문제인가:

| | 서브에이전트 | 팀메이트 |
|---|---|---|
| 결과 전달 | 완료 시 Claude가 **결과를 받음** | idle 알림만 옴. **출력은 안 담김** |

그래서 서브에이전트 결과를 기다리는 오케스트레이션이 **멈출 수 있다.**

되돌리려면 `"0"`으로 설정. **새 세션을 시작할 필요 없다** — 설정 파일의 `env` 값은 저장하면 도는 세션에 재적용되고, Claude가 서브에이전트를 스폰할 때마다 변수를 다시 읽는다.

단 우선순위 주의: 사용자 `settings.json`의 `0`은 셸 export를 덮어쓰지만, **프로젝트 설정 / 로컬 설정 / `--settings` 페이로드**의 `1`이 이긴다. **managed settings**는 모든 것 다음에 적용된다.

### 4.4.3 팀이 시작되는 경로 2가지

**① 사용자가 명시적으로 요청**

```
I'm designing a CLI tool that helps developers track TODO comments across
their codebase. Spawn three teammates to explore this from different angles:
one on UX, one on technical architecture, one playing devil's advocate.
```

역할 셋이 서로 독립적이고 대기 없이 탐색 가능해서 잘 맞는 예다.

**② Claude가 병렬 작업에 유리하다고 판단해 제안 → 사용자 확인**

두 경우 모두 사용자가 통제권을 유지한다. Claude는 승인 없이 팀메이트를 스폰하지 않는다.

**③ (문서에 명시된 세 번째 경로)** — 위 4.4.2의 부작용. Claude가 이름을 붙여 Agent 도구를 호출하면 팀메이트로 런치되고, **이건 확인을 묻지 않는다.**

> Claude가 팀 대신 서브에이전트를 쓸 때도 있다. 서브에이전트와 팀메이트가 **같은 agent panel에 나타나므로 패널만 보고는 팀이 생겼는지 알 수 없다.** 팀이 필요하면 다시 명시적으로 요청한다.

### 4.4.4 생애 주기 관리

**스폰** — Agent 도구를 `name`과 함께 호출

**표시** — 리드 터미널의 agent panel

| 키 | 동작 |
|---|---|
| ↑ / ↓ | 팀메이트 선택 |
| Enter | 선택한 팀메이트의 트랜스크립트를 열고 **직접 메시지** |
| Esc | 선택한 팀메이트의 현재 턴 중단 |
| `x` | 선택한 팀메이트 중지 |
| Ctrl+T | 태스크 리스트 토글 |

idle 행 숨김 규칙 (v2.1.199+):
- **누구든 아직 일하는 중이면 idle 행도 패널에 남는다** → 선택해서 트랜스크립트를 보거나 추가 작업을 줄 수 있다
- 패널 전체가 idle이 되면 30초 후 숨겨지고, 그 팀메이트의 다음 턴에 다시 나타난다. **숨겨져 있어도 계속 살아 있고 주소 지정 가능**
- 3개 초과가 동시에 idle이면 나머지가 `2 idle agents` 같은 한 행으로 접힌다. Enter로 펼침
- v2.1.181~v2.1.198은 자기 턴이 끝난 지 30초면 다른 팀메이트가 일해도 숨겼다

**모델·모드는 스폰 시점에 고정된다**
- `/model`, `/fast`는 팀메이트를 보고 있어도 **리드에만 적용**된다 (v2.1.199부터 그렇다는 안내가 뜬다)
- `/effort`는 보고 있는 팀메이트의 이후 턴에 적용된다 (팀메이트가 리드의 effort를 따르므로)
- **plan / default 모드도 스폰 시 고정** — 전환 불가. 계획→구현이 필요하면 새 팀메이트를 스폰해 계획을 넘기거나, plan approval 기능을 쓴다

**plan approval**

```
Spawn an architect teammate to refactor the authentication module.
Require plan approval before they make any changes.
```

- 팀메이트가 계획을 마치면 리드에 승인 요청을 보낸다
- 리드가 승인하거나 피드백과 함께 거절한다. 거절되면 팀메이트는 plan 모드에 머물러 수정 후 재제출
- 승인되면 plan 모드를 나가 구현 시작
- **리드가 자율적으로 판단**한다. 기준을 주려면 프롬프트에: "테스트 커버리지가 포함된 계획만 승인해라", "DB 스키마를 바꾸는 계획은 거절해라"
- 이건 사용자에게 별도 프롬프트가 뜨지 않는 **설계된 예외**다

**종료**

```
Ask the researcher teammate to shut down
```
리드가 종료 요청을 보내고, 팀메이트는 승인(정상 종료)하거나 설명과 함께 거절한다.

**정리**
- 세션 종료 시 공유 디렉터리 자동 정리
- 팀 config 디렉터리(`~/.claude/teams/{team-name}/`)는 **삭제**
- 태스크 리스트 디렉터리(`~/.claude/tasks/{team-name}/`)는 **로컬에 남고 업로드되지 않는다** → resume한 세션이 태스크를 유지. 보관 기간은 `cleanupPeriodDays`

### 4.4.5 컨텍스트와 권한

**컨텍스트**

각 팀메이트는 자기 컨텍스트 윈도우를 가진다. 스폰 시 **일반 세션과 동일한 프로젝트 컨텍스트**를 로드한다:
- CLAUDE.md
- MCP 서버
- 스킬
- \+ 리드의 스폰 프롬프트

**리드의 대화 기록은 넘어가지 않는다.** 그래서 스폰 프롬프트에 작업별 디테일을 다 넣어야 한다:

```
Spawn a security reviewer teammate with the prompt: "Review the authentication
module at src/auth/ for security vulnerabilities. Focus on token handling,
session management, and input validation. The app uses JWT tokens stored in
httpOnly cookies. Report any issues with severity ratings."
```

**서브에이전트 정의를 팀메이트 역할로 재사용**

```
Spawn a teammate using the security-reviewer agent type to audit the auth module.
```

- 모든 서브에이전트 스코프에서 참조 가능: project / user / plugin / CLI-defined
- 팀메이트는 그 정의의 **`tools` 허용목록과 `model`을 따른다**
- 정의의 본문은 팀메이트 시스템 프롬프트에 **추가 지시로 덧붙여진다** (대체가 아니다)
- in-process 팀메이트면 Claude Code가 `SendMessage`를 허용목록에 추가한다. Task 도구가 있는 세션이면 `TaskCreate`/`TaskGet`/`TaskList`/`TaskUpdate`도 추가
- ⚠️ **`skills`와 `mcpServers` frontmatter는 적용되지 않는다.** 팀메이트는 일반 세션처럼 프로젝트·사용자 설정에서 로드한다

**권한**

- 팀메이트는 **리드의 권한 설정으로 시작**한다. 리드가 `--dangerously-skip-permissions`면 전원 그렇다
- **스폰 시점에 팀메이트별 모드를 지정할 수 없다.** 스폰 후 개별 변경만 가능
- **팀메이트의 권한 프롬프트는 리드 세션에 뜬다** → 거기서 직접 승인. plan approval만 예외
- 팀메이트가 많으면 프롬프트 마찰이 커진다 → **스폰 전에 흔한 작업을 권한 설정에서 미리 허용**해두는 게 실무 요령

**에이전트 간 메시지의 보안 모델**

한 에이전트가 `SendMessage`로 다른 에이전트에 메시지를 보내면, Claude Code는 수신 에이전트에게 **이건 사용자가 아니라 다른 Claude 세션에서 왔다**고 알린다.

- 팀메이트는 권한 프롬프트를 승인하거나 사용자를 대신해 동의할 수 없다
- **거부된 행동을 다른 팀메이트에게 전달해 우회할 수 없다**
- auto mode에선 분류기가 두 가지를 더 한다:
  - 다른 에이전트가 전달한 **승인 주장을 untrusted input으로** 취급
  - 배달 **전에** 모든 메시지를 검토 — 평문이든 shutdown request·plan approval 같은 구조화 메시지든. 차단되면 수신자에게 도달하지 않는다
- 같은 규칙이 **팀 밖의 다른 세션에서 온 메시지**에도 적용된다 (4.6)

### 4.4.6 메시지 전달 시스템

**메일박스 구조**

```
~/.claude/teams/{team-name}/inboxes/{agent-name}.json
```

- 메일박스 파일을 **읽을 때마다 모든 항목을 검증**한다. 형식에 안 맞는 항목은 에러로 보고하고 파일에서 제거하되, **유효한 메시지는 정상 배달**된다
  - v2.1.207 이전엔 항목 하나가 깨지면 1초마다 에러가 반복되고 그 메일박스의 배달이 막혀서 파일을 손으로 지워야 했다
- **전송 성공 보고는 수신자 메일박스 파일 쓰기가 성공했을 때만** 한다. 디스크 풀이나 쓰기 권한 문제로 실패하면 발신 에이전트가 에러를 받고 아무것도 전송되지 않는다

**정보 공유 방식 4가지**

| 방식 | 동작 |
|---|---|
| **자동 배달** | 팀메이트가 메시지를 보내면 자동으로 수신자에게 배달. **리드가 폴링할 필요 없음** |
| **idle 알림** | 팀메이트가 끝나면 리드에 자동 통지. ⚠️ **알림에는 출력이 담기지 않는다** — 결과 공유는 리드에게 메시지를 보내거나 태스크 리스트를 갱신해서 한다. v2.1.198부터 API 에러로 턴이 끝나면 실패했다고 알리고 에러 텍스트를 포함한다 |
| **공유 태스크 리스트** | Task 도구가 있는 에이전트가 상태를 보고 가용 작업을 claim |
| **팀메이트 메시징** | 이름으로 특정 팀메이트 하나에게 |

**`broadcast`는 없다**

> 공식문서: **전원에게 보내려면 수신자당 한 통씩 보낸다.**

브로드캐스트 프리미티브가 없다는 뜻이다. 필요하면 리드가 루프를 돌아야 한다. (책에 broadcast가 나온다면 이 부분은 확인이 필요하다.)

**이름 규칙**

- 리드가 스폰할 때 **모든 팀메이트에 이름을 부여**하고, 누구나 그 이름으로 누구에게나 메시지를 보낼 수 있다
- 나중 프롬프트에서 참조할 예측 가능한 이름을 원하면 **스폰 지시에 이름을 지정**한다
- 팀 config의 `members` 배열에 이름과 agent ID가 있고, **팀메이트가 이 파일을 읽어 다른 멤버를 발견**할 수 있다
- `SendMessage` 도구를 가진 에이전트는 시작 시 **sibling roster**(같은 세션의 다른 named 에이전트 목록)를 시스템 리마인더로 받는다 (v2.1.206+). 시작 시점의 스냅샷이라 나중에 이름이 붙은 에이전트는 안 보인다

### 4.4.7 태스크 조정 시스템

**상태 3개**: `pending` → `in progress` → `completed`

**의존성**
- 태스크는 다른 태스크에 의존할 수 있다
- **미해결 의존성이 있는 pending 태스크는 claim할 수 없다**
- 팀메이트가 선행 태스크를 완료하면 **자동으로 의존 태스크를 unblock**한다 — 사용자 개입 불필요

**할당 2가지**

| 방식 | 동작 |
|---|---|
| **리드 명시 할당** | 어떤 태스크를 어떤 팀메이트에게 줄지 리드에게 지시 |
| **self-claim** | 태스크를 끝낸 팀메이트가 **미할당·미차단 태스크를 스스로 집는다** |

**파일 잠금으로 race condition 방지**

> 태스크 claim은 파일 잠금을 사용해, 여러 팀메이트가 동시에 같은 태스크를 claim하려 할 때의 race condition을 막는다.

self-claim 방식이 성립하는 이유가 이것이다. 잠금이 없으면 두 팀메이트가 같은 태스크를 집어 중복 작업이 나거나, 더 나쁘게는 같은 파일을 동시에 편집한다.

> Task 도구가 없는 에이전트는 태스크 리스트 대신 **메시지로 조정**한다.

**저장 위치**

```
~/.claude/teams/{team-name}/config.json    ← 팀 config (세션 종료 시 삭제)
~/.claude/tasks/{team-name}/               ← 태스크 리스트 (남음, 업로드 안 됨)
```

팀 이름 = `session-` + 세션 ID 앞 8자.

- 세션 시작 시 자동 생성되고, 팀메이트가 합류·idle·이탈할 때마다 갱신된다
- config는 **런타임 상태**(세션 ID, tmux pane ID)를 담는다 → **손으로 편집하거나 미리 작성하지 말 것.** 다음 상태 갱신에서 덮어써진다
- **프로젝트 레벨 팀 config는 없다.** `.claude/teams/teams.json` 같은 파일을 프로젝트에 두어도 설정으로 인식되지 않고 평범한 파일로 취급된다

**품질 게이트 훅 — exit 2로 되돌린다**

| 훅 | 발화 시점 | exit 2의 효과 |
|---|---|---|
| `TeammateIdle` | 팀메이트가 idle이 되려 할 때 | **피드백을 보내고 계속 일하게 한다** |
| `TaskCreated` | 태스크 생성 시도 | 생성을 막고 피드백 전송 |
| `TaskCompleted` | 태스크 완료 표시 시도 | 완료를 막고 피드백 전송 |

`TeammateIdle`이 특히 강력하다 — "테스트가 통과하지 않으면 끝난 게 아니다"를 **결정론적으로** 강제할 수 있다.

### 4.4.8 파일 소유권 전략

공식문서는 한 줄이다:
> 두 팀메이트가 같은 파일을 편집하면 덮어쓰기가 난다. 각 팀메이트가 다른 파일 집합을 소유하도록 작업을 나눠라.

짧지만 무게가 크다. **에이전트 팀은 팀메이트를 worktree로 격리하지 않기 때문이다.**

| | 격리 수단 |
|---|---|
| 서브에이전트 | `isolation: worktree` 가능 |
| 내가 직접 띄운 병렬 세션 | worktree 가능 |
| agent view 디스패치 세션 | **자동으로** 각자 worktree로 이동 |
| **에이전트 팀 팀메이트** | **worktree 격리 없음 → 소유권 분할이 유일한 방어선** |

**분할 축 4가지**

1. **레이어별** — frontend / backend / tests / docs. 공식문서의 "cross-layer coordination" 케이스가 이것
2. **모듈·패키지별** — 모노레포면 경계가 이미 있다
3. **읽기 전용 역할 분리** — 리뷰·아키텍처 역할은 **plan 모드로 스폰**한다. 애초에 쓰지 못하므로 충돌이 원천 차단된다. 모드는 스폰 후 못 바꾸니 이 선택은 처음에 해야 한다
4. **직렬화** — 같은 파일을 꼭 만져야 하면 병렬이 아니라 **태스크 의존성으로 순서를 강제**한다

**실무 규칙**

- **스폰 프롬프트에 파일 경계를 명시한다.** `"src/auth/ 아래만 수정해라"`
- **공유 파일은 리드가 소유한다.** 마이그레이션 파일, 인덱스, 라우트 등록부, 의존성 파일처럼 모두가 건드리는 것 — 팀메이트는 리드에게 요청하고 리드가 반영
- **태스크 크기**: 자기완결적 산출물 단위 — 함수 하나, 테스트 파일 하나, 리뷰 하나
  - 너무 작으면 조율 오버헤드가 이득을 넘는다
  - 너무 크면 체크인 없이 오래 일해 헛수고 위험이 커진다
- **팀메이트당 5~6개 태스크**가 적당하다. 모두가 바쁘고, 누가 막히면 리드가 재할당할 여지가 남는다
- **팀 크기는 3~5명으로 시작.** 독립 태스크가 15개여도 3명이 좋은 출발점이다. 공식문서: *흩어진 5명보다 집중한 3명이 낫다.*
- **연구·리뷰부터 시작하라.** 코드를 안 쓰는 작업(PR 리뷰, 라이브러리 조사, 버그 조사)은 경계가 명확해서 **병렬 구현의 조율 난이도 없이** 팀의 가치를 보여준다

**모니터링**
- 진행을 확인하고, 안 되는 접근은 방향을 돌리고, 발견을 그때그때 종합한다
- **리드가 조율 대신 직접 구현을 시작하는** 흔한 실패가 있다. `"Wait for your teammates to complete their tasks before proceeding"`
- 리드가 태스크가 다 안 끝났는데 끝났다고 판단하는 경우도 있다 → 계속하라고 지시

### 4.4.9 실전 케이스 2가지

**① 병렬 코드 리뷰**

```
Spawn three teammates to review PR #142:
- One focused on security implications
- One checking performance impact
- One validating test coverage
Have them each review and report findings.
```

단일 리뷰어는 한 번에 한 종류의 이슈로 끌린다. 리뷰 기준을 독립 도메인으로 쪼개면 셋 다 동시에 제대로 검토된다. 프롬프트가 각 팀메이트에 **다른 렌즈**를 배정해 겹치지 않게 한다.

**② 경쟁 가설 조사** — 이 패턴이 특히 중요하다

```
Users report the app exits after one message instead of staying connected.
Spawn 5 agent teammates to investigate different hypotheses. Have them talk to
each other to try to disprove each other's theories, like a scientific
debate. Update the findings doc with whatever consensus emerges.
```

핵심 메커니즘은 **토론 구조**다:

> 순차적 조사는 앵커링에 취약하다 — 한 이론을 탐색하고 나면 이후 조사가 그쪽으로 편향된다.
> **서로를 적극적으로 반증하려는 독립 조사자들 사이에서 살아남은 이론**이 실제 근본 원인일 확률이 훨씬 높다.

이건 4.3.7 (B)의 "생성과 검증의 분리"와 같은 원리를, 팀 레벨에서 **양방향으로** 적용한 것이다.

### 4.4.10 서브에이전트 vs 에이전트 팀

**공식 비교표**

| | 서브에이전트 | 에이전트 팀 |
|---|---|---|
| **컨텍스트** | 자기 컨텍스트 윈도우, 결과는 호출자에게 | 자기 컨텍스트 윈도우, **완전히 독립** |
| **통신** | 호출자에게 결과 반환. Claude가 이름 붙인 것끼리는 메시지 가능 | **팀메이트끼리 직접 메시지** |
| **조율** | 메인 에이전트가 모든 작업 관리 | 메시지를 통한 자기조율 + 공유 태스크 리스트 |
| **적합** | 결과만 중요한 집중 작업 | **논의와 협업이 필요한 복잡한 작업** |
| **토큰 비용** | 낮음 — 결과가 요약되어 돌아옴 | 높음 — 팀메이트마다 별도 Claude 인스턴스 |

**공식 판단축 3개**

1. **누가 조율하는가?**
   - Claude가 한 대화 안에서 위임하고 결과를 모음 → 서브에이전트
   - 내가 독립 작업을 넘기고 나중에 확인 → agent view
   - Claude가 계획·할당·감독 → **에이전트 팀**
   - 스크립트가 계획을 들고 있음 → dynamic workflows
2. **워커끼리 대화가 필요한가?** 필요하면 팀
3. **같은 파일을 건드리는가?** 서브에이전트/직접 세션은 worktree로 격리 가능. **팀은 격리가 안 되니 파일을 나눠 소유**해야 함

**책의 3기준을 여기에 매핑하면**

| 기준 | 서브에이전트 쪽 | 에이전트 팀 쪽 |
|---|---|---|
| **도메인 교차 정도** | 단일 도메인 안에서 끝난다 | frontend/backend/test처럼 **여러 도메인을 가로지른다** |
| **영향 파일 수** | 적고, 소유권 충돌이 없다 | 많고, **파일 집합을 나눠 소유**해야 한다 |
| **복잡도 점수** | 결과만 있으면 되는 자기완결 작업 | **논의·이견·상호 검증**이 필요한 작업 |

> ⚠️ **"복잡도 점수"는 공식문서에 없는 개념이다.** 팀 자체 루브릭으로 쓰기엔 좋지만 공식 근거로 인용하면 안 된다. 공식문서가 주는 정량 기준에 가장 가까운 건 **"팀 크기 3~5명, 팀메이트당 태스크 5~6개"** 정도다.

**한 문장 기준**

> 빠르게 결과만 돌려주는 워커가 필요하면 서브에이전트. **팀메이트가 발견을 공유하고, 서로에게 이의를 제기하고, 스스로 조율해야 하면** 에이전트 팀.

### 4.4.11 표시 모드

| 모드 | 요구사항 | 특징 |
|---|---|---|
| **in-process** (기본) | 없음, 어떤 터미널에서든 | 메인 터미널 안에서 전부. agent panel에서 ↑↓ 선택 후 Enter |
| **split panes** | tmux 또는 iTerm2 + `it2` CLI | 팀메이트마다 자기 pane. 모두의 출력을 동시에 |

```json
{ "teammateMode": "auto" }
```
```bash
claude --teammate-mode auto   # 실험적, --help에 안 나옴
```

- 값: `in-process`(기본) / `auto` / `tmux` / `iterm2`(v2.1.186+)
- **v2.1.179 이전 기본값은 `auto`였다** → 업그레이드하면 전에 스플릿이 열리던 세션이 한 터미널에 머문다
- `auto`는 이미 tmux 안이거나 iTerm2 + `it2`면 스플릿, 아니면 in-process로 폴백

- **스플릿 페인 미지원**: VS Code 통합 터미널, Windows Terminal, Ghostty

### 4.4.12 한계 (실험적)

| 한계 | 내용 |
|---|---|
| **세션 재개 불가** | `/resume`·`/rewind`가 in-process 팀메이트를 복원하지 않는다. 재개 후 리드가 없는 팀메이트에게 메시지를 시도할 수 있다 → 새로 스폰하라고 지시 |
| **태스크 상태가 밀린다** | 팀메이트가 완료 표시를 빠뜨려 의존 태스크가 막히는 일이 있다. 수동으로 갱신하거나 리드에게 재촉 |
| **종료가 느리다** | 팀메이트가 현재 요청·도구 호출을 끝내고 종료 |
| **세션당 팀 하나** | 이름 붙은 추가 팀 불가, 팀 공유 불가 |
| **중첩 팀 없음** | 팀메이트는 자기 팀메이트를 못 만든다. 리드만 팀을 관리 |
| **in-process 팀메이트의 서브에이전트는 포그라운드만** | 팀메이트의 백그라운드 작업이 리드 프로세스보다 오래 살 수 없기 때문. `background: true` 정의면 에러 |
| **리드 고정** | 메인 세션이 평생 리드. 승격·이양 불가 |
| **권한은 스폰 시 결정** | 스폰 시점에 팀메이트별 모드 지정 불가 |
| **스플릿 페인은 tmux/iTerm2 필요** | |

## 4.5 CLI 기반 동적 에이전트 활용

### 4.5.1 `--agent` 플래그 — 세션 전체를 특정 역할로

```bash
claude --agent code-reviewer
```

**메인 스레드 자체가 그 서브에이전트의 시스템 프롬프트·도구 제한·모델을 뒤집어쓴다.**

- 서브에이전트의 시스템 프롬프트가 **기본 Claude Code 시스템 프롬프트를 완전히 대체**한다 (`--system-prompt`와 동일한 방식)
- **CLAUDE.md와 프로젝트 메모리는 정상 메시지 흐름으로 여전히 로드**된다
- 시작 헤더에 `@<name>`으로 표시되어 활성 여부를 확인할 수 있다
- 내장·커스텀 둘 다 가능
- **세션을 재개해도 유지**된다 — 시스템 프롬프트·도구 제한·모델이 대화와 함께 복원된다. 에이전트가 사라졌으면 기본 도구·프롬프트로 계속되고 **에이전트 이름을 담은 경고**가 뜬다

프로젝트 기본값:
```json
// .claude/settings.json
{ "agent": "code-reviewer" }
```
**CLI 플래그가 설정보다 우선.**

플러그인 에이전트:
```bash
claude --agent security-reviewer            # 이름만 줘도 찾음
claude --agent my-plugin:security-reviewer  # 여러 플러그인에 동명이 있으면
claude --agent my-plugin:review:security    # 플러그인 서브폴더면
```

조합:
```bash
claude --bg --agent investigator "flaky 테스트 조사"   # 백그라운드 + 역할
claude agents --agent code-reviewer                    # agent view 디스패치 기본값
```

**`--agent` 세션이 서브에이전트를 스폰할 때**

`--agent`로 메인 스레드로 도는 에이전트만 쓸 수 있는 문법이 있다:

```yaml
---
name: coordinator
description: Coordinates work across specialized agents
tools: Agent(worker, researcher), Read, Bash
---
```

- **화이트리스트다.** `worker`와 `researcher`만 스폰 가능. 다른 타입을 시도하면 실패하고, 에이전트는 프롬프트에서 허용된 타입만 보게 된다
- 제한 없이 허용하려면 괄호 없이 `Agent`
- `tools`에서 `Agent`를 빼면 **아예 스폰 불가**
- ⚠️ 이 괄호 문법은 `--agent`로 메인 스레드일 때만 적용된다. **서브에이전트 정의에서 `Agent`를 tools에 넣으면 중첩 스폰은 되지만 괄호 안의 타입 리스트는 무시**된다
- 일부만 막으려면 `permissions.deny`의 `Agent(<name>)`을 쓴다

### 4.5.2 에이전트 해석 과정

**① 정의 해석 — 스코프 우선순위**

```
1. Managed settings          (조직 전체, 최상위)
2. --agents CLI 플래그        (현재 세션)
3. .claude/agents/           (현재 프로젝트)
4. ~/.claude/agents/         (내 모든 프로젝트)
5. 플러그인 agents/           (최하위)
```

- **프로그램적 정의(SDK `agents`)가 동명의 파일 기반 정의를 덮어쓴다**
- 프로젝트 스코프는 **cwd에서 저장소 루트까지 거슬러 올라가며** 모든 `.claude/agents/`를 스캔한다. 중첩 디렉터리에 같은 `name`이 여럿이면 **cwd에 가장 가까운 정의가 이긴다** (v2.1.178+)
- 같은 디렉터리(서브폴더 포함) 안에서 겹치면 파일시스템 읽기 순서 — 문서화된 우선순위 없음
- `--add-dir` / `/add-dir`로 추가한 디렉터리의 `.claude/agents/`도 로드된다. 단 **감시하지 않으므로** 그 안의 파일을 추가·수정하면 세션 재시작 필요
- `permissions.additionalDirectories` 설정은 **파일 접근만** 주고 스킬·커맨드·서브에이전트를 로드하지 않는다

**② 모델 해석 순서**

```
1. CLAUDE_CODE_SUBAGENT_MODEL 환경변수  (alias 또는 모델 ID일 때)
2. 호출별 model 파라미터                (Claude가 Agent 호출 시 넘김)
3. 서브에이전트 정의의 model frontmatter
4. 메인 대화의 모델
```

- v2.1.196부터 `CLAUDE_CODE_SUBAGENT_MODEL=inherit`은 **미설정과 동일**하게 취급된다 (2·3번으로 해석이 계속됨). 이전엔 `inherit`이 메인 모델을 강제하고 나머지를 무시했다
- 조직의 `availableModels` 허용목록에 걸리면:
  - 차단된 값이 `opus` 같은 **패밀리 alias**면 허용목록이 허락하는 그 패밀리의 최신 버전으로 (v2.1.222+)
  - 그 외에는 **상속 모델**로 실행
  - 인터랙티브 세션에선 요청 모델과 실제 실행 모델을 알리는 경고가 뜬다
- 호출별 `model` 파라미터는 **재개·후속 메시지에도 유지**된다 (v2.1.211+)

**③ 도구 해석 순서**

```
메인 대화의 도구 풀 (내장 + MCP)
  ↓ 전역 필터 — 모든 서브에이전트에서 제거
     Agent(깊이 한도 시), AskUserQuestion, EndConversation, EnterPlanMode,
     ExitPlanMode(permissionMode: plan 아니면), ScheduleWakeup, TaskOutput,
     WaitForMcpServers, Workflow
  ↓ 백그라운드 필터 — 백그라운드 실행 시 (기본값)
     MCP 도구는 전부 유지 + 내장은 다음만:
     Read, Grep, Glob, Bash, PowerShell, Edit, Write, NotebookEdit,
     WebFetch, WebSearch, TodoWrite, Skill, ToolSearch, EnterWorktree,
     ExitWorktree, Monitor, TaskStop, SendMessage, Artifact
  ↓ disallowedTools
  ↓ tools (화이트리스트)
  = 최종 도구 집합
```

- **fork는 두 필터를 모두 건너뛰고** 메인 대화의 정확한 도구 풀을 받는다
- 같은 정의가 포그라운드/백그라운드에서 **다른 도구 집합으로 해석**될 수 있다 — 재현 안 되는 버그의 흔한 원인
- 백그라운드 필터에 의한 제거는 **에러를 내지 않는다**. `tools` 목록이 아무것도 안 남을 때만 에러

**④ 서브에이전트 vs 팀메이트 분기 (agent teams 켜진 경우)**

```
Claude가 Agent 도구 호출
  ├ name 없음                        → 일반 서브에이전트
  ├ name 있음 + fork                 → fork
  ├ name 있음 + 호출에 isolation 지정 → 서브에이전트
  ├ name 있음 + 인터랙티브 + 팀 활성  → 팀메이트로 런치
  └ name 있음 + -p / SDK             → 일반 서브에이전트
```

> frontmatter의 `isolation` 값은 팀메이트 런치를 막지 못한다 — **호출 자체에 `isolation`이 넘어와야** 한다. 팀메이트로 런치되면 메인 세션의 작업 디렉터리에서 돈다.

### 4.5.3 인라인 에이전트 정의 (`--agents`)

```bash
claude --agents '{
  "code-reviewer": {
    "description": "Expert code reviewer. Use proactively after code changes.",
    "prompt": "You are a senior code reviewer. Focus on code quality, security, and best practices.",
    "tools": ["Read", "Grep", "Glob", "Bash"],
    "model": "sonnet"
  },
  "debugger": {
    "description": "Debugging specialist for errors and test failures.",
    "prompt": "You are an expert debugger. Analyze errors, identify root causes, and provide fixes."
  }
}'
```

Windows PowerShell은 here-string:
```powershell
claude --agents @'
{ ... }
'@
```

- **세션 한정.** 디스크에 저장되지 않는다 → 빠른 테스트, 자동화 스크립트, CI
- 한 번의 `--agents` 호출로 **여러 개 정의 가능**
- `prompt`가 파일 기반의 마크다운 본문에 해당한다
- 받는 필드: `prompt` + `description`, `tools`, `disallowedTools`, `model`, `permissionMode`, `mcpServers`, `hooks`, `maxTurns`, `skills`, `initialPrompt`, `memory`, `effort`, `background`, `isolation`
- 스코프 우선순위 2위 — 프로젝트/사용자/플러그인 동명 정의를 덮어쓴다
- `~/.claude/agents/`의 사용자 에이전트처럼, **`--agents`로 넘긴 정의의 인라인 MCP 서버와 훅은 폴더 신뢰 확인 없이 로드**된다
- `--strict-mcp-config`는 `--agents`나 SDK `agents`로 넘긴 인라인 서버를 **필터링하지 않는다** (명시적 caller input이므로). 단 **managed settings 제한은 정의 방식과 무관하게 모든 서브에이전트에 적용**된다

### 4.5.4 CLI 에이전트와 에이전트 팀의 관계

**① CLI 정의도 팀메이트 역할로 쓸 수 있다**

팀메이트로 참조 가능한 서브에이전트 스코프는 **project / user / plugin / CLI-defined 전부**다.

```bash
claude --agents '{"security-reviewer":{...}}' \
       --teammate-mode auto
```
```
Spawn a teammate using the security-reviewer agent type to audit the auth module.
```

단 팀메이트로 돌 때의 규칙이 적용된다:
- `tools` 허용목록과 `model`은 따른다
- 본문/`prompt`는 시스템 프롬프트에 **덧붙여진다** (대체 아님)
- **`skills`와 `mcpServers`는 무시된다**
- in-process면 `SendMessage`가, Task 도구 세션이면 Task 계열 도구가 허용목록에 추가된다

**② `-p`에선 팀이 안 생긴다**

CI에서 `--agents`로 정의한 것은 **팀 활성 여부와 무관하게 순수 서브에이전트**로 동작한다. 이름이 붙어도 마찬가지. CI 파이프라인의 동작이 개발자 로컬 설정에 흔들리지 않는다는 뜻이라 오히려 다행이다.

**③ `--agent`로 리드 역할 자체를 파일로 관리**

`claude --agent team-lead`로 시작하면 **그 세션이 팀 리드**가 된다. 리드의 조율 규칙(승인 기준, 파일 경계 정책, 태스크 분할 방침)을 에이전트 정의 파일로 버전관리할 수 있다.

```yaml
---
name: team-lead
description: Coordinates an agent team
tools: Agent(api-worker, ui-worker, test-worker), Read, Bash, SendMessage
model: opus
---

You coordinate a team. You do NOT implement.

When given a task:
1. Break it into self-contained tasks (5-6 per teammate)
2. Assign explicit file ownership boundaries in each spawn prompt
3. Reserve shared files (migrations, route registries, lockfiles) for yourself
4. Only approve plans that include test coverage
5. Wait for teammates to finish before synthesizing

Never start implementing a task yourself.
```

**④ 헤드리스 조합 레시피**

```bash
claude -p \
  --agents "$(cat ci-agents.json)" \
  --output-format stream-json --verbose \
  --forward-subagent-text \
  --max-budget-usd 5.00 \
  --append-subagent-system-prompt "Cite file paths in every answer" \
  --permission-mode dontAsk \
  --max-turns 30 \
  "Audit every service for unhandled promise rejections"
```

| 플래그 | 역할 |
|---|---|
| `--agents` | 세션 한정 로스터 |
| `--forward-subagent-text` | 서브에이전트 트랜스크립트 재구성 (중첩 포함) |
| `--max-budget-usd` | 서브에이전트 비용 포함 상한 |
| `--append-subagent-system-prompt` | 모든 서브에이전트에 공통 규칙 덧붙임 (`-p` 전용) |
| `--max-turns` | 폭주 차단 |

환경변수로 걸 수 있는 한도:
```bash
CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1     # 중첩 끄기
CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS=5     # 동시 5개
CLAUDE_AGENT_SDK_DISABLE_BUILTIN_AGENTS=1  # 내장 타입 제거, 내 것만
CLAUDE_CODE_DISABLE_EXPLORE_PLAN_AGENTS=1  # Explore/Plan만 제거
```

**⚠️ `--bare` 주의**: 훅·스킬·커맨드·**서브에이전트**·플러그인·MCP·auto memory·CLAUDE.md의 자동 발견을 전부 건너뛴다. 스크립트 시작을 빠르게 하려고 켰다가 서브에이전트가 안 잡히는 일이 흔하다.

## 4.6 세션 간 대화 — Cross-Session Messaging

> v2.1.224+ (macOS / Linux / WSL 2), 네이티브 Windows는 v2.1.234+
> **조건을 만족하면 켤 것 없이 이미 켜져 있다.**

### 4.6.1 무엇이고, 무엇이 아닌가

> Cross-session messaging은 Claude가 내 Claude Code 세션 하나에서 다른 세션으로 **메시지를 전달**하게 해준다. 한 세션의 변경이 다른 세션이 딛고 있던 것을 깨뜨릴 때, Claude가 내가 알아채기 전에 그 세션에 경고할 수 있다. 한 세션이 다른 세션이 막혀 있던 질문을 해결하면 답을 건너 보낼 수 있다.

**핵심 제약 한 줄:**

> **메시지는 한 Claude가 다른 Claude에게 쓴 텍스트 한 조각이다. 절대 대화 기록이나 파일이 아니다.**
> 대화나 컨텍스트를 통째로 옮기려면 **세션을 resume**하는 게 맞는 도구다.

도구는 둘, **사용자가 직접 호출하지 않는다**:
- `ListAgents` — 도달 가능한 에이전트 발견
- `SendMessage` — 이름으로 배달

> **같은 `SendMessage`가 서브에이전트·팀메이트에도 쓰인다.** 그래서 `SendMessage`를 deny하면 셋 다 꺼진다.

### 4.6.2 사다리의 마지막 칸

```
서브에이전트          한 세션 안의 워커
   ↓
에이전트 팀           Claude가 스폰하고 감독하는 세션들
   ↓
cross-session         내가 직접 띄우고 조종하는 독립 세션들   ← 비어 있던 칸
```

각 기능의 제자리 (공식문서가 명시적으로 정리해준다):

| 하려는 것 | 쓸 것 |
|---|---|
| 한 대화를 다른 터미널에서 이어가기 / 컨텍스트를 새 세션과 공유 | **세션 resume** |
| Claude가 스폰·감독하는 조율된 세션 팀 | **agent teams** |
| 여러 세션을 한 화면에서 보고 조종 | **agent view** |
| 폰이나 다른 기기에서 세션을 직접 조종 | **Remote Control** |
| CI 결과·채팅 메시지 같은 **외부 이벤트**를 세션에 밀어넣기 | **channels** |
| 내가 띄운 세션들끼리 발견·상태·결정을 주고받기 | **cross-session messaging** |

### 4.6.3 언제 쓰나

- **발견 인계** — 한 세션이 breaking change를 찾거나 결정을 내렸을 때, 영향받는 영역을 작업 중인 세션에 Claude가 요약해 보낸다
- **병렬 worktree 조율** — 같은 저장소를 여러 worktree에서 작업할 때 무엇이 머지됐는지 알린다
- **장기 작업 상태** — 마이그레이션이나 테스트 실행이 내가 보고 있는 세션에 보고하게 하거나, 내가 거기서 물어본다
- **머신 간** — 다른 머신이나 웹의 세션에 도달

### 4.6.4 어떻게 쓰나

**내용은 Claude가 쓴다.** 내 프롬프트는 무엇을 알리고 싶은지만 말하면 된다.

```
Ask the session running in my other terminal whether the migration finished
```
```
Explain what we just did to the session working on the payments API
```

**타깃을 직접 지정** (v2.1.232+): `@` + 세션 이름 첫 글자들 → typeahead

```
Let @api-worker know the schema migration finished
```

- 한 글자 이상 타이핑해야 세션 행이 뜬다. 맨 `@`만으로는 안 나온다
- 클라우드/Remote Control 세션은 **Claude가 이미 머신 밖 세션을 나열하거나 메시지를 보낸 뒤에야** 제안에 나타난다
- 같은 이름의 라이브 세션이 여럿이면 **보내기 전에 어느 쪽인지 물어본다**

**세션 이름** — `--name`/`-n` 플래그, 또는 `/rename`. 안 정하면 Claude Code가 짓는다. 같은 머신에서 이름이 충돌하면 **기존 세션이 이름을 지키고 내 쪽이 변형된 이름**을 받는다.

**받는 쪽에서 어떻게 보이나**

```
Schema migration finished: the new column is tenant_id, and rebasing on main is safe now.
```

발신 세션 이름 아래에 나타나고 그대로 남는다. 발신자 이름과 **회신 주소**가 함께 온다 (단방향 머신 간 메시지는 회신 주소 없음).

### 4.6.5 배달 메커니즘

- **수신 Claude는 도구 호출 사이에 읽는다** → 실행 중인 도구는 절대 중단되지 않는다
- 수신 세션이 idle이면 그 메시지로 **새 턴을 시작**한다
- 배달되면 **내가 타이핑한 프롬프트처럼 usage에 카운트**된다
- 수신 Claude는 같은 방식으로 회신할 수 있다

**3가지 결과**

| 결과 | 의미 |
|---|---|
| **Delivered** | Claude에게 전달 |
| **Held** | 배달하지 않고 보류. 내가 승인하거나 이후 모드·설정 변경이 허용해야 도달 |
| **Refused** | 배달 없이 드롭 |

**보내기 전에 거절되는 경우**

- **크기 초과** — 직렬화 형태가 약 100만 자를 넘으면 발신 세션에서 거절. 아무것도 도달하지 않는다
- **급격한 버스트** — 같은 머신 세션의 inbox 수용치에 도달하면 발신 측에서 추가 전송을 거절하고, **하나로 묶거나 기다리라고** Claude에게 알린다. v2.1.236 이전엔 보냈다고 보고하면서 수신 측이 드롭했다
- **reply target 안전성 검사 실패** — 심링크된 타깃, 예상 프로세스가 아닌 엔드포인트
- **자기 세션 이름으로 보낼 때** — 거절하고 타깃이 현재 세션이라고 알린다

### 4.6.6 보안 모델 — 여기가 진짜 핵심

세션 A가 세션 B에 메시지를 보내면, Claude Code는 B의 Claude에게 **사용자가 아니라 다른 세션에서 왔다**고 알리고 다음을 제한한다:

| 제한 | 내용 |
|---|---|
| **아무것도 승인할 수 없다** | 다른 세션의 메시지는 절대 내 동의로 치지 않는다. 대기 중인 권한 프롬프트를 대신 답할 수 없다 |
| **설정을 바꿀 수 없다** | 다른 세션이 요청했다는 이유로 권한 설정·`CLAUDE.md`·기타 구성을 바꾸지 말라고 지시받는다 |
| **커맨드가 실행되지 않는다** | 메시지 안의 `/compact` 같은 건 **평문으로 도착**한다. 절대 실행되지 않는다 |
| **권한 프롬프트는 그대로 뜬다** | 메시지대로 행동하는 데 필요한 권한이 없으면 평소와 똑같은 프롬프트가 뜬다 |

발신 측에도 규칙이 있다:
> Claude는 **자기 세션에서 거부·차단된 행동, 또는 자기 권한 설정이 막을 행동을 다른 세션에 요청하지 말고 사용자에게 되돌리라고** 지시받는다.

즉 **권한 경계는 세션별로 유지된다.** 이게 이 기능이 성립하는 조건이다.

### 4.6.7 inbound 제어 (`crossSessionInbound`)

| 값 | 동작 |
|---|---|
| `accept` | 각 메시지를 Claude에게 배달 |
| `hold` | 메시지마다 알림만 표시하고 배달하지 않음. 이후 `accept`가 적용되면 보류분을 방출 |
| `refuse` | 배달 없이 드롭 |

- `/config`의 **"Messages from your other sessions"** 행에서도 선택 가능 (v2.1.232+). 선택한 값은 사용자 설정에 기록된다. managed settings나 `--settings`가 이 키를 정하고 있으면 행이 안 나타난다
- `/config crossSessionInbound=value` 축약형은 이 키에 대해 거부된다

**값이 없을 때의 기본 규칙 — 권한 모드 클래스로 판단**

두 클래스로 나눈다: **권한 프롬프트를 건너뛰는 세션**(bypassPermissions, 그리고 bypass가 가능한 세션의 plan 모드) vs **묻는 세션**(auto, acceptEdits, dontAsk 포함).

| 수신 세션 | 동작 |
|---|---|
| **묻는 쪽** | 각 메시지를 배달한다. 단 **발신 세션이 bypass라고 밝히면 승인 대기로 보류** |
| **bypass 쪽** | 각 메시지를 **보류**한다. 발신도 bypass일 때만 배달 |

> 논리: **bypass 세션으로 들어가는 메시지가 명백한 실패 모드**다. 승인 없이 뭐든 실행하는 세션에 외부 텍스트가 들어가는 것이니, 그쪽을 조인다.

**보류 시 승인 다이얼로그**
- 발신자와 미리보기를 보여준다
- **Approve** → 그 한 통만 배달 / **Deny** 또는 닫기 → 드롭
- `dialogExpiry` 기한(**기본 5분**)을 넘기면 닫고 드롭. 백그라운드 세션에 터미널이 안 붙어 있으면 기한을 넘겨 열어둔다. 붙은 뒤 다시 기한 전체가 지나야 드롭
- 이 세션의 권한 모드 클래스가 보류 중에 바뀌면 **규칙을 재적용**해 배달 가능한 것을 방출
- 설정 변경으로 `refuse`가 적용되면 **보류분을 전부 드롭하고 각 발신자에게 거절 보고**
- **보류는 최대 100통**, 넘으면 오래된 것부터 드롭

발신 측 피드백: 같은 머신의 인터랙티브 세션이 발신자면, 수신이 보류했을 때 알림이 뜨고 이후 배달·거부·만료 시 후속 알림이 온다. 수신이 refuse면 "수신 세션이 메시지를 받지 않는다"는 알림과 함께 **기다리거나 재전송하지 말라고** Claude에게 알린다.

### 4.6.8 루프 방지

수신 세션에서 Claude Code가:
- 발신자별로 **반복 메시지를 rate limit**
- 짧은 시간 안에 도착한 **동일 반복을 드롭**
- Claude가 읽을 큐를 **최대 50통**으로 제한

> **따라서 두 세션 사이의 메시지 루프는 저절로 멈춘다.**

같은 머신의 인터랙티브 세션에서 온 메시지가 이 셋 중 하나로 드롭되면, **그 세션에 어느 것이 드롭됐는지 알리고 바로 재전송하지 말라고** Claude에게 지시한다.

### 4.6.9 경로와 프라이버시

| 상대 세션 위치 | 경로 |
|---|---|
| **이 머신** | 세션별 **Unix 도메인 소켓**(macOS/Linux) 또는 **named pipe**(네이티브 Windows). **Anthropic 서버를 거치지 않는다** |
| **내 다른 머신** | Anthropic 서버 경유 → 그 머신의 **Remote Control** 연결로 도착 |
| **Claude Code on the web** | Anthropic 서버 경유 → 클라우드 세션으로 직접 |

**같은 머신 배달의 도달 조건**

각 세션이 **디스크의 파일에 자기를 등록**한다. 로컬 세션을 나열하거나 메시지를 보낼 때 그 파일들을 읽어 찾는다. → **같은 파일을 볼 수 있어야 서로 도달 가능하다.**

- 컨테이너 안 세션과 호스트 세션은 **서로 못 본다** (파일시스템이 다름)
- 같은 컨테이너 안 세션끼리는 가능 (self-hosted runner 포함)
- **WSL 2 세션과 네이티브 Windows 세션도 서로 못 본다** — 홈 디렉터리가 다르고 리스닝하는 소켓 타입도 다르다

**머신 밖 전송에 승인 요구**

```json
{ "isolatePeerMachines": true }
```

- **`bypassPermissions` 모드에서도 물어본다**
- **어떤 설정 스코프에서든 `true`면 적용된다** → 체크인된 프로젝트 파일이 요구사항을 **켤 수는 있어도 끌 수는 없다**
- 같은 머신 세션 간에는 묻지 않는다

**Remote Control 이름 표시**: 이 세션이 `laptop-graceful-unicorn`으로 Remote Control에 연결된 상태에서 데스크톱에 메시지를 보내면, 데스크톱 세션에는 그 이름으로 표시되고 그쪽 Claude가 그 이름으로 회신할 수 있다. **Remote Control에 연결되어 있지 않으면** 메시지는 가되 **회신 주소가 없어** 상대가 답할 수 없다 (Claude도 그렇게 안내받는다).

### 4.6.10 idle 알림 구독 (v2.1.236+)

> "마이그레이션 세션 끝나면 알려줘"

```
Tell me when the migration session finishes what it's working on
```

- Claude가 `SendMessage`의 **`notify_when_idle`** 입력으로 구독한다. 보내려던 메시지에 붙이거나 단독으로
- **단독이면 감시 대상 세션에서 턴을 시작하지도, 토큰을 쓰지도 않고** 구독한다. 이미 idle이면 즉시 통지
- 메시지에 붙이면 메시지를 먼저 배달하고 통지는 나중에
- **idle의 정의**: 큐에 아무것도 없이 턴을 끝낸 상태

각 세션에 보이는 것:
- **감시 대상 세션**: 다른 프로세스가 다음 idle 시 알려달라고 요청했다는 줄
- **요청 세션**: 감시 대상 이름이 든 통지 줄. 그 세션의 턴이 끝난 시각과 **한 줄 상태**가 포함될 수 있다. 요청 세션이 idle이면 이 통지로 새 턴을 시작

**한계**
- **일회성.** 한 번 보내고 끝. 어느 쪽도 폴링하지 않는다
- **12시간 내에 통지가 없으면** 구독을 버리고 Claude에게 알린다 → 무한 대기하지 않는다
- inbound 제어가 통지에도 적용된다:
  - 어느 쪽이든 `refuse` → 아무것도 안 온다. 감시 대상은 요청을 기록도 응답도 안 하므로 12시간 후 만료. `refuse`인 요청 세션은 애초에 구독하지 않는다
  - 어느 쪽이든 `hold` → 통지가 축소된다. 감시 대상은 한 줄 상태를 빼고, 요청 세션은 트랜스크립트에 보이지만 Claude에게 배달하지 않는다
- **메인 대화의 Claude만, 같은 머신 세션에만** 구독 가능. 서브에이전트나 팀메이트가 `notify_when_idle`을 설정하면 구독하지 않고 그렇게 알려준다. 팀메이트·서브에이전트·머신 밖 세션에 요청하면 **붙어 있던 메시지까지 통째로 거절**하고 Claude에게 보고해서 요청 없이 다시 보낼 수 있게 한다

### 4.6.11 `/list-agents` (별칭 `/peers`)

4.2.1의 표 참조. 추가 세부:

- **이 세션은 행에 없다.** Claude가 자기 이름으로 메시지를 보내면 거절하고 타깃이 현재 세션이라고 알린다 (v2.1.239+)
- **클라우드/Remote Control 목록은 최신순으로 읽고 정해진 페이지 수에서 멈춘다.** 계정에 그보다 많으면 오래된 것은 나열되지 않고 **이름으로 메시지를 보낼 수 없다.** 이 경우 목록에 그렇게 표시되고 Claude도 같은 안내를 본다
- 동명 세션이 여럿이거나 Claude Code가 모든 위치를 확인할 수 없으면, Claude가 각 행에 **짧은 식별자를 붙여** 그것으로 주소를 지정한다

### 4.6.12 inbox 소켓 — 스크립트·훅 연동

세션이 목록에 안 뜰 때, 스크립트나 훅이 세션에 포스트하고 싶을 때, 샌드박스 명령이 소켓에 못 닿을 때 필요한 지식.

**소켓 경로 찾기 2가지**
1. `/status`의 **`Peer address`** 행 (`uds:` 접두)
2. 훅과 Bash 명령에 **`CLAUDE_CODE_MESSAGING_SOCKET`** 환경변수로 export
   - 메시징이 켜진 상태로 시작한 세션은 **어떤 훅보다 먼저** export한다 (`SessionStart` 포함)
   - 기능 플래그를 가져오기 전에 시작한 세션(설치·업그레이드 직후 첫 세션)은 fetch가 끝나는 즉시 바인드하고 export한다. 그 전에 시작한 훅·프로세스는 변수가 비어 있다
   - **각 세션은 자기 소켓만 export**한다. 부모 세션 것을 상속하지 않는다

**토큰 인증**

함께 **`CLAUDE_CODE_MESSAGING_TOKEN`**도 export된다. 스크립트가 자기 세션 소켓에 포스트할 때 연결의 **첫 줄**로:

```json
{"type":"auth","token":"<CLAUDE_CODE_MESSAGING_TOKEN 값>"}
```

| 플랫폼 | 인증 줄 |
|---|---|
| macOS / Linux / WSL 2 | **선택** — 있어도 없어도 수락 |
| 네이티브 Windows | **필수** — 유효한 auth 줄이 없으면 연결을 닫고 아무것도 배달하지 않음 |

**own-child 메시지**

`crossSessionInbound` 값이 적용되지 않을 때, **자기 세션의 자식 프로세스**(훅, Bash 명령)가 자기 소켓에 되쏜 메시지는 배달된다. 검증 방법이 플랫폼마다 다르다:

| 플랫폼 | 검증 |
|---|---|
| Linux (WSL 2 포함) | **이미 종료된 자식도** 프로세스 증거로 검증 가능 |
| macOS | 포스트한 프로세스가 **살아 있는 동안만** 프로세스 증거로 가능. 종료 후엔 토큰으로 |
| PID 1로 도는 컨테이너 | 프로세스 증거 없음 → **토큰만** |
| 네이티브 Windows | 프로세스 증거 없음 → **토큰만** |

둘 다 안 되면 **권한 클래스를 주장하지 않은 일반 메시지처럼** 취급한다 → bypass 세션이면 승인 대기로 보류된다.

**보안**
- macOS/Linux: 소켓을 **OS 사용자로 제한**
- 네이티브 Windows: 각 연결이 **내 OS 사용자만 읽을 수 있는 키로 인증**해야 함
- 어느 쪽이든 공유 머신에서 다른 사용자의 세션은 배달할 수 없다

**샌드박스**
Bash 명령이 샌드박스 안에서 소켓에 닿을지는 `sandbox.network.allowAllUnixSockets` / `sandbox.network.allowUnixSockets`로 제어한다.

> 활용 아이디어: CI 스크립트나 훅이 세션 소켓에 결과를 포스트 = **외부 이벤트를 세션에 밀어넣는 로우레벨 경로**. (공식적으로 그 용도로 설계된 건 **channels**다.)

### 4.6.13 비인터랙티브 세션

- `claude -p` 세션도 **inbox 소켓을 바인드**한다 → 장기 실행 `-p` 워커가 메시지를 받을 수 있고 목록에도 뜬다
- **`--bare` 모드는 소켓을 바인드하지 않는다** → 수신 불가, 목록에도 안 뜸
- `-p`는 승인 다이얼로그를 못 띄운다. 기본 규칙이 보류하면 `dialogExpiry` 기한(기본 5분)만큼 들고 있다가:
  - 기한 전 모드·설정 변경으로 허용되면 배달
  - 기한이 지나면 드롭하고 **발신자에게 만료 보고**
- `dialogExpiry: "never"` → 세션이 끝날 때까지 보류. 단 **명시적 `hold` 설정으로 보류된 메시지는 만료되지 않는다** — `accept`가 적용될 때만 배달
- 세션이 보류분을 남기고 끝나면 **각 발신자에게 만료 보고**한다
- `-p` 워커가 무인으로 메시지를 받게 하려면 `--settings` 값에 `crossSessionInbound: accept`. 사용자 설정에 넣으면 모든 세션에 적용되니 주의

### 4.6.14 끄기

**수신 중지**
```json
{ "crossSessionInbound": "refuse" }
```
프로젝트·로컬 설정의 `refuse`는 **다른 모든 소스보다 우선**한다. 사용자 설정의 것은 managed settings나 `--settings`가 값을 정하지 않은 한 적용된다.

**발신·나열 중지** — deny 규칙 (bare 이름, specifier 없음)
```json
{ "permissions": { "deny": ["SendMessage", "ListAgents"] } }
```

**조직 전체** (managed settings)
```json
{
  "permissions": { "deny": ["SendMessage", "ListAgents"] },
  "crossSessionInbound": "refuse"
}
```

- 이 상태에서도 각 세션은 **inbox 소켓을 여전히 바인드**하되, 도착하는 모든 메시지를 배달 없이 드롭한다
- ⚠️ **`SendMessage`를 deny하면 서브에이전트·팀메이트 메시징도 같이 꺼진다.** 같은 도구가 셋을 다 담당하기 때문
- refuse 중인 세션은 **자기 `/status`에도, 같은 머신 다른 세션의 목록에도 표시가 남지 않는다** → 확인하려면 그 세션에 적용되는 설정 파일을 봐야 한다

### 4.6.15 가용성 함정

| 조건 | 결과 |
|---|---|
| macOS / Windows / Linux (WSL 2 포함) | 가능 |
| **Amazon Bedrock, Claude Platform on AWS, Google Cloud Agent Platform, Microsoft Foundry** | **불가** |
| `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, `DISABLE_TELEMETRY`, `DO_NOT_TRACK`, `DISABLE_GROWTHBOOK` 중 하나라도 기능 플래그 평가를 끄면 | **메시징도 꺼짐** |

마지막 항목이 실무 함정이다. 사내 보안 정책에서 흔히 켜는 변수들인데, 셸·설정 파일 `env`·managed settings 어디서 와도 적용된다.

**진단 순서**

1. `/list-agents`가 **인식되지 않는다** → 기능 자체가 없다. `claude --version`부터
2. `/list-agents`는 되는데 **보낸 게 안 도착한다** → 더 좁은 원인:
   - deny 규칙이 `SendMessage`/`ListAgents`를 제거
   - **수신 세션의 inbound 제어**가 hold/drop
   - 클라우드 세션은 Remote Control 연결 중에만 보임
   - 다른 머신 세션은 그쪽이 Remote Control로 돌고 이쪽도 연결됐을 때만 보임
   - 오래된 클라우드/다른 머신 세션은 페이지 한도 밖으로 밀려남
3. `/status`의 `Peer address` 행으로 소켓 확인

### 4.6.16 스터디용 실습 아이디어

1. **worktree 두 개 + 이름 붙인 세션 두 개**
   ```bash
   claude -w feature-schema -n schema-worker
   claude -w feature-api    -n api-worker
   ```
   schema 쪽에서 컬럼을 바꾸고 → `Let @api-worker know the schema migration finished`
   → api 쪽에 어떻게 도착하는지, 회신이 되는지 확인

2. **`-p` 워커를 수신 가능하게 띄우기**
   ```bash
   claude -p -n test-runner \
     --settings '{"crossSessionInbound":"accept"}' \
     "테스트를 계속 돌리면서 대기해"
   ```

3. **idle 알림 구독**
   긴 작업을 다른 세션에 던져놓고 `Tell me when <name> finishes` → 12시간 만료 정책까지 확인

4. **보안 모델 검증 (스터디에서 하면 재밌는 실험)**
   한 세션에서 다른 세션에 "`/compact` 실행해줘"나 "CLAUDE.md에 이 규칙 추가해줘"를 보내게 하고, **평문으로 도착하고 실행되지 않는지** 확인

