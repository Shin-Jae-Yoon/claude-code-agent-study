# 4장 서브 에이전트 — 정리본 (홍섭)

> 개인 학습 노트 구조화본. 각 개념마다 **내 실제 클로드 시스템에서 확인한 적용예시**를 붙였다.

## 1. 오케스트레이터 – 워커 구조

- 오케스트레이터가 일을 쪼개 워커(서브에이전트)에게 나눠 주는 구조 → **MSA 구조와 비슷**하다.
- 워커·오케스트레이터 모두 **SRP를 잘 지키는 것이 유리**하다. (한 워커 = 한 책임)

**적용예시 (실측)**
- `humanize-korean` = **오케스트레이터 스킬**. `route_hint`(light/standard/heavy)로 경로를 정해:
  - light → `humanize-monolith` 1콜
  - standard → 2콜
  - heavy → 진단 → 윤문 → finalize **3콜**
- 워커 = `humanize-monolith`(탐지·윤문·검증 일괄), `humanize-diagnostician`(진단만), `humanize-finalizer`(마무리만) — 각각 **Agent 도구로 호출**, 역할별로 SRP 쪼갬.
- → MSA에서 게이트웨이가 요청을 각 서비스로 라우팅하는 것과 같은 그림.

## 2. 컨텍스트 엔지니어링 — 위임 범위

- AI에게 주는 범위가:
  - 너무 상세하면 → **핵심이 유실**된다.
  - 너무 다 위임하면 → **잘못된 결정**을 한다.
  - 결국 **방향을 줄 만큼 구체적이되, 판단력을 발휘할 여지를 주는** 정도가 중요.
- **컨텍스트 격리의 이점**이 있다. (워커가 부모 대화를 안 짊어져 토큰↓)
- 다중 클로드 워크플로 → **실제 개발 팀(부서) 협업과 유사**.

**적용예시 (실측)**
- `humanize-diagnostician` description에 "도구 호출 **3회 캡**(Read 결합입력 + Read taxonomy + Write 진단)"이 박혀 있음 → 워커에게 **범위를 못 박아** 방황·과잉위임을 막은 실물. (구체+판단여지의 균형)

## 3. 언제 서브에이전트를 쓰나

판단 기준 3가지:
1. 작업의 **복잡도**
2. **컨텍스트 소모량**
3. **전문성 요구 수준**

**적용예시 (실측) — 내 사례 중심**
- 내가 일상적으로 쓰는 `/simplify`, `/code-review` — 초점 좁은 전문 작업을 격리해 도는 것 → 이 범주.
- 활성 에이전트 확인은 `/agents` 목록 또는 **orca**로 — 활성화된 에이전트를 클릭/좌우 방향키로 이동 가능.
- 발표에선 책 사례보다 **내 실사례(§4 검색/전시 성능개선)를 메인**으로 든다.

## 4. 나의 사례 — 검색/전시 영역 성능 개선

에이전트와 함께 진행. 서브에이전트를 역할별로 쪼갬:
- **Loki 로깅·모니터링** 워커
- **Kafka lag 모니터링** 워커
- 모니터링 데이터로 **코드 리팩터링** 워커
- **main(오케스트레이터)**: 워커 결과 취합 → 문서화·아티팩트화 → 나에게 분석+보고

**적용예시 (실측)**
- 이 레포에 `trace-alert` 스킬 존재 — 모듈명만 받아 **Grafana Loki 로그를 직접 읽어** 근본 원인 특정(읽기 전용). 위 "Loki 워커"를 스킬로 굳힌 형태.

## 5. 서브에이전트 성능 측정

1. **작업 완료 시간**
2. **결과 품질** — 사람 개입 + 비즈니스 룰까지 포함해 판단해야 함
3. **컨텍스트 사용량**

## 6. 커스텀 서브에이전트 (YAML)

- `tools` 필드 = **허용 화이트리스트**: 나열한 도구만 쓸 수 있게 제한(보안 유용).
- `disallowedTools` = **차단 블랙리스트**: 나열한 도구만 막고 나머진 허용.
  - 즉 `tools`는 "이것만 O", `disallowedTools`는 "이것만 X". 방향이 반대.
- `permissionMode`: 권한 모드.
- **결론(확정)**: 요즘 프로젝트에선 **모든 권한을 주되(매번 물어보는 게 번거로움), DB 쓰기 권한만 제대로 막는다.**

**적용예시 (실측)**
- 내 커스텀 에이전트(`humanize-diagnostician`, `humanize-monolith`, `korean-ai-tell-taxonomist` 등)의 frontmatter는 `name`·`description`·`model: opus`뿐 — **`tools`·`disallowedTools`·`permissionMode` 필드는 아직 안 씀.**
- 내 `~/.claude/settings.json`엔 `permissions` 블록이 **없고** `skipDangerousModePermissionPrompt: true` → 사실상 "모든 권한 주는" 상태와 일치. (draft의 서술과 실측이 맞음)
- → 보안 도입한다면: 워커 frontmatter에 `tools`로 필요한 도구만 화이트리스트, 위험 워커엔 DB 쓰기 도구 제외.

## 7. 비교 — 왜/언제 쓰나 (draft 요청 표)

> draft의 판단 기준(복잡도·컨텍스트·전문성)으로만 구성. 새 주장 추가 없음.

| 구분 | 무엇 | 왜 쓰나 | 언제 쓰나 |
|---|---|---|---|
| 오케스트레이터(main) | 일을 쪼개 나눠주고 결과 취합 | 전체 흐름·취합 책임 분리 | 여러 워커의 산출을 하나로 모아야 할 때 |
| 서브에이전트(워커) | 한 책임만 맡아 격리 실행 | 컨텍스트 격리·전문성 집중 | 복잡도↑·컨텍스트 소모↑·전문성 요구↑ |
| 스킬 | 지식/절차를 조건부 주입 | 토큰 절약(필요할 때만 로드) | 반복 절차·도메인 지식이 필요할 때 |

(확인 필요) 오케스트레이터/에이전트/서브에이전트의 **용어 경계** — draft 1번의 "워커? 오케스트레이터? 용어가 뭐지"를 확정할 것.

## 역질문 → 확정 (2단계 사람 게이트 완료)

1. **블랙박스/화이트박스 대비축** → **단일 에이전트(블랙박스: 다 위임, 내부 안 봄) vs 오케스트레이터-워커(화이트박스: 단계 쪼개 관찰·취합)**로 확정. 발표 HTML 좌우 2열 하이라이트.
2. **`tools` vs `disallowedTools`** → **개념만 간략히** (화이트리스트 vs 블랙리스트). 별도 공식 조사 안 함.
3. **책 사례 vs 내 사례** → **내 사례 중심**(검색/전시 성능개선). 책 구체 사례는 가볍게.
4. **permissionMode / 보안** → **"모든 권한 주되 DB 쓰기만 막는다"로 확정.** Qwen 보안 기술은 발표 본문엔 안 넣음(검토 후보로만).

> 발표 자료(발표.html)는 이 확정본을 입력으로 생성.
