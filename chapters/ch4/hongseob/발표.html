4장 · 서브 에이전트

오케스트레이터-워커, 컨텍스트 엔지니어링, 그리고 내 실측 사례 — 홍섭

한눈에

① 단일 에이전트(블랙박스: 다 위임) vs 오케스트레이터-워커(화이트박스: 단계 쪼개 관찰·취합) — 이 장의 핵심 대비.

② 오케스트레이터-워커 구조는 MSA와 유사 + SRP(한 워커 = 한 책임)가 핵심.

③ 위임 범위는 상세 ↔ 완전위임 사이 균형점 — 방향은 주되 판단 여지는 남긴다.

④ 쓰는 기준은 복잡도·컨텍스트 소모·전문성 3가지. 커스텀 에이전트 권한은 "모두 허용 + DB 쓰기만 차단"으로 실무 결론.

단일 에이전트 vs 오케스트레이터-워커

📦
Black Box
단일 에이전트
한 콜에 다 위임 · 내부 안 봄

작업 전체를 한 에이전트에 통째로 맡긴다. 중간에 무슨 판단을 거쳤는지, 어디서 흔들렸는지 사람은 볼 수 없다.

구조: 요청 → [ 블랙박스 ] → 결과
  • 빠르고 단순하지만 단계별 관찰·개입 불가
  • 실패해도 어디서 잘못됐는지 추적 어려움
🔬
White Box
오케스트레이터-워커
단계 쪼개 관찰 · 결과 취합

오케스트레이터가 일을 워커별 책임으로 쪼개고, 각 단계 산출물을 확인하며 취합한다.

구조: 요청 → 오케스트레이터 → 워커1·워커2·워커3 → 취합
  • 실측 — humanize-korean(오케스트레이터) → route_hint 분기
  • 워커별로 중간 산출물이 보인다 → 관찰·재시도 가능
이 발표의 하이라이트 — 같은 작업도 어떻게 쪼개느냐에 따라 블랙박스가 되기도, 화이트박스가 되기도 한다.

오케스트레이터-워커 = MSA + SRP

오케스트레이터가 일을 쪼개 워커(서브에이전트)에게 나눠 주는 구조 → MSA 구조와 비슷하다. 워커·오케스트레이터 모두 SRP를 잘 지키는 것이 유리하다(한 워커 = 한 책임).

실측

humanize-korean = 오케스트레이터 스킬. route_hint(light/standard/heavy)로 경로를 정해 분기한다.

route_hint
→
light: monolith 1콜
/
standard: 2콜
/
heavy: 진단→윤문→finalize 3콜

워커 = humanize-monolith(탐지·윤문·검증 일괄), humanize-diagnostician(진단만), humanize-finalizer(마무리만) — 각각 Agent 도구로 호출, 역할별 SRP.

→ MSA에서 게이트웨이가 요청을 각 서비스로 라우팅하는 것과 같은 그림.

컨텍스트 엔지니어링 — 위임 범위

과다 상세

지시가 너무 상세하면 → 핵심이 유실된다. 나무만 보고 숲을 놓친다.

전부 위임

판단까지 다 맡기면 → 잘못된 결정을 한다. 방향성 없이 흔들린다.

결국 방향을 줄 만큼 구체적이되, 판단력을 발휘할 여지를 주는 정도가 중요하다. 여기에 컨텍스트 격리의 이점도 있다 — 워커가 부모 대화를 안 짊어지므로 토큰이 줄어든다. 다중 클로드 워크플로는 실제 개발 팀(부서) 협업과 유사하다.

실측

humanize-diagnostician description에 "도구 호출 3회 캡"(Read 결합입력 + Read taxonomy + Write 진단)이 박혀 있다 → 워커에게 범위를 못 박아 방황·과잉위임을 막은 실물. 구체성과 판단여지의 균형을 보여준다.

언제 서브에이전트를 쓰나

판단 기준 3가지 — ① 작업의 복잡도 ② 컨텍스트 소모량 ③ 전문성 요구 수준.

실측 — 내 사례

내가 일상적으로 쓰는 /simplify, /code-review — 초점 좁은 전문 작업을 격리해서 도는 것 → 이 범주에 정확히 해당한다.

활성 에이전트 확인은 /agents 목록 또는 orca로 — 활성화된 에이전트를 클릭/좌우 방향키로 이동할 수 있다.

내 실사례 — 검색/전시 성능 개선

에이전트와 함께 진행. 서브에이전트를 역할별로 쪼갰다.

WORKER
Loki 로깅·모니터링 워커
WORKER
Kafka lag 모니터링 워커
WORKER

ORCHESTRATOR

실측

이 레포에 trace-alert 스킬 존재 — 모듈명만 받아 Grafana Loki 로그를 직접 읽어 근본 원인을 특정한다(읽기 전용). 위 "Loki 워커"를 스킬로 굳힌 형태.

서브에이전트 성능 측정

  1. 작업 완료 시간
  2. 결과 품질 — 사람 개입 + 비즈니스 룰까지 포함해 판단해야 함
  3. 컨텍스트 사용량

커스텀 서브에이전트 (YAML)

tools

허용 화이트리스트 — 나열한 도구만 쓸 수 있게 제한(보안 유용).

disallowedTools

차단 블랙리스트 — 나열한 도구만 막고 나머진 허용. 방향이 반대.

permissionMode — 권한 모드. 결론(확정): 요즘 프로젝트에선 모든 권한을 주되(매번 물어보는 게 번거로움), DB 쓰기 권한만 제대로 막는다.

실측

내 커스텀 에이전트(humanize-diagnostician, humanize-monolith, korean-ai-tell-taxonomist 등)의 frontmatter는 name·description·model: opus뿐 — tools·disallowedTools·permissionMode는 아직 안 씀.

내 ~/.claude/settings.json엔 permissions 블록이 없고 skipDangerousModePermissionPrompt: true → 사실상 "모든 권한 주는" 상태와 일치한다.

→ 보안 도입한다면: 워커 frontmatter에 tools로 필요한 도구만 화이트리스트, 위험 워커엔 DB 쓰기 도구 제외.

정리

  • 단일 에이전트(블랙박스)는 다 위임하고 안 보는 것, 오케스트레이터-워커(화이트박스)는 단계를 쪼개 관찰·취합하는 것 — 이 대비가 이 장의 핵심.
  • 오케스트레이터-워커는 MSA + SRP — 워커 하나는 책임 하나. humanize-korean이 실물.
  • 위임 범위는 상세와 완전위임 사이 균형, 컨텍스트 격리로 토큰도 아낀다.
  • 쓰는 기준은 복잡도·컨텍스트·전문성 3가지 — 내 검색/전시 성능개선 사례(Loki·Kafka lag·리팩터링 워커 + main)가 대표.
  • 권한은 모두 허용 + DB 쓰기만 차단으로 실무 결론.
