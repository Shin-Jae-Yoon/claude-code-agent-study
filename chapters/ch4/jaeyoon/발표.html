Chapter 04 · 재윤

서브에이전트

스킬이 무엇을 아는지라면, 서브에이전트는 어떻게 일하는지다

이 장의 한 문장

서브에이전트를 서브에이전트로 만드는 건 도구도 모델도 아니고, 컨텍스트 격리다.

3장의 스킬이 점진적 공개로 지식의 비용을 0에 수렴시켰다면, 4장의 서브에이전트는 컨텍스트 격리로 작업의 비용을 격리한다. 자체 컨텍스트에서 일하고, 메인에는 정제된 결과만 돌려준다. 나머지 전부(오케스트레이터-워커, 적정 고도, 체인·병렬, 프론트매터, 스킬 주입)는 이 한 문장을 실현하는 수단이다.

실측 기준일 2026-08-27 claude 2.1.247 + 에이전트 팀 (교재 밖 보강)

핵심 개념 셋

이 셋만 잡으면 4장은 끝난다

서브에이전트는 클로드 코드의 Agent 도구로 호출되는 특화된 AI 어시스턴트다. 자체 컨텍스트 윈도우 · 커스텀 시스템 프롬프트 · 할당된 도구를 갖고, YAML 프론트매터 + 마크다운 본문으로 정의된다. 본문이 곧 시스템 프롬프트다.

01

컨텍스트 격리

서브에이전트는 자기 컨텍스트에서 대규모 파일을 읽고 명령을 돌린다. 메인은 그 과정을 보지 않고 정제된 결과만 받는다. 그래서 메인 컨텍스트가 깨끗하게 유지된다.

02

오케스트레이터 - 워커

메인 = 오케스트레이터, 핵심 역할은 작업 분배 + 결과 통합. 서브 = 워커. 스킬과 똑같이 단일 책임 원칙(SRP)이 적용된다.

03

적정 고도 (right altitude)

너무 상세하면 핵심을 놓치고, 너무 모호하면 잘못된 결정을 내린다. 방향을 줄 만큼 구체적이되 판단 여지를 남기는 지침이 컨텍스트 엔지니어링의 핵심.

언제 서브에이전트를 쓰는가 — 판단 기준 3개

① 작업의 복잡도

여러 파일에 걸친 분석, 장기간 실행되는 작업

② 컨텍스트 소모량

대규모 파일 읽기, 명령 실행이 필요한 작업

③ 전문성 요구 수준

특정 도메인에 상세한 지침이 필요한 작업

1절 · 개념과 아키텍처

위임의 모양

메인 에이전트 (오케스트레이터) — 분배 + 통합
▼   ▼   ▼
분석 워커
수정 워커
테스트 워커
▲ 정제된 결과만 반환 ▲

워커가 읽은 수백 줄은 메인 컨텍스트에 올라오지 않는다. 이게 격리의 실익.

실행 패턴 — 순차 체인 vs 병렬

🔗 순차 실행 (체인)

앞 에이전트의 결과가 뒤 에이전트의 입력이 되는 파이프라인.

코드 분석 → 문제 식별 → 수정 → 코드 변경 → 테스트 → 변경 검증

⚡ 병렬 실행

독립적인 작업을 동시에 처리.

예: 여러 모듈의 코드 품질을 동시에 검토. 서로 기다리지 않아도 되는 작업일 때만 이득.

내 클로드 시스템에서 확인한 예시
  • 커스텀 서브에이전트는 아직 0개다. .claude/agents/도 ~/.claude/agents/도 디렉터리 자체가 없다.
  • 대신 플러그인 서브에이전트는 실측된다 — humanize-korean@im-not-ai v2.3.2가 9개를 제공한다.
  • 순차 체인의 실물: 이 플러그인의 정밀 모드가 humanize-diagnostician(진단) → 윤문 → humanize-finalizer(마무리) 3콜 파이프라인이다. 앞 단계 산출물 02_diagnosis.md를 뒤 단계가 읽는다.
  • SRP도 문서로 못박혀 있다 — 진단가는 "윤문하지 않는다", 마무리는 "전체 재작성 금지".
  • 같이 깔린 ouroboros v0.51.0에는 agents/가 없다. 스킬만 주는 플러그인 — 스킬과 서브에이전트가 별개 축이라는 증거.
  • 병렬 실행은 이 저장소에 아직 없다. 도입한다면 3인 정리본을 한 명씩 맡겨 동시에 검토하는 자리가 가장 자연스럽다.

2절 · 사용하기

호출 · 재개 · 측정

/agents로 목록을 본다. 교재는 우선순위를 3단(프로젝트 > 사용자 > 내장)으로 설명하지만, 현재 버전은 5단으로 늘었다.

1관리형 설정(managed settings)추가조직 전체
2--agents CLI 플래그추가현재 세션
3.claude/agents/현재 프로젝트
4~/.claude/agents/내 모든 프로젝트
5플러그인의 agents/추가플러그인이 켜진 곳

내장 에이전트도 general-purpose·Explore·Plan에 claude(catch-all)가 추가됐다. Explore와 Plan은 조사 속도·비용을 위해 CLAUDE.md와 git status를 건너뛴다.

호출 문법 — 자동 위임은 description에 달렸다

# 자연어 명시 호출
code-review 서브에이전트 사용해서 내 최근 변경 사항 검토해 줘

# 적극적 자동 위임 유도 키워드 (description 필드에)
use PROACTIVELY / MUST BE USED

# 컨텍스트와 함께 호출
@code-reviewer(agent) 서브에이전트로 @src/auth/login.ts 파일 리뷰해줘
미확정

현재 공식 문서 표기는 소문자 use proactively이고, (agent) 접미 표기는 공식 서브에이전트 문서에서 확인되지 않았다. 교재 표기를 그대로 두고 미검증으로 남긴다.

내 클로드 시스템에서 확인한 예시
  • description이 위임의 유일한 근거라는 게 플러그인에서 극단적으로 드러난다. 공식 pr-review-toolkit의 code-reviewer.md는 description 한 필드에 위임 시나리오 3개(기능 구현 직후 / 작성 코드 자체 리뷰 / PR 직전 최종 점검)를 통째로 서술해 넣었다.
  • 본문이 아니라 description에 넣어야 위임 판단에 쓰인다.

작업 재개 — 교재와 현재 버전이 갈리는 지점

📘 교재

호출할 때마다 새 인스턴스. 이어가려면 resume 명시 필요. 실행마다 고유 agentId가 붙고, 대화는
~/.claude/projects/{project}/{sessionId}/subagents/agent-{agentId}.jsonl에 저장.

🆕 현재 (2.1.247)

agentId 대신 이름(name). 클로드가 Agent 호출에 name을 붙이면 그 이름이 SendMessage의 to가 되고, 완료된 서브에이전트가 메시지를 받으면 백그라운드에서 자동 재개된다.

미확정 — 정직하게

교재가 말한 트랜스크립트 경로를 확인하지 못했다. ~/.claude/projects 아래 6개 프로젝트 전체에 subagents/도 agent-*.jsonl도 없다. 서브에이전트를 돌린 이력이 없어서일 가능성이 크며, 경로가 틀렸다는 근거는 아니다. 실재하는 건 {sessionId}.jsonl과 {sessionId}/tool-results/toolu_*.txt뿐.

성능 측정 3지표

⏱ 작업 완료 시간

시작 ~ 결과 반환. 동일 유형끼리 비교해 효율성 평가.

🎯 결과 품질

발견한 문제의 타당성, 수정 제안의 적절성.

🪙 컨텍스트 사용량

같은 결과를 더 적은 토큰으로 낸 쪽이 효율적.

내 클로드 시스템에서 확인한 예시
  • 세 지표를 강제하는 장치는 아직 없다. 다만 humanize-monolith가 "도구 호출 총 3회"로 컨텍스트 상한을 못박고, 그 근거로 "5인 파이프라인이 wall-clock 25분에 도달했다"는 완료 시간 측정 결과를 든다 — 측정 → 재설계의 실물 사례.
  • 도입 자리는 이미 있다. ~/.claude/settings.json에 SubagentStart/SubagentStop 훅이 등록돼 있어(현재 orca-cli가 점유), 타임스탬프 로깅만 붙이면 완료 시간은 자동 수집된다.

3절 · 커스텀 개발과 스킬 주입

프론트매터는 경계, 본문은 행동

---
name: code-reviewer            # 필수 · 소문자·하이픈만
description: 코드 품질·보안·유지보수성 전문가. 코드 변경 직후 사용   # 필수 · 자동 위임의 근거
tools: Read, Grep, Glob, Bash  # 생략 시 전체 상속
model: inherit                 # 기본값이 inherit
skills: moai-foundation-core, moai-lang-unified
---
여기부터 본문 = 시스템 프롬프트

교재 9필드는 전부 유효하고, 7개가 더 붙었다

namedescriptiontools disallowedToolsmodelpermissionMode skillshooksmemory maxTurnsmcpServersbackground effortisolationcolorinitialPrompt

permissionMode도 5종 → 7종(auto, manual 추가). 특히 isolation: worktree는 교재 1.6의 "깃 워크트리로 병렬 작업" 패턴이 필드 하나로 내장화된 것.

우선순위 — permissionMode > tools

⚠️ 상위가 이긴다

tools에 Write·Edit가 있어도 permissionMode: plan이면 실제 파일 수정 불가.

acceptEdits vs bypassPermissions

acceptEdits — 파일 편집에 한해 자동화
bypassPermissions — 파이프라인급 완전 자동화, 모든 확인 건너뜀

hooks — 에이전트 스코프 생애 주기

시점호출 타이밍용도
PreToolUse도구 실행 직전실행 검증, 전처리
PostToolUse도구 실행 직후결과 로깅, 후처리
Stop에이전트 종료 시정리 작업, 결과 보고
내 클로드 시스템에서 확인한 예시
  • 에이전트 스코프 훅은 없지만 전역 훅은 실측된다 — ~/.claude/settings.json에 11개 등록: SessionStart UserPromptSubmit Stop StopFailure SubagentStart SubagentStop TeammateIdle PreToolUse PostToolUse PostToolUseFailure PermissionRequest.
  • 전부 ~/.orca/agent-hooks/claude-hook.sh 하나를 가리키는 orca-cli 텔레메트리 훅. 교재의 3종은 훅 이벤트 전체 중 일부다.
  • SubagentStart/SubagentStop은 서브에이전트 전용, TeammateIdle은 에이전트 팀 전용 이벤트다. → 4절로 이어짐
  • memory: project가 쓸 자리 — 이 프로젝트의 …/memory/ 디렉터리는 존재하지만 비어 있다.

여기서 얻은 평가

교재는 프론트매터를 "완전 가이드"로 길게 다루지만, 내 시스템에서 실측된 정의 15개는 전부 3~4개 필드만 쓴다. humanize-korean 9개는 name/description/model 3개, 공식 code-reviewer.md는 거기에 color 하나 더.

즉 프론트매터가 정하는 건 경계(어떤 도구를, 어떤 모델로, 어떤 권한에서)일 뿐이고, 에이전트의 행동을 결정하는 무게 중심은 본문(시스템 프롬프트)에 있다. 진단가가 "윤문하지 않는다"를 tools 제한이 아니라 본문 문장으로 강제하는 게 그 증거다.

→ 필드 16개를 외우는 것보다 본문에 명시적 금지 문장 한 줄을 잘 쓰는 게 품질을 더 많이 좌우한다.

skills 주입 — 순서가 곧 우선순위, 인데…

skills: moai-foundation-core, moai-lang-unified, moai-project-specific
(확인 필요) 원문이 스스로 모순된다

본문: "프로젝트 특화 규칙을 마지막에 배치 … 마지막에 로드하여 오버라이드"
코드 주석: "3. moai-project-specific(낮은 우선순위)"

"마지막 = 오버라이드(강함)"와 "마지막 = 낮은 우선순위(약함)"는 반대 방향이다. 현재 공식 문서도 skills를 "시작 시 컨텍스트에 프리로드"라고만 설명해 순서-우선순위 관계를 명시하지 않는다 → 문서로 판정 불가. 단정하지 않는다.

내 클로드 시스템에서 확인한 예시
  • skills 필드를 쓰는 에이전트 정의는 내 시스템에 하나도 없다.
  • 대신 이 저장소는 에이전트 없이 스킬만으로 같은 목적을 달성한다 — .claude/skills/에 9개, 서브에이전트 0개.
  • 중요: 서브에이전트 정의를 에이전트 팀의 팀원으로 쓰면 skills·mcpServers 프론트매터는 적용되지 않는다(공식 문서 명시). → 3절의 스킬 주입은 서브에이전트에선 되고, 팀원에선 안 된다.

4절 · 교재 밖 보강

에이전트 팀 (agent teams)

교재 1.6 "다중 클로드 워크플로"(터미널 여러 개를 사람이 띄우는 수동 패턴)가 현재 클로드 코드에 정식 기능으로 흡수된 결과다. 조율(태스크 분배·메시지·정리)을 클로드 코드가 직접 맡는다. 실험 기능이며 기본 비활성.

◧

서브에이전트

한 세션 안에서 위임
  • 컨텍스트자체 컨텍스트, 결과는 호출자에게 반환
  • 통신호출자에게 결과 반환
    (이름 붙은 것끼리는 메시지 가능)
  • 조율메인 에이전트가 전부 관리
  • 적합결과만 중요한 초점형 작업
  • 토큰 비용낮음 — 결과가 요약되어 메인에 돌아옴
VS
◨

에이전트 팀

독립 세션들의 팀
  • 컨텍스트자체 컨텍스트, 완전 독립
  • 통신팀원끼리 직접 메시지 (메일박스)
  • 조율자기 조율 — 메시지 + 공유 태스크 리스트
  • 적합논의·협업이 필요한 복잡한 작업
  • 토큰 비용높음 — 팀원 하나하나가 별도 클로드 인스턴스
빠르고 초점 잡힌 워커가 보고만 하면 되면 → 서브에이전트
팀원끼리 발견을 공유하고 서로 반박해야 하면 → 에이전트 팀

활성화 — 그리고 켤 때의 부작용

// settings.json
{ "env": { "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1" } }
켜는 순간 평범한 위임의 동작도 바뀐다

클로드는 나중에 메시지를 보내려고 서브에이전트에 스스로 이름을 붙인다. 에이전트 팀이 켜져 있으면 이름 붙은 서브에이전트가 팀원으로 실행된다 — 팀을 요청한 적 없어도 팀이 생긴다. 서브에이전트는 결과를 반환하지만 팀원은 "멈췄다"는 idle 알림만 보내므로, 결과를 기다리는 흐름은 여기서 멈출 수 있다. 되돌리려면 값을 0으로. (또한 팀원 생성은 대화형 세션에서만 — -p 헤드리스·SDK에선 그냥 서브에이전트로 돈다.)

구성 요소와 저장 위치

👤 팀 리드

팀원을 스폰하고 작업을 조율하는 메인 세션. 고정 — 팀원을 리드로 승격할 수 없다.

👥 팀원

배정된 작업을 수행하는 별도의 클로드 코드 인스턴스. 리드의 대화 이력은 상속하지 않는다.

📋 태스크 리스트

공유 작업 목록. pending / in progress / completed 3상태 + 의존성. claim은 파일 잠금으로 경쟁 조건 방지.

📮 메일박스

에이전트 간 메시징. 각자 JSON 파일 하나.

무엇경로수명
팀 설정~/.claude/teams/{team-name}/config.json세션 종료 시 삭제
메일박스~/.claude/teams/{team-name}/inboxes/{agent-name}.json팀 설정과 함께
태스크 리스트~/.claude/tasks/{team-name}/로컬에 잔존·업로드 안 됨
cleanupPeriodDays 적용

팀 이름은 session- + 세션 ID 앞 8자리로 자동 생성된다. config.json은 런타임 상태(세션 ID·tmux pane ID)라 손으로 고치거나 미리 만들면 안 된다.

권한 — 여기가 가장 중요하다

상속되고, 되돌릴 수 없다

팀원은 리드의 권한 설정 그대로 시작한다. 리드가 --dangerously-skip-permissions면 팀원 전부가 그렇다. 스폰 시점 팀원별 모드 지정은 불가. 팀원의 권한 프롬프트는 리드 세션에 뜬다.

에이전트 메시지 ≠ 사용자 승인

SendMessage로 온 메시지는 "다른 클로드 세션에서 왔다"고 알려진다. 팀원은 사용자 대신 승인할 수 없고, 거부당한 팀원이 다른 팀원에게 시켜 우회하는 것도 막힌다. auto 모드에선 분류기가 배달 전 모든 메시지를 검사한다.

📐 운용 권고

팀 크기 3~5명부터. 독립 태스크 15개라도 3명이 좋은 출발점. 팀원당 태스크 5~6개. 파일 충돌 회피 — 팀원마다 다른 파일 집합. 입문은 리서치·리뷰부터.

🚧 한계 (실험 기능)

/resume·/rewind가 팀원 복원 못 함 · 태스크 상태 지연 · 세션당 팀 하나 · 중첩 팀 없음 · 리드 고정 · split pane은 tmux/iTerm2 필요

내 클로드 시스템에서 확인한 예시 — 꺼져 있는데 흔적은 이미 있다
  • 에이전트 팀은 꺼져 있다. settings.json에 env 블록 자체가 없고, 세션 환경변수에도 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS가 없다.
  • 그런데 ~/.claude/teams/ 디렉터리는 존재하되 비어 있다 — 문서의 "변수가 없으면 팀 디렉터리가 기록되지 않는다"와 정확히 일치.
  • ~/.claude/tasks/session-4a0a2b53/가 남아 있다 — 팀 이름 session-+8자 규칙, "태스크 디렉터리는 세션이 끝나도 남는다"는 서술의 실물.
  • settings.json 훅 목록에 TeammateIdle이 등록되어 있다 — 이 버전에 팀 전용 훅 이벤트가 실재한다는 증거.
  • 이번엔 켜지 않기로 했다 — 부작용(이름 붙은 서브에이전트가 전부 팀원화)과 토큰 비용 때문. 위 세 흔적만으로 문서 서술은 검증된다.

정리

가져갈 것 넷, 모르는 것 셋

1

컨텍스트 격리가 전부다

도구도 모델도 아니고, 자기 컨텍스트에서 일하고 정제된 결과만 돌려주는 것 — 그게 서브에이전트를 서브에이전트로 만든다.

2

프론트매터는 경계, 본문은 행동

실측 정의 15개는 전부 3~4필드만 쓴다. 필드 16개보다 본문의 명시적 금지 문장 한 줄이 품질을 더 좌우한다.

3

교재의 "다중 클로드"는 이제 기능이다

수동 터미널 병렬 → 에이전트 팀. 깃 워크트리 → isolation: worktree 필드. 교재가 패턴으로 설명한 걸 제품이 흡수했다.

4

보고만 하면 서브, 논쟁해야 팀

토큰은 팀원 수만큼 선형으로 늘고 조율 오버헤드는 그보다 빨리 는다. 3~5명, 리서치·리뷰부터.

발표에서 "모른다"고 말할 것

skills 순서 방향

원문이 스스로 모순("마지막=오버라이드" vs "마지막=낮은 우선순위"). 공식 문서로도 판정 불가.

(agent) 표기

현재 공식 문서 미확인. 실행 검증도 하지 않음.

트랜스크립트 경로

6개 프로젝트 전체에서 해당 파일 없음. 단, 경로가 틀렸다는 근거는 아니다.
