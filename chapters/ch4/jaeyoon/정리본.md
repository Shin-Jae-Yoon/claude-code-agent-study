# Chapter 4. 서브에이전트

> 상태: **확정본** — 역질문 7개 답변 반영 완료
> 실측 기준일: 2026-08-27 (내 클로드 시스템 · 공식 문서 모두 이 날짜 기준)
> 실측 환경: `claude --version` = **2.1.247**, 이 세션이 실제로 실행 중인 바이너리는 **2.1.241** (`CLAUDE_CODE_EXECPATH=~/.local/share/claude/versions/2.1.241`)

## 중심 메시지

> **스킬이 "무엇을 알아야 하는지"라면, 서브에이전트는 "그 지식으로 실제 작업을 어떻게 수행하는지"다. 그리고 그것을 가능하게 하는 단 하나의 메커니즘이 컨텍스트 격리다.**
>
> (원문의 "핵심은 컨텍스트 격리"를 장 전체의 축으로 승격했다 — 3장의 "점진적 공개"와 대구.)

3장의 스킬이 점진적 공개로 **지식의 비용**을 0에 수렴시켰다면, 4장의 서브에이전트는 컨텍스트 격리로 **작업의 비용**을 격리한다. 서브에이전트는 자체 컨텍스트 윈도우에서 일하고, 메인 에이전트에게는 **정제된 결과만** 돌려준다. 이 장의 나머지(오케스트레이터-워커 패턴, 적정 고도, 체인·병렬, 프론트매터 필드, 스킬 주입)는 전부 이 한 문장을 실현하는 수단이다.

## 1. 서브에이전트의 개념과 아키텍처

### 1.1 스킬과 서브에이전트

| 구분 | 스킬 | 서브에이전트 |
| --- | --- | --- |
| 답하는 질문 | 무엇을 알아야 하는지 | 그 지식을 어떻게 활용해 실제 작업을 수행하는지 |

서브에이전트는 클로드 코드의 **Agent 도구**를 기반으로 호출되는 특화된 AI 어시스턴트다.

- 자체 컨텍스트 윈도우, 커스텀 시스템 프롬프트, 할당된 도구를 보유한다.
- 핵심은 **컨텍스트 격리**.
- 구성은 **YAML 프론트매터 + 마크다운 본문**이며, 마크다운 본문이 곧 서브에이전트의 시스템 프롬프트다.

**내 클로드 시스템에서 확인한 예시**

- 프로젝트(`.claude/agents/`)·사용자(`~/.claude/agents/`) 어디에도 **커스텀 서브에이전트는 아직 없다.** 두 디렉터리 자체가 존재하지 않는다.
- 대신 **플러그인 서브에이전트**는 실측된다. `humanize-korean@im-not-ai` v2.3.2가 `agents/` 아래 9개를 제공한다 (`humanize-diagnostician`, `humanize-finalizer`, `humanize-monolith`, `korean-ai-tell-taxonomist`, `korean-translation-scholar`, `post-editese-metric-engineer`, `quick-rules-integrator`, `taxonomy-gap-analyzer`, `translationese-research-distiller`).
- 9개 파일 전부 구조가 **프론트매터(`name`/`description`/`model`) + 마크다운 본문**이고, 본문이 그대로 시스템 프롬프트 역할을 한다 — 교재 설명과 일치.
- 같이 설치된 `ouroboros@ouroboros` v0.51.0에는 `agents/` 디렉터리가 **없다**. 스킬만 제공하는 플러그인이다. → 스킬과 서브에이전트가 별개 확장 축이라는 걸 플러그인 구성이 그대로 보여준다.

### 1.2 에이전트 위임 패턴: 오케스트레이터 - 워커

- **메인 에이전트 = 오케스트레이터.** 핵심 역할은 **작업 분배 + 결과 통합**.
- **서브에이전트 = 워커.**

**내 클로드 시스템에서 확인한 예시**

- `humanize-korean` 플러그인이 이 패턴의 실물이다. `humanize-monolith`는 문서에 "본 에이전트는 다른 에이전트를 호출하지 않는다"고 명시되어 있고, 정밀 모드는 `humanize-diagnostician`(진단) → 윤문 → `humanize-finalizer`(마무리)의 3콜 파이프라인으로 오케스트레이션된다. 워커는 워커 역할만 하고, 조율은 상위가 한다.

### 1.3 단일 책임 원칙과 서브에이전트

스킬과 동일하게 서브에이전트에도 SRP를 적용한다.

**내 클로드 시스템에서 확인한 예시**

- `humanize-korean`의 9개 에이전트가 SRP를 문서로 못박아 둔 사례다. `humanize-diagnostician`의 설명에는 **"윤문하지 않는다 — 진단만 한다"**, `humanize-finalizer`에는 **"전체 재작성 금지 — 검증 + 국소 보정"**이라고 명시되어 있다. 역할 경계를 프롬프트 안에 금지 문장으로 박아두는 방식.

### 1.4 컨텍스트 엔지니어링 원칙

서브에이전트를 효과적으로 활용하려면 컨텍스트 엔지니어링에 대한 이해가 필요하다.

**컨텍스트 엔지니어링** = 모델에 제공하는 컨텍스트를 체계적으로 설계하는 방법론.

- **적정 고도(right altitude)**
  - 너무 상세하면 핵심을 놓친다.
  - 너무 모호하면 잘못된 결정을 내린다.
  - 에이전트에 방향을 줄 만큼 구체적이되, **판단력을 발휘할 여지를 남기는** 지침.

이 원칙이 서브에이전트에 작동하는 지점은 둘이다.

1. 에이전트에 전달하는 **초기 컨텍스트의 설계**
2. 에이전트가 작업 중 수집하는 **컨텍스트의 관리**

결국 컨텍스트 격리의 이점은, 서브에이전트가 작업 후 **정제된 정보만** 메인 에이전트에 전달하므로 메인 컨텍스트가 정제된 상태로 유지된다는 것이다.

**내 클로드 시스템에서 확인한 예시**

- 이 저장소의 `.claude/skills/pre-chapter-prep/SKILL.md`가 적정 고도의 실물이다. "HTML 생성은 초점이 좁아 서브에이전트에 위임해도 좋다 (**컨텍스트 격리**)"라고 위임 판단 근거를 명시하되, HTML을 어떻게 짜라는 세부는 규칙 4~5개(자체완결·인라인·2열 대비)로만 제한한다.
- 반대로 `humanize-monolith`는 "도구 호출 총 3회"처럼 **수치로 못박은 저고도 지침**을 쓴다. 같은 시스템 안에 고도가 다른 두 스타일이 공존한다.

### 1.5 에이전트 체인과 병렬 실행

**순차 실행**
- 이전 에이전트의 결과가 다음 에이전트의 입력이 되는 파이프라인 구조.
- 예: 코드 분석 에이전트가 문제 식별 → 수정 에이전트가 코드 변경 → 테스트 에이전트가 변경 사항 검증.

**병렬 실행**
- 독립적인 작업을 동시에 처리.
- 예: 여러 모듈의 코드 품질 동시 검토.

**내 클로드 시스템에서 확인한 예시**

- 순차 체인: `humanize-korean` 정밀 모드가 진단 → 윤문 → 마무리로, 앞 단계 산출물(`02_diagnosis.md`)을 뒤 단계가 읽는 구조로 문서화되어 있다.
- 병렬: 이 저장소에서 **아직 없다.** 도입한다면 스터디 산출물 검토(`chapters/chN/<이름>/정리본.md` 3인분)를 한 명씩 맡겨 동시에 돌리는 게 가장 자연스러운 자리다.

### 1.6 다중 클로드 워크플로

- 여러 클로드 코드 인스턴스를 **서로 다른 터미널에서 병렬로** 실행해 복잡한 작업을 처리하는 고급 패턴.
- 하나의 인스턴스가 코드를 작성하는 동안 다른 인스턴스가 리뷰를 수행하거나, 독립적인 작업을 위해 **깃 워크트리**를 사용한다.

> ※ 이 패턴이 4장 이후 클로드 코드 본체에 **에이전트 팀(agent teams)** 이라는 기능으로 흡수됐다. → [4장 보강](#4-교재-밖-보강--에이전트-팀-agent-teams)

### 1.7 언제 서브에이전트를 사용하는가

1. **작업의 복잡도** — 여러 파일에 걸친 분석, 장기간 실행되는 작업
2. **컨텍스트 소모량** — 대규모 파일 읽기, 명령 실행이 필요한 작업
3. **전문성 요구 수준** — 특정 도메인에 대해 상세한 지침이 필요한 작업

## 2. 서브에이전트 사용하기

### 2.1 목록과 우선순위

`/agents`로 사용 가능한 서브에이전트 목록을 본다.

교재가 제시하는 우선순위:

| 순위 | 종류 | 위치 |
| --- | --- | --- |
| 상 | 프로젝트 에이전트 | `.claude/agents/` |
| 중 | 사용자 에이전트 | `~/.claude/agents/` |
| 하 | 기본 내장 에이전트 | general-purpose, Explore, Plan |

**현재 버전(2.1.247) 공식 문서와의 차이** — 스코프가 5단계로 늘었다.

| 순위 | 위치 | 범위 |
| --- | --- | --- |
| 1 (최상) | 관리형 설정(managed settings) | 조직 전체 |
| 2 | `--agents` CLI 플래그 | 현재 세션 |
| 3 | `.claude/agents/` | 현재 프로젝트 |
| 4 | `~/.claude/agents/` | 내 모든 프로젝트 |
| 5 (최하) | 플러그인의 `agents/` | 플러그인이 켜진 곳 |

내장 에이전트도 `general-purpose`, `Explore`, `Plan`에 **`claude`(무엇에도 안 맞는 작업의 catch-all)** 가 추가됐다. `Explore`와 `Plan`은 조사 속도·비용을 위해 **CLAUDE.md와 git status를 건너뛴다**는 점이 문서에 명시되어 있다.

**내 클로드 시스템에서 확인한 예시**

- 이 세션에서 실제로 노출되는 에이전트 타입: 내장 4종(`claude`, `Explore`, `general-purpose`, `Plan`) + 특수 2종(`claude-code-guide`, `statusline-setup`) + 플러그인 스코프 9종(`humanize-korean:*`). 프로젝트·사용자 스코프는 **0개**.
- 플러그인 에이전트가 `humanize-korean:humanize-monolith`처럼 `플러그인명:에이전트명` 형태로 식별되는 것도 문서 설명(plugin-scoped ID, `name`에 `:` 금지)과 일치한다.

### 2.2 에이전트 호출 문법

**자연어로 명시적 호출**
- 자동 위임 메커니즘은 `description` 필드에 의존한다.
- 예: `code-review 서브에이전트 사용해서 내 최근 변경 사항 검토해 줘`
- 적극적인 자동 위임을 원하면 `description`에 키워드를 포함한다: `use PROACTIVELY`, `MUST BE USED` [^1]

**컨텍스트와 함께 호출**
- 추가 컨텍스트(파일 경로, 오류 메시지, 특정 요구사항)를 함께 전달할 수 있다.
- 표기: `@<에이전트이름>(agent)`
- 예: `@code-reviewer(agent) 서브에이전트로 @src/auth/login.ts 파일 리뷰해줘` [^2]

[^1]: 현재 공식 문서(2026-08-27 조회)의 표기는 소문자 `use proactively`다. 대소문자 차이일 뿐인지 별도 취급인지는 문서로 판정되지 않는다. 교재 표기를 그대로 둔다.
[^2]: `(agent)` 접미 표기는 현재 공식 서브에이전트 문서에서 확인되지 않았다. 교재 표기를 그대로 두고 실제 동작은 미검증으로 남긴다.

**내 클로드 시스템에서 확인한 예시**

- `description`이 자동 위임의 유일한 근거라는 점은 플러그인 쪽에서 극단적으로 드러난다. `pr-review-toolkit`의 `code-reviewer.md`는 `description` 한 필드에만 **위임 시점 시나리오 3개**(기능 구현 직후 리뷰 요청 / 작성한 코드의 사전 자체 리뷰 / PR 직전 최종 점검)를 통째로 서술해 넣었다. 본문이 아니라 `description`에 넣어야 위임 판단에 쓰인다.

### 2.3 에이전트 결과 통합

메인에서 결과를 취합할 때 서브에이전트들의 **우선순위가 서로 다를 수 있으므로** 프로젝트 상황에 맞게 조정한다.

- 예: 코드 리뷰 에이전트는 추상화를 권장하는데, 성능 분석 에이전트는 인라인 처리를 권장하는 충돌.

### 2.4 작업 재개 기능 활용

서브에이전트는 기본적으로 **호출할 때마다 새 인스턴스**로 시작한다.

- 이전 작업을 이어가려면 resume을 명시적으로 써야 한다.
- 각 서브에이전트 실행에는 고유한 **agentId**가 할당되고, 이 ID로 재개한다.
- 에이전트 대화 내용은 별도 파일에 저장된다: `~/.claude/projects/{project}/{sessionId}/subagents/agent-{agentId}.jsonl`

**작업 재개 워크플로**

1. `@agent-code-analyzer 에이전트로 인증 모듈 리뷰 시작. 완료되면 agentId 알려줘`
2. `인증 모듈 분석 결과가 어떻게 되었나요?`
3. `에이전트 a9adef5 재개하고 권한 부여 로직도 함께 분석해 줘`

**내 클로드 시스템에서 확인한 예시**

- 교재가 말한 경로를 **확인하지 못했다.** `~/.claude/projects` 아래 6개 프로젝트 전체를 뒤졌지만 `subagents/` 디렉터리도 `agent-*.jsonl` 파일도 **하나도 없다.** 서브에이전트를 실제로 돌린 이력이 없어서일 가능성이 크다 — 경로가 틀렸다고 단정할 근거는 아니다.
- 실제로 존재하는 건 세션 단위 `{sessionId}.jsonl`과 `{sessionId}/tool-results/toolu_*.txt`뿐이다.
- 현재 공식 문서는 재개를 **agentId 대신 이름(name)** 으로 설명한다: 클로드가 Agent 호출 시 `name`을 붙이면 그 이름이 `SendMessage`의 `to` 값이 되고, **완료된 서브에이전트가 `SendMessage`를 받으면 백그라운드에서 자동 재개**된다. 교재의 "명시적 resume + agentId"보다 한 단계 자동화된 형태다.

### 2.5 에러 처리 및 복구

- **파일 접근 오류** — 경로 확인 및 권한 설정 점검
- **명령 실행 실패** — 명령어 구문과 환경 설정 검토
- **컨텍스트 초과** — 작업 범위를 줄이거나 `/clear` 후 재시도

핵심적인 오류면 워크플로를 중단하고 사용자에게 알리고, 재시도 가능한 오류는 일정 횟수까지 자동 재시도한다.

### 2.6 서브에이전트 성능 측정

| 지표 | 정의 | 평가 방법 |
| --- | --- | --- |
| **작업 완료 시간** | 작업 시작 ~ 결과 반환까지 | 동일 유형 작업끼리 시간 비교 |
| **결과 품질** | 결과의 정확성과 유용성 | 발견한 문제의 타당성, 수정 제안의 적절성 |
| **컨텍스트 사용량** | 작업 중 소모한 토큰 양 | 같은 결과를 더 적은 컨텍스트로 낸 쪽이 효율적 |

에이전트 실행 시 "완료 후 측정 지표를 보고해 달라"고 요청할 수 있다.

**내 클로드 시스템에서 확인한 예시**

- 이 세 지표를 **강제하는 장치는 아직 없다.** 다만 `humanize-korean`이 컨텍스트 사용량을 프롬프트 레벨에서 관리하는 사례를 보여준다 — `humanize-monolith`는 "**도구 호출 총 3회**. 그 이상 늘어나면 v1.4와 다를 게 없다"로 상한을 못박고, 그 근거로 5인 파이프라인이 wall-clock 25분에 도달했다는 **작업 완료 시간 측정 결과**를 든다. 측정 → 재설계의 실물 사례.
- 도입한다면 자리는 정해져 있다. `~/.claude/settings.json`에 이미 `SubagentStart`/`SubagentStop` 훅이 등록되어 있어(현재는 orca-cli가 점유), 여기에 타임스탬프 로깅을 붙이면 완료 시간은 자동 수집이 된다.

## 3. 커스텀 서브에이전트 개발과 스킬 주입

### 3.1 서브에이전트 정의 파일 구조

커스텀 서브에이전트는 **마크다운 파일**로 정의하며 스킬과 유사하다.

- **상단 프론트매터** — 에이전트의 메타데이터
- **본문** — 시스템 프롬프트 (역할, 동작 방식, 제약 조건 등)

예시 (`.claude/agents/`):

```
code-reviewer.md      # 코드 리뷰 전문 에이전트
debugger.md           # 디버깅 전문 에이전트
test-writer.md        # 테스트 작성 에이전트
security-auditor.md   # 보안 감사 에이전트
```

### 3.2 YAML 프론트매터

```yaml
---
name: code-reviewer
description: 코드 품질 전문가, 보안, 유지보수성 전문가. 코드 변경 직후 사용
tools: Read, Grep, Glob, Bash
model: inherit
skills: moai-foundation-core, moai-lang-unified
---
```

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `name` | ✅ | 에이전트 고유 식별자 (소문자·하이픈만) |
| `description` | ✅ | 에이전트 목적 설명. **자동 위임 판단이 이 필드를 참조** |
| `tools` | | 사용 가능 도구 제한 (생략 시 모든 도구 상속) |
| `model` | | 사용할 모델 지정 |
| `skills` | | 주입할 스킬 목록 |
| `disallowedTools` | | 사용 금지 도구 목록 |
| `permissionMode` | | 권한 동작 모드 (`default`, `acceptEdits`, `dontAsk`, `bypassPermissions`, `plan`) |
| `hooks` | | 에이전트 스코프 생애 주기 훅 |
| `memory` | | 영속 메모리 스코프 |

**현재 버전(2.1.247) 공식 문서와의 차이** — 교재의 9개 필드는 전부 유효하고, **7개가 추가**됐다.

| 추가 필드 | 값 | 설명 |
| --- | --- | --- |
| `maxTurns` | 정수 | 서브에이전트가 멈추기 전 최대 에이전틱 턴 수 |
| `mcpServers` | 목록 | 이 서브에이전트가 쓸 MCP 서버 |
| `background` | `true` | 클로드가 포그라운드를 원해도 백그라운드 유지 |
| `effort` | `low`~`max` | 이 에이전트가 활성일 때의 사고 강도 |
| `isolation` | `worktree` | 임시 깃 워크트리에서 실행 (→ 1.6 다중 클로드 패턴의 내장화) |
| `color` | 8색 | 표시 색 |
| `initialPrompt` | 문자열 | 이 에이전트가 메인 세션 에이전트로 돌 때 첫 유저 턴으로 자동 제출 |

- `model`은 `sonnet`/`opus`/`haiku`/`fable`/풀 모델 ID/`inherit`을 받고 **기본값이 `inherit`** 이다. 교재 예시가 `model: inherit`을 명시한 건 기본값을 적어둔 셈.
- `permissionMode`에 **`auto`와 `manual`이 추가**됐다 (교재 5종 → 현재 7종).

**내 클로드 시스템에서 확인한 예시**

- 실측 가능한 에이전트 정의 파일은 플러그인 것뿐인데, **아무도 이 필드들을 다 쓰지 않는다.** `humanize-korean`의 9개 파일은 전부 `name`/`description`/`model: opus` **3개 필드만** 쓴다. `tools`, `skills`, `hooks`, `memory` 전무.
- 공식 마켓플레이스의 `pr-review-toolkit/agents/code-reviewer.md`도 `name`/`description`/`model`/`color` **4개뿐**이다.
**여기서 얻은 평가** — 교재는 프론트매터를 "완전 가이드"로 길게 다루지만, **내 시스템에서 실측된 정의 15개는 전부 3~4개 필드만 쓴다.** 즉 프론트매터가 정의하는 건 **경계**(어떤 도구를, 어떤 모델로, 어떤 권한에서)일 뿐이고, 에이전트의 **행동을 결정하는 무게 중심은 본문(시스템 프롬프트)** 에 있다. `humanize-diagnostician`이 "윤문하지 않는다"를 `tools` 제한이 아니라 **본문 문장**으로 강제하는 게 그 증거다.

이 관찰은 3.8 프롬프트 작성 가이드가 왜 이 장의 실질적 핵심인지를 설명한다. 프론트매터 16개 필드를 외우는 것보다, 본문에 **명시적 금지 문장 한 줄**을 잘 쓰는 게 에이전트 품질을 더 많이 좌우한다.

### 3.3 permissionMode와 tools의 우선순위

**`permissionMode`가 `tools` 필드보다 상위에서 동작한다.**

- `tools`에 `Write`, `Edit`가 포함되어 있어도 `permissionMode: plan`이면 실제 파일 수정은 불가.

**`acceptEdits` vs `bypassPermissions`**

| 모드 | 범위 |
| --- | --- |
| `acceptEdits` | **파일 편집에 한해** 자동화 |
| `bypassPermissions` | 파이프라인 같은 **완전 자동화**. 모든 확인을 건너뜀 |

### 3.4 hooks — 에이전트 스코프 생애 주기 훅

`hooks`는 에이전트 실행 과정의 특정 시점에 **셸 명령**을 자동 실행하는 메커니즘이다.

| 시점 | 호출 타이밍 | 용도 |
| --- | --- | --- |
| `PreToolUse` | 도구 실행 **직전** | 도구 실행 검증, 전처리 |
| `PostToolUse` | 도구 실행 **직후** | 실행 결과 로깅, 후처리 |
| `Stop` | 에이전트 실행 **종료 시** | 정리 작업, 결과 보고 |

```yaml
---
name: audited-coder
description: 모든 작업이 감사 로그에 기록되는 개발 에이전트
tools: Read, Write, Edit, Grep, Glob, Bash
hooks:
    PostToolUse:
    - matcher: Write
      command: "echo '[AUDIT] File written: $CLAUDE_FILE_PATH' >> .audit-log.txt"
    Stop:
    - command: "echo '[AUDIT] Agent session ended' >> .audit-log.txt"
---
```

**내 클로드 시스템에서 확인한 예시**

- 에이전트 스코프 훅은 없지만, **전역 스코프 훅은 실측된다.** `~/.claude/settings.json`에 9종이 등록되어 있다: `SessionStart`, `UserPromptSubmit`, `Stop`, `StopFailure`, `SubagentStart`, `SubagentStop`, `TeammateIdle`, `PreToolUse`(`matcher: "*"`), `PostToolUse`(`matcher: "*"`), `PostToolUseFailure`, `PermissionRequest`.
- 전부 `~/.orca/agent-hooks/claude-hook.sh` 한 스크립트를 가리키는 orca-cli 텔레메트리 훅이다. 교재의 3종(`PreToolUse`/`PostToolUse`/`Stop`)은 훅 이벤트 전체 중 일부다.
- 특히 **`SubagentStart`/`SubagentStop`은 서브에이전트 전용 이벤트**이고, **`TeammateIdle`은 에이전트 팀 전용 이벤트**다 (→ 4장 보강).

### 3.5 memory — 영속 메모리

`memory` 필드는 세션 간 학습한 내용을 유지하는 기능이다. 스코프는 `user` / `project` / `local`.

종합 예시:

```yaml
---
name: security-auditor
description: 보안 취약점 분석 전문가. 코드 보안 검토 필요시 사용
disallowedTools: Write, Edit
permissionMode: plan
memory: project
hooks:
    Stop:
    - command: "echo 'Security audit completed at $(date)' >> .security-audit-log.txt"
---

보안 감사 전문가로서 다음 역할을 수행합니다.

작업 시작 전:
- 메모리에서 이전 감사에서 발견된 취약점 패턴을 확인합니다.

감사 프로세스:
1. 대상 코드의 보안 취약점 분석
2. OWASP Top 10 기준 검토
3. 민감 정보 노출 확인

작업 완료 후:
- 새로 발견된 취약점 패턴을 메모리에 기록합니다.
```

**내 클로드 시스템에서 확인한 예시**

- 이 프로젝트의 메모리 디렉터리 `~/.claude/projects/-Users-jaeyoon-Desktop-Coding-claude-code-agent-study/memory/`는 **존재하지만 비어 있다.** 즉 `memory: project` 스코프가 쓰일 자리는 만들어져 있고, 아직 아무 에이전트도 쓰지 않았다.

### 3.6 skills 주입과 로딩 순서

`skills` 필드는 쉼표로 구분해 지정하고, **나열 순서가 곧 우선순위**다.

1. **일반 규칙 먼저, 특수 규칙 나중에** 배치 — 특수 규칙이 필요한 경우에만 오버라이드되도록.
2. **프로젝트 특화 규칙을 마지막에** 배치 — 범용 규칙을 프로젝트 규칙이 오버라이드하도록.

```
skills: moai-foundation-core, moai-lang-unified, moai-project-specific

# 로딩 순서:
# 1. moai-foundation-core   (최고 우선순위) - 기본 규칙
# 2. moai-lang-unified      (중간 우선순위) - 언어별 규칙
# 3. moai-project-specific  (낮은 우선순위) - 프로젝트 규칙
```

> ⚠️ **(확인 필요)** 원문의 두 서술이 서로 어긋난다.
> - 본문: "프로젝트 특화 규칙을 마지막에 배치. 범용성 있는건 마지막에 로드하여 **오버라이드**"
> - 코드 주석: "3. `moai-project-specific`(**낮은 우선순위**) - 프로젝트 규칙"
>
> "마지막 = 오버라이드(강함)"와 "마지막 = 낮은 우선순위(약함)"는 반대 방향이다. 현재 공식 문서도 `skills` 필드를 **"시작 시 서브에이전트 컨텍스트에 프리로드"** 라고만 설명할 뿐 나열 순서와 우선순위의 관계를 명시하지 않아 **문서로는 판정되지 않는다.** 어느 쪽으로도 단정하지 않고 미확정으로 남긴다.

**내 클로드 시스템에서 확인한 예시**

- `skills` 필드를 쓰는 에이전트 정의는 **내 시스템에 하나도 없다.** 앞서 본 대로 플러그인 9+6개 정의 전부 미사용.
- 대신 이 저장소는 **에이전트 없이 스킬만으로** 같은 목적을 달성한다. `.claude/skills/`에 9개(`pre-chapter-prep`, `pre-chapter-ideas`, `pre-tell-me-about-claude-code`, `mid-chapter-merge`, `mid-zettelkasten-synthesis`, `mid-study-deep-dive`, `mid-study-wrapup`, `mid-update-claude-code-docs`, `sync-claude-skills-to-codex`)가 있고, 서브에이전트는 0개다.
- **현재 버전 주의사항**: 서브에이전트 정의를 **에이전트 팀의 팀원으로** 쓰면 `skills`와 `mcpServers` 프론트매터는 **적용되지 않는다**(공식 문서 명시). 팀원은 프로젝트·사용자 설정에서 일반 세션과 동일하게 스킬을 로드한다. → 4장 보강 4.4

### 3.7 스킬 조합 방식

컨텍스트가 급격히 증가하므로 **토큰 효율성을 고려해 선별**해서 넣는다.

**기반 스킬 + 도메인 스킬** 조합:
- 기반 스킬 — 공통 규칙과 원칙
- 도메인 스킬 — 특정 분야 지식
- 예: `skills: moai-foundation-core, moai-security-patterns, moai-owasp-top10`

### 3.8 프롬프트 작성 가이드

- 너무 긴 프롬프트는 에이전트의 **주의를 분산**시킨다.
- **상충하는 지시**는 예측 불가능한 동작을 유발한다.
- **암묵적인 가정**은 오해를 부른다.
- 모든 지시는 **명시적이고 구체적**으로.

### 3.9 출력 포맷 지정

에이전트 출력 형식을 명시해 결과의 일관성과 활용도를 높인다 — JSON, 마크다운, 구조화된 텍스트 등.

**내 클로드 시스템에서 확인한 예시**

- `humanize-korean`이 출력 포맷을 파일명 단위까지 고정한 사례다. `humanize-diagnostician`은 "산출물은 `02_diagnosis.md` 1개", `humanize-finalizer`는 "`final.md` + `09_finalize.json`", `humanize-monolith`는 "`final.md` 1개(본문 끝에 `<!-- HUMANIZE-SUMMARY -->` HTML 주석 블록으로 메트릭 통합)". 다음 단계 에이전트가 읽을 것을 전제하면 포맷은 곧 인터페이스가 된다.

## 4. (교재 밖 보강) — 에이전트 팀 (agent teams)

> 이 절은 교재에 없다. 4장 1.6 "다중 클로드 워크플로"가 현재 클로드 코드에 **정식 기능으로 흡수된 결과**를 공식 문서 기준으로 정리한 것이다.
> 근거: 공식 문서 [Orchestrate teams of Claude Code sessions](https://code.claude.com/docs/en/agent-teams) (2026-08-27 조회, 문서 기준 v2.1.178 이후 동작)

### 4.1 한 줄 정의

여러 클로드 코드 인스턴스를 **하나의 팀**으로 묶어, 한 세션이 **팀 리드**로서 작업을 배분·통합하고 **팀원(teammate)** 들이 각자 독립 컨텍스트에서 일하며 **서로 직접 메시지를 주고받는** 기능. 실험 기능이며 **기본 비활성**이다.

교재의 다중 클로드 워크플로가 "사람이 터미널 여러 개를 띄우는 수동 패턴"이었다면, 에이전트 팀은 그 조율(태스크 분배·메시지·정리)을 **클로드 코드가 직접** 맡는다.

### 4.2 서브에이전트 vs 에이전트 팀 (← 이 장의 핵심 대비)

|  | **서브에이전트** | **에이전트 팀** |
| --- | --- | --- |
| **컨텍스트** | 자체 컨텍스트, 결과는 **호출자에게 반환** | 자체 컨텍스트, **완전 독립** |
| **통신** | 호출자에게 결과 반환 (이름 붙은 서브에이전트끼리는 메시지 가능) | 팀원끼리 **직접 메시지** |
| **조율** | **메인 에이전트가 전부 관리** | **자기 조율** — 메시지 + 공유 태스크 리스트 |
| **적합** | 결과만 중요한 초점형 작업 | **논의·협업**이 필요한 복잡한 작업 |
| **토큰 비용** | **낮음** — 결과가 요약되어 메인에 돌아옴 | **높음** — 팀원 하나하나가 별도 클로드 인스턴스 |

한 줄 정리: **빠르고 초점 잡힌 워커가 보고만 하면 되면 서브에이전트, 팀원끼리 발견을 공유하고 서로 반박하며 스스로 조율해야 하면 에이전트 팀.**

### 4.3 활성화

기본 꺼짐. 환경변수 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`로 켠다 (셸 또는 `settings.json`).

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

주의할 부작용이 하나 있다. **켜는 순간 평범한 위임의 동작도 바뀐다.** 클로드는 나중에 메시지를 보내려고 서브에이전트에 스스로 이름을 붙이는데, 에이전트 팀이 켜져 있으면 **이름 붙은 서브에이전트는 팀원으로 실행된다.** 즉 팀을 요청한 적이 없어도 팀이 생긴다. 서브에이전트는 결과를 반환하지만 팀원은 **"멈췄다"는 idle 알림만** 보내므로, 결과를 기다리는 오케스트레이션 흐름은 여기서 멈출 수 있다. 되돌리려면 값을 `0`으로 둔다.

또한 팀원 생성은 **대화형 세션에서만** 된다. `-p` 헤드리스 모드나 Agent SDK 세션에서는 팀이 켜져 있어도 이름 붙은 서브에이전트가 그냥 서브에이전트로 돈다.

### 4.4 구성 요소와 저장 위치

| 구성 요소 | 역할 |
| --- | --- |
| **팀 리드(team lead)** | 팀원을 스폰하고 작업을 조율하는 메인 세션 |
| **팀원(teammates)** | 배정된 작업을 수행하는 별도의 클로드 코드 인스턴스 |
| **태스크 리스트(task list)** | 팀원들이 **claim**해서 처리하는 공유 작업 목록 |
| **메일박스(mailbox)** | 에이전트 간 메시징 시스템 |

저장 위치 — 팀 이름은 `session-` + 세션 ID 앞 8자리로 **자동 생성**된다.

- 팀 설정: `~/.claude/teams/{team-name}/config.json` — **세션 종료 시 삭제**
- 메일박스: `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`
- 태스크 리스트: `~/.claude/tasks/{team-name}/` — **로컬에 남고 업로드되지 않음**(재개 세션이 태스크를 유지). 보존 기간은 세션 트랜스크립트와 같은 `cleanupPeriodDays`를 따른다.

태스크 claim은 **파일 잠금**으로 경쟁 조건을 막는다. 태스크는 pending / in progress / completed 3상태이고 **의존성**을 가질 수 있다 — 선행 태스크가 끝나야 claim 가능하고, 해제는 자동이다.

`config.json`은 세션 ID·tmux pane ID 같은 런타임 상태를 담으므로 **손으로 고치거나 미리 만들어두면 안 된다** (다음 상태 갱신에서 덮어써진다). 프로젝트 레벨 대응물은 없다 — `.claude/teams/teams.json`은 설정으로 인식되지 않는 그냥 파일이다.

### 4.5 서브에이전트 정의를 팀원으로 재사용 (← 3장과 이어지는 지점)

팀원을 스폰할 때 **기존 서브에이전트 타입을 이름으로 지목**할 수 있다. 역할을 한 번 정의해 **위임용 서브에이전트로도, 팀원으로도** 쓴다.

```
security-reviewer 에이전트 타입으로 팀원을 스폰해서 auth 모듈을 감사해 줘
```

동작 규칙:

- 정의의 `tools` 허용목록과 `model`은 **그대로 적용**된다.
- 정의의 **본문은 팀원 시스템 프롬프트를 대체하지 않고 뒤에 덧붙는다.**
- 인프로세스 팀원에게는 `SendMessage`가 허용목록에 자동 추가된다. Task 도구가 있는 세션이면 `TaskCreate`/`TaskGet`/`TaskList`/`TaskUpdate`도 추가된다.
- ⚠️ **`skills`와 `mcpServers` 프론트매터는 팀원으로 돌 때 적용되지 않는다.** 팀원은 일반 세션처럼 프로젝트·사용자 설정에서 스킬과 MCP를 로드한다. → **3.6의 "스킬 주입"은 서브에이전트에서는 되지만 팀원에서는 안 된다.**

### 4.6 실행 모드와 조작

- **in-process (기본)** — 팀원 전부가 메인 터미널 안에서 돈다. 프롬프트 아래 에이전트 패널에서 ↑↓로 선택, Enter로 그 팀원의 트랜스크립트를 열고 직접 메시지, Esc로 현재 턴 인터럽트, `x`로 정지, Ctrl+T로 태스크 리스트 토글.
- **split panes** — 팀원마다 독립 창. **tmux 또는 iTerm2(+`it2` CLI)** 필요. VS Code 통합 터미널·Windows Terminal·Ghostty는 미지원.
- 설정: `~/.claude/settings.json`의 `teammateMode` (`"in-process"` 기본 / `"auto"` / `"tmux"` / `"iterm2"`), 또는 `claude --teammate-mode auto`.
- 모델: 프롬프트에서 지정하지 않으면 **리드의 현재 모델**을 따른다(또는 `CLAUDE_CODE_SUBAGENT_MODEL`). `teammateDefaultModel`은 **v2.1.234에서 제거**됐다. effort는 리드를 상속한다.
- **플랜 승인 게이트**: "변경 전 플랜 승인을 요구해" 라고 하면 팀원이 읽기 전용 플랜 모드로 일하고, 리드가 승인/반려한다. 반려되면 팀원은 플랜 모드에 머물며 수정 후 재제출한다. **승인 판단은 리드가 자율적으로** 하므로, 기준("테스트 커버리지 없는 플랜은 반려")을 프롬프트로 줘야 한다.

### 4.7 권한 — 여기가 가장 중요하다

- 팀원은 **리드의 권한 설정을 그대로** 갖고 시작한다. 리드가 `--dangerously-skip-permissions`면 팀원 전부가 그렇다. 스폰 시점에 팀원별 모드 지정은 **불가**(스폰 후 개별 변경만 가능).
- 팀원의 권한 프롬프트는 **리드 세션에 뜬다.**
- **에이전트 간 메시지는 사용자 승인이 아니다.** `SendMessage`로 온 메시지는 "다른 클로드 세션에서 왔다"고 수신 측에 알려지며, 팀원은 사용자 대신 권한 프롬프트를 승인하거나 동의를 제공할 수 없다. **거부당한 팀원이 다른 팀원에게 시켜 우회하는 것도 막힌다.**
- auto 모드에서는 분류기가 (1) 다른 에이전트가 전달한 승인 주장을 **신뢰하지 않는 입력**으로 취급하고, (2) 배달 전 모든 메시지를 검사해 차단된 메시지는 수신자에게 도달하지 않는다.

### 4.8 훅으로 품질 게이트 걸기

| 훅 | 시점 | exit code 2의 효과 |
| --- | --- | --- |
| `TeammateIdle` | 팀원이 idle로 들어가기 직전 | 피드백을 보내고 **계속 일하게** 한다 |
| `TaskCreated` | 태스크 생성 시점 | 생성을 **막고** 피드백 전달 |
| `TaskCompleted` | 태스크 완료 표시 시점 | 완료를 **막고** 피드백 전달 |

### 4.9 운용 권고와 한계

**권고**
- 팀원은 CLAUDE.md·MCP·스킬은 자동 로드하지만 **리드의 대화 이력은 상속하지 않는다.** 스폰 프롬프트에 작업별 세부를 다 넣어야 한다.
- 팀 크기는 **3~5명**에서 시작. 독립 태스크 15개라도 3명이 좋은 출발점. 토큰은 선형 증가하고 조율 오버헤드는 그보다 빨리 는다.
- 태스크 크기는 "함수 하나, 테스트 파일 하나, 리뷰 하나"처럼 **자기완결 산출물** 단위. 팀원당 5~6개.
- **파일 충돌 회피**: 두 팀원이 같은 파일을 고치면 덮어쓴다. 팀원마다 다른 파일 집합을 소유하게 쪼갠다.
- 입문은 **리서치·리뷰**부터 (PR 리뷰, 라이브러리 조사, 버그 조사) — 병렬 탐색의 이득은 보고 병렬 구현의 조율 난이도는 피한다.

**한계 (실험 기능)**
- `/resume`·`/rewind`가 in-process 팀원을 **복원하지 못한다.** 재개 후 리드가 없는 팀원에게 말을 걸 수 있다.
- 태스크 상태가 **지연**된다 — 팀원이 완료 표시를 빠뜨려 의존 태스크가 막힐 수 있다.
- 종료가 느리다 (현재 요청·도구 호출을 끝내고 종료).
- **세션당 팀 하나.** 추가 팀 생성·팀 공유 불가.
- **중첩 팀 없음.** 팀원은 자기 팀원을 스폰할 수 없다.
- in-process 팀원은 **백그라운드 서브에이전트를 못 돌린다** (`background: true` 정의는 에러).
- **리드 고정.** 팀원을 리드로 승격하거나 리더십을 넘길 수 없다.

### 4.10 내 클로드 시스템에서 확인한 예시 (실측)

- **에이전트 팀은 꺼져 있다.** `~/.claude/settings.json`에 `env` 블록 자체가 없고, 이 세션 환경변수에도 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`가 없다.
- 그럼에도 **흔적은 이미 파일 시스템에 있다.**
  - `~/.claude/teams/` 디렉터리가 존재한다 (2026-08-11 생성). **내용은 비어 있다** — 문서가 말한 "변수가 없으면 팀 디렉터리가 기록되지 않는다"와 정확히 일치한다.
  - `~/.claude/tasks/session-4a0a2b53/`가 남아 있다. 문서의 태스크 리스트 경로 `~/.claude/tasks/{team-name}/`, 팀 이름 = `session-` + 세션 ID 앞 8자 규칙과 **형식이 정확히 일치**한다. "태스크 디렉터리는 세션이 끝나도 남는다"는 서술의 실물.
  - `~/.claude/settings.json`의 훅 목록에 **`TeammateIdle`이 등록되어 있다.** orca-cli가 심어둔 것으로, 에이전트 팀 전용 훅 이벤트가 이 버전에 실재함을 보여준다.
- **이번 장에서는 켜지 않기로 했다.** 켜는 순간 이름 붙은 서브에이전트가 전부 팀원으로 실행되는 부작용(4.3)이 있고 토큰도 크게 늘기 때문이다. 위 세 흔적(`teams/` 빈 디렉터리 · `tasks/session-*` 잔존 · `TeammateIdle` 훅)만으로도 문서 서술이 이 버전에서 실재함은 확인된다.
- **도입한다면 어디에**: 이 저장소의 스터디 워크플로에서 가장 자연스러운 자리는 `.claude/skills/mid-chapter-merge`(3인 정리본 병합)다. 사람 3명분 정리본을 팀원 3명이 각자 읽고 서로 반박하게 한 뒤 리드가 통합하는 구조가 문서의 "리서치·리뷰" 권장 용례에 정확히 들어맞는다. 단, 현재 이 저장소는 **서브에이전트조차 0개**이므로 순서상 서브에이전트를 먼저 거치는 게 맞다.

### 확정하지 않고 남긴 것 (미확정 목록)

발표에서 "모른다"고 말해야 하는 지점들이다.

1. **`skills` 나열 순서와 우선순위의 방향** — 원문 자체가 모순, 공식 문서로도 판정 불가. (3.6)
2. **`@code-reviewer(agent)` 표기의 실제 동작** — 현재 공식 문서 미확인, 실행 검증도 하지 않음. (2.2)
3. **서브에이전트 트랜스크립트 경로** `~/.claude/projects/{project}/{sessionId}/subagents/agent-{agentId}.jsonl` — 내 시스템 6개 프로젝트 전체에서 해당 파일·디렉터리 없음. 서브에이전트 실행 이력이 없어서일 가능성이 크며, **경로가 틀렸다는 근거는 아니다.** (2.4)
