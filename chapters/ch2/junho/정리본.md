# 2-1. 기본 작업 방식

## 2-1-1. 탐색 → 계획 → 구현 → 커밋 워크플로우

공식문서 [Best practices](https://code.claude.com/docs/en/best-practices)가 권장하는 4단계. 책의 서술과 동일하다.

| 단계 | 하는 일 | 모드/도구 |
|---|---|---|
| **Explore (탐색)** | 파일 읽고 구조 파악. 수정 없음 | Plan mode (`Shift+Tab`) |
| **Plan (계획)** | 변경 계획 문서화. `Ctrl+G`로 에디터에서 직접 수정 가능 | Plan mode |
| **Implement (구현)** | 계획 승인 후 코드 작성 + 테스트 실행 | acceptEdits / auto |
| **Commit (커밋)** | 커밋 메시지 작성, PR 생성 | Bash(git), `gh` |

```txt
# 1. 탐색 (plan mode)
read /src/auth and understand how we handle sessions and login.
also look at how we manage environment variables for secrets.

# 2. 계획
I want to add Google OAuth. What files need to change?
What's the session flow? Create a plan.

# 3. 구현 (plan 승인 후)
implement the OAuth flow from your plan. write tests for the
callback handler, run the test suite and fix any failures.

# 4. 커밋
commit with a descriptive message and open a PR
```

### 이 워크플로우의 핵심 전제
문서가 명시하는 **가장 중요한 제약은 컨텍스트 윈도우**다.

> "Most best practices are based on one constraint: Claude's context window fills up fast, and performance degrades as it fills."

즉 탐색/계획/구현을 나누는 이유는 "체계적이어서"가 아니라 **탐색으로 컨텍스트를 오염시키지 않고 구현에 들어가기 위해서**다.

### 계획을 건너뛰어야 할 때
문서가 명시적으로 경고한다. Plan mode는 오버헤드가 있다.
- 오타 수정, 로그 한 줄 추가, 변수명 변경 → **바로 시키기**
- 판단 기준: **"diff를 한 문장으로 설명할 수 있으면 계획을 생략하라"**
- 계획이 유용할 때: 접근법이 불확실할 때 / 여러 파일이 바뀔 때 / 익숙하지 않은 코드일 때

### 📌 검증 루프(verification loop)가 4단계보다 상위 개념
최신 문서는 4단계 워크플로우보다 **"Claude가 스스로 돌릴 수 있는 검증 수단을 줘라"**를 첫 번째 베스트 프랙티스로 올렸다.

> Claude는 "다 된 것처럼 보이면" 멈춘다. 검증 수단이 없으면 **사람이 검증 루프가 된다.**

검증을 거는 4가지 강도 (약 → 강):

| 방법 | 설명 |
|---|---|
| 프롬프트 안에서 | "테스트 돌리고 통과할 때까지 고쳐" 를 같은 메시지에 포함 |
| `/goal` 조건 | 별도 평가자가 매 턴마다 조건 충족 여부를 재검사, 충족될 때까지 계속 작업 |
| **Stop hook** | 스크립트로 검사, 통과 못 하면 턴 종료 자체를 차단 (연속 8회 차단되면 강제 종료) |
| 검증 서브에이전트 | 신선한 컨텍스트의 다른 모델이 결과를 반증 시도 |

📌 `/goal` 은 신규 기능. `/verify` 번들 스킬로 실제 앱 동작까지 확인 가능.

## 2-1-2. 탐색과 분석

### (1) `@` 참조 기능

파일/디렉터리/MCP 리소스를 **즉시 컨텍스트에 밀어 넣는다.** Claude가 Read 툴로 읽기를 기다릴 필요가 없음.

```txt
Explain the logic in @src/utils/auth.js      # 파일 전체 내용 포함
What's the structure of @src/components?      # 디렉터리 = 파일 목록만 (내용 X)
Show me the data from @github:repos/owner/repo/issues   # MCP 리소스
```

알아둘 동작:
- 상대/절대 경로 모두 가능
- `@` 입력 시 경로 자동완성 메뉴 → `Enter`/`Tab`으로 선택 후 `Enter`로 전송
- **⚠️ `@`로 파일을 참조하면 그 파일이 있는 디렉터리와 상위 디렉터리의 `CLAUDE.md`도 함께 컨텍스트에 들어온다** (모노레포에서 예상보다 컨텍스트가 커지는 원인)
- 한 메시지에 여러 개 가능: `@file1.js and @file2.js`
- 디렉터리 참조는 **파일 목록만** 보여준다 (내용 X)

### (2) 파일 탐색 방법

| 방식 | 언제 |
|---|---|
| 자연어 질문 | `find the files that handle user authentication` |
| 실행 흐름 추적 | `trace the login process from front-end to database` |
| `@` 참조 | 어느 파일인지 이미 아는 경우 |
| **서브에이전트 위임** | 탐색 범위가 넓을 때 (아래) |
| 📌 **Code intelligence 플러그인** | 타입 언어에서 심볼 단위 "정의로 이동 / 참조 찾기" |

📌 **Code intelligence는 신규**. LSP를 붙여서 grep 대신 정확한 심볼 네비게이션을 제공. 파일 통째로 읽는 걸 대체하므로 **오히려 컨텍스트를 줄인다**. `/plugin`에서 언어별로 설치.

**탐색은 서브에이전트에 위임하는 게 정석:**
```txt
use a subagent to investigate how our auth system handles token refresh
```
서브에이전트는 자기 컨텍스트에서 파일을 읽고 **요약만 반환**한다. 메인 대화는 깨끗하게 유지됨.

문서가 꼽는 대표적 실패 패턴:
> **The infinite exploration** — 범위를 안 정하고 "조사해봐"라고 하면 수백 개 파일을 읽어 컨텍스트를 다 태운다.
> → 범위를 좁히거나 서브에이전트를 쓸 것.

### (3) Plan mode로 안전하게 코드 분석

```bash
claude --permission-mode plan     # 시작할 때
# 또는 세션 중 Shift+Tab 반복 → 상태바에 "⏸ plan mode on"
# 또는 프롬프트 한 개만 /plan 접두어
```

Plan mode에서 되는 것 / 안 되는 것:
- ✅ 파일 읽기, 탐색용 셸 명령
- ❌ 소스 편집 (계획 승인 전까지 차단)

📌 **Plan mode 중 명령 실행 방식이 바뀌었다**
`useAutoModeDuringPlan` 설정(**기본값 on**)이 켜져 있고 auto mode를 쓸 수 있으면,
계획 중 셸 명령을 **사람에게 묻지 않고 classifier(별도 모델)가 심사**한다. 승인되면 실행, 거부되면 차단.
auto mode를 못 쓰면 read-only 명령 외에는 매번 승인 프롬프트.

**계획 승인 시 선택지 (📌 3지선다로 바뀜):**
1. `Yes, and use auto mode` — 승인 후 auto 모드로 진행 (auto 불가 시 "auto-accept edits"로 표시)
2. `Yes, manually approve edits` — 편집마다 개별 승인
3. `No, keep planning` — 계획 모드 유지, 수정 요청

부가 동작:
- `Ctrl+G` → 계획을 **내 에디터로 열어서 직접 수정** 후 진행
- 계획을 승인하면 세션에 **계획 기반 제목이 자동 부여**된다 (이름을 안 지어놨을 경우)
- `showClearContextOnPlanAccept` 설정을 켜면 "승인 + 계획 컨텍스트 비우기" 옵션이 추가된다

프로젝트 기본값으로 두려면:
```json
// .claude/settings.json
{ "permissions": { "defaultMode": "plan" } }
```

## 2-1-3. 점진적 개발 전략

### (1) 작업 범위의 명확한 정의

문서의 before/after 표가 핵심이다.

| 전략 | ❌ Before | ✅ After |
|---|---|---|
| **범위 지정** | "add tests for foo.py" | "write a test for foo.py covering the edge case where the user is logged out. avoid mocks." |
| **출처 지정** | "why does ExecutionFactory have such a weird api?" | "look through ExecutionFactory's git history and summarize how its api came to be" |
| **기존 패턴 참조** | "add a calendar widget" | "look at how existing widgets are implemented... HotDogWidget.php is a good example. follow the pattern..." |
| **증상 서술** | "fix the login bug" | "users report that login fails after session timeout. check src/auth/, especially token refresh. **write a failing test that reproduces the issue, then fix it**" |
| **검증 기준 제시** | "implement a function that validates email addresses" | "...example test cases: user@example.com is true, invalid is false. **run the tests after implementing**" |

단, 문서는 **모호한 프롬프트가 유용할 때**도 인정한다: `"what would you improve in this file?"` 처럼 탐색 단계에서 내가 못 떠올린 걸 발굴할 때.

### 📌 큰 기능은 "Claude가 나를 인터뷰"하게 한다
신규로 추가된 패턴. 스펙을 먼저 뽑고 새 세션에서 구현한다.

```txt
I want to build [기능 요약]. Interview me in detail using the AskUserQuestion tool.

Ask about technical implementation, UI/UX, edge cases, concerns, and tradeoffs.
Don't ask obvious questions, dig into the hard parts I might not have considered.

Keep interviewing until we've covered everything, then write a complete spec to SPEC.md.
```
- 스펙이 완성되면 **새 세션에서** 구현 → 구현용 컨텍스트가 깨끗함
- 좋은 스펙의 조건: 관련 파일/인터페이스 명시, **범위 밖(out of scope) 명시**, 마지막에 end-to-end 검증 단계

### (2) 피드백 루프 활용 — 빨리, 자주 교정

| 조작 | 효과 |
|---|---|
| `Esc` | 작업 중단. **컨텍스트는 유지**되므로 방향만 틀면 됨 |
| `Esc` `Esc` 또는 `/rewind` | rewind 메뉴 — 대화만/코드만/둘 다 복원, 또는 특정 시점부터 요약 |
| "Undo that" | Claude가 직접 되돌림 |
| `/clear` | 컨텍스트 전체 리셋 |

**문서의 2회 규칙:**
> 같은 문제로 **두 번 이상 교정했다면** 컨텍스트가 실패한 시도들로 오염된 상태다.
> → `/clear` 하고, 배운 걸 반영한 더 구체적인 프롬프트로 새로 시작하라.
> 깨끗한 세션 + 좋은 프롬프트가 긴 세션 + 누적된 교정보다 거의 항상 낫다.

**체크포인트(rewind)**
- 프롬프트를 보낼 때마다 자동으로 체크포인트 생성
- 파일은 편집 직전 스냅샷 → 코드까지 복원 가능
- **⚠️ Bash 명령이나 외부 프로세스로 바뀐 파일은 추적 안 됨. git 대체재가 아니다**
- 세션과 함께 저장되므로 터미널을 닫았다 재개해도 rewind 가능
- → "위험한 시도를 그냥 해보고 안 되면 되돌린다"는 전략이 가능해짐

### (3) 컨텍스트 관리

| 명령 | 동작 |
|---|---|
| `/clear` | 컨텍스트 완전 초기화 (이전 대화는 저장됨, `/resume`으로 복귀 가능) |
| `/compact [지시]` | 히스토리를 요약으로 치환. `/compact Focus on the API changes` 처럼 초점 지정 |
| `/context` | 지금 무엇이 컨텍스트를 차지하는지 확인 |
| 📌 `/btw` | **곁다리 질문**. 답변이 대화 히스토리에 남지 않음 → 컨텍스트를 안 늘리고 확인만 |
| 📌 `/recap` | 세션 요약을 터미널에 출력 (`/compact`과 달리 히스토리를 대체하지 않음) |
| `Esc Esc` → Summarize from/up to here | 대화의 **일부만** 요약 |

**CLAUDE.md로 압축 동작을 커스터마이즈 가능:**
```markdown
When compacting, always preserve the full list of modified files and any test commands
```

원칙:
- 관련 없는 작업 사이에는 **`/clear`**
- 자동 압축(auto-compact)을 기다리지 말고 **작업 경계에서 직접 `/compact`** (캐시 비용 이유는 2-4 참고)
- 조사 작업은 **서브에이전트**로 격리

### (4) TDD 기본 패턴

Claude Code에서 TDD가 잘 맞는 이유는 **테스트가 곧 검증 루프**이기 때문이다.

**패턴 A — 실패 테스트 먼저 (버그 수정)**
```txt
users report that login fails after session timeout.
write a failing test that reproduces the issue, then fix it
```

**패턴 B — 테스트 케이스를 프롬프트에 명시 (신규 구현)**
```txt
write a validateEmail function.
example test cases: user@example.com is true, invalid is false, user@.com is false.
run the tests after implementing
```

**패턴 C — 커버리지 보강 4단계**
```txt
1) find functions in NotificationsService.swift that are not covered by tests
2) add tests for the notification service
3) add test cases for edge conditions in the notification service
4) run the new tests and fix any failures
```

**패턴 D — Writer / Reviewer 분리 (세션 2개)**

| 세션 A (작성) | 세션 B (검토) |
|---|---|
| `Implement a rate limiter for our API endpoints` | |
| | `Review @src/middleware/rateLimiter.ts. Look for edge cases, race conditions, and consistency with our existing middleware patterns.` |
| `Here's the review feedback: [B의 출력]. Address these issues.` | |

같은 방식으로 **한 세션이 테스트를 쓰고, 다른 세션이 그 테스트를 통과시키는 코드를 쓰는** TDD도 가능.
신선한 컨텍스트가 자기가 쓴 코드에 대한 편향을 없앤다.

**패턴 E — 적대적 리뷰 단계 추가**
```txt
Use a subagent to review the rate limiter diff against PLAN.md. Check that
every requirement is implemented, the listed edge cases have tests, and
nothing outside the task's scope changed. Report gaps, not style preferences.
```
번들 스킬 `/code-review`를 쓰면 현재 diff를 신선한 서브에이전트가 리뷰한다.

> ⚠️ 문서 경고: "gap을 찾아라"고 지시받은 리뷰어는 **멀쩡한 코드에서도 뭔가를 찾아낸다.**
> 모든 지적을 다 반영하면 과잉 설계(불필요한 추상화, 방어 코드, 일어날 수 없는 케이스의 테스트)로 간다.
> → "정확성이나 명시된 요구사항에 영향을 주는 것만 지적하라"고 범위를 못박을 것.

**Claude가 스스로 증거를 제시하게 하기**
"됐습니다"가 아니라 **테스트 출력 / 실행한 명령과 결과 / 스크린샷**을 남기게 한다. 내가 다시 돌려보는 것보다 빠르고, 안 보고 있던 세션에도 적용된다.

## 2-1-4. Git 통합 워크플로우

### (1) Bash 도구로 git 직접 수행

Claude Code는 별도 git 통합 레이어 없이 **Bash 툴로 실제 git 명령을 실행**한다. 그래서 권한 설정이 곧 git 정책이 된다.

**읽기 전용 git은 기본적으로 승인 없이 실행된다.**
`git status`, `git log`, `git diff` 등은 내장 read-only 명령 집합에 포함.

**⚠️ 주의점 3가지 (문서가 명시)**
1. **`cd` + `git` 조합은 프롬프트가 뜬다** — 다른 디렉터리에서 git을 돌리면 그 디렉터리의 git hook이 실행될 수 있기 때문
2. **`Bash(git * main)` 같은 규칙은 위험** — `*`가 서브커맨드 자리에 오면 `git -c core.fsmonitor=<script> diff main` 같은 임의 실행까지 매칭된다. **와일드카드는 서브커맨드 뒤에** (`Bash(git log *)`)
3. **compound 명령은 각각 매칭돼야 한다** — `Bash(safe-cmd *)`가 있어도 `safe-cmd && other-cmd`는 통과 못 함

**실무 권한 예시:**
```json
{
  "permissions": {
    "allow": ["Bash(git diff *)", "Bash(git log *)", "Bash(git status *)", "Bash(git commit *)"],
    "ask":   ["Bash(git push *)"],
    "deny":  ["Bash(git push --force *)"]
  }
}
```

**PR 만들기**
```txt
create a pr for my changes
```
- `gh` CLI를 설치해 두면 이슈/PR/코멘트를 훨씬 컨텍스트 효율적으로 다룬다 (문서 권장)
- 📌 Claude가 `gh pr create` / `glab mr create`로 PR을 만들면 **세션이 그 PR에 링크된다**
  → 나중에 `claude --from-pr 1234` 로 그 PR 관련 세션만 필터링해서 재개 가능

📌 **커밋 attribution 설정** — `includeCoAuthoredBy`, `attribution.commit`, `attribution.pr`, `attribution.sessionUrl` 로 커밋/PR에 Claude 서명을 넣을지 제어. `includeGitInstructions`로 git 관련 시스템 지침 자체를 끌 수도 있음.

### (2) git worktree — 병렬 세션

📌 **`--worktree` 플래그가 내장되었다.** (예전엔 `git worktree add`를 수동으로 해야 했음)

```bash
claude --worktree feature-auth      # 또는 -w
claude -w feature-auth --tmux       # tmux 세션까지 함께 생성
```

동작:
- `<repo>/.claude/worktrees/<name>/` 에 생성, 브랜치는 `worktree-<name>`
- 이름 생략 시 `bright-running-fox` 같은 이름 자동 생성
- 다른 터미널에서 다른 이름으로 실행 → 완전히 격리된 병렬 세션
- 💡 `.gitignore`에 `.claude/worktrees/` 추가 권장

**PR에서 바로 워크트리 만들기 (📌 신규)**
```bash
claude --worktree "#1234"     # GitHub PR / GitLab MR 번호 또는 URL
```

**base 브랜치 선택**
```json
{ "worktree": { "baseRef": "head" } }   // 기본값 "fresh"(원격 기본 브랜치) / "head"(현재 로컬 HEAD)
```

**gitignore된 파일 자동 복사 — `.worktreeinclude`**
워크트리는 새 체크아웃이라 `.env` 같은 파일이 없다. 프로젝트 루트에 `.worktreeinclude`를 두면 자동 복사:
```text
.env
.env.local
config/secrets.json
```
(gitignore 문법. **gitignore된 파일만** 복사되므로 추적 파일이 중복되진 않는다.)

**격리 강제 (📌 신규)**
워크트리 세션에서 Claude Code가 **차단하는 것**:
- 메인 체크아웃 경로에 대한 `Edit`/`Write`/`NotebookEdit`
- 작업 디렉터리가 메인 체크아웃으로 해석되는 Bash/PowerShell 명령
- `git -C`, `--git-dir`, `GIT_DIR`, `cd` 후 git 등 **메인 체크아웃으로 git을 리다이렉트하는 명령**
- 추적 불가능한 셸 구문(브레이스 확장, 인용부호 없는 heredoc 등) → **끌 수 없음**

**정리**
- 인터랙티브 세션 종료 시: 워크트리가 깨끗하면 자동 삭제(이름 없는 세션), 작업이 남아 있으면 유지/삭제를 묻는다
- **`-p` 비대화형 실행은 종료 프롬프트가 없어 워크트리가 정리되지 않는다** → `git worktree remove` 수동 필요
- 서브에이전트/백그라운드 세션 워크트리는 `cleanupPeriodDays` 지나면 주기적으로 청소(작업이 남아 있으면 건너뜀)

**서브에이전트도 워크트리에 격리 가능 (📌 신규)**
```markdown
---
name: refactorer
description: Applies mechanical refactors across many files
isolation: worktree
---
```

**공유되는 것 / 안 되는 것**
- 공유: `.git` 디렉터리, 프로젝트 스코프 플러그인, **권한 승인("don't ask again")**
- 비공유: 파일, 브랜치, 의존성 설치 상태(직접 세팅 필요)

**git이 아닌 VCS**는 `WorktreeCreate` / `WorktreeRemove` 훅으로 대체 로직 작성 (SVN 예시가 문서에 있음).

### (3) 병렬 실행 방법 비교 (📌 선택지가 늘었다)

| 방식 | 특징 |
|---|---|
| **Worktrees** | 파일 격리. 터미널 여러 개 |
| **Desktop 앱** | 새 세션마다 워크트리 자동 생성, GUI 관리 |
| **Claude Code on the web** | 클라우드 VM에서 실행 |
| 📌 **Agent view** (`claude agents`) | 리서치 프리뷰. 백그라운드 세션을 한 화면에서 dispatch/모니터링 |
| 📌 **Agent teams** | 실험적, 기본 비활성. 태스크·메시징 공유하는 다중 세션 자동 조율 |
| 📌 **`/batch <instruction>`** | 변경을 5~30개 서브에이전트로 분할, 각자 워크트리에서 작업 후 PR 생성 |

## 2-1-5. `claude --continue` — 비대화형 모드에서의 세션 재개

### 기본 재개 명령

| 명령 | 동작 |
|---|---|
| `claude --continue` (`-c`) | 현재 디렉터리의 **가장 최근 인터랙티브 세션** 재개 |
| `claude --resume` (`-r`) | 세션 피커 열기 |
| `claude --resume <이름\|ID>` | 지정 세션 바로 재개 |
| `claude --from-pr <번호>` | 해당 PR에 링크된 세션만 필터링해 피커 열기 |
| `/resume` | 세션 안에서 다른 대화로 전환 |

### 비대화형(`-p`)과의 조합
```bash
# 첫 요청
claude -p "Review this codebase for performance issues"

# 이어서
claude -p "Now focus on the database queries" --continue
claude -p "Generate a summary of all issues found" --continue
```

세션 ID를 잡아두고 특정 대화만 이어가기:
```bash
session_id=$(claude -p "Start a review" --output-format json | jq -r '.session_id')
claude -p "Continue that review" --resume "$session_id"
```

### ⚠️ 헷갈리는 규칙 (문서에 명시)

| 상황 | `--continue` 대상에 포함? |
|---|---|
| `claude -p` / Agent SDK로 만든 세션 | ❌ 제외 (단 **`claude -p --continue`로 실행하면 포함**) |
| 백그라운드 세션 | ❌ 항상 제외 |
| 첫 프롬프트가 `/loop`인 세션 | ❌ 제외 (`-p --continue`면 포함) |
| `/add-dir`로 이 디렉터리를 추가한 세션 | ✅ 포함 |

- `-p`로 만든 세션은 **세션 ID로 `--resume`하면** 재개 가능
- 📌 `claude --resume <session-id>`는 **아무 디렉터리에서나** 동작 (v2.1.223+). 현재 프로젝트 → 워크트리 → 머신의 모든 프로젝트 순으로 탐색
- 재개할 세션이 없으면 `No conversation found to continue` 출력 후 종료

### 재개 시 복원되는 것 / 안 되는 것

**복원됨**: 대화 히스토리(툴 호출·결과 포함), 모델, `--agent`로 지정한 에이전트, 권한 모드, 활성 `/goal`, 만료 안 된 예약 작업

**복원 안 됨**:
- `plan`, `bypassPermissions` 모드 → **항상 새 세션 기본 모드로 시작**
- `--mcp-config`, `--settings`, `--plugin-dir`, `--fallback-model`, `--add-dir` → **재개할 때 다시 넘겨야 함**
- `settings.json` 류의 설정 파일은 launch 시 다시 읽으므로 재전달 불필요

📌 **Resume from a summary** (Pro/Max): 1시간 이상 방치 + 10만 토큰 초과 세션을 재개하면 3지선다 다이얼로그가 뜬다.
- `Resume from summary` — 즉시 `/compact` (이후 요청이 가벼워짐)
- `Resume full session as-is` — 전체 히스토리 유지 (요청마다 비쌈)
- `Don't ask me again`

### 세션 이름 붙이기 (병렬 작업 시 필수)
```bash
claude -n auth-refactor          # 시작할 때
/rename auth-refactor            # 세션 중
claude --resume auth-refactor    # 이름으로 재개
```
- 📌 이름을 안 붙이면 첫 프롬프트 기반 **제목을 Haiku급 모델이 자동 생성** → 이 제목으로도 `--resume` 가능
- 📌 같은 머신에서 이름이 겹치면 `auth-refactor-graceful-unicorn` 식 변형이 붙는다 (v2.1.232+)

### 세션 분기
```bash
/branch try-streaming-approach      # 세션 내부
claude --continue --fork-session    # CLI
```
원본은 그대로 남고 복사본에서 다른 접근을 시도할 수 있다.

### 트랜스크립트 위치
```
~/.claude/projects/<프로젝트경로-변환>/<session-id>.jsonl
```
- 기본 보존 30일 (`cleanupPeriodDays`)
- ⚠️ **JSONL 포맷은 내부 구현이라 버전마다 바뀐다.** 직접 파싱하지 말고 `/export`나 `claude -p --resume --output-format json` 사용

## 2-1-6. 파이프와 Claude

### 기본형
```bash
git log --oneline -20 | claude -p "summarize these recent commits"
cat build-error.txt | claude -p 'concisely explain the root cause' > output.txt
```
stdin/stdout이 일반 유닉스 도구처럼 동작한다.

⚠️ **파이프 stdin은 10MB 제한.** 넘으면 에러 + non-zero 종료. 더 큰 입력은 파일로 쓰고 경로를 프롬프트에 넘길 것.

### 출력 포맷
| 포맷 | 설명 |
|---|---|
| `text` (기본) | 평문 |
| `json` | `result`, `session_id`, `total_cost_usd`, 모델별 비용 등 메타데이터 포함 |
| `stream-json` | 줄 단위 JSON 이벤트 (실시간 처리) |

```bash
claude -p "Summarize this project" --output-format json | jq -r '.result'

# 스트리밍 텍스트만 뽑기
claude -p "Write a poem" --output-format stream-json --verbose --include-partial-messages | \
  jq -rj 'select(.type == "stream_event" and .event.delta.type? == "text_delta") | .event.delta.text'
```

### 📌 구조화 출력 — `--json-schema` (신규)
```bash
claude -p "Extract the main function names from auth.py" \
  --output-format json \
  --json-schema '{"type":"object","properties":{"functions":{"type":"array","items":{"type":"string"}}},"required":["functions"]}'
```
결과는 `structured_output` 필드에 담긴다.

### 📌 `--bare` 모드 (신규, 중요)
```bash
claude --bare -p "Summarize README.md" --allowedTools "Read"
```
훅/스킬/커맨드/서브에이전트/플러그인/MCP/auto memory/CLAUDE.md **자동 탐색을 전부 건너뛴다.**

왜 중요한가:
- CI/스크립트에서 **어느 머신에서 돌려도 같은 결과**를 보장
- 남의 저장소에서 `claude -p`를 그냥 돌리면 **그 저장소의 훅과 `.mcp.json` 서버가 신뢰 다이얼로그 없이 실행된다**
  → 신뢰하지 않는 저장소에서는 `--bare` 또는 `--setting-sources user` 사용
- ⚠️ bare 모드는 OAuth/키체인을 읽지 않는다 → `ANTHROPIC_API_KEY` 필요
- 📌 문서: **향후 `-p`의 기본값이 될 예정**

### 빌드 스크립트에 넣기
```json
{
  "scripts": {
    "lint:claude": "git diff main | claude -p \"you are a typo linter. for each typo in this diff, report filename:line on one line and the issue on the next. return nothing else.\""
  }
}
```
diff를 파이프로 넘기면 Claude가 Bash 권한 없이도 읽을 수 있다는 게 포인트.

### 대량 처리 (fan-out)
```bash
for file in $(cat files.txt); do
  claude -p "Migrate $file from Python 2 to Python 3. Return OK or FAIL." \
    --allowedTools "Edit,Bash(git commit *)"
done
```
2~3개로 프롬프트를 다듬은 뒤 전체 실행하라는 게 문서 권장.

### 시스템 프롬프트 커스터마이즈
```bash
gh pr diff "$1" | claude -p \
  --append-system-prompt "You are a security engineer. Review for vulnerabilities." \
  --output-format json
```

| 플래그 | 동작 |
|---|---|
| `--append-system-prompt` | 기본 프롬프트 **뒤에 추가** (툴 가이드·안전 지침 유지) |
| `--append-system-prompt-file` | 파일 내용을 추가 |
| `--system-prompt` | 기본 프롬프트 **전체 교체** (안전 지침도 사라짐) |
| `--system-prompt-file` | 파일로 전체 교체 |

### 비대화형에서의 권한
`-p`는 **모든 플랜에서 기본 권한 모드가 Manual(`default`)**이다. 그래서 명시가 필요하다:
```bash
claude -p "Run the test suite and fix any failures" --allowedTools "Bash,Read,Edit"
claude -p "Apply the lint fixes" --permission-mode acceptEdits
claude -p "run the test suite" --permission-mode dontAsk --allowedTools "Bash(npm test)" "Read"
claude --permission-mode auto -p "fix all lint errors"
```

📌 기타 유용한 `-p` 전용 플래그:
- `--max-turns N` — 에이전트 턴 수 제한
- `--max-budget-usd 5.00` — 지출 상한 (서브에이전트 지출 포함)
- `--no-session-persistence` — 트랜스크립트 미저장
- `--include-partial-messages`, `--forward-subagent-text` — 스트리밍 세부 제어

### 종료 코드
- 성공 `0`, 실패 non-zero
- SIGTERM으로 중단 시 `143` (진행 중이던 턴은 미완료로 남고, 재개하면 이어서 진행)
- 잘못된 플래그는 실행 전 stderr로, 실행 중 실패(인증 누락 등)는 stdout에 결과로 출력

# 2-2. 설정 관리

## 2-2-1. settings.json이란

Claude Code의 동작을 바꾸는 **JSON 키들의 집합**. 어떤 모델로 시작할지, 무엇을 묻지 않고 실행할지, 어떤 파일을 못 읽게 할지, 터미널 외형, 조직이 강제하는 정책까지 전부 여기서 정한다.

⚠️ **엄격한 JSON이다.** `//` 주석이나 trailing comma는 문법 에러 → 다음 실행 때 `Settings Error`.

**스키마 자동완성 붙이기:**
```json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  ...
}
```
(VS Code/Cursor 등에서 자동완성·검증. 다만 스키마가 최신 CLI보다 늦을 수 있어 경고가 떠도 무효는 아님)

### 설정 파일 4종 + 관리형

| 스코프 | 파일 | 적용 대상 | 용도 |
|---|---|---|---|
| **User** | `~/.claude/settings.json` | 나, 이 머신의 모든 프로젝트 | 테마, 에디터 모드, 기본 모델, 개인 권한 규칙 |
| **Shared project** | `.claude/settings.json` | 이 폴더에서 시작한 모두 (커밋해서 공유) | 팀 권한/훅/플러그인/환경변수 |
| **Project local** | `.claude/settings.local.json` | 나, 이 프로젝트만 | 개인 오버라이드, 공유 전 테스트 |
| **Managed** | `managed-settings.json`, MDM, claude.ai 콘솔 | 조직 전체 | 보안·컴플라이언스 정책 |

📌 **`~/.claude.json` 은 5번째 파일**이지만 Claude Code가 스스로 쓰는 파일이다. 로그인 세션, MCP 서버 설정, 프로젝트별 신뢰 결정, `/config`가 저장하는 global config 키들이 들어 있다. 직접 편집할 필요 없음.

**설치해도 설정 파일은 안 만들어진다.** 다음 시점에 자동 생성된다:
- `~/.claude/settings.json` — `/config` 메뉴에서 테마 같은 걸 처음 바꿀 때
- `.claude/settings.local.json` — 권한 프롬프트에서 "Yes, and don't ask again"을 처음 고를 때

📌 **`settings.local.json`은 자동으로 git에서 제외된다.** Claude Code가 git 저장소에서 이 파일을 처음 쓸 때 **전역 git excludes 파일**에 `**/.claude/settings.local.json`을 추가한다. (내가 직접 손으로 만들었다면 `.gitignore`에 직접 추가해야 함)

📌 **저장 위치가 저장소 루트로 바뀌었다 (v2.1.211+)**
서브디렉터리나 워크트리에서 시작해도 `.claude/settings.local.json`은 **저장소 루트**에서 읽고 쓴다.
→ 워크트리에서 준 권한 승인이 저장소 전체에 적용되고, 워크트리를 지워도 살아남는다.
예외(시작 디렉터리에 그대로 두는 경우): git 저장소 밖 / 저장소 루트가 홈 디렉터리 / **Windows** / 소유권 문제.

## 2-2-2. 설정 우선순위

```
1. Managed settings          ← 조직 (managed-settings.json / MDM / claude.ai 콘솔)
2. Command line              ← claude --settings, 이번 세션만
3. Project local             ← .claude/settings.local.json
4. Shared project            ← .claude/settings.json
5. User                      ← ~/.claude/settings.json
```
위가 아래를 덮어쓴다.

### 알아야 할 예외 4가지

**(1) 리스트는 덮어쓰지 않고 병합된다**
`permissions.allow` 등 배열 키는 여러 파일의 값이 **합쳐진다.** 단 예외:
- `fallbackModel` — 순서가 의미를 가지므로 최상위 파일의 값을 통째로 사용
- `modelPicker` — 병합 안 함. managed / `--settings` / user 중 최상위 값만
- `availableModels` — managed가 정의하면 그것만 적용(하위 무시), managed가 없으면 병합

**(2) 환경변수는 이 스택에 속하지 않는다**
키 쌍마다 규칙이 다르다.
- `ANTHROPIC_MODEL` — **어느 파일의 `model`보다 우선**
- `ANTHROPIC_DEFAULT_MODEL` — 파일에 `model`이 없을 때만 적용
- settings 파일의 `env` 블록은 일반 키라서 위 스택을 따른다

**(3) 보안 키는 "더 엄격한 값"이 이긴다 (📌 신규)**
관리형 설정보다 하위 스코프의 값이 이기는 예외 목록:

| 키 | 어느 값이 이기는가 |
|---|---|
| `disableClaudeAiConnectors` | 어느 스코프든 `true` |
| `isolatePeerMachines` | 어느 스코프든 `true` |
| `remoteControlAtStartup` | 프로젝트/로컬의 `false` |
| `crossSessionInbound` | 프로젝트/로컬의 더 엄격한 값 (`accept` < `hold` < `refuse`) |
| `useAutoModeDuringPlan` | managed/`--settings`/user/local의 `false` |
| `syncClaudeAiSkills` | 위와 동일 |

**(4) 저장소 파일에서는 아예 안 먹는 키가 있다**
[settings reference](https://code.claude.com/docs/en/settings-reference)의 Scope 열이 `User, local, or managed` / `User or managed` / `Managed` / `Global config`인 키는 **`.claude/settings.json`(공유 파일)에서 적용되지 않는다.**
그리고 `permissions.allow`, `permissions.additionalDirectories`, `extraKnownMarketplaces`, 대부분의 `env` 값은 **각자가 폴더를 신뢰(workspace trust)해야** 적용된다. `deny`와 `ask`는 즉시 적용.

### 설정을 바꾸는 3가지 방법
1. `/config` 메뉴 (개인 옵션 일부) / `/config verbose=true` 처럼 직접 지정도 가능
2. settings 파일 직접 편집
3. 세션 1회용: `claude --settings '{"model": "claude-opus-4-8"}'`, 전용 플래그(`--model`), 환경변수

### 언제 반영되는가
- 대부분 **파일 저장 즉시** 반영 (`permissions`, `hooks`, `apiKeyHelper` 포함). `ConfigChange` 훅도 발화
- **세션 시작 시 1회만 읽는 키**:
  - `model` → `/model`로 전환 (모델별 캐시가 달라 첫 요청이 비쌈, 2-4 참고)
  - `effortLevel` → `/effort`
  - `outputStyle` → `/clear` 또는 재시작 후 적용

### 확인/디버깅
| 명령 | 용도 |
|---|---|
| `/status` | `Setting sources` 줄에 로드된 설정 파일 목록. 관리형이면 전달 경로도 표시 |
| `claude doctor` | 거부된 항목/에러 상세 (세션 시작 없이 터미널에서) |
| `/doctor` | 세션 내 셋업 점검 + 자동 수정 제안 |
| `/context` | 컨텍스트에 실제로 로드된 것 확인 |
| `claude --safe-mode` | 모든 커스터마이즈 끄고 실행 (설정 문제 격리) |

⚠️ **`-p` 실행은 에러 다이얼로그를 안 띄운다.** 깨진 설정을 조용히 건너뛰므로, 실행 후 `claude doctor`로 확인해야 한다.

## 2-2-4. 프로젝트별 설정 전략

### 무엇을 어디에 둘 것인가

| 내용 | 위치 | 이유 |
|---|---|---|
| 팀 공통 권한(allow/ask/deny) | `.claude/settings.json` (커밋) | 클론하면 바로 적용 |
| 팀 훅, 텔레메트리, 플러그인 마켓플레이스 | `.claude/settings.json` | 위와 동일 |
| 내 모델/테마/에디터 모드 | `~/.claude/settings.json` | 모든 프로젝트에 적용 |
| 이 프로젝트에서만 나만의 예외 | `.claude/settings.local.json` | 커밋 안 됨 |
| 조직 보안 정책 | managed | 아무도 못 덮어씀 |

예: 팀이 `"model": "claude-sonnet-5"`로 정했는데 나는 Opus를 쓰고 싶으면
→ `.claude/settings.local.json`에 `"model": "claude-opus-4-8"`

```json
{

  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",

    "OTEL_EXPORTER_OTLP_PROTOCOL": "grpc",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "http://collector.example.com:4317"

      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-rm.sh" }
        ]
      }
    ]
  },
  "extraKnownMarketplaces": {
    "acme-tools": { "source": { "source": "github", "repo": "acme-corp/claude-plugins" } }
  },
  "enabledPlugins": { "code-formatter@acme-tools": true },
  "sandbox": {
    "enabled": true,
    "filesystem": { "allowWrite": ["/tmp/build"] },

```

### 커밋 전에 알아야 할 3가지
1. 📌 **클라우드 세션도 이 파일을 읽는다** — Claude Code on the web은 저장소 클론에서 시작하므로 공유 설정이 그대로 적용됨
2. **allow 규칙은 각자가 폴더를 신뢰해야 적용** — deny/ask는 신뢰 여부와 무관하게 즉시 적용
3. **훅은 저장소 안의 스크립트를 실행한다** — 위 예시의 `.claude/hooks/block-rm.sh`

### 📌 모노레포 전략
- 디렉터리별로 `CLAUDE.md`를 계층 배치 (하위는 그 디렉터리 파일을 읽을 때 로드)
- `claudeMdExcludes`로 다른 팀의 CLAUDE.md 제외
- 디렉터리별 스킬 배치
- 자세히는 [Monorepos and large repos](https://code.claude.com/docs/en/large-codebases)

## 2-2-5. 환경 변수 관리

### 두 가지 설정 방법

**(1) 셸에서** — 그 터미널 세션에만 적용
```bash
export API_TIMEOUT_MS="1200000"
claude
```

**(2) settings 파일의 `env` 블록** — `claude`를 어떻게 띄우든 적용
```json
{
  "env": {
    "API_TIMEOUT_MS": "1200000",
    "BASH_DEFAULT_TIMEOUT_MS": "300000"
  }
}
```

### ⚠️ 우선순위 함정
- **셸과 `env` 블록 둘 다 설정하면 → `env` 블록이 이긴다.** Claude Code가 시작 시(그리고 파일 변경 시) 프로세스 환경에 덮어쓴다
- **`env` 블록으로 변수를 "제거"할 수는 없다.** 셸 프로파일이 강제로 넣은 변수를 무력화하려면 빈 문자열로:
  ```json
  { "env": { "CLAUDE_CODE_USE_VERTEX": "" } }
  ```
- 셸 환경변수는 **시작 시 1회만** 읽는다 → 바꾸면 재실행 필요
- `env` 블록 값은 파일 저장 시 실행 중 세션에 반영. 단 **OpenTelemetry처럼 시작 시 1회만 읽는 기능은 재시작 필요**
- `env` 블록에서 변수를 **지워도** 실행 중 세션에서는 unset되지 않는다 (다음 실행부터)

### 📌 숫자 표기 (v2.1.211+)
`2e3` → 2000, `64_000` → 64000 처럼 지수/구분자 표기를 인식한다.
(⚠️ 예전 버전은 `1e6`을 1로 읽는 버그가 있었다. `CLAUDE_CODE_AUTO_COMPACT_WINDOW`처럼 **평문 정수만 받는** 변수도 있으니 각 항목 확인 필요)

### 자주 쓰는 변수

**모델**
| 변수 | 용도 |
|---|---|
| `ANTHROPIC_MODEL` | 세션 모델 (파일의 `model`보다 우선) |
| 📌 `ANTHROPIC_DEFAULT_MODEL` | 새 세션 기본 모델 (v2.1.236+) |
| `ANTHROPIC_DEFAULT_OPUS_MODEL` / `_SONNET_` / `_HAIKU_` / 📌 `_FABLE_` | 별칭이 가리킬 실제 모델 ID 고정 |
| `CLAUDE_CODE_SUBAGENT_MODEL` | 모든 서브에이전트/에이전트팀/워크플로우 모델 |
| `CLAUDE_CODE_EFFORT_LEVEL` | effort 레벨 (다른 모든 설정보다 우선) |

**타임아웃·한도**
| 변수 | 기본값 |
|---|---|
| `API_TIMEOUT_MS` | 600000 (10분) |
| `BASH_DEFAULT_TIMEOUT_MS` | 120000 (2분) |
| `BASH_MAX_TIMEOUT_MS` | 600000 |
| `BASH_MAX_OUTPUT_LENGTH` | 30000자 (최대 150000) |
| `MAX_THINKING_TOKENS` | `0`이면 thinking 끔 (Fable 5 제외) |

**컨텍스트·캐시**
`CLAUDE_CODE_AUTO_COMPACT_WINDOW`, `CLAUDE_CODE_DISABLE_1M_CONTEXT`, `CLAUDE_CODE_MAX_CONTEXT_TOKENS`, `DISABLE_PROMPT_CACHING*`, `ENABLE_PROMPT_CACHING_1H`, `FORCE_PROMPT_CACHING_5M`

**프라이버시·텔레메트리** (2-3에서 상세)
`DISABLE_TELEMETRY`, `DISABLE_ERROR_REPORTING`, `DISABLE_FEEDBACK_COMMAND`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, `CLAUDE_CODE_DISABLE_FEEDBACK_SURVEY`

**경로·저장**
`CLAUDE_CONFIG_DIR`, 📌 `CLAUDE_CODE_PROJECT_DIR_NAME`, `CLAUDE_CODE_SKIP_PROMPT_HISTORY`, `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD`

**서브프로세스 감지 (스크립트에서 유용)**
- `CLAUDECODE=1` — Claude Code가 띄운 모든 서브프로세스(Bash/훅/statusline/stdio MCP). IDE 통합 터미널도 설정함
- 📌 `CLAUDE_CODE_CHILD_SESSION=1` — Claude Code가 **직접** 띄운 서브프로세스만 (stdio MCP 제외). 중첩 세션 판별에 더 정확

## 2-2-6. 팀 표준 설정 구축 (CLAUDE.md, Skill)

### (1) CLAUDE.md

**위치별 스코프 (로드 순서 = 넓은 것 → 좁은 것)**

| 스코프 | 위치 | 공유 대상 |
|---|---|---|
| **Managed policy** | macOS `/Library/Application Support/ClaudeCode/CLAUDE.md`<br>Linux/WSL `/etc/claude-code/CLAUDE.md`<br>Windows `C:\Program Files\ClaudeCode\CLAUDE.md` | 조직 전체 (**제외 불가**) |
| **User** | `~/.claude/CLAUDE.md` | 나, 모든 프로젝트 |
| **Project** | `./CLAUDE.md` 또는 `./.claude/CLAUDE.md` | 팀 (커밋) |
| **Local** | `./CLAUDE.local.md` | 나, 이 프로젝트 (gitignore 필요) |

📌 `claudeMd` 키로 **managed-settings.json 안에 CLAUDE.md 내용을 직접** 넣을 수도 있다:
```json
{ "claudeMd": "Always run `make lint` before committing.\nNever push directly to main." }
```

**로드 방식**
- 작업 디렉터리 **및 그 상위 모든 디렉터리**의 CLAUDE.md를 로드 → **덮어쓰지 않고 전부 이어붙인다**
- 순서: 루트 → 작업 디렉터리 (가까운 게 나중에 = 마지막에 읽힘)
- 같은 디렉터리에서는 `CLAUDE.md` 다음에 `CLAUDE.local.md`
- **하위 디렉터리의 CLAUDE.md는 그 디렉터리 파일을 읽을 때 로드**
- 📌 `<!-- 주석 -->` 블록 HTML 주석은 컨텍스트에 넣기 전에 제거된다 → 사람용 메모를 토큰 소모 없이 남길 수 있음

**작성 원칙 (문서의 표를 그대로)**

| ✅ 넣을 것 | ❌ 뺄 것 |
|---|---|
| Claude가 추측 못 하는 Bash 명령 | 코드를 읽으면 알 수 있는 것 |
| 기본값과 다른 코드 스타일 규칙 | Claude가 이미 아는 표준 관례 |
| 테스트 방법, 선호하는 테스트 러너 | 상세 API 문서 (링크로) |
| 저장소 에티켓 (브랜치명, PR 관례) | 자주 바뀌는 정보 |
| 프로젝트 고유 아키텍처 결정 | 긴 설명, 튜토리얼 |

| 흔한 함정, 비직관적 동작 | "깨끗한 코드를 작성하라" 같은 자명한 것 |

- **목표: 200줄 이하.** 4 MiB 넘으면 아예 안 읽는다
- 각 줄마다 자문: *"이 줄을 지우면 Claude가 실수를 하나?"* 아니면 삭제
- **CLAUDE.md가 길면 Claude가 지시를 무시하기 시작한다** — 문서가 명시한 대표적 실패 패턴
- 한 줄만 강조하려면 그 줄에만 `IMPORTANT`. 여러 줄을 강조하면 아무것도 강조되지 않음
- `/init`으로 초기 생성 → 이후 다듬기
  📌 `CLAUDE_CODE_NEW_INIT=1` 설정 시 대화형 다단계 플로우 (CLAUDE.md/스킬/훅 중 선택 → 서브에이전트 탐색 → 검토 후 작성)
- 📌 `/doctor`가 **커밋된 CLAUDE.md의 축약안을 제안**한다 (코드에서 유추 가능한 내용 제거)

## 2-2-7. 민감한 파일 보호 — `permissions.deny`

```json
{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)",
      "Read(~/.ssh/**)",
      "Bash(curl *)"
    ]
  }
}
```

### 반드시 알아야 할 동작

**(1) 평가 순서는 deny → ask → allow. 먼저 매칭되는 것이 이긴다.**
- 넓은 deny(`Bash(aws *)`)는 좁은 allow(`Bash(aws s3 ls)`)까지 다 막는다 → **deny 규칙에 예외를 둘 수 없다**
- 어느 스코프에서든 deny면 다른 스코프의 allow가 이길 수 없다
- managed의 deny는 `--allowedTools`로도 못 뚫는다

**(2) 툴 이름만 쓰면 툴 자체가 사라진다**
- `"deny": ["Bash"]` → Claude의 컨텍스트에서 Bash 툴이 **제거**됨 (존재 자체를 모름)
- `"deny": ["Bash(rm *)"]` → 툴은 남고 매칭 호출만 차단
- 📌 `"deny": ["mcp__*"]` → 모든 MCP 툴 제거

**(3) ⚠️ `Read` deny는 Claude의 파일 툴과 Claude Code가 인식하는 Bash 파일 명령(`cat`, `head`, `tail`, `sed`)까지만 막는다**
> **파이썬/노드 스크립트가 직접 파일을 여는 것은 못 막는다.**
> OS 레벨로 막으려면 **샌드박스**(`sandbox.filesystem.denyRead`)를 켜야 한다.

**(4) 📌 `Read` deny는 Edit/Write까지 막는다** (v2.1.208+/v2.1.228+)
단 `NotebookEdit`은 제외 → 절대 못 바꾸게 하려면 `Edit` deny도 함께.

**(5) 경로 패턴 4종 — 앵커 위치가 다르다**

| 패턴 | 의미 | 예시 |
|---|---|---|
| `//path` | **파일시스템 루트**부터 절대 경로 | `Read(//Users/alice/secrets/**)` |
| `~/path` | 홈 디렉터리 기준 | `Read(~/Documents/*.pdf)` |
| `/path` | **설정 파일 소스 기준** (⚠️ 절대경로 아님) | 프로젝트 설정의 `Edit(/src/**)` = `<project root>/src/**` |
| `path`, `./path` | 현재 디렉터리 기준 | `Read(*.env)` |

⚠️ **`/Users/alice/file`은 절대 경로가 아니다.** 절대 경로는 `//`로 시작해야 한다.

`/path`가 가리키는 곳:

| 규칙이 정의된 곳 | `/path`가 해석되는 위치 |
|---|---|
| `.claude/settings.json` | `<project root>/path` |
| `.claude/settings.local.json` | `<원래 cwd>/path` |
| `~/.claude/settings.json` | **`~/.claude/path`** ⚠️ |
| `--settings <file>` | `<파일이 있는 디렉터리>/path` |

⚠️ 그래서 user settings의 `Read(/secrets/**)`은 `~/.claude/secrets/**`를 막지 프로젝트의 secrets를 막지 않는다. 모든 프로젝트에 적용하려면 `//` 또는 `~/`를 쓸 것.

**(6) allow와 deny의 깊이 매칭이 다르다**

| 규칙 | `src/app.ts` | `vendor/pkg/src/lib.js` |
|---|---|---|
| `Edit(src/**)` **allow** | ✅ | ❌ |
| `Edit(src/**)` **deny/ask** | ✅ | ✅ (어느 깊이든) |
| `Edit(/src/**)` | ✅ | ❌ |
| `Edit(**/src/**)` | ✅ | ✅ |

**(7) 심볼릭 링크**
- **allow**: 링크와 대상이 **둘 다** 매칭돼야 허용. 아니면 프롬프트
- **deny**: 링크 또는 대상 중 **하나만** 매칭돼도 차단

**(8) 📌 리다이렉션도 파일 쓰기로 검사한다**
`ls > out.txt`의 `out.txt`는 `Edit` 규칙 / protected path / working directory 검사를 받는다. `Bash(git commit *)` allow는 명령을 허용할 뿐 리다이렉트 대상을 허용하지 않는다. `/dev/null`은 검사 제외.

### ⚠️ URL 필터링은 Bash 패턴으로 하지 마라
문서가 명시적으로 경고한다. `Bash(curl http://github.com/ *)`는 다음을 못 막는다:
- 옵션이 앞에 오는 경우: `curl -X GET http://github.com/...`
- 프로토콜 차이: `curl https://...`
- 리다이렉트: `curl -L http://short.example.com/xyz`
- 변수: `URL=http://github.com && curl $URL`
- 공백: `curl  http://github.com`

**대신:**
1. `curl`, `wget`을 deny하고 `WebFetch(domain:github.com)` allow
2. PreToolUse 훅으로 URL 검증
3. CLAUDE.md 가이드 (강제력 없음 — 위 둘과 병행)

## 2-2-8. 도구별 설정 — 승인이 필요한 도구 / 필요 없는 도구

### 기본 승인 정책 (Manual 모드 기준)

| 툴 유형 | 예 | 승인 필요? | "don't ask again" 지속성 |
|---|---|---|---|
| **읽기 전용** | Read, Grep, Glob | ❌ (작업 디렉터리 + additionalDirectories 내) | 해당 없음 |
| **Bash** | 셸 실행 | ✅ (내장 read-only 명령 제외) | **저장소+명령 단위로 영구** |
| **파일 수정** | Edit / Write | ✅ | **세션 종료까지만** |
| **WebFetch** | 웹 페이지 | ✅ (사전승인 문서 도메인 제외) | 저장소+도메인 단위로 영구 |
| **WebSearch** | 웹 검색 | ✅ | 저장소 단위로 영구 |

### 승인 없이 실행되는 내장 read-only Bash 명령
`ls`, `cat`, `echo`, `pwd`, `head`, `tail`, `grep`, `find`, `wc`, `which`, `diff`, `stat`, `du`, `cd`, 그리고 **읽기 전용 형태의 `git`**
→ **이 목록은 설정으로 바꿀 수 없다.** 프롬프트를 띄우고 싶으면 `ask`/`deny` 규칙을 추가.

**단, 이 명령들도 프롬프트가 뜨는 예외:**
- 쓰기/실행 가능 플래그가 있는 명령(`find`, `sort`, `sed`, `git`)에 **인용 없는 glob**이 있을 때 (`-delete`로 확장될 수 있으므로)
- `docker`에 다른 데몬을 가리키는 플래그(`-H`, `--context`)가 있을 때
- `file`에 `-m`/`-f` 같은 경로 여는 플래그가 있을 때
- **Windows 네트워크(UNC) 경로**가 인자에 있을 때 (자격증명 유출 위험)
- **파싱 불가능한 명령** / 10,000자 초과 명령
- `cd` + `git` 조합 (다른 디렉터리의 git hook 실행 위험)
- `cd` + 출력 리다이렉트 (대상 경로 해석 불가)

### 래퍼 처리 (📌 알아둘 함정)
매칭 전에 **벗겨지는** 래퍼: `timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin`, zsh `noglob`, 플래그 없는 `xargs`
→ `Bash(npm test *)`가 `timeout 30 npm test`도 매칭

**⚠️ 벗겨지지 않는 것**: `direnv exec`, `devbox run`, `mise exec`, `npx`, `docker exec`
→ `Bash(devbox run *)`는 `devbox run rm -rf .`까지 허용해 버린다.
→ **런너와 내부 명령을 함께 명시**: `Bash(devbox run npm test)`

**exec 래퍼**(`watch`, `setsid`, `ionice`, `flock`)와 `find -exec`/`-delete`는 prefix 규칙으로 자동 승인 불가 → 정확한 전체 명령 규칙 필요

### 도구 자체를 제한하는 플래그
```bash
claude --tools "Bash,Edit,Read"          # 사용 가능한 내장 툴 자체를 제한
claude --tools ""                        # 전부 비활성
claude --disallowedTools "mcp__*"        # MCP 툴 전부 제거
claude --allowedTools "Bash(git log *)" "Read"   # 승인 없이 쓸 도구
```
⚠️ `--tools`는 **MCP 툴에는 영향이 없다** → MCP도 막으려면 `--disallowedTools "mcp__*"`

### 📌 입력 파라미터로 매칭 (신규)
deny/ask 규칙은 툴의 최상위 스칼라 파라미터로 매칭할 수 있다.
```json
{ "permissions": { "deny": ["Agent(model:opus)", "Agent(isolation:worktree)", "Bash(run_in_background:true)"] } }
```
- allow에는 못 쓴다 (파라미터 하나로 안전성을 판단할 수 없으므로)
- 한 규칙에 파라미터 하나. 두 개면 규칙 두 개
- ⚠️ 툴의 **주 콘텐츠 필드**(Bash의 `command`, Read의 `file_path` 등)로는 매칭 불가 — `Bash(command:rm *)`는 compound 명령으로 우회되므로 **무시되고 시작 시 경고**가 뜬다

### 서브에이전트 제어
```json
{ "permissions": { "deny": ["Agent(Explore)", "Agent(my-custom-agent)"] } }
```

### 📌 `Cd` 규칙 (신규)
`/cd` 명령으로 이동 가능한 디렉터리 제어. Claude가 호출하는 툴이 아니라 **내가 `/cd`를 칠 때만** 적용.
- `Cd` deny → `/cd` 자체 비활성
- `Cd` allow 규칙을 **하나라도** 추가하면 allowlist 모드로 전환

### 훅으로 권한 확장
`PreToolUse` 훅은 권한 프롬프트 **전에** 실행되며 deny/prompt/skip을 반환할 수 있다.

⚠️ 하지만 **훅이 권한 규칙을 우회하지는 못한다**:
- deny 규칙 매칭 → 훅이 `"allow"`를 반환해도 차단
- ask 규칙 매칭 → 훅이 `"allow"`를 반환해도 프롬프트

반대로 **훅의 차단은 allow 규칙을 이긴다**: 훅이 exit code 2로 끝나면 권한 규칙 평가 전에 호출이 중단됨.
→ **"Bash 전부 allow + 특정 명령만 훅으로 차단"** 패턴이 가능.

### 작업 디렉터리 확장
```bash
claude --add-dir ../apps ../lib
/add-dir <path>                              # 세션 중
```
```json
{ "permissions": { "additionalDirectories": ["../shared"] } }
```

📌 **⚠️ 중요한 차이**: 디렉터리 추가는 **파일 접근 권한만** 준다. 설정 루트가 되지는 않는다.

`--add-dir`(플래그/명령)로 추가한 디렉터리에서 로드되는 것:

| 설정 | 로드? |
|---|---|
| `.claude/skills/` | ✅ (라이브 리로드까지) |
| `.claude/commands/` | ✅ (라이브 리로드 X) |
| `.claude/agents/` | ✅ (라이브 리로드 X) |
| `.claude/settings*.json` | `enabledPlugins`, `extraKnownMarketplaces` 키만 |
| `CLAUDE.md`, `.claude/rules/` | ❌ (`CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` 필요) |

⚠️ **settings 파일의 `additionalDirectories`로 추가한 디렉터리는 위 예외도 적용 안 된다** — 순수 파일 접근만.

📌 `/cd`는 `/add-dir`와 다르다 — 세션의 **주 작업 디렉터리를 이동**시키고, 새 디렉터리의 CLAUDE.md를 로드하며, `--resume`도 거기서 찾게 된다.

## 2-2-9. 📌 다섯 가지 확장 도구 비교 (문서 기준으로는 9가지)

책은 5개(Skill / Subagent / MCP / Hook / Plugin)로 다루지만, 현재 문서는 확장 레이어를 더 넓게 정의한다.

### 전체 목록

| 기능 | 무엇을 하는가 | 언제 쓰는가 |
|---|---|---|
| **CLAUDE.md** | 매 대화에 로드되는 영구 컨텍스트 | 프로젝트 관례, "항상 X 하라" |
| **Skill** | 지식·워크플로우를 담은 마크다운 | 재사용 콘텐츠, 레퍼런스, 반복 작업 |
| **Subagent** | 격리된 컨텍스트에서 실행 후 요약 반환 | 컨텍스트 격리, 병렬 작업, 전문화 |
| **MCP** | 외부 서비스 연결 | 외부 데이터/액션 (DB, Slack, 브라우저) |
| **Hook** | 라이프사이클 이벤트에 스크립트/HTTP/MCP툴/프롬프트/서브에이전트 실행 | **예외 없이 매번** 실행돼야 하는 자동화 |
| **Plugin** | 위 요소들을 묶은 배포 단위 | 여러 저장소 재사용, 마켓플레이스 배포 |
| 📌 **Dynamic workflow** | Claude가 작성한 스크립트가 다수 서브에이전트를 백그라운드 실행 | 서브에이전트 몇 개로 안 되는 규모, 교차 검증 |
| 📌 **Cross-session messaging** | 내 세션 A → 세션 B로 메시지 전달 | 병행 세션 간 발견 공유 |
| 📌 **Code intelligence** | LSP 기반 심볼 탐색·진단 | 타입 언어, grep이 느리거나 부정확한 대형 코드베이스 |
| 📌 **Artifact** | 세션 결과를 인터랙티브 웹 페이지로 발행 | 시각적으로 보거나 공유해야 할 산출물 |

### 짝별 비교

**Skill vs Subagent**

| | Skill | Subagent |
|---|---|---|
| 정체 | 재사용 가능한 지시/지식/워크플로우 | 자기 컨텍스트를 가진 격리 워커 |
| 핵심 이점 | 컨텍스트 간 공유 | **컨텍스트 격리** — 요약만 돌아옴 |
| 컨텍스트 영향 | 메인 윈도우에 추가됨 | 별도 윈도우 (입출력 토큰 분리) |
| 적합 | 레퍼런스, 호출형 워크플로우 | 파일 많이 읽는 작업, 병렬 작업 |

> 결합 가능: 서브에이전트의 `skills:` 필드로 스킬 프리로드 / 스킬의 `context: fork`로 격리 실행

**CLAUDE.md vs Skill**

| | CLAUDE.md | Skill |
|---|---|---|
| 로드 | 매 세션 자동 | 필요할 때 |
| `@path` import | ✅ | ✅ |
| 워크플로우 트리거 | ❌ | ✅ `/<name>` |
| 적합 | "항상 X" 규칙 | 레퍼런스, 호출형 워크플로우 |

**MCP vs Skill** — 서로 보완재다.
- MCP = 외부 시스템에 대한 **연결과 툴** (인증까지 서버가 처리)
- Skill = 그 툴을 **잘 쓰는 방법에 대한 지식** (DB 스키마, 쿼리 패턴, Slack 메시지 포맷 규칙)

**Hook vs Skill** ← 실무에서 가장 중요한 구분

| | Hook | Skill |
|---|---|---|
| 실행 대상 | 셸 명령, HTTP 요청, MCP 툴 호출, LLM 프롬프트, 서브에이전트 | Claude가 읽고 따르는 지시문 |
| 트리거 | `PostToolUse`, `SessionStart` 등 **라이프사이클 이벤트** | `/<name>` 또는 Claude의 판단 |
| **결정성** | **항상 발화. 보장됨** | Claude가 해석 → 결과가 달라질 수 있음 |
| 컨텍스트 비용 | **0** (출력을 반환하지 않는 한) | description은 매 요청, 본문은 사용 시 |
| 적합 | 린트, 위험 명령 차단, 로깅, 알림 | 추론이 필요한 워크플로우, 레퍼런스 |

> **문서의 핵심 문장:**
> CLAUDE.md나 스킬의 `"never edit .env"`는 **요청**이지 보장이 아니다.
> `PreToolUse` 훅이 편집을 막는 것이 **강제(enforcement)**다.
> **매번 지켜져야 하는 규칙이면 프롬프트가 아니라 훅으로 만들어라.**

**Subagent vs Dynamic workflow (📌)**
- Subagent: Claude가 턴마다 다음에 뭘 할지 결정
- Dynamic workflow: **스크립트가 결정**. 코드베이스 전체 감사, 대규모 마이그레이션, 여러 각도의 계획 초안

### 계층이 겹칠 때 (같은 이름이 여러 레벨에 있을 때)

| 기능 | 병합 방식 |
|---|---|
| **CLAUDE.md** | **가산적** — 모든 레벨이 동시에 컨텍스트에 기여. 충돌 시 Claude가 판단(보통 더 구체적인 쪽 우선) |
| **Skill** | 이름으로 오버라이드: **managed > user > project** |
| **Subagent** | **managed > CLI 플래그 > project > user > plugin** |
| **MCP 서버** | **local > project > user** |
| **Hook** | **병합** — 매칭되는 모든 훅이 소스와 무관하게 전부 발화 |

### 컨텍스트 비용 비교

| 기능 | 로드 시점 | 무엇이 로드되나 | 비용 |
|---|---|---|---|
| CLAUDE.md | 세션 시작 | 전체 내용 | **매 요청** |
| Skills | 세션 시작 + 사용 시 | 시작 시 description만, 사용 시 전체 | 낮음 |
| MCP 서버 | 세션 시작 | 툴 이름만, 스키마는 지연 로드 | 사용 전까지 낮음 |
| Code intelligence | 편집 후/조회 시 | 진단, 심볼 위치 | 낮음 (**오히려 파일 읽기를 줄임**) |
| Subagents | spawn 시 | 격리된 새 컨텍스트 | **메인과 분리** |
| Hooks | 트리거 시 | 없음 (외부 실행) | **0** |

📌 **MCP tool search가 기본 on** → 안 쓰는 MCP 툴의 컨텍스트 비용이 거의 없다.
`/context all`로 로드된 MCP 툴별 토큰 수 확인 가능.

### 조합 패턴

| 패턴 | 예시 |
|---|---|
| Skill + MCP | MCP가 DB에 연결, 스킬이 스키마와 쿼리 패턴을 문서화 |
| Skill + Subagent | `/audit` 스킬이 보안/성능/스타일 서브에이전트를 병렬로 띄움 |
| CLAUDE.md + Skills | CLAUDE.md는 "우리 API 관례를 따르라", 스킬에 전체 스타일 가이드 |
| Hook + MCP | 편집 후 훅이 MCP로 Slack 알림 전송 |

## 2-3-1. IAM 개념 — Claude Code에서의 의미

일반적인 클라우드 IAM(사용자/역할/정책)과 대응시키면:

| 일반 IAM | Claude Code |
|---|---|
| 인증 (누구인가) | 구독 로그인 / Console API 키 / Bedrock·Vertex·Foundry 자격증명 / `forceLoginMethod`, `forceLoginOrgUUID` |
| 인가 (무엇을 할 수 있나) | `permissions.allow/ask/deny` 규칙 + **permission mode** |
| 정책 (누가 정하나) | 설정 파일 계층 (managed > CLI > local > project > user) |
| 최소 권한 경계 | 작업 디렉터리 + **샌드박스**(OS 레벨) |
| 감사 | OpenTelemetry 메트릭/이벤트, 클라우드 세션 감사 로그 |

**Claude Code IAM의 핵심 문장 (문서에서):**
> **권한은 Claude Code(클라이언트)가 강제한다. 모델이 아니다.**
> 프롬프트나 CLAUDE.md는 Claude가 **무엇을 시도할지**를 형성할 뿐, **무엇이 허용되는지**를 바꾸지 않는다.

📌 **인증 우선순위** (authentication 문서)
Anthropic 프로파일 / federation 자격증명 > `/login` 자격증명.
`ANTHROPIC_API_KEY`가 설정되어 있으면 구독보다 우선한다 (`-p`에서는 항상, 인터랙티브에서는 1회 승인 후).

📌 **CI용 장기 토큰**: `claude setup-token` (구독 필요, 저장하지 않고 출력만)

## 2-3-2. 도구별 권한 체계 (permission modes)

📌 **여기가 책과 가장 크게 달라진 부분이다.** 모드가 6개로 늘었고, **기본 모드가 바뀌었다.**

| 모드 | 묻지 않고 실행되는 것 | 적합 |
|---|---|---|
| `default` (**UI 표시명: Manual**) | 읽기만 | 모든 액션을 직접 검토, 민감한 작업 |
| `acceptEdits` | 읽기 + 파일 편집 + 일반 파일시스템 명령(`mkdir`,`touch`,`mv`,`cp`,`rm`,`rmdir`,`sed`) | 리뷰하며 반복 작업 |
| `plan` | 읽기 (+ auto mode 가능 시 classifier 승인 명령) | 변경 전 탐색 |
| 📌 `auto` | **거의 전부 — 단 백그라운드 안전성 검사 통과 시** | 긴 작업, 프롬프트 피로 감소 |
| 📌 `dontAsk` | 사전 승인된 도구만 (나머지는 **자동 거부**) | 잠긴 CI/스크립트 |
| `bypassPermissions` | 전부 | **격리된 컨테이너/VM 전용** |

📌 **이름 변경**: `default` 모드의 UI 표시명이 **"Manual"**로 바뀌었다. `claude --permission-mode manual`도 동작(v2.1.200+). 설정값과 훅/SDK에서는 여전히 `default`.

### 📌 기본 시작 모드가 auto가 되었다 (매우 중요)

**Pro / Max / Team 플랜의 터미널·VS Code 세션은 기본이 `auto` 모드다.** (v2.1.228+ / Windows v2.1.233+)

세션 시작 모드 결정 순서:
1. `--permission-mode` 플래그 / `--dangerously-skip-permissions`
2. 설정 파일의 `permissions.defaultMode`
3. 내장 기본값

내장 기본값 표:

| 조건 | 시작 모드 |
|---|---|
| 어느 설정 파일이든 `disableAutoMode: "disable"` | `default` |
| 피처플래그 fetch 꺼짐 / 설치·업그레이드 후 첫 세션 | `default` |
| **`claude -p` 또는 Agent SDK** | **`default`** |
| Bedrock / Agent Platform / Foundry / Claude Platform on AWS / gateway | `default` |
| **Pro, Max, Team — 터미널 또는 VS Code** | **`auto`** |
| Enterprise 플랜 또는 Console API 키 | `default` |

⚠️ **함정**: `.claude/settings.json`이나 `.claude/settings.local.json`의 `"defaultMode": "auto"`는 **적용되지 않는다** (v2.1.142+). `~/.claude/settings.json`으로 옮겨야 한다.

### 📌 auto mode — classifier가 사람을 대신한다

별도의 분류 모델(기본 **Claude Sonnet 5**)이 액션을 실행 전에 심사한다.

**심사 순서 (먼저 매칭되는 것이 이김):**
1. allow/ask/deny 규칙 → 즉시 결정
   (단 **protected path 쓰기와 critical path 삭제는 allow 규칙이 있어도 classifier로 감**)
2. 읽기 전용 + 작업 디렉터리 내 파일 편집 → 자동 승인
3. **나머지는 전부 classifier로**
4. classifier가 차단하면 Claude가 이유를 받고 대안을 시도

**classifier가 보는 것 / 못 보는 것**
- 본다: 사용자 메시지, 툴 호출(읽기 전용 조회 제외), **CLAUDE.md 내용**
- **못 본다: 툴 결과(stripped)** → 파일이나 웹페이지의 적대적 콘텐츠가 classifier를 직접 조작할 수 없음
- 별도의 서버측 probe가 툴 결과를 스캔해 의심 콘텐츠를 Claude가 읽기 전에 플래그

**기본 차단 항목 (일부)**
- `curl | bash` 류 다운로드 후 실행
- 민감 데이터를 외부 엔드포인트로 전송
- 프로덕션 배포/마이그레이션, 클라우드 스토리지 대량 삭제
- IAM/저장소 권한 부여, 공유 인프라 변경
- **force push**
- `git reset --hard`, `git checkout -- .`, `git restore .`, `git clean -fd`, `git stash drop/clear`
- 이번 세션에서 만들지 않은 커밋에 대한 `git commit --amend` / 이미 push된 커밋 amend
- `terraform/pulumi/cdk/terragrunt destroy`
- 시크릿을 저장소 밖으로 내보내는 커밋/푸시 (public 저장소 포함, 브랜치 무관)
- 시크릿 매니저 쓰기, DNS/TLS 인증서 변경
- 사람이 승인하지 않은 PR 머지, 자기 PR 승인, CI 체크 비활성화
- 프로덕션 피처플래그 토글/삭제
- 라이브 자격증명을 트랜스크립트나 파일에 출력
- `--insecure` 같이 안전장치를 끄는 플래그
- 보안 동작(인증/접근제어/입력검증/샌드박싱)을 지키는 테스트·어서션 주석 처리·삭제
- `git remote set-url`/`add`로 push 대상 변경 (내가 새 remote를 명시하지 않은 경우)
- 다른 저장소/조직으로의 PR, `gh repo fork`
- 📌 **Claude Code 자신의 트랜스크립트(`~/.claude/projects/*.jsonl`) 쓰기** (읽기는 허용)
- 📌 대화에서 값이 확인되지 않는 셸 변수 대상 `rm -rf "$VAR"`

**기본 허용 항목**
- 작업 디렉터리 내 로컬 파일 조작
- lock 파일/매니페스트에 선언된 의존성 설치
- `.env` 읽기 + 대응 API로 자격증명 전송
- 읽기 전용 HTTP 요청
- **작업 중인 저장소의 아무 브랜치로의 push** (기본 브랜치 포함). 단 `production`, `gh-pages` 처럼 배포 대상임이 이름에 드러나면 별도 판단
- 신뢰된 도메인/버킷/서비스로의 데이터 전송 (`autoMode.environment`에 등록한 것)

**📌 대화로 경계를 설정할 수 있다**
> "don't push" / "wait until I review before deploying" 라고 말하면 classifier가 **기본 규칙이 허용하는 액션도 차단**한다.
> 한 번 설정한 경계는 내가 해제할 때까지 유효. **Claude가 "조건이 충족됐다"고 판단해도 해제되지 않는다.**
>
> ⚠️ **단, 경계는 규칙으로 저장되지 않는다.** classifier가 매번 트랜스크립트에서 다시 읽으므로 **압축(compaction)으로 그 메시지가 사라지면 경계도 사라진다.**
> → 확실한 보장이 필요하면 **deny 규칙**을 쓸 것.

**auto mode에 들어가면 넓은 allow 규칙이 자동으로 무력화된다**
- `Bash(*)`, `PowerShell(*)` 통짜 allow
- `Bash(python*)` 같은 와일드카드 인터프리터
- 패키지 매니저 run 명령
- `Agent` allow 규칙, `Monitor` allow 규칙

`Bash(npm test)` 같은 좁은 규칙은 유지된다. auto mode를 나가면 복원.

**차단이 반복될 때 (fallback)**
- 연속 3회 또는 누적 20회 차단 → auto mode 일시정지, 프롬프트 재개 (**이 임계값은 설정 불가**)
- `/permissions`의 **Recently denied** 탭에서 `r`로 수동 승인 재시도
- **`-p` 실행에서는** 프롬프트할 곳이 없으므로 → 해당 액션은 실행되지 않고 **Claude는 계속 작업한다** (실행이 중단되지 않음)

**비용/지연**
- classifier는 기본 Sonnet 5. 세션 모델이 Sonnet 4.6이거나 `availableModels`가 Sonnet 5를 제외하면 세션 모델로 실행
- **Enterprise 플랜, API, Bedrock/Vertex/Foundry에서는 classifier 호출이 토큰 사용량에 포함된다**
- 읽기와 작업 디렉터리 편집은 classifier를 건너뛰므로 오버헤드는 주로 셸 명령·네트워크에서 발생

**서브에이전트도 3단계로 검사**
1. spawn 전: 위임된 태스크 설명을 평가
2. 실행 중: 각 액션을 부모와 같은 규칙으로 심사 (**서브에이전트 frontmatter의 `permissionMode`는 무시됨**)
3. 종료 시: 전체 액션 히스토리 리뷰 → 문제 발견 시 결과 앞에 보안 경고 추가

### 어떤 모드로도 자동 승인되지 않는 것
- 명시적 `ask` 규칙에 매칭된 툴
- 조직이 `ask`로 설정한 커넥터 툴
- `AskUserQuestion` 툴, `requiresUserInteraction` 표시된 MCP 툴
- **critical path 대상 `rm`/`rmdir`**
- 교차 세션 메시징 안전장치

### `bypassPermissions`의 실제 동작
- `--dangerously-skip-permissions`와 동일
- **세션 도중에 진입할 수 없다.** 시작할 때 활성화해야 함
- 첫 인터랙티브 실행 시 책임 동의 다이얼로그 (거절하면 종료). 이후 안 뜸
- **Linux/macOS에서 root/sudo로는 실행 거부됨** (인식된 샌드박스 안에서는 예외)
- Claude Code on the web은 설정 파일의 `bypassPermissions`/`dontAsk`를 **무시**한다 → 저장소 커밋으로 클라우드 세션을 bypass로 띄울 수 없음

## 2-3-3. 파일 및 명령 권한 설정

### 규칙 문법 요약
```
Tool                    # 모든 사용 (deny면 툴 자체 제거)
Tool(specifier)         # 세부 지정
Tool(param:value)       # 📌 입력 파라미터 매칭 (deny/ask 전용)
```

### 와일드카드 매칭 규칙 3가지

| 쓰는 것 | 매칭됨 | 매칭 안 됨 |
|---|---|---|
| `Bash(npm run build)` | `npm run build` | `npm run build --watch` |
| `Bash(npm run *)` | `npm run build`, `npm run test --watch`, `npm run` | `npm install` |
| `Bash(git log * main)` | `git log --oneline main`, `git log -5 main` | `git log main` |
| `Bash(git * main)` | `git merge main`, `git push origin main`, **`git -c core.fsmonitor=<script> diff main`** | `git log` |
| `Bash(* --version)` | `node --version`, **`bash -c 'echo hi' --version`** | `node -v` |
| `Bash(ls *)` | `ls -la`, `ls` | `lsof` |
| `Bash(ls*)` | `ls -la`, **`lsof`** | |

1. `*`는 그 자리의 아무 텍스트나 대신한다 → 서브커맨드 자리에 두면 위험
2. **끝에 있고 앞에 공백이 있는 `*`는 맨 명령도 매칭**한다 (`Bash(ls *)` → `ls`도 OK). 단 그게 유일한 와일드카드일 때만
3. **trailing `*` 앞의 공백은 규칙의 일부다** — `ls *`는 `lsof`를 매칭 안 하고 `ls*`는 매칭한다

`:*` 접미사는 trailing wildcard와 동일: `Bash(ls:*)` == `Bash(ls *)`
⚠️ `Bash(git:* push)`처럼 중간에 쓰면 콜론이 리터럴로 취급된다.

### compound 명령
인식되는 구분자: `&&`, `||`, `;`, `|`, `|&`, `&`, 개행
→ **각 서브커맨드가 독립적으로 매칭돼야 한다.** `Bash(safe-cmd *)`가 있어도 `safe-cmd && other-cmd`는 통과 못 함.

"don't ask again"으로 compound를 승인하면 **승인이 필요한 서브커맨드마다 별도 규칙**이 저장된다 (최대 5개).

### 환경변수 접두
- 알려진 안전 변수(`NODE_ENV=test` 등)는 벗겨짐 → `Bash(npm test *)`가 `NODE_ENV=test npm test` 매칭
- **allow 규칙은 그 외 변수 할당을 넘어 매칭하지 않는다**
- **deny/ask는 어떤 할당이든 넘어서 매칭한다** → `Bash(rm *)` deny가 `FOO=bar rm -rf tmp/`도 차단

### PowerShell
Bash와 같은 문법. 별칭이 정규화되므로 `PowerShell(Get-ChildItem *)`가 `gci`, `ls`, `dir`도 매칭. 대소문자 무시.

### WebFetch
```
WebFetch(domain:example.com)     # 정확히 그 호스트
WebFetch(domain:*.example.com)   # 모든 서브도메인 (example.com 자체는 제외)
WebFetch(domain:*)               # 모든 도메인 + 샌드박스 네트워크 허용목록에도 추가
WebFetch                         # 모든 도메인, 단 샌드박스 목록은 안 건드림
```
⚠️ `WebFetch(domain:example.*)`는 `example.org`는 매칭하지만 `example.evil.com`은 매칭 안 한다 (점을 넘지 않음).

`WebFetch` (bare) vs `WebFetch(domain:*)`:

| 규칙 | allow에서 | deny에서 |
|---|---|---|
| `WebFetch` | 묻지 않고 fetch. **샌드박스 허용 호스트는 그대로** | 툴 자체 제거 |
| `WebFetch(domain:*)` | 묻지 않고 fetch + **샌드박스가 모든 호스트 도달 가능** | 툴은 남고 모든 fetch 거부 + 샌드박스도 전 호스트 차단 |

⚠️ **WebFetch만 제한해도 네트워크가 막히지 않는다.** Bash가 허용되어 있으면 `curl`/`wget`으로 아무 URL이나 갈 수 있다.

### MCP
```
mcp__puppeteer                        # 그 서버의 모든 툴
mcp__puppeteer__*                     # 동일
mcp__puppeteer__puppeteer_navigate    # 특정 툴
mcp__*                                # (deny/ask에서만) 모든 MCP 툴
```
⚠️ allow 규칙의 글로브는 **`mcp__<server>__` 리터럴 접두 뒤에만** 허용된다. `"*"`나 `"mcp__*"` 같은 allow는 경고와 함께 무시된다.

### 📌 Protected paths (어떤 모드에서도 자동 승인 안 되는 쓰기 대상)

**디렉터리**: `.git`, `.config/git`, `.vscode`, `.idea`, `.husky`, `.cargo`, `.devcontainer`, `.yarn`, `.mvn`, `.claude` (단 `.claude/worktrees`는 예외)

**파일**: `.gitconfig`, `.gitmodules`, `.bashrc`/`.zshrc`/`.profile`/`.envrc` 등 셸 rc 파일 전부, `.npmrc`/`.yarnrc`/`bunfig.toml`, `.bazelrc`, `.pre-commit-config.yaml`/`lefthook.*`, `gradle-wrapper.properties`, `.devcontainer.json`, `.ripgreprc`, `pyrightconfig.json`, **`.mcp.json`, `.claude.json`**

모드별 동작:

| 모드 | protected path 쓰기 |
|---|---|
| `default`, `acceptEdits` | 프롬프트 |
| `plan` | (bypass 가능 세션이면 허용) auto 가능 시 classifier, 아니면 프롬프트 |
| `auto` | classifier로 |
| `dontAsk` | 거부 |
| `bypassPermissions` | 허용 |

⚠️ **`permissions.allow`의 `Edit(.claude/**)` 같은 규칙은 이걸 우회하지 못한다.** 안전 검사가 allow 규칙 평가보다 먼저 실행되기 때문.

### 📌 Critical paths (allow 규칙도, PreToolUse 훅의 "allow"도 통하지 않는 삭제)

`rm`/`rmdir` 대상이 다음이면:
- 파일시스템 루트, **루트의 직속 하위 디렉터리** (`/usr`, `/etc`, `/data`)
- **홈 디렉터리**
- Windows 드라이브 루트와 그 최상위 디렉터리 (`C:\`, `C:\Windows`)
- **작업 디렉터리와 그 상위 디렉터리들**
- 추가 작업 디렉터리와 상위 (단 `rm -rf <dir>/*` 형태의 glob일 때만)
- **셸 변수 바로 아래의 glob** (`rm -rf "$DIR"/*`) — 변수가 비면 루트 삭제가 되므로

⚠️ `$(...)`, 백틱, `<(...)` 안에 숨겨도 검사를 피하지 못한다.

모드별: `default`/`acceptEdits`/**`bypassPermissions`** → 프롬프트 / `auto` → classifier / `dontAsk` → 거부

📌 **PowerShell `Remove-Item`은 별도 검사**
- 시스템 경로 → **모든 모드에서 무조건 거부**
- 와일드카드(`*`, `/*`, `\*`, `$dir/*`) → **classifier에도 안 가고 즉시 거부**
- 작업 디렉터리/상위 + `-Recurse` → 일반 승인 흐름

## 2-3-4. 안전한 실행 환경 구축

### 📌 샌드박스 (책 출간 이후 대폭 확장된 영역)

권한이 **"Claude가 무엇을 시도할 수 있나"**를 정한다면, 샌드박스는 **"실행된 명령이 무엇에 도달할 수 있나"**를 OS 레벨에서 정한다.

```bash
/sandbox        # 세션 내에서 설정
```
```json
{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false,
    "filesystem": { "allowWrite": ["/tmp/build"], "denyRead": ["~/.ssh/**"] },
    "network": {
      "allowedDomains": ["registry.npmjs.org", "github.com"],
      "allowManagedDomainsOnly": true
    }
  }
}
```

- macOS / Linux / WSL2 지원
- **Bash 명령과 그 자식 프로세스에만** 적용 (다른 툴에는 X)
- **auto-allow 모드**: 샌드박스 안이면 프롬프트 없이 실행 (`autoAllowBashIfSandboxed`, 기본 true)
- 권한 규칙과 **합쳐진다**: `sandbox.filesystem` + Read/Edit deny 규칙 → 최종 경계
- 네트워크: `WebFetch(domain:...)` + `allowedDomains`/`deniedDomains` 결합
- **📌 Plan mode에서는 auto-allow 치환이 적용되지 않는다** (v2.1.212+)
- 📌 자격증명 마스킹 지원 (`sandbox.credentials.*`) — AWS 요청 재서명 등

### 권한 + 샌드박스 = 다층 방어
- **권한 deny**: Claude가 시도 자체를 못 하게
- **샌드박스**: 프롬프트 인젝션으로 Claude의 판단이 뚫려도, **Bash 명령이 경계 밖에 도달 못 하게**

문서의 명확한 경고:
> Read/Edit deny 규칙은 Claude의 내장 파일 툴과 인식 가능한 Bash 파일 명령까지만 막는다.
> **파이썬/노드 스크립트가 직접 파일을 여는 건 못 막는다. OS 레벨 강제가 필요하면 샌드박스를 켜라.**

### 격리 수준 선택

| 방법 | 격리 강도 | 비고 |
|---|---|---|
| Sandboxed Bash tool | 중 | 내장, 설정 간단 |
| 📌 Sandbox runtime | 중상 | 무인 실행용 런타임 |
| Dev container | 상 | `/docs/en/devcontainer` 참조 구성 존재 |
| 커스텀 컨테이너 / VM | 최상 | `--dangerously-skip-permissions` 실행 시 **필수** |
| Claude Code on the web | 상 | Anthropic 관리 VM, 네트워크 프록시 경유 |

### 완전 무인 실행의 정석
```bash
claude -p "<prompt>" --dangerously-skip-permissions
```
**전제 조건 (문서가 "Required"로 명시)**: 컨테이너/VM/샌드박스 런타임 + Linux·macOS는 **non-root 사용자**로 실행.

### CI를 위한 잠긴 구성
```bash
claude -p "run the test suite" \
  --permission-mode dontAsk \
  --allowedTools "Bash(npm test)" "Read"
```
`dontAsk`는 프롬프트를 기다리지 않고 **바로 거부**하므로 CI가 멈추지 않는다.

## 2-3-5. 권한 문제 해결

### 증상별 진단

**① 설정한 값이 무시된다**
- 상위 레벨이 같은 키를 설정 → `/status`의 `Setting sources` 확인
- 환경변수/플래그가 그 키를 덮어씀 → settings-reference의 해당 키 항목 확인
- 보안 키라서 더 엄격한 값이 유지됨 (2-2-2의 예외 표)
- **설정 파일이 깨짐** → `claude doctor`

**② `Yes, and don't ask again`을 했는데 계속 물어본다**
→ 그 선택은 **로컬 파일에 allow 규칙**을 저장한다. 그런데 **로컬의 allow는 프로젝트/관리형의 ask 규칙을 이기지 못한다.**
(deny → ask → allow 순서를 기억할 것)
📌 VS Code 확장은 승인 카드에서 **저장할 파일을 선택**할 수 있다(프로젝트 공유 파일 포함). CLI는 로컬 파일에만 쓴다.

**③ 커밋한 설정이 팀원에게 안 먹는다**
두 가지 원인:
- **저장소 파일에서는 무시되는 키**다 (Scope 열이 `User, local, or managed` 등)
- **워크스페이스 신뢰 대기 중**이다 — `permissions.allow`, `additionalDirectories`, `extraKnownMarketplaces`, 대부분의 `env`는 각자가 폴더를 신뢰해야 적용. **deny/ask는 즉시 적용**

**④ 관리형 설정 변경이 반영 안 됨**
→ 세션을 재시작. 그래도 `/status`가 다른 소스를 가리키면 우선순위 높은 소스가 있는 것

**⑤ 승인 프롬프트에 "don't ask again" 옵션이 안 보인다**
프롬프트가 **허용 범위를 전부 보여줄 수 없을 때** 옵션이 빠진다:
- 명령/편집이 너무 커서 전부 표시 불가
- 규칙이 커버할 명령/경로가 라벨에 다 안 들어감
- 시작 디렉터리 경로가 너무 길거나 표시 불가 문자 포함
→ 1회 승인하거나 `/permissions`에서 직접 규칙 추가

**⑥ 시작 시 경고가 뜬다**
- `has a wildcard before the rest of the command` → `Bash(git * main)` 같은 위험한 allow 규칙
- `is not matched by file permission checks` → `Write(...)`, `Glob(...)` 등 참조되지 않는 경로 규칙. **`Edit(...)`, `Read(...)`만 파일 경로 검사에 쓰인다**
- deny/ask의 툴 이름이 알려진 툴과 불일치 → 오타 탐지

⚠️ **툴 표시명과 정규 이름이 다를 수 있다.** 트랜스크립트에 `Stop Task`로 보이는 툴의 정규명은 `TaskStop`. 권한 규칙과 훅 matcher는 **정규명만** 매칭한다. → [tools-reference](https://code.claude.com/docs/en/tools-reference) 확인.

### 유용한 진단 명령
```bash
claude doctor                     # 설정/설치 진단 (세션 없이)
claude --safe-mode                # 모든 커스터마이즈 끄고 실행
claude auto-mode defaults         # auto mode 기본 규칙 전체를 JSON으로 출력
claude auto-mode config           # 내 설정이 적용된 실효 config
claude --verbose                  # 툴 호출의 실제 파라미터 이름/값 확인
```
세션 내: `/permissions`, `/status`, `/context`, `/doctor`, `/hooks`

📌 **권한 프롬프트에서 `Ctrl+E`** → 그 명령이 무엇을 하고 왜 실행되며 뭐가 잘못될 수 있는지 설명 + **Low/Med/High risk** 라벨. (누를 때만 모델 호출)
`permissionExplainerEnabled: false`로 끌 수 있다.

📌 **승인/거부에 코멘트 달기**: 프롬프트에서 Yes/No로 이동 후 `Tab` → 코멘트 입력.
- Yes + 코멘트 → 실행 후 코멘트를 Claude에게 전달
- No + 코멘트 → 거부 사유로 전달되고 **Claude가 계속 작업** (코멘트 없이 No면 턴이 종료됨)

## 2-3-6. 보안 유의 사항

### 프롬프트 인젝션 방어 (문서의 목록)
- **권한 시스템** — Manual에서 민감 작업은 명시적 승인
- **컨텍스트 인지 분석** — 요청 전체를 보고 유해 지시 탐지
- **입력 새니타이즈**
- **네트워크 명령 승인** — `curl`, `wget`은 기본 자동승인 안 됨
- **격리된 컨텍스트 윈도우** — WebFetch는 별도 컨텍스트에서 실행
- **신뢰 검증** — 첫 실행 저장소, 새 MCP 서버는 신뢰 확인
  ⚠️ **`-p`로 실행하면 신뢰 검증이 비활성화된다**
  ⚠️ 홈 디렉터리에서 시작하면 신뢰가 디스크에 저장되지 않아 매번 다시 묻는다 (지속 설정 없음)
- **명령 인젝션 탐지** — 의심스러운 bash는 allowlist에 있어도 수동 승인
- **fail-closed 매칭** — 매칭 안 되면 승인 필요
- **자격증명 저장** — macOS Keychain, Windows/Linux는 파일 권한

⚠️ **Windows WebDAV 경고**: WebDAV 활성화나 `\\*` 경로 접근 허용은 권한 시스템을 우회한 네트워크 요청을 유발할 수 있다.

### 신뢰하지 않는 콘텐츠 다룰 때 (문서 권장 5가지)
1. 승인 전에 제안된 명령을 검토
2. **신뢰하지 않는 콘텐츠를 Claude에 직접 파이프하지 말 것**
3. 중요 파일 변경은 검증
4. 외부 웹서비스와 상호작용할 때는 **VM 사용**
5. 의심스러운 동작은 `/feedback`으로 신고

### ⚠️ 남의 저장소에서 `claude -p`를 돌리기 전에

`-p` 실행은 **신뢰 다이얼로그도, MCP 서버 승인 프롬프트도 뜨지 않는다.**

| 저장소가 제공하는 것 | 부모 폴더만 신뢰한 경우 | `claude -p` / SDK (폴더 미신뢰) |
|---|---|---|
| settings의 **훅**, `env` 블록, `apiKeyHelper`, 프로젝트 스킬의 훅/`allowed-tools` | **실행됨** | **실행됨** |
| `permissions.allow`, `additionalDirectories` | 미적용 (다이얼로그 재표시) | 미적용 (stderr 경고) |
| 서브에이전트 frontmatter 훅, `@skills-dir` 플러그인, `extraKnownMarketplaces` | 미적용, 다이얼로그도 없음 | 미적용 |
| **`.mcp.json` 서버** | 연결 전 물어봄 | **묻지 않고 연결됨** |
| MCP `headersHelper` | 신뢰 전까지 미실행 | 미실행 (경고) |

**대응책 (하나 이상 적용):**
```bash
claude -p --setting-sources user "..."                    # 프로젝트 설정/.mcp.json 무시
claude --bare -p "..."                                    # 훅/스킬/커맨드/서브에이전트/플러그인/.mcp.json 전부 스킵
claude -p --settings '{"disableAllHooks": true}' "..."    # 훅만 끄기
```
⚠️ `disableAllHooks`를 **user settings에만** 넣는 건 소용없다. 프로젝트 설정이 우선이라 다시 `false`로 되돌릴 수 있기 때문. **`--settings`로 넘겨야 한다.**

수동으로 폴더를 신뢰시키려면 `~/.claude.json`의 `projects["<path>"].hasTrustDialogAccepted`를 `true`로.

### MCP 보안
> Anthropic은 커넥터를 디렉터리에 올리기 전 **listing criteria로 검토**하지만, **어떤 MCP 서버도 보안 감사하거나 관리하지 않는다.**
→ 직접 만들거나 신뢰하는 제공자의 것만 사용.

### 팀 보안 체크리스트
- 관리형 설정으로 조직 표준 강제
- 승인된 권한 구성을 버전 관리로 공유
- OpenTelemetry로 사용 모니터링
- 📌 **`ConfigChange` 훅으로 세션 중 설정 변경을 감사하거나 차단**
- `/permissions`로 정기 감사
- 민감 저장소는 프로젝트별 권한 설정
- 📌 `/security-review` 명령, `security-guidance` 플러그인, `claude-security` 플러그인 활용

### 취약점 신고
공개하지 말고 [HackerOne 프로그램](https://hackerone.com/4f1f16ba-10d3-4d09-9ecc-c721aad90f24/embedded_submissions/new)으로.

## 2-3-7. 권한 설정 실무 예시

### ① 개인 개발 — 프롬프트 줄이면서 통제 유지
```json
// ~/.claude/settings.json
{
  "permissions": {
    "allow": ["Bash(npm run lint)", "Bash(npm run test *)", "Bash(git diff *)", "Bash(git log *)"],
    "deny":  ["Read(./.env)", "Read(./.env.*)", "Read(~/.ssh/**)"]
  }
}
```
+ `/sandbox`에서 auto-allow 모드 → classifier 없이도 프롬프트가 대폭 줄어든다.

### ② 팀 공유 — 안전망 중심
```json
// .claude/settings.json (커밋)
{
  "permissions": {
    "allow": ["Bash(npm run *)"],
    "ask":   ["Bash(git push *)"],
    "deny":  ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)", "Bash(git push --force *)"]
  }
}
```
포인트: **deny/ask는 신뢰 없이도 즉시 적용**되므로 안전망을 여기에 둔다.

### ③ CI — 정확한 allowlist
```bash
claude -p "run the test suite and report failures" \
  --bare \
  --permission-mode dontAsk \
  --allowedTools "Bash(npm test)" "Read" \
  --output-format json \
  --max-turns 10
```

### ④ 컨테이너 무인 실행
```bash
# 반드시 컨테이너/VM 안, non-root로
claude -p "<prompt>" --dangerously-skip-permissions
```

### ⑤ 조직 관리형 설정 (`managed-settings.json`)
```json
{
  "forceLoginMethod": "claudeai",
  "forceLoginOrgUUID": ["xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"],
  "availableModels": ["opus", "sonnet"],
  "enforceAvailableModels": true,
  "permissions": {
    "deny": ["Bash(curl *)", "Read(./.env)", "Read(./secrets/**)"],
    "disableBypassPermissionsMode": "disable"
  },
  "allowManagedPermissionRulesOnly": true,
  "allowedMcpServers": [{ "serverUrl": "https://api.githubcopilot.com/*" }],
  "allowManagedMcpServersOnly": true,
  "strictKnownMarketplaces": [{ "source": "github", "repo": "acme-corp/approved-plugins" }],
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false,

}
```

📌 관리형 전용 키(managed에서만 유효): `allowManagedPermissionRulesOnly`, `allowManagedMcpServersOnly`, `allowManagedHooksOnly`, `disableSideloadFlags`, `policyHelper` 등
📌 `disableBypassPermissionsMode`는 **어느 스코프에서든** 동작한다 — 개인이 자기 자신을 잠글 수도 있다.

📌 **auto mode 신뢰 인프라 등록** (`autoMode.environment`) — 조직의 신뢰 저장소/버킷/서비스를 등록해 false positive를 줄인다.
`/auto-mode-setup`으로 초안 생성 가능. `/permissions`의 Auto mode 탭에서 편집.

📌 **전달 방식별 도달 범위**

| 전달 방식 | CLI/IDE | Desktop 로컬 | 웹·모바일·클라우드 | SDK/비대화형 |
|---|---|---|---|---|
| **Server-managed** (claude.ai 콘솔) | ✅ | ✅ | ✅ | ✅ |
| **MDM / managed-settings.json** | ✅ | ✅ | ❌ (자체 호스팅 환경은 예외) | ✅ |

- 제출 전 포함 범위 선택: 현재 세션(기본) / 같은 프로젝트의 24시간 / 7일

- 📌 third-party provider 사용 시엔 전송 대신 `~/.claude/feedback-bundles/`에 로컬 아카이브 생성 (API 키/토큰 패턴은 마스킹됨)

### 📌 세션 품질 설문 (신규)
"How is Claude doing this session?" 프롬프트:
- **평점만 기록된다.** 대화 내용/입출력은 수집하지 않음
- 그 뒤에 별도로 뜨는 "트랜스크립트를 봐도 되나?"는 **완전히 별개의 2단계**:
  - **Yes** → 대화 트랜스크립트 + 서브에이전트 트랜스크립트 + **디스크의 원본 세션 로그**를 업로드. 알려진 API 키/토큰 패턴만 마스킹, **소스코드와 파일 내용은 그대로 업로드된다.** 최대 6개월 보존
  - No / Don't ask again
- **명시적으로 Yes를 선택하지 않으면 아무것도 업로드되지 않는다**
- 이 설문 응답은 **학습에 사용되지 않는다**
- 끄기: `CLAUDE_CODE_DISABLE_FEEDBACK_SURVEY=1` (또는 `DISABLE_TELEMETRY`/`DO_NOT_TRACK`/`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`)
- 빈도 조절: `feedbackSurveyRate` (0~1 확률)

## 2-3-10. 원격 분석과 비활성화 옵션

### 두 종류의 운영 텔레메트리

**① Metrics** — 지연/신뢰성/사용 패턴
- Anthropic + 서드파티 로깅 인프라로 TLS 전송
- **코드, 프롬프트, 파일 경로는 절대 포함하지 않는다**
- 끄기: `DISABLE_TELEMETRY=1`

**② Error reports** — Claude Code 내부의 에러 메시지/스택 트레이스
- 서드파티 에러 추적 서비스로 TLS 전송
- 시크릿·파일 경로·이메일 등 알려진 패턴은 **전송 전에 마스킹**
- 끄기: `DISABLE_ERROR_REPORTING=1`
- 📌 **다음 조건을 모두 만족할 때만 켜진다**: Pro/Max 구독 로그인 + v2.1.198+ + Claude API 직접 연결 + 조직에 ZDR/HIPAA 계약 없음

### 한 번에 끄기
```bash
export CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1
```
⚠️ **`DISABLE_TELEMETRY`나 `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`을 켜면 피처플래그 평가도 꺼진다.**
→ Remote Control 등 피처플래그에 의존하는 기능이 비활성화되고, **auto mode도 기본 모드에서 빠진다.**
(`DISABLE_ERROR_REPORTING`은 피처플래그에 영향 없음)

### 프로바이더별 기본 동작

| 서비스 | Claude API | Vertex / Bedrock / Foundry / AWS |
|---|---|---|
| Metrics | **기본 on** (`DISABLE_TELEMETRY=1`로 off) | **기본 off** |
| Error reports | Pro/Max + v2.1.198+ 이면 on | **기본 off** |
| `/feedback` | 기본 on (`DISABLE_FEEDBACK_COMMAND=1`) | **기본 off** |
| 세션 품질 설문 | **기본 on** | **기본 on** ← 프로바이더 무관 |
| WebFetch 도메인 안전검사 | **기본 on** | **기본 on** ← 프로바이더 무관 |

📌 서명된 Claude apps gateway 세션은 **게이트웨이 자격증명 자체가** 사용 분석·에러 리포트·설문 평점 전송을 끈다 (되살릴 설정 없음).

### ⚠️ WebFetch 도메인 안전 검사 (예외적으로 항상 켜짐)
- URL을 가져오기 전에 **호스트명만** `api.anthropic.com`으로 보내 안전 blocklist와 대조
- **전체 URL, 경로, 페이지 내용은 전송하지 않는다**
- 통과한 호스트는 5분 캐시
- `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`에 영향받지 않는다
- 네트워크가 `api.anthropic.com`을 차단하면 **WebFetch가 전부 실패한다** → 도메인 허용 또는 `skipWebFetchPreflight: true`
- ⚠️ 끄면 blocklist 조회 없이 아무 URL이나 가져오므로, `WebFetch` 권한 규칙과 병행할 것

### 📌 조직용 OpenTelemetry 모니터링
```json
{
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "OTEL_METRICS_EXPORTER": "otlp",
    "OTEL_EXPORTER_OTLP_PROTOCOL": "grpc",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "http://collector.example.com:4317"
  }
}
```
**수집 가능한 메트릭**: 세션 수, 코드 라인 수, PR 수, 커밋 수, 비용, 토큰(캐시 read/create 포함), 코드 편집 도구 결정, 활성 시간

**이벤트**: user prompt, assistant response, tool result, API request/error/refusal, tool decision, **permission mode changed**, auth, MCP server connection, **plugin installed/loaded**, **skill activated**, hook 실행, compaction, subagent completed, retention sweep 등

📌 관리형 설정으로 OTLP 목적지를 잠글 수 있다.
📌 `CLAUDE_CODE_ENABLE_FEEDBACK_SURVEY_FOR_OTEL=1` — 비필수 트래픽은 차단하면서 설문 평점만 자체 collector로 수집

## 2-4-2. 모델 설정 방법의 우선순위

**높은 것부터:**
1. **세션 중** — `/model <alias|name>` 또는 `/model`로 피커
2. **시작 시** — `claude --model <alias|name>`
3. **환경변수** — `ANTHROPIC_MODEL=<alias|name>`
4. **설정 파일** — `model` 필드
5. 📌 **새 세션 기본값** — `ANTHROPIC_DEFAULT_MODEL=<alias|name>` (v2.1.236+)

### 📌 `/model`이 이제 기본값으로 저장된다 (v2.1.153+)
피커에서:
- `Enter` → 모델 전환 **+ 내 기본값으로 저장** (user settings의 `model`에 기록)
- `s` → **이번 세션만** 전환

`/model <name>`을 직접 치면 `Enter`와 동일하게 저장된다.
⚠️ **`-p` 모드에서의 `/model`은 현재 세션에만 적용되고 저장되지 않는다.**
⚠️ 프로젝트/관리형 설정은 여전히 우선이며 다음 실행 때 다시 적용된다.

### 재개 시 모델
- 재개한 세션은 **트랜스크립트에 저장된 모델을 유지**한다 (다른 세션의 `/model` 선택에 영향받지 않도록)
- 예외: 모델이 은퇴했거나 `availableModels`에서 제외된 경우 / `--model`·`ANTHROPIC_MODEL`을 넘긴 경우 / 프로바이더별 배포 ID를 쓰는 경우(Bedrock/Vertex/Foundry는 아예 복원 안 함)

### 병렬 세션에서 다른 모델 쓰기
`--model` 플래그와 `ANTHROPIC_MODEL`은 **그 세션에만** 적용된다.
→ 터미널마다 다른 모델을 돌리려면 `/model`로 전환하지 말고 **각각 `--model`로 실행**할 것.

### 조직 통제 3종 (📌 신규/확장)

| 설정 | 효과 |
|---|---|
| `model` | 세션 시작 시 **초기 선택**. 강제 아님 (`/model`로 Default 고르면 런타임 기본값으로 감) |
| `availableModels` | **선택 가능한 모델 화이트리스트** |
| `enforceAvailableModels` | 화이트리스트를 **Default 옵션에까지 확대** |
| `ANTHROPIC_DEFAULT_*_MODEL` (env) | 별칭이 가리킬 **버전 고정** |

```json
{
  "model": "claude-sonnet-4-5",
  "availableModels": ["claude-sonnet-4-5", "haiku"],
  "enforceAvailableModels": true,
  "env": { "ANTHROPIC_DEFAULT_SONNET_MODEL": "claude-sonnet-4-5" }
}
```

📌 `availableModels`가 적용되는 곳: `/model`, `--model`, `ANTHROPIC_MODEL`, `model` 설정, 재개 시 복원 모델, 별칭 해석, fast mode, **서브에이전트/에이전트팀 모델**, **스킬/커맨드 frontmatter의 `model`**, advisor 모델, 백그라운드 에이전트 모델

📌 **Enterprise 조직 모델 제한**은 claude.ai 관리 콘솔에서 개별 모델을 비활성화하는 별개 메커니즘. `availableModels`(클라이언트 강제)와 달리 **서버가 강제**한다. Haiku는 항상 사용 가능해 최소 하나는 남는다.

📌 **조직 기본 모델**(Enterprise)도 콘솔에서 설정 가능. `/model` 피커에 "Org default" 라벨. 시작점일 뿐 강제는 아니지만, "override user selection" 옵션을 켜면 다음 실행 때 다시 적용된다.

## 2-4-3. 환경 변수를 통한 모델 커스터마이징

### 별칭 → 실제 모델 ID 매핑
```bash
export ANTHROPIC_DEFAULT_OPUS_MODEL='us.anthropic.claude-opus-4-8'   # Bedrock
export ANTHROPIC_DEFAULT_SONNET_MODEL='claude-sonnet-5'
export ANTHROPIC_DEFAULT_HAIKU_MODEL='claude-haiku-4-5'              # 백그라운드 작업에도 사용
export ANTHROPIC_DEFAULT_FABLE_MODEL='claude-fable-5'
export CLAUDE_CODE_SUBAGENT_MODEL='haiku'                            # 모든 서브에이전트
```
⚠️ `ANTHROPIC_SMALL_FAST_MODEL`은 **deprecated** → `ANTHROPIC_DEFAULT_HAIKU_MODEL` 사용

### 서드파티 배포 시 반드시 버전 고정
문서가 경고 박스로 명시:
> 고정하지 않으면 별칭이 프로바이더별 내장 기본 모델 ID로 해석되는데, **그 기본값이 최신 릴리스보다 뒤처져 있거나 계정에서 아직 활성화되지 않았을 수 있다.**
> Bedrock/Agent Platform은 알림 후 이전 버전으로 폴백하지만, **Microsoft Foundry는 그냥 에러가 난다.**

1M 컨텍스트를 쓰려면 ID 뒤에 `[1m]`:
```bash
export ANTHROPIC_DEFAULT_OPUS_MODEL='claude-opus-4-8[1m]'
```
- Claude Code가 프로바이더로 보내기 전에 접미사를 제거한다
- **접미사는 변수 단위로 읽힌다** — 한 변수에만 붙이면 다른 변수의 같은 모델은 200K

### 📌 표시명·기능 선언 (서드파티 배포)
프로바이더별 ID(ARN 등)는 Claude Code가 기능을 인식 못 해 effort/thinking이 꺼진다.
```bash
export ANTHROPIC_DEFAULT_OPUS_MODEL='arn:aws:bedrock:us-east-1:123456789012:custom-model/abc'
export ANTHROPIC_DEFAULT_OPUS_MODEL_NAME='Opus via Bedrock'
export ANTHROPIC_DEFAULT_OPUS_MODEL_DESCRIPTION='Opus routed through a Bedrock custom endpoint'
export ANTHROPIC_DEFAULT_OPUS_MODEL_SUPPORTED_CAPABILITIES='effort,xhigh_effort,max_effort,thinking,adaptive_thinking,interleaved_thinking'
```

| capability | 활성화되는 것 |
|---|---|
| `effort` | effort 레벨과 `/effort` |
| `xhigh_effort` / `max_effort` | 해당 레벨 |
| `thinking` | 확장 사고 |
| `adaptive_thinking` | 적응형 추론 |
| `interleaved_thinking` | 툴 호출 사이의 사고 |

### 📌 버전별 개별 매핑 — `modelOverrides`
```json
{
  "modelOverrides": {
    "claude-opus-4-7": "arn:aws:bedrock:us-east-2:123456789012:application-inference-profile/opus-prod",
    "claude-opus-4-6": "arn:aws:bedrock:us-east-2:123456789012:application-inference-profile/opus-46-prod",
    "claude-sonnet-4-6": "arn:aws:bedrock:us-east-2:123456789012:application-inference-profile/sonnet-prod"
  }
}
```
같은 패밀리의 여러 버전을 각각 다른 프로바이더 리소스로 라우팅. 거버넌스/비용 배분/리전 라우팅용.

### 📌 커스텀 모델 옵션 추가
```bash
export ANTHROPIC_CUSTOM_MODEL_OPTION="my-gateway/claude-opus-5"
export ANTHROPIC_CUSTOM_MODEL_OPTION_NAME="Opus via Gateway"
```

`/model` 피커 맨 아래에 항목 추가. **모델 ID 검증을 건너뛴다.**

### 📌 Effort level (신규 개념 — 책에 없을 가능성 큼)

"adaptive reasoning"의 강도를 조절한다. 모델이 각 단계마다 얼마나 생각할지를 스스로 결정하는데, 그 상한을 정하는 것.

| 모델 | 지원 레벨 |
|---|---|
| Fable 5, Opus 5, Sonnet 5, Opus 4.8, Opus 4.7 | `low`, `medium`, `high`, `xhigh`, `max` |
| Opus 4.6, Sonnet 4.6 | `low`, `medium`, `high`, `max` |

**기본값은 `high`** (Opus 4.7만 `xhigh`).

| 레벨 | 언제 |
|---|---|
| `low` | 짧고 범위가 명확하고 지연에 민감하며 지능이 중요하지 않은 작업 |
| `medium` | 비용에 민감하고 지능을 좀 양보해도 되는 작업 |
| `high` | **기본값.** 토큰과 지능의 균형 |
| `xhigh` | 더 깊은 추론, 더 많은 토큰 |
| `max` | 어려운 작업에 도움되지만 **수확 체감 + 과잉사고 경향.** 널리 쓰기 전에 테스트할 것 |
| 📌 `ultracode` | **effort 레벨이 아니라 Claude Code 설정.** `xhigh`를 보내면서 + 큰 작업마다 dynamic workflow를 오케스트레이션 |

설정 방법:
```bash
/effort                    # 인터랙티브 슬라이더
/effort xhigh              # 직접 지정
/effort auto               # 모델 기본값으로
/model                     # 좌우 화살표로 슬라이더 조작
claude --effort high       # 세션 1회 (저장 안 됨)
export CLAUDE_CODE_EFFORT_LEVEL=high    # 다른 모든 방법보다 우선
```
```json
{ "effortLevel": "xhigh" }    // max는 여기 못 씀, ultracode는 별도 키
```
- 스킬/서브에이전트 frontmatter의 `effort`로 개별 오버라이드 가능
- **우선순위: 환경변수 > 설정한 레벨 > 모델 기본값**
- `max`는 (환경변수로 설정하지 않는 한) **현재 세션에만** 적용
- 📌 프롬프트에 **`ultrathink`** 를 넣으면 그 턴만 더 깊이 생각한다 (API로 보내는 effort는 그대로). `"think"`, `"think hard"` 같은 표현은 **키워드로 인식되지 않는다** — 그냥 프롬프트 텍스트

### 📌 확장 컨텍스트 (1M)

지원: Fable 5, Sonnet 5, Opus 4.6+, Sonnet 4.6
**Anthropic API에서 Fable 5 / Sonnet 5 / Opus 4.7+는 항상 1M으로 동작한다.**

| 플랜 | Opus 1M | Sonnet 4.6 1M |
|---|---|---|
| Max, Team, Enterprise | 구독에 포함 (**자동 업그레이드**) | usage credits 필요 |
| Pro | usage credits 필요 | usage credits 필요 |
| API / 종량제 | 전체 접근 | 전체 접근 |

- 1M 컨텍스트는 **표준 요금**. 200K 초과분에 프리미엄 없음
- 끄기: `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` → 네이티브 1M 모델도 200K로 취급
- **Sonnet 5는 200K 변형이 없다.** 기본 약 967K에서 auto-compact

### 컨텍스트와 auto-compaction
```bash
/autocompact 500k          # 이 세션 + 이후 (user settings에 저장)
/autocompact auto          # 모델 기본값으로
claude --autocompact 500k  # 이번 실행만 (관리형 설정에 선점되지 않음)
export CLAUDE_CODE_AUTO_COMPACT_WINDOW=500000   # 위 전부보다 우선, 평문 정수만
```
100K~1M 범위. `500k`, `1M`, `200`(=200,000), `200000` 형식 지원 (**환경변수는 평문 정수만**).

## 2-4-4. 프롬프트 캐싱 이해와 최적화

📌 [전용 문서 페이지](https://code.claude.com/docs/en/prompt-caching)가 새로 생겼다. **2장에서 가장 실무적으로 값진 부분.**

### 원리
매 메시지마다 새 API 요청이 나가고, 모델은 요청 간 기억이 없으므로 **전체 컨텍스트를 매번 다시 보낸다.**
API는 요청의 **앞부분(prefix)** 을 최근 처리한 것과 대조해 재처리를 피한다.
- 매칭은 **정확 일치**. prefix 어딘가가 바뀌면 **그 뒤 전부 재계산**
- **파일 단위나 세그먼트 단위 캐싱은 없다**

### 요청의 3계층 (덜 바뀌는 것이 앞)

| 계층 | 내용 | 언제 바뀌나 |
|---|---|---|
| **System prompt** | 핵심 지시, **툴 정의**, output style | 로드된 툴 정의가 바뀔 때, **Claude Code 업그레이드** |
| **Project context** | CLAUDE.md, auto memory, 무조건 로드되는 rules | 세션 시작, `/clear`, `/compact` 이후 |
| **Conversation** | 내 메시지, 응답, 툴 결과 | **매 턴** |

대화 계층 변경 → 앞 두 계층은 캐시 유지.
**시스템 프롬프트 변경 → 전부 무효화.**

📌 **프롬프트 텍스트가 아니지만 캐시 키에 포함되는 두 가지**: **모델**, **effort level**

### ❌ 캐시를 무효화하는 행동

| 행동 | 설명 |
|---|---|
| **모델 전환** (`/model`) | 모델마다 별도 캐시 → 전체 히스토리 재처리 |
| **effort 변경** (`/effort`) | 동일 모델이어도 레벨마다 별도 캐시 |
| **fast mode 켜기** | 요청 헤더가 캐시 키의 일부. **대화당 1회만** 비용 발생 |
| **MCP 서버 연결/해제** | ⚠️ **tool search로 지연 로드되면 캐시 유지.** prefix에 로드되는 경우만 무효화 |
| **플러그인 활성/비활성** | MCP 서버를 제공하는 플러그인만 문제. 스킬/커맨드/에이전트/훅/모니터/테마는 **캐시 유지** |
| **툴 전체 deny** | `Bash`, `WebFetch` 같은 bare 이름 deny는 시스템 프롬프트를 바꾼다. `Bash(rm *)` 같은 scoped 규칙은 영향 없음 |
| **`/compact`** | 설계상 대화 계층 무효화 |
| **Claude Code 업그레이드** | 시스템 프롬프트/툴 정의가 바뀜 |

📌 **`/model` 실행 시 캐시가 아직 살아 있을 때만 확인 프롬프트가 뜬다** (v2.1.238+). TTL이 지났으면 그냥 전환.

⚠️ **`opusplan`은 plan mode 토글마다 모델이 바뀐다** → 매번 캐시 새로 시작.

### ✅ 캐시를 유지하는 행동

| 행동 | 이유 |
|---|---|
| **저장소 파일 편집** | 파일 내용은 Claude가 읽을 때만 컨텍스트에 들어감. 편집하면 `<system-reminder>`가 **뒤에 추가**될 뿐 |
| **CLAUDE.md 중간 수정** | 캐시는 유지되지만 **수정도 적용되지 않는다** (아래) |
| **output style 변경** | 캐시 유지 + **적용도 안 됨** |
| **permission mode 전환** | 시스템 프롬프트/툴 정의를 안 바꿈 (`opusplan` 제외) |
| **스킬·커맨드 호출** | 호출 지점에 user message로 주입 |
| `/recap` | 요약을 커맨드 출력으로 추가 (히스토리 대체 X) |
| **`/rewind`** | 이전 시점으로 잘라내면 **그 시점 캐시에 히트한다** |
| 서브에이전트 spawn | 부모 prefix는 그대로 |

### ⚠️ "설정이 중간에 반영 안 되는" 이유가 여기 있다
- **프로젝트 루트/유저 CLAUDE.md는 세션 시작 시 1회 읽어 메모리에 보관.** 중간에 고쳐도 세션은 시작 시 버전을 계속 쓴다. `/clear`, `/compact`, 재시작 후 반영
- **하위 디렉터리 CLAUDE.md와 `paths:` rule은 나중에 로드**되므로, 로드 **전에** 고치면 반영된다. 로드 후엔 대화 히스토리의 일부라 소급 안 됨
- **output style도 동일** — 시스템 프롬프트 일부라 `/clear`나 재시작 필요

### `/compact` 비용의 진실
- 요약을 만들기 위해 **같은 시스템 프롬프트+툴+히스토리 + 요약 지시**로 별도 요청을 보낸다
- **캐시가 따뜻하면** 그 요청이 prefix를 캐시에서 읽으므로 **컨텍스트 크기 대비 훨씬 싸다**
- **캐시가 만료된 뒤(오래된 세션 재개)** 는 전체 히스토리를 uncached로 재처리 → **`/compact`가 가장 비싼 순간**
- 압축 직후 턴은 짧은 요약만 캐싱하므로 오히려 가볍다

💡 **문서 팁:**
> 버릴 컨텍스트가 진짜 필요 없는 것일 때 compaction이 이득이다.
> auto-compaction이 작업 중간에 터지길 기다리지 말고 **작업 경계에서 직접 `/compact`** 하라.
> **완전히 버릴 경로로 갔다면 `/compact` 대신 `/rewind`** — rewind는 **이미 캐시된 prefix로 잘라내는** 것이라 새로 만들지 않는다.

### 캐시 수명 (TTL)

| 상황 | TTL |
|---|---|
| **Claude 구독** | **1시간 자동 요청** |
| 구독인데 usage credits로 넘어감 | **5분으로 자동 하향** (1h 캐시 쓰기가 더 비싸므로). `ENABLE_PROMPT_CACHING_1H=1`로 유지 가능 |
| API 키 / Bedrock / Agent Platform / Foundry / AWS | **5분** (기본). `ENABLE_PROMPT_CACHING_1H=1`로 1시간 |
| 강제 5분 | `FORCE_PROMPT_CACHING_5M=1` |

캐시에 히트할 때마다 타이머가 리셋되므로 계속 작업하면 계속 따뜻하다.

### 캐시 스코프
> Claude Code에서 캐시는 사실상 **머신 + 디렉터리 단위**다.

시스템 프롬프트에 작업 디렉터리, 플랫폼, 셸, OS 버전, auto memory 경로가 박혀 있기 때문.
- **다른 디렉터리의 두 세션은 서로의 캐시를 못 쓴다** → **워크트리도 마찬가지** (각자 다른 작업 디렉터리)
- 같은 디렉터리에서 **동시에** 돌리는 세션들은 서로의 캐시를 읽는다
- 순차 세션은 **시작 시점의 git status(브랜치, 최근 커밋)까지 일치**해야 공유된다
- 📌 SDK로 여러 머신에서 돌린다면 `--exclude-dynamic-system-prompt-sections`로 머신별 섹션을 첫 user 메시지로 옮겨 캐시를 공유할 수 있다

### 캐시 성능 확인
API가 매 응답에 보고하는 두 값:

| 필드 | 의미 |
|---|---|
| `cache_creation_input_tokens` | 이번 턴에 캐시에 쓴 토큰 (**cache write 요금**) |
| `cache_read_input_tokens` | 캐시에서 읽은 토큰 (**표준 입력 요금의 약 10%**) |

**read/creation 비율이 높으면 캐싱이 잘 되는 것.** creation이 계속 높으면 prefix가 매번 바뀌고 있다는 신호.
→ statusline 스크립트로 `current_usage` 객체를 읽어 실시간 확인
→ 조직 단위는 OpenTelemetry로 사용자/세션별 집계

### 서브에이전트와 캐시
- 서브에이전트는 **자기 시스템 프롬프트와 툴셋**으로 시작 → 부모 캐시를 읽지 않는다. 자기 캐시를 따로 데운다
- **구독이어도 서브에이전트는 5분 TTL** (1시간 자동 적용은 메인 대화만)
- **부모 캐시는 영향 없음** — 호출과 결과가 뒤에 추가될 뿐
- 📌 **fork**는 다르다. 부모의 시스템 프롬프트/툴/히스토리를 그대로 물려받으므로 **첫 요청이 부모 캐시에 히트한다**

### 캐싱 끄기 (디버깅용)
```bash
DISABLE_PROMPT_CACHING=1          # 전체
DISABLE_PROMPT_CACHING_HAIKU=1
DISABLE_PROMPT_CACHING_SONNET=1
DISABLE_PROMPT_CACHING_OPUS=1
DISABLE_PROMPT_CACHING_FABLE=1
```
> 일반적인 사용에서는 켜둘 것.

### ⚠️ 게이트웨이/프록시 사용 시 주의
`ANTHROPIC_BASE_URL`이나 LLM 게이트웨이를 쓰면, Claude Code가 대화 중간에 붙이는 시스템 컨텍스트(파일 변경 알림 등)를 **캐싱 대상으로 표시하지 않는다** → 매 요청 uncached input으로 계산됨.
대화 자체의 cache breakpoint는 유지되므로 게이트웨이가 전달만 하면 대화는 캐싱된다.

### 💡 실무 요약
> **세션 시작 시점에 모델과 effort를 정하고, `/compact`는 작업 사이의 자연스러운 경계에서만 쓴다.**
> **작업 중간에 바꾸는 것이 적을수록 캐시 히트율이 높다.**

## 2-4-5. 모델 선택 전략

### 작업 유형별

| 상황 | 선택 |
|---|---|
| 일상 코딩, 대부분의 구현 | `sonnet` (Sonnet 5, 1M 컨텍스트) |
| 복잡한 추론, 아키텍처 결정 | `opus` |
| 단순 반복, 대량 배치 | `haiku` |
| 계획은 깊게, 구현은 빠르게 | **`opusplan`** |
| 📌 한 세션을 넘어가는 큰 작업, 근본원인 조사, 장애 디버깅 | **`fable`** |
| 서브에이전트 대량 실행 | `CLAUDE_CODE_SUBAGENT_MODEL=haiku` |

### `opusplan` 상세
- plan mode: `opus` / 실행: `sonnet`
- 구독 티어에서 Opus가 1M으로 자동 업그레이드되면 **plan 단계도 1M**을 받는다
- 양쪽 다 1M을 강제하려면 `opusplan[1m]`
- ⚠️ **plan mode 토글마다 모델이 바뀌므로 캐시가 매번 초기화된다** — 비용/지연 트레이드오프를 감안할 것

### 📌 Fallback model chain (가용성 기반)
```bash
claude --fallback-model sonnet,haiku
```
```json
{ "fallbackModel": ["claude-sonnet-5", "claude-haiku-4-5"] }
```
- 과부하/불가용/기타 재시도 불가 서버 에러일 때 순서대로 시도
- **인증·과금·rate limit·요청 크기·전송 에러는 전환하지 않는다** (일반 재시도 처리)
- **현재 턴에만 적용.** 다음 메시지는 다시 primary부터
- 중복 제거 후 **최대 3개**
- 📌 **compaction에도 적용되지만, primary보다 컨텍스트 윈도우가 작은 모델로는 폴백하지 않는다** (요약 자체가 잘리므로)
- ⚠️ 시작 시 체인을 확인해주지 않고 `/status`에도 안 나온다. **전환 알림이 첫 신호**

### 📌 Advisor (신규)
`advisorModel` / `--advisor <model>` / `/advisor` — 세션 중 Claude가 **필요할 때 두 번째 모델에게 자문**을 구한다.
`opusplan`이 plan 경계에서 전환하는 것과 달리, **작업 중간에 Claude가 판단해서** 호출.
📌 advisor 툴 정의는 cache breakpoint 뒤에 있어서 **켜고 꺼도 캐시가 유지된다.**

### 📌 Fast mode (신규)
`/fast` — 더 빠른 응답, 대신 비용 증가.
- 요청 헤더가 캐시 키의 일부라 **켜는 순간 전체 히스토리가 uncached로 재처리** → **세션 초반에 켜는 게 훨씬 싸다**
- 비용은 **대화당 1회**만 발생. 껐다 켜도 캐시 유지
- rate limit에 걸리면 표준 속도로 자동 폴백 (캐시 유지)

### 토큰 사용량 줄이기 (costs 문서 요약)
1. **컨텍스트를 능동적으로 관리** — `/clear`, `/compact`, `/btw`
2. **작업에 맞는 모델 선택**
3. **MCP 서버 오버헤드 줄이기** — 안 쓰는 서버 연결 해제
4. **타입 언어면 code intelligence 플러그인 설치** (파일 읽기 대체)
5. **훅과 스킬로 처리 오프로드**
6. **CLAUDE.md의 내용을 스킬로 이동** ← 매 요청 vs 필요할 때
7. **extended thinking / effort 조정**
8. **장황한 작업은 서브에이전트에 위임**
9. **구체적인 프롬프트 쓰기**

📌 **백그라운드 토큰 사용**: 세션 제목 생성, 대화 요약 등은 Haiku급 모델이 처리한다 (`ANTHROPIC_DEFAULT_HAIKU_MODEL`).

### 확인 방법
- `/model` — 현재 모델과 effort 슬라이더
- `/status` — 모델 + 계정 정보
- 세션 헤더 — 모델명 옆에 "with low effort" 같은 표시
- `/usage` — 플랜 사용량 내역
- statusline 스크립트 — 실시간 모델/컨텍스트/비용

## B. 스터디에서 각자 실험해볼 것

1. **auto mode를 실제로 켜고 며칠 써보기** — 어떤 액션이 차단되는지, `/permissions`의 Recently denied 탭 확인
2. **`claude auto-mode defaults`** 로 기본 규칙 전체를 뽑아서 읽어보기 (JSON, 꽤 길다)
3. **캐시 히트율 statusline** 만들어서 `/compact`, `/model` 전환 전후 비교
4. **`.claude/rules/`** 로 CLAUDE.md 쪼개보고 `/context`로 로드량 비교
5. **`--worktree`** 로 병렬 세션 2개 돌려보고 격리 차단 메시지 확인
6. **`--bare -p`** 로 CI 스크립트 하나 만들어보기
7. **PreToolUse 훅**으로 특정 파일 편집 차단 → CLAUDE.md 지시와 강제력 차이 체감
8. **effort 레벨** low/high/xhigh 같은 작업에 돌려서 토큰·품질 비교

## C. 논쟁거리

- **auto mode를 팀 기본으로 쓸 것인가?** classifier 비용(Enterprise/API는 토큰 과금) vs 프롬프트 피로
- **"대화로 설정한 경계는 compaction으로 사라진다"** — 이걸 어떻게 운영에 반영할 것인가 (중요한 건 deny 규칙으로?)
