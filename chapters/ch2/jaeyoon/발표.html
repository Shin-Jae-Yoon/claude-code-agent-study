Chapter 02 · 10분 발표

워크플로와 설정

Claude Code를 잘 쓰는 일은 프롬프트 한 번을 잘 쓰는 일이 아니라, 탐색부터 검증까지의 과정을 설계하는 일이다.

좋은 결과는 탐색 → 계획 → 구현 → 검증 워크플로에서 나온다.
01 · CORE LOOP

한 번에 정답 대신,
검증 가능한 반복

각 단계는 독립적이지만 검증 결과에 따라 다시 탐색과 계획으로 돌아간다.

탐색

프로젝트 구조와 관련 파일, 구성 요소의 상호작용을 좁혀 간다.

계획

변경 범위와 순서, 검증 기준을 구현 전에 정한다.

구현

작은 단위로 변경하고 각 단위가 독립적으로 동작하게 만든다.

검증

테스트·린터·빌드 로그를 근거로 수정하거나 커밋한다.

검증 실패는 종료가 아니라 다음 탐색의 입력이다 ↺
02 · EXPLORE

넓게 묻지 말고
단계적으로 좁힌다

탐색 범위를 구체화하면 불필요한 파일 읽기와 컨텍스트 소비를 줄일 수 있다.

1

관련 파일 찾기

Glob과 Grep으로 후보를 모은다.

2

상호작용 파악

Read로 파일 사이의 연결을 읽는다.

3

실행 흐름 추적

프런트엔드에서 데이터베이스까지 실제 경로를 따라간다.

넓은 질문“인증 시스템 전체를 설명해 줘.”
좁혀 가는 질문“인증 파일을 찾고 → 함께 동작하는 방식을 읽고 → 로그인 흐름을 추적해 줘.”
03 · PLAN

구현 전에
불확실성을 줄인다

여러 파일을 건드리거나 되돌리기 어려운 결정을 할수록 계획 단계가 필요하다.

PLAN MODE

읽기 전용으로
구조부터 확인

다단계 기능, 아키텍처 결정, 변경 전 코드 조사, 사용자와의 반복 협의에 사용한다.

claude --permission-mode plan claude --permission-mode plan -p "인증 시스템을 분석하고 개선 방안을 제안해 줘"
OUROBOROS의 사고 구조

Double Diamond

첫 번째 다이아몬드는 문제를 이해하고, 두 번째 다이아몬드는 설계를 검증된 결과로 좁힌다.

Wonder · 탐색
질문과 가능성을 넓힌다
→
Ontology · 정의
정확히 무엇인지 좁힌다
Design · 창조
설계 후보를 넓힌다
→
Evaluate · 전달
검증된 결과로 좁힌다
모호한 목표를 바로 구현하지 않는다 → 목표 · 제약 · 성공 조건부터 확인한다.
04 · BUILD

점진적 개발의
세 가지 축

복잡한 기능을 테스트 가능한 단위로 나누고, 구조화된 피드백으로 교정한다.

SCOPE

범위 정의

전체 작업을 독립적으로 테스트할 수 있는 작은 단위로 분해한다.

FEEDBACK

피드백 루프

테스트, 린터, 빌드 로그의 통과·실패를 다음 수정의 근거로 삼는다.

CONTEXT

컨텍스트 관리

/compact로 요약하고 새 작업은 /clear로 분리한다.

Red → Green → Refactor. 실패하는 테스트에서 시작해 최소 구현과 구조 개선으로 이어간다.
테스트통과·실패가 다음 수정의 근거
린터·빌드구조화된 오류를 즉시 피드백
Git worktree독립 작업 공간에서 병렬 개발
검토·커밋변경과 메시지가 일치하는지 확인
05 · SETTINGS

설정은 범위와
우선순위가 핵심

팀 공통 설정과 개인 예외를 분리하고, 더 구체적인 범위가 낮은 범위를 덮어쓴다.

설정 계층
관리·정책조직이 배포하는 엔터프라이즈 설정
프로젝트.claude/settings.json
프로젝트 개인.claude/settings.local.json
사용자 전역~/.claude/settings.json

권한 규칙: allow·ask·deny의 병합과 충돌을 별도로 살펴야 하며, deny가 보호 경계를 만든다.

주요 옵션

07 · EXTEND

확장 도구는
역할이 다르다

모든 것을 Skill로 만들거나 MCP로 연결하기보다 해결하려는 문제의 모양에 맞춘다.

◈

Skill

지식과 반복 절차를 필요할 때 로드한다.

◎

Subagent

별도 컨텍스트에서 독립적인 능력을 수행한다.

⇄

MCP

데이터·도구·컨텍스트를 표준 방식으로 연결한다.

⚡

Hook

생명주기 이벤트에서 결정론적으로 실행한다.

▣

Plugin

여러 확장을 하나의 배포 단위로 묶는다.

정리한 구분

Skill = 지식 확장

무엇을 알고 어떤 절차를 따를지 정의한다.

정리한 구분

Subagent = 능력 확장

격리된 컨텍스트에서 특정 역할을 수행한다.

08 · REFERENCE

그래프 두 개와
명세 수렴 엔진 하나

Graphify·CodeGraph는 현재 시스템을 읽고, Ouroboros는 만들려는 시스템의 모호함을 줄인다.

KNOWLEDGE MAP

Graphify

코드와 문서의 관계를 함께 본다

코드는 Tree-sitter AST로 로컬 파싱하고, 문서·PDF·미디어는 선택적 의미 추출을 거쳐 하나의 graph.json으로 연결한다.

AST + 의미 추출 → graph.json
→ query · path · explain

결과와 쓰임

graph.html과 아키텍처 보고서EXTRACTED / INFERRED 근거 표시설계 문서가 많은 저장소

경계: 문서 의미 분석은 선택한 모델로 전달될 수 있고, 최신성은 update·Git hook으로 관리한다.

LIVE CODE INDEX

CodeGraph

에이전트가 즉시 질의하는 코드 인덱스

Rust 커널이 심볼·호출·참조를 분석해 .codegraph/ SQLite에 저장한다. 파일 watcher가 바뀐 범위만 자동 동기화한다.

codegraph init → SQLite + FTS5
→ codegraph_explore

한 번의 질의가 주는 것

관련 원문 코드심볼 사이 호출 경로변경 blast radius

경계: 문서 지식보다 코드 변화에 집중하며 reflection·DI 같은 런타임 관계에는 정적 분석의 한계가 있다.

SPEC FIRST

Ouroboros

코드 전에 숨은 가정을 드러낸다

“어떻게 만들까?”보다 “만들려는 것이 정확히 무엇인가?”를 먼저 묻는다. 소크라테스식 인터뷰를 검증 가능한 Seed 명세로 수렴시킨다.

Interview → Seed → Execute
→ Evaluate → Evolve ↺

Double Diamond와 종료 조건

문제 탐색 → 온톨로지 정의설계 확장 → 검증된 결과로 수렴Ambiguity ≤ .2 · Similarity ≥ .95

경계: 작고 명확한 작업에는 절차 비용이 크며, 점수는 판단 보조 지표이지 요구사항의 진실을 보장하지 않는다.

10 · SECURITY

대표 보안 사례:
.env 보호

민감 파일 보호는 Read 차단 한 줄로 끝나지 않는다.

1. 파일 접근 차단

permissions.deny로 환경 변수와 자격 증명 파일의 읽기를 제한한다.

→

2. 우회 경로 점검

Bash가 허용되면 cat .env처럼 다른 경로로 읽을 가능성도 함께 살핀다.

권한 규칙은 도구 하나가 아니라 가능한 전체 경로를 기준으로 설계한다.
BASH PATTERN

공백 하나가 범위를 바꾼다

Bash(ls *) → ls -la Bash(ls*) → ls -la, lsof

접두사 와일드카드는 예상보다 넓게 매칭될 수 있다.

DOCKER

파괴적 명령은 ask

시스템 정리·이미지 삭제는 확인 대상으로 두고, Docker socket 직접 접근은 허용 범위를 명시한다.

CURRENT STATE

아직 권한 규칙 없음

현재 사용자·프로젝트 settings에 allow·ask·deny가 없다. 팀 공통 보호는 프로젝트 설정에 둘 수 있다.
