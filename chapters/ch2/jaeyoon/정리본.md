# Chapter 2. 워크플로와 설정

> 상태: 확정본 — 역질문 답변 반영

Claude Code의 작업 흐름을 탐색, 계획, 구현, 검증과 커밋으로 나누고, 이 흐름을 안정적으로 반복하기 위한 설정과 확장 도구를 정리한다. 이번 챕터의 중심 메시지는 **좋은 결과는 `탐색 → 계획 → 구현 → 검증` 워크플로에서 나온다**는 것이다.

## 1. 기본 작업 흐름

기본 흐름은 다음과 같다.

```text
탐색 → 계획 → 구현 → 검증 → 커밋
   ↑                 │
   └──── 필요하면 반복 ┘
```

사용자가 고수준 목표를 제시하면 Claude Code가 코드베이스를 탐색하고, 계획을 수립하고, 코드를 구현한 뒤 변경 이력을 남긴다. 각 단계는 독립적으로 수행할 수도 있고, 검증 결과에 따라 앞 단계로 돌아가 반복할 수도 있다.

### 1.1 탐색

탐색 단계의 목적은 프로젝트 구조와 구성 요소 간 상호작용을 파악하는 것이다. 처음부터 광범위한 설명을 요구하기보다 다음처럼 범위를 단계적으로 좁힌다.

1. 관련 파일을 찾는다: Glob, Grep
2. 파일 간 상호작용을 읽는다: Read
3. 실제 실행 흐름을 추적한다

예를 들어 인증 시스템을 탐색한다면 다음 순서로 질문한다.

- 사용자 인증을 처리하는 파일을 찾아줘.
- 이 인증 파일들은 어떻게 함께 동작해?
- 프런트엔드에서 데이터베이스까지 로그인 과정을 추적해 줘.

처음부터 “인증 시스템 전체를 설명해 줘”라고 묻는 것보다 탐색 범위를 좁혀 가는 편이 컨텍스트를 절약한다.

#### 탐색과 계획을 보조하는 세 가지 도구

2026년 8월 5일 기준 공식 저장소를 확인했다. Graphify와 CodeGraph는 코드베이스 탐색을 돕지만, Ouroboros는 탐색 결과를 포함한 사용자 요구를 명세로 수렴시키는 계획 도구다. 같은 종류의 경쟁 도구로 보기보다 워크플로의 서로 다른 병목을 해결한다고 보는 편이 정확하다.

##### Graphify: 코드와 문서의 관계를 함께 보는 지식 그래프

[Graphify](https://github.com/Graphify-Labs/graphify)는 코드, Markdown, PDF, Office 문서, 이미지, 영상, SQL 스키마와 설정 파일을 하나의 질의 가능한 그래프로 만든다. 핵심 목적은 “어떤 심볼이 어디서 호출되는가”뿐 아니라 “왜 이런 구조가 되었는가”까지 코드와 문서의 연결을 통해 설명하는 것이다.

코드는 Tree-sitter AST로 로컬에서 결정론적으로 파싱한다. 코드 분석 자체에는 LLM이나 임베딩, 벡터 저장소가 필요하지 않다. 문서·PDF·이미지·영상에 대한 의미 추출은 사용 중인 어시스턴트의 모델이나 별도로 설정한 API를 선택적으로 사용한다.

```text
코드 ── Tree-sitter AST ─┐
문서·미디어 ─ 의미 추출 ├─→ graph.json ─→ query / path / explain
DB·설정 ─ 구조 추출 ────┘          ├─ graph.html
                                   └─ GRAPH_REPORT.md
```

관계에는 근거 수준이 붙는다.

- `EXTRACTED`: import, call, inherit처럼 원본에서 직접 확인한 관계
- `INFERRED`: 이름이나 구조를 해석해 Graphify가 연결한 관계
- `AMBIGUOUS`: 하나로 확정하지 못한 관계

대표 사용법은 다음과 같다.

```bash
uv tool install graphifyy
graphify install
/graphify .

graphify query "인증 흐름을 보여줘"
graphify path "UserService" "DatabasePool"
graphify explain "RateLimiter"
```

결과물은 브라우저에서 탐색하는 `graph.html`, 아키텍처 요약인 `GRAPH_REPORT.md`, 기계가 질의하는 `graph.json`이다. Leiden 커뮤니티 탐지로 하위 시스템을 묶고, 연결이 많은 god node, 모듈을 가로지르는 의외의 관계, `NOTE`·`WHY`·ADR·RFC 같은 설계 근거도 그래프에 포함한다.

**잘 맞는 경우**

- 코드와 설계 문서가 함께 있는 저장소를 처음 이해할 때
- Markdown, PDF, DB 스키마까지 포함한 지식 지도가 필요할 때
- 사람이 볼 수 있는 아키텍처 보고서와 시각화가 필요할 때

**경계와 주의점**

- 코드만 분석할 때는 완전 로컬이지만 문서·미디어 의미 추출은 선택한 모델 백엔드로 내용이 전달될 수 있다.
- 기본 흐름은 그래프를 만든 뒤 `--update`나 Git hook으로 갱신하는 방식이다. 항상 실행 중인 파일 감시 인덱스를 원하는 경우 CodeGraph의 성격과 다르다.
- Graphify가 생성한 관계도 `EXTRACTED`와 `INFERRED`를 구분해 해석해야 한다.

##### CodeGraph: 에이전트가 즉시 질의하는 코드 인덱스

[CodeGraph](https://github.com/colbymchenry/codegraph)는 소스 코드의 심볼, 호출, import, 참조, 라우팅 관계를 프로젝트별 SQLite 인덱스인 `.codegraph/`에 미리 구성한다. 목적은 에이전트가 Grep과 Read를 여러 번 반복하지 않고, 한 번의 질의로 관련 소스와 호출 경로, 변경 영향 범위를 받게 하는 것이다.

```text
codegraph init
      ↓
Rust 파서 → 심볼·호출·참조 해결 → SQLite + FTS5
      ↑                              ↓
파일 변경 ───── 자동 증분 동기화 ─→ codegraph_explore
                                     ├─ 관련 원문 코드
                                     ├─ 호출 경로
                                     └─ blast radius
```

핵심 분석 엔진은 20개 주요 언어를 처리하는 Rust 커널이다. 프레임워크 라우트와 동적 디스패치, Swift와 Objective-C, React Native와 네이티브 코드처럼 일반적인 정적 분석이 끊기기 쉬운 경계도 별도 규칙으로 연결한다. 파일 변경은 운영체제의 파일 이벤트를 감지해 변경된 범위만 다시 동기화한다.

대표 설치와 사용 흐름은 다음과 같다.

```bash
npm i -g @colbymchenry/codegraph
codegraph install   # Claude Code, Codex 등에 MCP 연결
codegraph init      # 현재 프로젝트에 .codegraph/ 생성
```

MCP의 중심 도구인 `codegraph_explore`는 질문과 관련된 심볼의 실제 소스, 심볼 사이의 호출 경로, 변경 시 영향을 받는 범위를 한 번에 반환한다. 이름 검색은 SQLite FTS5를 사용한다. 파일 저장 직후 아직 동기화되지 않은 결과에는 staleness 경고를 표시해 에이전트가 최신 파일을 직접 읽도록 안내한다.

**잘 맞는 경우**

- 코드 중심 저장소에서 callers, callees와 변경 영향 범위를 반복해서 확인할 때
- 리팩터링 전에 어떤 코드와 테스트가 영향을 받는지 알고 싶을 때
- 대형 저장소를 매번 Grep·Read하는 비용을 줄이고 싶을 때

**경계와 주의점**

- 문서와 설계 근거를 함께 연결하는 범용 지식 지도보다는 코드 구조와 변화 영향에 집중한다.
- 인덱스가 있어도 런타임 reflection, DI, 동적으로 생성되는 관계까지 완전히 정적으로 복원할 수 있다고 가정하면 안 된다.
- MCP 권한을 `mcp__codegraph__*`처럼 광범위하게 허용하면 활성화한 모든 CodeGraph 도구가 자동 승인되므로 권한 범위를 함께 검토해야 한다.

##### 두 코드 그래프의 차이

| 기준 | Graphify | CodeGraph |
| --- | --- | --- |
| 해결하려는 질문 | 저장소에 무엇이 있고 코드와 문서가 왜 연결되는가? | 이 심볼은 어디서 쓰이고 바꾸면 무엇이 영향을 받는가? |
| 주요 대상 | 코드 + 문서 + 미디어 + DB·설정 | 소스 코드 + 프레임워크·언어 경계 |
| 그래프 저장 | `graph.json` 중심 파일 산출물 | `.codegraph/` SQLite + FTS5 인덱스 |
| 최신성 유지 | `--update`, Git hook | 파일 watcher와 자동 증분 동기화 |
| 에이전트 연동 | Skill·CLI 중심, MCP 선택 | MCP 중심 |
| 대표 결과 | HTML 그래프, 보고서, 경로와 근거 설명 | 원문 코드, 호출 경로, blast radius |
| 선택 기준 | 사람도 읽는 아키텍처·지식 지도 | 에이전트가 쓰는 실시간 코드 컨텍스트 |

이 스터디 저장소처럼 Markdown과 발표 산출물의 비중이 크면 Graphify가 자연스럽다. 애플리케이션 소스가 중심이고 리팩터링 영향 분석이 우선이면 CodeGraph가 자연스럽다. 둘을 함께 쓴다면 Graphify는 장기적인 지식·아키텍처 레이어, CodeGraph는 현재 작업 트리의 코드 탐색 레이어로 역할을 나눌 수 있다.

[Serena MCP](https://github.com/oraios/serena)는 LSP를 활용해 심볼 단위 코드 탐색과 편집을 지원한다. 별도 그래프 산출물보다 언어 서버가 제공하는 심볼 정보를 에이전트 도구로 연결하는 접근이다.

**내 Claude 시스템에서 확인한 예시**

- 이 프로젝트의 `CLAUDE.md`에는 `chapters/`, `members/`, `.claude/skills/`, `insight/`, `meeting-notes/`의 역할이 적혀 있다. 따라서 루트 지침을 읽는 것만으로도 탐색의 첫 범위를 정할 수 있다.
- Graphify, CodeGraph, Serena는 현재 사용자 설정이나 프로젝트 `.claude/`에 설치되어 있지 않다. 도입한다면 프로젝트 루트에 각 도구의 인덱스 또는 MCP 설정을 두고 이 저장소를 대상으로 사용해야 한다.

### 1.2 계획

계획 단계에서는 구현 전에 전략을 세운다. 여러 파일을 바꾸는 기능, 복잡한 아키텍처 결정, 변경 전 코드 조사에는 플랜 모드가 적합하다. 플랜 모드는 읽기 전용 상태에서 구조를 탐색하고 사용자와 반복적으로 방향을 조정할 때 사용할 수 있다.

```bash
# 새 세션에서 플랜 모드로 시작
claude --permission-mode plan

# 비대화형 플랜 모드
claude --permission-mode plan -p "인증 시스템을 분석하고 개선 방안을 제안해 줘"
```

세션 중에는 `Shift+Tab`으로 권한 모드를 전환할 수 있다.

계획을 보조하는 사례로 [Ouroboros](https://github.com/Q00/ouroboros/blob/main/README.ko.md)를 살펴봤다. 이 도구는 명세 우선 AI 개발 시스템이며, 소크라테스식 질문과 온톨로지 분석을 활용한다. “AI 코딩은 출력보다 입력 단계에서 실패하는 경우가 많고, 사람이 무엇을 만들지 충분히 정하지 않은 채 시작하는 것이 병목”이라는 문제의식에서 출발한다.

#### Ouroboros: 아이디어를 검증 가능한 명세로 수렴시키는 루프

Ouroboros는 코드베이스를 검색하는 도구가 아니라, 구현 전에 사용자의 숨은 가정과 모호함을 드러내는 워크플로 엔진이다. “어떻게 만들까?”보다 “만들려는 것이 정확히 무엇인가?”를 먼저 묻는다.

예를 들어 “Task CLI를 만들자”는 요청을 바로 구현하지 않고 Task가 삭제 가능한지, 보관 가능한지, 개인용인지 팀용인지부터 질문한다. “인증 버그를 고치자”는 요청도 증상과 근본 원인을 구분하는 질문으로 바꾼다. 이런 온톨로지 질문으로 나중에 발생할 재작업의 범위를 줄이려는 것이다.

전체 흐름은 순환 구조다.

```text
Interview → Seed → Execute → Evaluate
    ↑                         ↓
    └────── Evolve/Reflect ───┘
```

- `Interview`: 소크라테스식 질문으로 숨은 가정과 제약을 드러낸다.
- `Seed`: 답변을 목표, 제약, 성공 조건을 가진 확정 명세로 정리한다.
- `Execute`: Double Diamond의 발견 → 정의 → 설계 → 전달 흐름으로 실행한다.
- `Evaluate`: Mechanical → Semantic → Multi-Model Consensus의 단계로 결과를 평가한다.
- `Evolve`: 평가 결과와 새로 발견한 질문을 다음 세대 Seed의 입력으로 돌려보낸다.

첫 번째 다이아몬드는 문제를 넓게 탐색한 뒤 온톨로지를 좁히고, 두 번째 다이아몬드는 설계 후보를 넓힌 뒤 검증된 결과물로 좁힌다.

```text
Wonder/탐색 ── 넓히기 ──→ 온톨로지/정의 ── 좁히기
설계/창조   ── 넓히기 ──→ 평가/전달       ── 좁히기
```

Ouroboros는 종료 조건도 수치화한다. 공식 문서상 Goal, Constraint, Success의 명확성을 가중 계산해 Ambiguity가 `0.2` 이하일 때 Seed 생성을 허용한다. 세대 사이의 온톨로지 유사도가 `0.95` 이상이면 수렴으로 판단하며, 진동·질문 반복·30세대 hard cap 같은 정체 감지도 둔다. 이 수치는 일반적인 소프트웨어 공학 표준이 아니라 Ouroboros가 채택한 내부 운영 기준으로 이해해야 한다.

Claude Code에서는 Plugin으로 설치하고 `ooo` 명령을 사용한다.

```bash
claude plugin marketplace add Q00/ouroboros
claude plugin install ouroboros@ouroboros

# Claude Code 세션 안에서
ooo setup
ooo interview
ooo seed
ooo run
ooo evaluate
```

**잘 맞는 경우**

- 사용자가 고수준 목표만 알고 세부 요구사항을 아직 정하지 못했을 때
- 구현 비용이 크고 아키텍처 결정을 되돌리기 어려울 때
- 성공 조건과 제약이 이해관계자마다 다를 수 있을 때

**경계와 주의점**

- 요구가 이미 작고 명확한 작업에는 인터뷰와 다중 평가가 오히려 절차 비용이 될 수 있다.
- 모호성·유사도 점수는 판단을 돕는 운영 지표이지 요구사항의 진실을 자동으로 보장하는 값은 아니다.
- Multi-Model Consensus와 장기 진화 루프는 단순한 1회 구현보다 시간과 모델 비용이 커질 수 있다.
- 결국 Interview 질문에 답하고 우선순위를 결정하는 책임은 사람에게 남는다.

#### 세 도구가 워크플로에 들어가는 위치

```text
Ouroboros ── 목표·제약·성공 조건을 명세로 수렴
    ↓
Graphify ─── 코드·문서·설계 근거로 저장소 전체를 탐색
CodeGraph ── 현재 코드의 호출 경로와 변경 영향 범위를 탐색
    ↓
계획 → 구현 → 테스트와 평가
```

세 도구는 서로를 완전히 대체하지 않는다. Ouroboros가 “무엇을 만들지”의 모호함을 줄인다면, Graphify와 CodeGraph는 “현재 시스템이 어떻게 구성되어 있는지”를 서로 다른 범위와 최신성 전략으로 보여준다.

> `think`, `ultrathink`, `/config`, `MAX_THINKING_TOKENS`의 현재 동작과 권장 사용법은 확인이 필요하다.

**내 Claude 시스템에서 확인한 예시**

- 현재 프로젝트에는 계획 전용 Skill이나 `.claude/agents/`가 없다.
- 도입한다면 반복해서 사용하는 요구사항 질문 절차는 `.claude/skills/`에 두고, 별도 컨텍스트에서 계획을 전담하게 하려면 `.claude/agents/`에 계획용 에이전트를 둘 수 있다.

### 1.3 구현과 점진적 개발

복잡한 기능은 독립적으로 테스트 가능한 작은 단위로 나누어 순차적으로 구현한다. 점진적 개발은 다음 세 축으로 구성된다.

1. 작업 범위를 명확하게 정의한다.
2. 테스트, 린터, 빌드 로그 같은 피드백 루프를 활용한다.
3. 세션의 컨텍스트를 관리한다.

Claude Code는 통과와 실패가 명확한 구조화된 피드백을 받을 때 오류를 교정하기 쉽다. TDD를 적용한다면 다음 사이클을 반복한다.

```text
Red: 실패하는 테스트 작성
  ↓
Green: 테스트를 통과하는 최소 코드 구현
  ↓
Refactor: 동작을 유지하며 구조 개선
```

세션이 길어지면 `/compact`로 대화를 요약하고, 완전히 다른 작업을 시작할 때는 `/clear`로 컨텍스트를 초기화한다. 사용하지 않는 MCP 서버의 도구 정의도 컨텍스트를 차지할 수 있으므로 `/mcp`에서 비활성화하는 방법을 고려한다.

여러 기능을 동시에 개발할 때는 Git worktree를 사용하면 독립된 작업 공간에서 병렬로 작업할 수 있다.

**내 Claude 시스템에서 확인한 예시**

- 루트 `CLAUDE.md`에는 한국어 문서 작성, 개인 작업 경계, 공통 Skill 승격 규칙은 있지만 빌드·테스트·린트 명령은 아직 없다.
- 이 저장소에서 반복 검증 명령이 생긴다면 루트 `CLAUDE.md`에 공통 명령을 기록하거나, 절차가 길 경우 `.claude/skills/<검증-skill>/SKILL.md`로 분리할 수 있다.

### 1.4 검토와 커밋

구현 후에는 변경 사항을 검토하고 변경 이력을 남긴다. 자동 생성된 커밋 메시지를 그대로 사용하기보다 실제 변경 내용과 일치하는지 확인해야 한다.

Claude Code를 npm 스크립트로 등록하면 ESLint나 Prettier처럼 AI 코드 검토를 자동화할 수도 있다.

```bash
npm run lint:claude
```

이 방식은 함수명과 실제 동작의 불일치, 주석과 코드의 불일치처럼 정적 분석기가 찾기 어려운 맥락적 오류를 검토하는 데 활용할 수 있다.

**내 Claude 시스템에서 확인한 예시**

- 현재 프로젝트에서 `lint:claude` 스크립트나 Claude 기반 검토 자동화 설정은 확인되지 않았다.
- 도입한다면 프로젝트의 `package.json`에 검토 스크립트를 추가하고, 실행 기준과 결과 처리 방법은 `CLAUDE.md` 또는 검토 Skill에 기록할 수 있다.

## 2. 설정 관리

### 2.1 `settings.json`과 설정 범위

`settings.json`은 Claude Code의 동작을 구성한다. 설정 범위에는 관리자·엔터프라이즈 정책, 프로젝트 설정, 프로젝트 로컬 설정, 사용자 설정 등이 있으며 더 구체적이고 우선순위가 높은 설정이 낮은 설정을 덮어쓴다. 권한 배열의 병합 방식과 `deny` 우선 규칙은 별도로 이해해야 한다.

- 프로젝트 공유 설정: `.claude/settings.json`
- 프로젝트 개인 설정: `.claude/settings.local.json`
- 사용자 전역 설정: `~/.claude/settings.json`

기본 설정 후보는 다음과 같다.

- `apiKeyHelper`: 인증값을 생성하는 사용자 정의 스크립트 경로
- `cleanupPeriodDays`: 로컬 채팅 기록 유지 기간
- `env`: 모든 세션에 적용할 환경 변수
- `includeCoAuthoredBy`: Git 커밋의 `Co-Authored-By` 표시 여부
- `outputStyle`: 출력 형식과 스타일
- `hooks`: 도구 실행 전후 등 생명주기 이벤트에서 실행할 명령

환경 변수는 셸에서 직접 `export`하거나 `settings.json`의 `env`에서 정의할 수 있다. 셸 환경 변수가 이미 존재할 때와 `settings.json` 값이 충돌하는 경우의 우선순위는 확인이 필요하다.

**내 Claude 시스템에서 확인한 예시**

- `~/.claude/settings.json`은 현재 `{}`로 비어 있다.
- 프로젝트 `.claude/settings.json`과 `.claude/settings.local.json`은 아직 없다.
- 따라서 환경 변수, 권한, Hooks, 출력 스타일을 Claude 설정 파일로 관리하는 실제 사례는 아직 없다. 팀 공통 설정을 도입한다면 `.claude/settings.json`, 개인 예외는 `.claude/settings.local.json`에 둘 수 있다.

### 2.2 `CLAUDE.md`로 팀 표준 만들기

- 프로젝트 루트 `CLAUDE.md`: 팀 전체가 공유하고 Git에 커밋하는 지침
- 프로젝트 루트 `CLAUDE.local.md`: 개인용 지침
- `~/.claude/CLAUDE.md`: 모든 프로젝트에 적용하는 사용자 전역 지침

빌드, 테스트, 린트, 배포 명령과 코드 스타일, 커밋 메시지 규칙을 `CLAUDE.md`에 기록할 수 있다. 문서가 길어지면 참조용 절차를 Skill로 분리한다.

**내 Claude 시스템에서 확인한 예시**

- 프로젝트 루트 `CLAUDE.md`가 실제로 존재한다. 이 파일은 저장소의 목적과 디렉터리 구조를 설명하고, 문서·주석·커밋 설명은 한국어로 작성할 것, 개인 제작물은 `members/<이름>/` 안에서 작업할 것, 공통 Skill은 합의 후 승격할 것을 규정한다.
- `CLAUDE.local.md`와 `~/.claude/CLAUDE.md`는 현재 없다. 개인 전용 지침이 필요하면 두 위치의 역할을 구분해 도입할 수 있다.

## 3. Skills와 커스텀 Commands

커스텀 Commands는 현재 Skills에 통합되어 있으며 기존 `.claude/commands/*.md`도 계속 사용할 수 있다. 신규 기능은 디렉터리 단위로 보조 파일을 포함할 수 있고, 상황에 따라 자동 로드할 수 있는 Skills가 적합하다.

| 구분 | `.claude/commands/` | `.claude/skills/` |
| --- | --- | --- |
| 형식 | 명령당 Markdown 파일 하나 | 디렉터리와 필수 `SKILL.md` |
| 호출 | 사용자가 `/이름`으로 호출 | `/이름` 호출 또는 Claude의 자동 선택 |
| 보조 자료 | 단일 파일 중심 | `references/`, `scripts/`, 템플릿, 예제 |
| 용도 | 간단한 수동 실행 프롬프트 | 워크플로, 도메인 지식, 반복 작업 |
| 표준 | Claude Code 전용 레거시 형식 | Agent Skills 공개 표준 |
| 권장 여부 | 기존 파일 유지 가능 | 신규 작성 권장 |

Skill은 YAML frontmatter로 호출 방식과 도구 사용을 제어할 수 있다.

```yaml
---
name: deploy
description: 애플리케이션 배포 절차를 수행한다
disable-model-invocation: true
allowed-tools:
  - Bash(git status *)
---
```

- `disable-model-invocation: true`: 사용자만 직접 호출
- `user-invocable: false`: Claude만 필요할 때 사용
- `allowed-tools`: Skill 실행 중 사전 승인할 도구
- `context: fork`: 별도 컨텍스트에서 실행
- `agent`: 사용할 서브에이전트 지정
- `argument-hint`: 명령 인자 안내

같은 이름의 Command와 Skill이 있으면 Skill이 우선한다. 내장 `/help`, `/compact`, `/permissions`는 CLI에 구현된 명령이므로 커스텀 Commands와는 별개다.

**내 Claude 시스템에서 확인한 예시**

- 현재 프로젝트의 `.claude/skills/`에는 `pre-chapter-prep`, `mid-study-deep-dive`, `mid-study-wrapup`, `mid-zettelkasten-synthesis` 등의 프로젝트 Skill이 있다.
- `mid-study-deep-dive`는 `references/research-lenses.md`를, `sync-claude-skills-to-codex`는 `references/codex-adaptation-rules.md`를 보조 자료로 사용한다. 이는 단일 파일 Command보다 Skill 디렉터리가 적합한 실제 사례다.
- 사용자 전역 `~/.claude/skills/`와 프로젝트·전역 `.claude/commands/`는 현재 없다.

## 4. Claude Code의 확장 도구

### 4.1 Skill

Skill은 Markdown으로 작성하는 가장 가볍고 선언적인 확장 방식이다. `SKILL.md`와 스크립트, 템플릿, 참조 문서를 함께 구성할 수 있다. `name`과 `description`을 바탕으로 관련 요청에서 로드할 수 있다.

**내 Claude 시스템에서 확인한 예시**

- 지금 사용 중인 `.claude/skills/pre-chapter-prep/SKILL.md`는 개인 챕터 노트를 정리본으로 만들고, 사람의 역질문 답변 후 발표 HTML을 만드는 순차 워크플로를 정의한다.

### 4.2 서브에이전트

서브에이전트는 별도 컨텍스트에서 독립적인 능력 단위로 작업한다. Skill을 지식이나 절차의 확장으로 본다면, 서브에이전트는 컨텍스트 격리와 독립 실행을 이용한 역할 확장으로 볼 수 있다.

이 정리에서는 Skill을 **지식 확장**, 서브에이전트를 **능력 확장**으로 구분한다.

**내 Claude 시스템에서 확인한 예시**

- 사용자와 프로젝트의 `.claude/agents/` 디렉터리는 현재 없다.
- 도입한다면 반복적인 코드베이스 탐색, 계획 검토, 발표 자료 생성처럼 독립 컨텍스트가 유리한 역할을 `.claude/agents/`에 정의할 수 있다.

### 4.3 MCP 서버

MCP 서버는 Claude Code가 외부 데이터에 연결하고, 외부 도구를 실행하며, 그 결과를 표준화된 방식으로 컨텍스트에 제공하도록 연결한다. 이 정리에서는 세 역할 중 하나만 고르기보다 **외부 데이터 연결 + 외부 도구 실행 + 표준화된 컨텍스트 제공의 조합**으로 이해한다.

**내 Claude 시스템에서 확인한 예시**

- 이 프로젝트에서 `.mcp.json`이나 프로젝트 MCP 설정은 확인되지 않았다.
- Graphify, CodeGraph, Serena를 MCP 방식으로 도입한다면 프로젝트 단위 MCP 설정에 서버를 등록하는 방식이 후보가 된다.

### 4.4 Hooks

Hooks는 LLM의 판단과 별개로 생명주기 이벤트에 바인딩되어 결정론적으로 실행되는 명령이다. matcher 패턴을 이용해 특정 도구나 상황에만 반응하도록 설정할 수 있다.

**내 Claude 시스템에서 확인한 예시**

- 사용자 `settings.json`은 비어 있고 프로젝트 settings 파일도 없으므로 현재 등록된 Hook은 없다.
- 도입한다면 포맷 검사나 위험 명령 감지는 `.claude/settings.json`의 `hooks`에 정의할 수 있다.

### 4.5 Plugins

Plugin은 Skills, 서브에이전트, MCP 서버, Hooks를 하나의 배포 단위로 묶는 컨테이너다. 매니페스트로 메타데이터를 정의하고 Marketplace를 통해 배포·설치할 수 있다.

> 노트의 `.claude-plugin/lugin.json`은 `.claude-plugin/plugin.json`의 오타로 보인다.

**내 Claude 시스템에서 확인한 예시**

- 현재 저장소에서는 `.claude-plugin/plugin.json`과 프로젝트 Plugin 설정이 확인되지 않았다.
- 팀에 여러 확장 요소를 함께 배포할 필요가 생기면 개인 제작 공간에서 Plugin 구조를 만든 뒤, 합의된 구성만 프로젝트 설정으로 연결할 수 있다.

## 5. 권한과 보안

### 5.1 파일 및 명령 권한

Bash와 파일 수정처럼 부작용이 있는 도구는 권한 규칙으로 제어한다. Bash 규칙에서는 정확한 명령과 접두사 패턴을 구분하며, 와일드카드 앞 공백이 매칭 범위를 바꿀 수 있다.

```text
Bash(ls *)  → ls -la와 매칭, lsof와는 매칭하지 않음
Bash(ls*)   → ls -la와 lsof 모두 매칭 가능
```

환경 변수 파일, 시크릿 디렉터리, 자격 증명 파일은 `permissions.deny`로 차단할 수 있다. 다만 Read 차단만으로 Bash를 통한 우회까지 완전히 막을 수 있는지는 별도로 고려해야 한다. 예를 들어 Bash가 허용되면 `cat .env` 같은 명령이 파일 읽기 제한과 다른 경로가 될 수 있다.

이번 발표에서 권한과 보안의 대표 사례는 **`.env` 보호**로 잡는다. 핵심은 민감 파일에 대한 Read 차단만 설정하고 끝내지 않고, Bash를 통한 우회 가능성까지 함께 점검하는 것이다.

Docker 환경에서는 시스템 정리나 이미지 삭제 명령을 `ask` 규칙으로 보호하고, Docker socket 직접 접근을 허용할 때는 범위를 명시적으로 제한해야 한다.

**내 Claude 시스템에서 확인한 예시**

- 사용자와 프로젝트 settings 파일에 `allow`, `ask`, `deny` 규칙이 현재 정의되어 있지 않다.
- 민감 파일 보호를 도입한다면 팀 공통 규칙은 `.claude/settings.json`, 개인 예외는 `.claude/settings.local.json`에 둘 수 있다.

### 5.2 원격 분석

Claude Code의 운영 메트릭과 오류 로깅, 비활성화 옵션에 관한 노트가 있으나 기본값과 현재 수집 방식은 확인이 필요하다.

**내 Claude 시스템에서 확인한 예시**

- `~/.claude/settings.json`에는 원격 분석 관련 설정이 없다.
- 따라서 현재 로컬 설정만으로는 활성화 여부를 판단할 수 없다.

## 6. 현재 프로젝트에 적용된 구성 요약

| 구성 요소 | 현재 상태 | 확인한 위치 또는 도입 위치 |

## 7. 확정한 관점과 다음 적용

- 중심 메시지: 좋은 결과는 `탐색 → 계획 → 구현 → 검증` 워크플로에서 나온다.
- Graphify·CodeGraph·Ouroboros는 탐색과 계획 단계에서 맡는 역할, 내부 흐름, 적합한 조건과 한계를 비교한다.
- 이 프로젝트에 다음으로 적용해 볼 설정은 Hook이다.
- Skill은 지식 확장, 서브에이전트는 능력 확장이라는 구분을 유지한다.
- MCP는 외부 데이터 연결, 외부 도구 실행, 표준화된 컨텍스트 제공의 조합으로 이해한다.
- 권한과 보안의 대표 사례는 `.env` 보호다.

## 8. 이번 보강에 사용한 공식 자료

기준일: 2026년 8월 5일

- [Graphify 공식 저장소](https://github.com/Graphify-Labs/graphify): 로컬 AST 추출, 관계 근거 표시, 산출물, 설치와 갱신 방식을 확인했다.
- [CodeGraph 공식 저장소](https://github.com/colbymchenry/codegraph): Rust 커널, SQLite·FTS5 인덱스, 자동 동기화, MCP 질의와 영향 분석 방식을 확인했다.
- [Ouroboros 한국어 공식 README](https://github.com/Q00/ouroboros/blob/main/README.ko.md): Interview·Seed·Execute·Evaluate·Evolve 흐름, Double Diamond, 모호성·수렴 기준과 Claude Code 설치 방식을 확인했다.

세 프로젝트가 제시하는 성능 수치와 내부 임계값은 각 프로젝트의 자체 문서와 평가 방식에서 나온 값이다. 일반적인 업계 표준이나 모든 저장소에 동일하게 적용되는 보장으로 해석하지 않는다.
